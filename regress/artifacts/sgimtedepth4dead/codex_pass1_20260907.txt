For Q2, the missing distinction is **copy versus fill**. For a serviced pixel, take source bytes `12 34 56 78` and an initial BG register value `0x12345678`:

| Observation | Present CI route | Activated RGBA route |
|---|---|---|
| Successful copy GET leaves local `bg` | `0x00000012` | `0x12345678` |
| Copy PUT supplies bytes | `12 ? ? ?` | `12 34 56 78` |
| Fill PUT supplies bytes | `78 ? ? ?` | `12 34 56 78` |

Here `?` means **unassigned PUT-local storage**, not preserved destination bytes or necessarily different bytes. GET and PUT have separate automatic-object lifetimes; incidental stack reuse could make a defective copy appear correct. A pre-fix inequality oracle cannot assume otherwise. [Serialization and memory accesses](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_sgi_re.c:284)

The resulting changes are:

- Copy GET consumes all four returned bytes into `bg`; PUT explicitly supplies all four bytes.
- Fill changes even the explicitly assigned first byte: BG’s low byte becomes its high byte.
- If a source GET returns early, the dependent PUT still occurs. It now serializes the full retained BG value—initial BG or a previous successful pixel’s value.
- Transfer length remains four bytes. Address calculation, tile selection, coordinate conversion and iteration are unaffected by the type override.

The branch is outside the `MTE_MODE_COPY` condition. A repair described merely as “32-bit copy correction” would therefore understate its scope. [Branch and loop](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_sgi_re.c:1368)

I would also qualify “a code path that has never executed”: **the MTE-to-RGBA combination is currently unreachable; the RGBA helper arms are already selected by drawing-engine paths.** The existing `copy lin_a` control explicitly requests RGBA for both source and destination. Its assertions provide no MTE-fill evidence. [Existing control](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/regress/sgi_re_rgb_probe.py:273)

There is some independent representation evidence: GBE scanout assembles four bytes in the same order and takes RGB from the first three. That supports the framebuffer layout; it does not establish how `CRIME_MTE_BG` must expand into that layout. [Scanout](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_sgi_gbe.c:283)

Finally, I found two additional concerns relevant to activation:

**Signed shifts:** RGBA GET assembles the word using byte operands promoted to signed `int`. On a 32-bit `int` host, high-bit leading bytes encounter signed-shift undefined behaviour. Activation adds this site to MTE copy execution. The fork already has unsigned `READ_WORD_BE`/`READ_WORD_LE` helpers specifically addressing this defect class. The tiled pointer shifts have an analogous promotion issue. These are separate from buffer initialization.
