## 1. Premise audit — enumerated, not agreed

**`depth` is `{8, 16, 32, 64}` and `if (depth == 4)` never runs. True.**

Producer is one assignment:

```c
int depth = 8 << ((mode & MTE_MODE_DEPTH_MASK) >> MTE_DEPTH_SHIFT);
```

`MTE_MODE_DEPTH_MASK` is `0x00000300`, shift 8. Walk the two-bit field:

| field `(mode>>8)&3` | `depth = 8<<field` | `bufdepth = 1<<field` | header name |
|---|---|---|---|
| 0 | 8 | 1 | `MTE_DEPTH_8` |
| 1 | 16 | 2 | `MTE_DEPTH_16` |
| 2 | 32 | 4 | `MTE_DEPTH_32` |
| 3 | 64 | 8 | *undefined* |

None is 4. Nothing else writes `depth`. `x1 /= (depth/8)` is  `/1`, `/2`, `/4`, `/8` — never divide-by-zero.

**The comment’s intent is 32-bit transfers. True.** The sentence is “copy 32 bits when doing 32-bit transfers.” The author converted bits→bytes two lines earlier, then compared the bit-count to 4.

**Stronger reading than the brief, and it supports F1 rather than replacing it:** if `depth` had been `1 << field` (bytes, i.e. the helper’s `bufdepth`), then `== 4` *would* be the 32-bit case. They computed bits and tested bytes. Flipping the formula instead of the constant would make `x1 /= (depth/8)` divide by 0 at field 0. **Do not touch the formula.**

**`depth == 32` and `bufdepth == 4` are the same condition *for MTE-synthesized modes*. True.** Same two-bit field is copied into bits 8–9 of `src_mode`/`dst_mode`, and the helper does `1 << ((mode>>8)&3)`. Not a general DE fact: `draw_primitive()` reads guest `CRIME_DE_MODE_*` words that can set BUFDEPTH and TYPE independently.

**Follow-on (1): both `|= DE_MODE_TYPE_RGBA` never run, so tiled MTE is always CI. True.** Constructed word is `(tlb<<10) + (field<<8)`. `DE_MODE_TYPE_MASK` is `0xf0` (bits 4–7). Those bits stay 0. `DE_MODE_TYPE_CI` is 0. The helper’s `color_mode` is therefore CI on every tiled A/B/C transfer.

**Follow-on (2): at `MTE_DEPTH_32`, CI assigns one byte and copies four. True for a FILL.** `buf` is `uint8_t buf[8]` with no initialiser, per-call. FILL never GETs. PUT CI writes `buf[0] = *color` and `memory_rw(..., buf, bufdepth=4, MEM_WRITE)`. `buf[1..3]` are stack. I am *not* treating dest[1..3] as an oracle, same as the brief.

**Follow-on (3): comment means 32. True**, as above.

**Premises I could not settle from the packet alone (settled from the tree):**

- `DE_MODE_PIXDEPTH_16` is literally `0x00000004`. A reading “`== 4` meant pixdepth-16” exists in the header and the comment kills it.
- No other `depth == 4` in this file. `dev_fb.c` has a real 4-*bit* framebuffer; different unit, different device.
- The DE path does not synthesize type bits; the guest supplies them. This dead `|=` is the only in-tree attempt to invent a DE type from an MTE depth. There is no second site to copy a working idiom from.
- I did not re-run the 5/6 boot. The probe’s `MODE_TILED_FILL = 0x200`, `BG = 0x11223344`, TLB valid-bit, START on `DST1`, and `topbyte()` all match the handler.

## 4. Scope — one round, not three of the same class

Three documented/undefined depths write `bufdepth` bytes after CI assigned one. That is **one uninit class** (`sgirebufuninit` / F4). The **type-byte** defect (`0x44` vs `0x11`) exists only at 32, and only F1 repairs it. F1 cannot close 16 (RGBA would write a 4-byte layout into a 2-byte copy) and must not close 64 (F2).

A later `sgirebufuninit` round that only rows depth 32 on this path will look fixed and will not be. Keep that sibling alive on **depth 16** (documented, F1 does not touch it).
