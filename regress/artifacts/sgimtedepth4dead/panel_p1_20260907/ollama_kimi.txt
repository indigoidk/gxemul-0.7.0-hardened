## 3. Copy-top arithmetic — and the wrong cell

READ from the helper: CI read sets `*color = buf[0]`; RGBA read reconstructs the full word `buf[0]<<24 | buf[1]<<16 | buf[2]<<8 | buf[3]`; CI write does `buf[0] = *color` (low byte); RGBA write does `buf[0] = *color >> 24` (high byte). Walking source pixel `aa bb cc dd`:

| shape | read color | write buf[0] | dest[0] |
|---|---|---|---|
| both CI (today) | 0x000000aa | 0xaa | **0xaa** |
| both RGBA (after F1) | 0xaabbccdd | 0xaa | **0xaa** |
| E2: src RGBA, dst CI | 0xaabbccdd | 0xdd | **0xdd** |
| E3: src CI, dst RGBA | 0x000000aa | 0x00 | **0x00** |

This matches your table, and the row is **legitimate, not self-satisfying**: 0xaa / 0xdd / 0x00 are three distinct reachable outcomes and each one-sided edit turns the row red. It pins coupling, not the fix — `fill top` remains the bug witness; `copy top` is a regression guard. **However, the E3 mechanism as described in your table is wrong:** you tabulate "dest RGBA only → read gives 0xaa; write puts 0x00 first" — true only because `*color` is assigned (0-extended) on the CI read. `color` in the caller is `bg`; had the CI read left it untouched (or the call passed an uninitialised variable), RGBA write would emit `bg >> 24 = 0x11`, not 0x00. The row works, but for a different reason than "write puts high byte of a low-byte colour first" in general. Worth one sentence in the row's comment so a future seat doesn't "fix" the want to 0x11.
