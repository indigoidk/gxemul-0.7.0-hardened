### 3. The Q5 disagreement (section 3)

**The flag is correct; ADOPT.** The code path:

```c
static int sc_g;   /* initialised 0, set ONLY in the G-line arm */
...
if (!sc_bad && sc_first_bad == 0) { sc_g = 1; printf("ok SELFCHECK ...\n"); }
...
if (failures == 0 && sc_g) printf("WDC_IDENTIFY_PASS\n");
return (failures || !sc_g) ? 1 : 0;
```

- `sc_g` is set in exactly one place, exactly where the G line prints — which is exactly when the self-check passed AND the first run passed.
- For a healthy run, `sc_g == 1` at verdict time; PASS prints, exit 0. The 14-of-14 byte-identity (modulo the SELFCHECK stanza) at -O2 and -O0 across seven device variants is consistent with that: `sc_g` does not appear in any output line, only in the control flow.
- grok's "failures++ on the success path" objection does not apply: `sc_g` is not a failure increment, it is a separate gate. Healthy runs are unchanged because `sc_g` is 1 for them.
- agy's "that is precisely why the G check was created" answers the wrong question. The G check ensures gate 2 sees the line; the run's own verdict needs a separate mechanism because nothing reads gate 2's log from inside the run.

**To grok and agy specifically:** there is no case where `sc_g` changes a healthy run — the only assignment is in the `!sc_bad && sc_first_bad == 0` arm, which is exactly the healthy-second-run arm. The run's verdict SHOULD go red when its self-check failed; a consumer (human, trailer-grep, CI) reading `WDC_IDENTIFY_PASS` with exit 0 is being lied to otherwise. The byte-identity measurement is the proof that the cost is zero on the green path.

### 5. Q4 — the smallest edit to #551b that keeps gate 2 green while a covered row can no longer fail, outside the disclosed classes

**Answer: change `!=` to `<` in `row_cmp()`.** One character.

Reasoning, REASONED from the probe arrays in 4c:

All six `row_cmp()` probes have every operand ≤ the reference (`rw`):

| i | rw | r57 | r60 | r57 > rw? | r60 > rw? |
|---|----|-----|-----|-----------|-----------|
| 0 | 2 | 1 | 2 | no | no |
| 1 | 2 | 2 | 1 | no | no |
| 2 | 1 | 0 | 0 | no | no |
| 3 | 3 | 3 | 3 | no | no |
| 4 | 2³² | 0 | 2³² | no | no |
| 5 | 2³² | 2³² | 0 | no | no |

For every probe, `r57 < rw || r60 < rw` evaluates to the **same boolean** as `r57 != rw || r60 != rw`, because no operand exceeds its reference. The self-check's `sc_bad` accounting is therefore undisturbed, the G line prints, `sc_g` is set, `WDC_IDENTIFY_PASS` and exit 0 are emitted. Gate 2's G row grep finds its line; H row grep finds `@@SELFCHECK@@`; `grep -c 'high byte'` is unchanged (the self-mutant row is untouched); the self-mutant lane's pristine-line count is unchanged (in-place edit).

But the comparator's semantic is broken: `got > want` no longer registers as a mismatch. A covered row whose `got` exceeds its `want` now passes silently. That is exactly "a covered row can no longer fail", and it is outside the disclosed classes (no value/name/position-keyed test is added; no feed edit; the comparator itself is edited).

The wide probes added in Q4 do **not** catch this — they were sized to catch `uint16_t` narrowing and `sectors<4` gating, not the `!=`-vs-`<` distinction, and as the table shows they cannot, because no probe has `got > want`.

A one-probe fix would close it: add a seventh `row_cmp` probe with `r57 > rw` (e.g., rw=1, r57=2, r60=1 → disjunct true under `!=`, false under `<`). That is a separate change, not part of the current repair; the repair as it stands ships with this hole.
