### 4. Section 4 Result Against Ruling Expectation (`P_scnoforce`)

**Analysis:**
Fable 5.1 ruling 6 asserted that under `P_scnoforce` (removing `failures = sc_f + 1;` in [`selfcheck()`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/regress/diff_wdc_identify.c#L469)), stubbing `chk()` must still "go red through `failures`".

This expectation was mathematically and logically impossible:
* If `chk()` is stubbed to pass (never bumping `failures`), the covered real rows calling `chk()` **cannot** bump `failures`.
* If `selfcheck()` restores `failures = sc_f` (0) and does not force `failures = sc_f + 1`, then at program termination `failures` is 0.
* Therefore, the run exits 0 with `0 failures`.

**Is Gate 2's G row an adequate sole carrier?**
**Yes.** Gate 2 checks [`gate_offline.sh:2347`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/regress/gate_offline.sh#L2347):
`grep -q 'SELFCHECK the comparator can still fail' "$LOGDIR/diff_$_stem.log"`
Because `selfcheck()` saw `sc_bad > 0`, it suppressed that string and printed `FAIL SELFCHECK(...)`. Gate 2 goes RED. That is precisely why the G check was created.

**Would making the run red standalone cost byte-identity?**
No. A standalone exit (e.g. `if (sc_bad) exit(1);` or forcing failures) only triggers when `sc_bad != 0`. On any passing run, `sc_bad == 0`, so it has zero cost to byte-identity. But within the gate architecture, the existing forced failure `failures = sc_f + 1;` already achieves this for all non-mutated selfcheck code.
