**Ruling (a).** I cannot run anything; everything below is from reading the diff and reasoning.

Steps a ruling must pass, in order: printable ASCII (`tr -d ' -~'` → wc-c == 0), regex `^[0-9]{4}-[0-9]{2}-[0-9]{2}: .{16,}$`, `date -d` round-trip, no `"`/`\`/`$`/`` ` ``, ≥16 ASCII alphanumerics in the reason.

- Printable-ASCII via `tr -d ' -~'` is correct: `' -~'` is the POSIX range 0x20..0x7e, and `LC_ALL=C` makes `tr` byte-wise; multi-byte UTF-8 (NBSP, U+0085, U+2028) has every byte ≥ 0x80, so all are deleted → wc-c ≠ 0 → refused. Matches the inlined measurements.
- Regex anchors the colon at byte 10 of the date. The 9 refused cases in the measurements (newline, tab, 21 spaces+x, 2026-99-99, 2026-02-30, 16 dots, 8 NBSP, U+0085, U+2028) all fail at one of: the printable-ASCII step (tabs/NL/U+0085/U+2028 are not printable), the regex (no `:` after the date, or no 16 chars of reason), or the date round-trip (2026-99-99, 2026-02-30). All nine refused (rc 2) matches.
- Alphanumeric-reason check via `tr -cd 'A-Za-z0-9'` correctly throws out punctuation-only reasons and multi-byte content. Matches the inlined t_rpunct/t_rnbsp.
- **One defect** (see VERDICT): `_day=${RULING%%:*}`. For a ruling whose reason contains a colon, this yields the part before the LAST colon; `date -d` fails on the resulting string and the legitimate ruling is REFUSED. The header does not document this restriction.

## Other finding (the VERDICT defect)

Diff context:

```
+    _day=${RULING%%:*}
+    [ "$(date -d "$_day" +%F 2>/dev/null)" = "$_day" ] || { echo "REFUSED: [$_day] is not a calendar date"; exit 2; }
```

`%%:*` removes the longest suffix matching `:*`. For pattern `:*` the `:` anchors at the rightmost position. Concrete trace:

```
RULING="2026-09-23: at 14:00 meeting"
RULING%%:*  =>  "2026-09-23: at 14"
date -d "2026-09-23: at 14" +%F     # invalid; outputs nothing (or anything != _day)
```

So `[ "" = "2026-09-23: at 14" ]` → FALSE → REFUSED. The other answer for `[[ "$_day" == "2026-09-23" ]]` can't help; `_day` literally has the extra chars in it. The header says "a real calendar date" and places no restriction on the reason's content beyond printable-ASCII + alphanumerics + 16-char minimum + the four punctuation exclusions. The header permits `"at 14:00 meeting"`; the implementation refuses it. Conflicting.

The 9 inlined refused cases and the t_rapos WRITTEN case all use reasons with no internal `:` -- they would never expose this. The F4 testing missed it because no test exercised it.

**Fix is one line.** Either `IFS=: read -r _day _ <<<"$RULING"` (gets the part before the FIRST colon), or `${RULING%%:*}` replaced by `${RULING%"${RULING#*:}"}-style acrobatics, or an explicit `case "$RULING" in $YYYY:$YYYY:$YYYY)` parse.
