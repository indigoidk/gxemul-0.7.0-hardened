For Q3:

- **`wide alive`:** None of the eight candidates, or the two supplied measured variants, makes this row alone fail. A terminating variant during GETENV also prevents the final value observation. This is a process-survival control, not an independent discriminator of write acceptance; a stopped guest can also leave its debugger process alive.
- **`wide live`:** It is a useful round-trip control, but **not a device signature**. The scratch register is an ordinary stored byte in [the UART implementation](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_ns16550.c:298), so RAM could reproduce `0x5a`. A genuinely missing device at these out-of-RAM addresses ordinarily reads zero in the checked dispatcher and fails the control. Also, ordinary RAM backing the sparse address would yield `'A'` after the wide copy, so `wide getenv` provides additional discrimination. That does not justify calling `wide live` itself a device signature.
- **`RET`:** Correct. Evaluating the committed encoder gives phase lengths `1, 4, 4, 9, 4`. Initialization occupies instruction 0; phases 1–3 occupy `1–4`, `5–8`, and `9–17`. CALL_PAL is instruction 17 at `0xfffffc0001040044`; phase 4 begins at **`0xfffffc0001040048`**, exactly `RET`.
- **Return-failure classification:** The script does not implement an automatic “construction failure” disposition. It retries missing prints once, then scores missing or incorrect values as failures. A failing baseline must be adjudicated externally as an invalid construction/run. A return failure occurring only in a variant is not automatically a construction failure. The reported `t4=0x5a` results support the intended refusal/fallthrough explanation for these particular runs.
- **Other wide producers:** **Unsettled globally.** GETENV is the wide producer identified in the permitted files; the other checked PAL memory operations use byte, word, or quadword helpers. PHYSICAL accesses really do bypass the split, as do accesses with a null translator. These seven files do not contain the complete machine/device DMA inventory, so I cannot honestly say “checked alphabook1 and found none.” The dispatcher alone does not exclude a larger device transfer.

There is a concrete reason to prefer isolation over an unchecked single-session sweep: **write-arm fallthrough overwrites the GETENV source string**. `store_buf` passes its source buffer to `memory_rw`; the mutant then enters the read arm and writes zeros and the fetched byte into that buffer. A later GETENV can consequently see a shorter string and issue smaller accesses. A single-session sweep needs an explicit source-restoration mechanism before each case.
