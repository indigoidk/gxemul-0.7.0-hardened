## 1. Head EQUIVALENCE reasoning is incomplete for RD2 — REASONED, not checkable from packet

The header says: *"at the split-HEAD cells it is EQUIVALENT on alphabook1 (heads land on ports 0x1f mod 0x20 -- 0x3ff SCR, or unmapped -- none with a read side effect)."*

The parenthetical addresses the END of the head (the lane-3 byte at 0x3ff / 0x1f). It does NOT address the middle of the head range. For a 6- or 7-byte head ending at 0x3ff, the byte at port 0x3fa is IIR, which is at lane 2, NOT at 0x1f mod 0x20. IIR has a read side effect when TXRDY is armed (`&= ~IIR_TXRDY`).

Per-channel breakdown (REASONED from the fix text and the settle section):

| channel | head mechanism | EQUIVALENT? |
|---|---|---|
| W1 (`len != 8`) | len-1 head bytes short-circuit | yes — len check, not port side-effect |
| W2 (`len != 2`) | len-1 head bytes short-circuit | yes — len check |
| W3 (`lane != 0`) | only lane-0 head bytes fall through; lane-0 port in 0x3f9–0x3ff is 0x3fc (MCR) | yes — MCR has no read side effect |
| W4 (`len == 1 \|\| 4`) | len-1 head bytes short-circuit | yes — len check |
| RD2 (forward duplicated) | EVERY head byte is read TWICE; 0x3fa's second read sees TXRDY consumed IF TXRDY was armed | **CONDITIONAL** — EQUIVALENT only if no head cell arms TXRDY |

The brief's stated reasoning ("heads land on ports 0x1f mod 0x20 — none with a read side effect") is wrong for RD2. The correct reasoning is: no probe session arms TXRDY before a head-cell read, so IIR returns 0x01 for both reads. I cannot verify from the packet that no earlier head-cell session (1–3) arms TXRDY. **One fact would settle it:** the full text of the head-cell sessions in the 77-row instrument, specifically whether any `k0(SP(UART_IER))` / `k0(SP(UART_IIR))` pair precedes a head read.

This is a defect in the *reasoning*, not necessarily in the *outcome*. POSTTABLE 5 RD2=110 (one red, `iir lca rd`) is consistent with no head row arming TXRDY — if any did, RD2 would red at that row too. So the measurement supports the EQUIVALENCE. But the brief should say so explicitly, and the "0x1f mod 0x20 — none with a read side effect" sentence should be replaced.

## 5. A contrived edit I considered and reject as a floor gap — REASONED

"RD2 gated to `len > 1`": duplicate the read forward only when `len > 1`. On the (1,2) direct read at IIR (len 1), no duplication — the `iir lca rd` row does not catch it. On multi-byte reads at lane 2, duplication happens — but POSTTABLE RD2=110 (one red) implies the multi-byte read cells at lane 2 do NOT arm TXRDY, so both reads return 0x01 and the duplication is invisible.

This edit would score 111/111 on the current instrument. But:
- The contract names "the read arm's forward DUPLICATED" — unconditional. A `len > 1` gate is a different edit.
- The contract's named edit (unconditional RD2) is caught at 110/111.
- "RD2 gated to len > 1" is not a named contract entry and is not the kind of edit the disposition-B class closure is designed to catch.

I do not call this a floor gap. The contract is for the named edits; contrived gates of named edits are a different class. The panel may disagree.
