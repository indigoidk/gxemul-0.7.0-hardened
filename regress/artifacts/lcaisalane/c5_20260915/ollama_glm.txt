## 1. The finding (Q3) — the enumeration's arm axis has only two forms; the forward-COUNT class has a third

READ: the class as ruled is exactly two forms — "a store's phantom read after its forward; a load's forward duplicated" — and the enumeration is that pair × width-kind × lane (FABLE_C4 part B; the header). READ: the tail cells are rowed on the 8042 queue at 0x60 (4p `tailq_w`, 4q `tailq_r`).

REASONED: the class's own name is forward-**count**. The write arm's count has a second simple mutant the two-form enumeration never disposes of — the store forward itself **duplicated** (the write-arm sibling of RD2). Its disposition by cell:

* DIRECT cells: caught — but by the **stub counter alone** (it bumps on every access, writes included; the stub sessions row w1/w2/w4/w8 at all four lanes). The architectural carriers are read-count or value channels (kbcq pops; cmos/iir observe read side effects), so for this form the stub is the sole carrier even at lanes 0–2, contrary to the ruling's "never the sole carrier" intent.
* HEAD cells: genuinely EQUIVALENT (SCR/unmapped; writing the same byte twice is idempotent).
* TAIL cells: caught by **nothing**.

Why 185/185 (REASONED from the inlined sessions):

* The only len-6 handler calls the instrument ever makes are split tails at port 0x60: `tailq_w` t6 (store), `tailq_r` t6 (load — the edit is on the write arm), and 4f's t6. No stub, cmos, iirr2, rdq, witness, host-ender, or head row sees a len-6 call (all are widths 1/2/4/8, or SCR-value head rows, idempotent under doubling).
* `tailq_w` t6's channel is DIB — the queue counts **pops**. A store, single or doubled, never pops; with 0xd1 pending both writes go toward output_byte, and even if the second queued a device reply, DIB is a full flag: still 1. Pass.
* READ + REASONED: the header's own sentence — "`tailw' (4f) stores into an EMPTY queue, so a phantom read there changes nothing" — plus WT6/WTsplit's measured 111/111 on an instrument that already contained 4f at 0x60, pin 4f tailw's store as queue-inert and its observable as value-based; a doubled identical write is idempotent to any value observable. Pass.

Guest-visible (REASONED; **the load-bearing premise, named**): the mapped tail ports are 0x20/0xa0 (8259), 0x40 (8253 counter 0), 0x60 (8042) — READ from the Q1 table. The packet itself attests the 8253's LSB/MSB access-mode machinery ("counter 1 at 0x41 after a LSB+MSB control word, F, MEASURED"); any faithful model mirrors it on the write side, so a doubled LSB write to counter 0 changes the 16-bit count. The realization is exactly the probe's own tail geometry one block down: head 2 at 0x3f (unmapped), tail 6 at 0x40. The 8259's ICW sequencing and a doubled data byte to a live 8042-attached model (the selftest reply proves a live model) behave likewise. **The one fact that settles it: dev_i8253's counter write path — does a second write advance the LSB/MSB flip-flop? (or dev_pckbc's data-write forwarding).** Not in the packet. If every mapped tail write path were idempotent, the finding downgrades to: the tail-write cells have no write-count channel and the contract owes a disposition sentence it does not have — still an incomplete enumeration.

Note the stub can never carry a tail: tails land at ports 0 mod 0x20, and within 0x60–0x6f that is 0x60 itself, which the stub branch explicitly excludes (`relative_addr != 0 && relative_addr != 4`).
