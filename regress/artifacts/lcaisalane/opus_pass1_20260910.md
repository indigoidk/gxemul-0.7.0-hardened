## 1(a) The lane decode is the hardware's for ten of eleven encodings, and the table is mis-transcribed

Walking `(0x3fd << 5) = 0x7fa0`: `a<6:5> = 01`, `a<4:3> = 00`, `a<2:0> = 000`; the model's `>> 5` gives
port `0x3fd`, `& 3` gives lane 1; Table 6-3 row `01 00 Byte` gives PCI I/O `ad<1:0> = 01`.  Agreement.

The seat then showed the agreement is structural rather than coincidental, which is the part a future edit
must not break: hardware computes `PCI addr = (a<31:7> << 2) | a<6:5>`, and `a >> 5` **is exactly that
number**, because bit *k* of `a >> 5` is `a<k+5>`.  So the one shift performs the `<31:7> -> <26:2>`
remap **and** drops `a<4:3>` into the low bits' place simultaneously.

**Three corrections to the brief's §S6, found by re-deriving rather than reading the brief's copy:**

* **The table is truncated.**  The manual carries ELEVEN data rows; the brief quoted nine and stopped at
  `01 10 Tribyte`.  The omitted rows are `00 11 Longword 0000 / 00 / 00 / Unmasked` and
  `11 11 Quadword 0000 / 00 / 00 / Unmasked`.
* **The DATA rows ARE staggered**, contradicting the brief's explicit claim that only the header is.  The
  brief reproduced the stagger verbatim without noticing (`01 00 Byte 1011 / 0111`, then a blank cell).
  Calibrated by pairing strictly in order down the column and cross-checked against the word group
  (`1100`, `1001`, `0011`, two adjacent zeros walking up) and the tribyte group (`1000`, `0001`), the true
  byte-enable column is `1110`, `1101`, `1011`, `0111` for lanes 0..3.
* **The identity breaks on the quadword row.**  For every masked row PCI I/O `ad<1:0> == a<6:5>`; for
  `11 11 Quadword`, `a<6:5> = 11` but `ad<1:0> = 00`.  So the brief's flat sentence *"the LANE is a<6:5>
  (it becomes PCI I/O ad<1:0>)"* is **true of ten of eleven encodings and false of the one a real driver
  uses for `ldq`** -- and the model therefore **mis-routes a legal quadword access by three ports**.

The seat named this as exactly the failure the carrier's own calibration refinement predicts: row 1 pairs
correctly, so a single calibration point taken from the top certifies a table that is wrong from row 2 down.

Two further constraints the brief did not carry: `a<6:3>` is the byte-enable generator and combinations not
shown are *unspecified*; and `a<2:0>` must be zero for sparse transfers, with the model having no guard for
it -- which is how a guest reaches the split cells.

## 1(b) Byte reads via LDL are correct; every wider encoding degrades to one byte

For the 21066's real path (LDL, `a<6:5> = 01`, `a<4:3> = 00`): `len 4`, `ofs 1`, `data[1] = byte`, the
guest register holds `LSR << 8`, the driver shifts by `8 * ad<1:0>`.  Correct, and correct for all four
byte rows.  Wrong today, enumerated against the calibrated table: Word at lanes 0/1/2 moves two bytes on
hardware and one here; Tribyte at lanes 0/1 moves three; Longword moves four; **Quadword moves eight at

The seat would file **TWO** rows rather than one: `lcaisasize` for honouring `a<4:3>` as the width, and a
separate `lcaisaqword` for the quadword mis-route, *"because it is an addressing defect, not a width

the model ignores entirely -- to be named in the row so a future round does not discover it mid-design.

## 1(d) A declined access, read end to end

1. `memory_rw.c` at the device dispatch: `res = mem->devices[i].f(...)`, then `if (res == 0) res = -1;`,
   then the `res <= 0` arm emits a `debug()` and its two exception arms are `#ifdef MEM_MIPS` and
   `#ifdef MEM_M88K` **only**, so an Alpha build falls through to `return MEMORY_ACCESS_FAILED`.
2. `MEMORY_ACCESS_FAILED` is 0.
3. `cpu_alpha_instr_loadstore.c`, `LS_GENERIC_N`: `if (!cpu->memory_rw(...)) { return; }` sits **before**
   the register assignment.  No exception, no PC rewind, no halt.
4. The fast path cannot intercept: `lca_isa` is registered `DM_DEFAULT`, so no `DM_DYNTRANS_OK`.

| direction | what the guest can observe |
|---|---|
| LOAD | the destination register **retains its pre-instruction value**; observable ONLY if the guest seeded it |
| plain STORE | **NOTHING**; the store path just returns and the source register is untouched |
| `stl_c`/`stq_c` | the success register is left unwritten -- observable, but no driver does this to I/O space |
| any | `memory_rw`'s own `debug()` line, which prints only when single-stepping or under `-v` |

**Consequences the brief had not drawn:** the decline channel is a seeded sentinel and only on the read
side; and **a write-side decline row keyed on the handler's return value is vacuous by construction**, so
the only non-vacuous write oracle is *the target port did not change*, read back through the flat mapping.

On the uninitialised-`byte` question the seat closed codex's "conditional" further: every failure route
leaves `byte` zero except one, and that one (`memory_warn_about_unimplemented_addr` under
`halt_on_nonexistant_memaccess`) also clears `cpu->running`, which the outer dispatch catches before the
Alpha template can write back.  **So on Alpha today the undefined byte is a real UB read with no guest
disclosure channel.  Fix it because it is UB, not because it leaks.**

## 1(e) The domain audit, and the six changed cells

**`len ∈ {1,2,4,8}` is incomplete**, by two producers the seat read rather than assumed: the 1 KB split in
the `MEMORY_RW` wrapper (a guest quadword at `vaddr & 0x3ff == 1021` yields a head chunk of `len == 3`),
and the end-of-window clamp against the `0x200000`-byte window.  Both are bounded in lane: a head chunk
requires an offset in `[1017,1023]`, all of which have `(offset >> 5) & 3 == 3`, and a remainder chunk
always starts 1024-aligned, so `ofs == 0`.

> **REACHABLE DOMAIN: `len ∈ {1..8}`; all four lanes for `len ∈ {1,2,4,8}`; only `ofs ∈ {0,3}` for
> `len ∈ {3,5,6,7}`.**  Not reachable: `len == 0`; `len == 16` (debugger only, and the debugger passes
> `NO_EXCEPTIONS`, which with `DM_DEFAULT` skips this handler entirely).

The full table labels every cell.  Its load-bearing rows: `(1,1)` read is a false success while the
`(1,1)` **write is correct by accident** (`data[1%1] = data[0]` is the only byte); `(2,2)` read is a false
success while the write forwards the **wrong byte**; `(2,3)` **exits, so the brief's `data[3 % 2]` is dead
code**; `(3,3)` is a **third false-success cell** from the split producer; every `len >= 4` cell is served.

> **The candidate changes exactly SIX cells: `(1,1) (1,2) (1,3) (2,2) (2,3) (3,3)`.  Three currently end
> the host; three currently lie.**  Since `ofs <= 3` always, `ofs >= len` is impossible for `len >= 4`, so
> **the fix is entirely confined to `len ∈ {1,2,3}` and cannot perturb any `ldl`/`ldq` path.**  That is the
