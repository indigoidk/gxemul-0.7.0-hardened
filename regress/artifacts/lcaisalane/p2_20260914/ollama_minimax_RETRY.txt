## Q2. Floor gap

**The exact edit that scores 37/37:**

```diff
-	ofs = (relative_addr & 3) % len;
+	ofs = (relative_addr & 1) % len;
```

**Why it is not caught:**

The detector's `(len, lane)` coverage is:
- `(1, *)` on both arms — but `L % 1 = 0` for all L, so `& 1` and `& 3` agree.
- `(2, *)` on both arms — `(2,2)` gives `(2&1)%2 = 0` and `(2&3)%2 = 0` (the `% 2` masks the difference); `(2,3)` gives `(3&1)%2 = 1` and `(3&3)%2 = 1`; `(2,1)` gives 1 either way. All agree.
- `(8,1)` on read (r81) — `(1&1)=1`, `(1&3)=1`. Agree.
- **No `(4, *)` tests on either arm. No `(8, 0|2|3)` tests on either arm.**

`& 1` differs from `& 3` only when the original bit 1 (lane 2 or 3) is set AND `len ≥ 4`. The probe never exercises `len=4` at all, and exercises `len=8` only at lane 1. So the edit is silent on every probed cell.

**The row I expected to catch it:** an `r43 byte` / `r83 byte` (LDL or LDQ at lane 3) — or equivalently a `w43`/`w83` (STL/STQ at lane 3). It would observe a full-register value of `byte << (lane*8)` for the fix, and `byte << (1*8)` for the `& 1` mutant. **That row does not exist.** [REASONED]

This is outside the DISCLOSED list (split heads / len-0 / a<4:3> / lcaisaqword / lcaisaphys). The `& 1` edit is reachable — any guest LDL/STL/LDQ/STQ at a sparse port with even byte address but lane 2 or 3 hits it. It is a real defect.
