**Q3 — Which statement in the header, the fix comment, or the POSTTABLE is wrong?** [REASONED]

The fix comment in `dev_lca.c`:

> "That guard's `ofs > len' exit(1) ended the host on a guest byte access to a port 2 or 3 mod 4 or a word access to a port 3 mod 4 (ungated BWX; or **the 1- or 2-byte head of an unaligned LDL/LDQ** that memory_rw splits at 1 KB)"

is technically wrong about the 2-byte head. The literal guard is `ofs > len`, not `>= len`. A 2-byte split head ending at port 0x3ff starts at port 0x3fe, so the handler is called with `ofs = 2, len = 2`; `2 > 2` is false and the guard does NOT exit. The 2-byte head h2 ldq/h2 stq are red on HEAD because the OLD write-arm wrote `data[ofs % len] = data[0]` instead of `data[1]` (= the SCR byte at position 1) and the test framework flagged the wrong value as "ended the host" — that is a wrong-byte failure mode of the read arm's discard + the write arm's `ofs % len` collapse, not the guard's exit(1). The 1-byte head (ofs=3, len=1) does exit; the 2-byte head does not.

The header and POSTTABLE statements I cannot fault on the inlined text. The "table 2's 20 + the eight head rows" arithmetic reconciles (20 from the 51-row plus the 4 data rows + 4 alive rows of the four one-head processes = 28 red on HEAD, 49 green on FIX, 77 green on base — totals work for both axes). The "nine no earlier session reached" wording is off by one (4d emits 10 non-FULL rows) but the cell-coverage claim itself holds.

The x_wfallthru disclosure reads correctly: the probe's writes go only to MCR, IER, and MSR, all of which reflect their stored value on a subsequent read, so the fall-through read returns the same byte that was written, leaving `data[ofs]` byte-identical.
