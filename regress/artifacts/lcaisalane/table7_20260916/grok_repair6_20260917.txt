### 1. Smallest edit that breaks the repair and still passes

**Mutant (one extra disjunct on the line this hunk added):**

```c
if (len == 0)
    return 0;
```
→
```c
if (len == 0 || len > 8)
    return 0;
```

**Rows expected green: all of them.** The 352-row instrument is instruction-driven (LDBU/LDWU/LDL/LDQ and stores, max `sizeof` 8) plus 1 KB-split fragments (heads 1–7, tails 3/5/6/7). Nothing in it calls the handler with `len > 8`. That is a **prediction from reading the probe**, not a table score — I did not build this mutant.

Why it is inside clause (d): `len == 0` is the predicate the hunk **added**. Widening it to `len > 8` is the canonical “keep the guard, null its repair” form: the `%` still runs for every rowed width, the early return still “looks like” the safety check, and the one-byte forward is refused on every width the rows never drive.

The same unrowed cell from the other dominating predicate:

```c
if (writeflag == MEM_WRITE)
```
→
```c
if (writeflag == MEM_WRITE && len <= 8)
```

That one is worse for the guest: a `len > 8` store **falls through into the read arm** (phantom read + clobber of the caller’s buffer) instead of declining. Also predicted 352/352. The probe’s own contract already names “a store arm narrowed to `len <= 2`” as in-scope; `<= 8` is that shape with the bound parked **above** every instruction-driven row.

`m_andmask` (`% len` → `& (len - 1)`) is **not** this answer any more. Table 1 predicted it equivalent because heads did not exist. Sessions `split` / `split67` now pin the cells where they differ (`h3 ldq` wants `3%3=0`; `& 2` puts the byte at position 2; `h5 ldq` wants `3%5=3`; `& 4` puts it at 0). I did not re-run `m_andmask` on the 352-row binary.

`m_lenzero` (delete the `len == 0` guard) is the **measured** equivalent, 37/37 and 51/51, disclosed in the probe header. It does not break any guest-visible cell the instrument has. It is a (d) null of the added predicate with no producer, not a clean-sweep of a reachable cell.

**On `len > 8` reachability (the in-flight measurement — not assumed either way):**

Verified in source, not from the packet:

- `store_buf` (`src/core/memory.c` 837–853) issues `memory_rw` at `psize ∈ {1024, 256, 64, 16, 4, 1}` with `CACHE_DATA` (translated, so the 1 KB split applies). A 16-aligned `len >= 16` access that does not straddle a 1 KB boundary is handed to the device **whole**.
- Sparse ports sit at `port << 5` (32-byte stride) → always 16-aligned. UART `0x3f8 << 5 = 0x7f00` is also 64- and 256-aligned, not 1024-aligned.
- Device length is `0x10000 << 5` (`dev_lca.c` 547–548) — no clamp below 1024.
- Alpha `PROM_R_GETENV` (`cpu_alpha_palcode.c` 121–144), dispatched from PAL `0x3fffffe` (496–498), calls `store_buf(cpu, a2, s, len)` with **guest-supplied** `a2`.

What is **not** established here: that a GETENV `a2` has been observed to decode into `lca_isa` on alphabook1. The producer of `len ∈ {16,64,256,1024}` exists; the hit on this handler is the measurement in flight. If that measurement is negative, this mutant is clause-(e) debt and must be disclosed by width (the probe header’s “1/2/4/8 plus the 1 KB split” currently **omits** those sizes). If it is positive, it is L2: a floor cell with no row.

`store_buf` **ignores** `memory_rw`’s return. Under the `return 0` form the 16-byte chunk is dropped and the pointer still advances — the bytes are not retried at size 4 or 1.

### 3. Is `(relative_addr & 3) % len` right? Is `len == 0` the only early return?

**As an emulator buffer rule, yes. As 21066 architecture, it is an ACCEPT of the write arm’s old wrap, not a decode of `a<4:3>`.**

GXemul hands this function a `len`-byte buffer whose size is the **instruction** (or the split fragment, or `store_buf`’s `psize`), not the sparse size field. For that convention:

- `len == 1` (LDBU/STB): `(P & 3) % 1 == 0` always. The only legal index in a 1-byte buffer. This is the actual fix of the ofs-1 zero-answer and the ofs-2/3 host deaths.
- `len == 2`: wraps 2→0, 3→1. Same wrap the write arm already did with `data[ofs % len]` when the old `ofs > len` guard let it run.
- `len == 4` or `8`: `P & 3` is already in range. `%` is a no-op. LE lane in the word/quad.
- `len == 0`: `% 0` is C99 UB. The early return is for that, not for the packing loop (which would simply not iterate).

**`len == 0` is the only `%` UB and the only case with no byte in the buffer.** `len` is `size_t` (`memory.h` `DEVICE_ACCESS`). Device-end truncation (`memory_rw.c` 495–523) cannot produce 0: a match requires `paddr < endaddr`, so `length - paddr >= 1`. I did not find a `memory_rw(..., 0, ...)` caller. That is why `m_lenzero` was equivalent. It is still the right refuse-before-`%`.

**What 3, 5, 6, 7 actually do to the formula** (`ofs_raw = P & 3 ∈ {0,1,2,3}`):

| `len` | `% len` | wraps? | vs `& (len-1)` |
|---|---|---|---|
| 3 | 0,1,2, **0** | **lane 3 only** | lane 3: 0 vs 2 |
| 5 | 0,1,2,3 (identity) | no | lane 3: 3 vs 0; lanes 1–2 also collapse under `& 4` |
| 6 | identity | no | lane 2: 2 vs 0; lane 3: 3 vs 1 |
| 7 | identity | no | lane 3: 3 vs 2 |

So among 3/5/6/7, **`%` only wraps at (len=3, lane=3)**. At 5/6/7 it is identity against dropping the `%`, and load-bearing only against `& (len-1)`, which the head rows now hold.

**Guest-reachable on this machine:**

- 1, 2, 4, 8: yes. Native Alpha load/store. `cpu_alpha_instr_loadstore.c` has **no alignment check** (grep for `align` is empty). `sizeof(data)` is 1/2/4/8.
- 3, 5, 6, 7: **yes on this emulator, no on a 21066.** They are 1 KB-split **heads** (always lane 3, port `0x1f` mod `0x20`) and **tails** (always lane 0) of unaligned LDL/LDQ/STL/STQ. Real hardware alignment-faults those instructions. This emulator does not, and the probe has already executed them (`SP(SCR)+0x1d` → len-3 head at SCR). `store_buf`’s ladder is `{1024,256,64,16,4,1}` — it never produces 3/5/6/7.
- `len > 8`: producer exists (`store_buf`); hit on this handler is the in-flight question. Not an instruction.

The size field `a<4:3>` still does not change `len` here. HRM 6.2.6 says it specifies transfer size and `a<2:0>` must be zero. The handler still shifts those bits away (`lcaisasize`). That is not this hunk, and a mutant keyed on `a<4:0>` is disclosed.

### 4. `return 0` on Alpha

A handler return of 0 does **not** mean “handled” and does **not** mean “unmapped → guest fault.”

Trace, all in `GXEMUL-SEC`:

1. `memory_rw.c` 595–596: `if (res == 0) res = -1;`
2. 603–624: `if (res <= 0 && !no_exceptions)` prints `debug("[ writing to/reading from device 'lca_isa' addr … failed ]")` — that is `debug()`, **silenceable** by `-q` / free-running `verbose`, unlike `fatal()`. Then MIPS/M88K exceptions only. **Then `return MEMORY_ACCESS_FAILED` (0) on Alpha anyway.** No `#ifdef MEM_ALPHA` arm.
3. `cpu_alpha_instr_loadstore.c` 68–74 (load) and 112–117 (store): `if (!cpu->memory_rw(…)) return;` **before** the destination register is written. Comment `#215` says “the translator already signalled a fault.” **False on this path.** Nothing delivered an Alpha exception. PC advances. The load is a nop on its destination.

So on Alpha, `return 0` is:

| member | what happens |
|---|---|
| 5 FAULT | **no** — S1 is right; no exception |
| 2 silent decline (`return 1`, `#95` zeros, dest := 0) | **no** |
| what you actually get | **silent incomplete access**: load leaves dest **unchanged**; store dropped; a `debug()` line |

That dest-preserved channel is **measured**: table 1’s `m_retzero` (read arm `return 1` → `return 0`) was predicted to keep the sentinel and scored 22/37 with those rows red. The `len == 0` `return 0` is the same contract, on a path with no producer.

Under `NO_EXCEPTIONS` (debugger `dump`): `res <= 0 && !no_exceptions` is false → `goto do_return_ok`. `return 0` becomes **success**. Opposite of the guest-instruction path.

`return 1` after a no-op would be the other refuse: load dest := 0 (`#95` already cleared the buffer), store dropped, instruction “succeeds.” For an unreachable `len == 0` either form avoids `% 0`. They are not interchangeable if a producer ever appears, and they are not FAULT.

Pre-existing asymmetry, not this hunk: the write arm already `return`s the inner `memory_rw` status, so a failed 1-byte forward already takes this Alpha path. The read arm ignores the inner return and `return 1`. The probe discloses that as equivalent on alphabook1 (no ISA device there fails).
