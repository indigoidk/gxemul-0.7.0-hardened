**Critical premise on a<4:3> — REASONED FALSE for "lcaisasize".** The sparse window stride is 32 (`>>= 5`), so the guest can only place accesses at 32-byte-aligned offsets. Bits <4:0> of relative_addr are FORCED to zero by the window design; therefore a<4:3> is always 00 on every access that reaches this handler. The model "discarding" a<4:3> is not a divergence — it is the only possible behaviour. A hardware-legal Word (a<4:3>=01) or Tribyte (a<4:3>=10) encoding **cannot be emitted through this window**, so the model cannot "serve it wrongly". The `lcaisasize` row is not real; it describes an access pattern the sparse window cannot produce.

## §E Question 2 — smallest edits that break the candidate (REASONED)

The brief lists six. I add:

- **Remove `exit(1)` without adding the decline branch.** Trap: with `fatal()` returning per S1, control falls through to the read/write arm after fatal(). For (1,2)/(1,3)/(2,3) the read packing loop would then silently produce all-zero data with `return 1` — exactly the false-success channel the fix is meant to close, just at different lanes.
- **Fix only the read packing loop (e.g. special-case len==1) but leave the write arm's `data[ofs%len]` for ofs >= len.** The (2,2) write would still emit a partial 1-byte write when it should be declined.
- **Move the decline check to *after* the read/write arms but before `return`.** Same trap as removing exit(1): the arms have already mutated the device or the caller's buffer.
- **Change the latch's "once" predicate to `>1` instead of `>=1`.** Second declined access prints the text twice.

## §E Question 3 — option set completeness (REASONED)

**Member 4 (ACCEPT) IS available for (len=1, ofs=1).** That cell is hardware-valid: a<6:5>=01, a<4:3>=00 is a Byte access at PCI I/O ad<1:0>=01 (Table 6-3). The model already reads the correct device byte (the PCI address carries the lane). The only thing wrong is the read packing loop discarding it. The correct serve is `data[0]=byte; for(i=1;i<len;i++)data[i]=0;` for the len==1 case (lane consumed by address, not by data placement). This is a *third* option distinct from the brief's binary decline/accept framing: **fix the loop, don't decline.**

**Member 7 (honour a<4:3>) is moot** — the sparse window cannot emit a<4:3>!=00, so there is nothing to honour. The cost is zero because the work is impossible.

## §E Question 4 — detector shape (REASONED, conditional on 1(d))

The (1,d) answer changes which rows are vacuous:
- If `return 0` leaves the register unchanged: the "decline row per refused cell reading the DECLINE CHANNEL" is the unchanged-register probe, **not** a zero read. The `ofs1 zero` witness row is meaningful *only* for the pre-fix false-success behaviour and becomes vacuous for the post-fix decline.
- If `return 0` writes zero: the `ofs1 zero` channel is reused, but the old false-success zero and the new decline zero are observationally identical from the guest — the detector cannot distinguish "bug" from "fix" by the zero alone, and must rely on the latched text or the death/undeath transition.

**Rows that are vacuous by construction regardless of 1(d):** the `latch indep` row against a #518 bit, unless #518's bit is itself reachable through `lca_isa`'s dispatch (it is not — the two `LCA_W_IOC_*` bits live in a different register window).

## §E Question 5 — things found while verifying

1. **Write-arm asymmetry at (len=1, ofs=1).** The write arm today does `byte = data[1%1] = data[0]` and writes it to the device at lane 1 (the lane is carried by the PCI address from relative_addr). That is *correct* — a 1-byte store at lane 1 puts the guest's only data byte at the addressed lane. The candidate's blanket decline of all `ofs >= len` therefore *regresses* this working write to a refusal. The brief's witness does not exercise stb at lane 1, so this regression is invisible to the inlined evidence but real. The fix should either (a) accept writes at (1,1) while declining reads (asymmetric, ugly), or (b) fix the read packing loop to place the byte at `data[0]` for `len==1` regardless of ofs, accepting the cell in both directions. The brief does not mention this.

2. **`(len=2, ofs=2)` write is partial, not just wrong-placed.** Today's code writes `data[2%2]=data[0]` to the device at lane 2 and drops `data[1]` entirely. The candidate declines it, which is strictly better, but a reader of the brief might think the only bug at (2,2) is the read zero — the write bug is a silent 1-byte-when-2-meant, which is worse than the decline.

3. **`(len=4, ofs=3)` and all `(len=8, ofs=*)` writes are also 1-byte-only.** The model writes only `data[ofs%len]` and drops the rest. Not flagged by the brief, not exercised by the witness. Out of scope for this round but worth noting in `lcaisalane`'s ledger row as "model is byte-lane for writes, multi-lane for reads — asymmetric by design."

4. **The format string `%i` for `size_t len`** is a real but minor defect, independent of the bounds bug. Codex noted it; it should be in the patch.

5. **The two downstream `memory_rw` calls lack `PHYSICAL`.** Codex noted; not checkable from the packet, but if true it means the calls go through the same sparse-window translate again — for ISA-space targets behind `LCA_ISA_BASE` this is probably fine since that base is itself a physical address, but worth confirming against memory_rw.c.
