## The one premise this packet states wrongly: the Q1(d) parenthetical

The brief asks which premise is false. It is the claim that "an interrupt delivered with BL set would be **rewritten** too, so the `cpu_dyntrans.c` gate is load-bearing." The packet's own code contradicts it.

READ: the packet's stated order is BL block (:910-918) → latch block (:941-955), with the switch after, and the `intevt > 0` branch inside the latch block writes `expevt = -1` and does **not** write `cpu->cd.sh.expevt` (that store is in the `else`). REASONED: for a BL-set interrupt, the block's rewrite lands on the local `expevt`, is then overwritten with -1, never reaches the EXPEVT register, and the switch sees -1 with or without the block. INTEVT, SPC/SSR/SGR, SR, and PC=VBR+0x100 are identical either way. The rewrite is observably vacuous on the interrupt path. The gate *is* load-bearing — but for the manual's pending rule (:12306), which this round does not touch, not for any EXPEVT rewrite. (The charitable reading — "the block would merely run" — makes the sentence vacuous, and the load-bearing role is still the pending rule.)

This does not weaken the fix; it strengthens it: the fix cannot corrupt interrupt delivery even if the dyntrans gate is not the only delivery site (which the packet cannot settle). It weakens only the fix's comment, which is change 1.
