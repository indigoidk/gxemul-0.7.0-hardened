## 2. `M_msr_argmask` — disclosure

Disclosure under clause (e). The loop row is the pin for that disclosed cell. It is not owed to close this floor.

The comment is a real depends-on. `X(msr)` writes `ic->arg[0]` from the register on every call, then calls `msr_imm`. `ic->arg[1]` is the field mask filled once at decode and never refreshed. The decline copies it into a local `mask` and clears `ARM_FLAG_MODE` there. A second execution of that same `ic` still declines, or still writes a later modelled mode, only if `arg[1]` still contains the mode bits.

`ic->arg[1] &= ~ARM_FLAG_MODE` breaks that for the register form: after one decline, that translated MSR never writes M[4:0] again, so a later accept through it stays in the old mode. The same write on an immediate MSR is guest-equivalent even in a loop, because that instruction's mode field is a constant unmodelled value. Stripping the cached mask's mode bits forever still declines the mode and still writes the other fields.

This probe cannot see the register-form case. Each grid observation is preceded by debugger commands, and `debugger()` clears every dyntrans translation before it reads them (`debugger.c` 781–797). It returns before that clear only while `debugger_n_steps_left_before_interaction > 0` (`debugger_cmd_step` sets that to `n - 1`). Inside one `step 2` the two MSRs are different PCs, so different `ic`s. The header's account of this is accurate, and `kt1b/LANE1b.out` is the measurement it cites.

Last pass's `& 0x17` cell was owed because the contract claimed the helper's answer on every mode value, and `0x18`–`0x1a` were the image of that one-bit edit. This contract now says the cached-mask write is not pinned, and says why. That is what clause (e) is for.
