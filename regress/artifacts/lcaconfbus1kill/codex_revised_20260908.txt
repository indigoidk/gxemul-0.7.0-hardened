**Q2. The observation technique transfers, but I cannot build or execute its regression here.**

No native GDB, LLDB, or C compiler was found on PATH. Both WSL enumeration and a direct `Gentoo` GDB invocation returned `E_ACCESSDENIED`. I cannot establish whether GDB is installed inside that inaccessible environment.

I inspected the available binaries directly: `../build/gxemul` and `../build-asan/gxemul` are x86-64 ELF files, retain both backend symbols, and contain actual calls from the configuration handler to both functions. The normal binary has a symbol table without DWARF; the ASan binary has DWARF.

The [SGI precedent](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/regress/sgi_eaddr_probe.py:35) therefore supplies a usable **argument-observation technique**, but its construction-only driver is insufficient here. An LCA observer must reach guest execution and associate its observations with individual completed accesses.

Use explicit function-entry breakpoints, `break *bus_pci_setaddr` and `break *bus_pci_data_access`, so argument registers are observed before the prologue. [GDB documents that distinction.](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Address-Locations.html)

| Entry | Values available under SysV AMD64 |
|---|---|
| `bus_pci_setaddr` | PCI object in `RSI`; bus, device, function, register in `EDX`, `ECX`, `R8D`, `R9D` |
| `bus_pci_data_access` | PCI object in `RSI`; data pointer in `RDX`; length in `ECX`; direction in `R8D` |

These mappings follow the signatures and [SysV AMD64 argument rules](https://gitlab.com/x86-psABIs/x86-64-ABI/-/raw/master/x86-64-ABI/low-level-sys-info.tex). **The second entry does not receive a BDF tuple in registers.** Inspecting its stored `cur_*` fields requires debug types or a separately verified structure layout.

For each permitted access, assert the exact requested tuple at the setter, followed by data access on the same PCI object with the expected length and direction. For reads, save the data pointer and inspect its contents after return: the function returns `void`, so `RAX` is not the result.

Routing rows must include distinct nonzero buses and high-bit bus values. Identical empty-slot results cannot prove correct routing. Missing breakpoints, missing tools, or an unfinished access must fail the observation, not count as successful rejection. GDB output also needs separation from the emulator’s debugger stream.

**Q3. The wrapper claim is correct; the claimed ordinary-enumeration consequence was overstated.**

In local [lca_pci.c](C:/DocumentNoSnc/CC/GXEMUL/_guest-src-openbsd22/sys/arch/alpha/pci/lca_pci.c:142), the supplied offset contributes to `datap`; `data` starts at `(pcireg_t)-1`; and only successful `badaddr()` permits `data = *datap`. There is no register-zero restriction.

Moreover, [badaddr()](C:/DocumentNoSnc/CC/GXEMUL/_guest-src-openbsd22/sys/arch/alpha/alpha/interrupt.c:179) returns whether a machine check occurred. It does not classify zero or all-ones data as a fault. Thus a faultless nonzero-register read returning zero would reach a caller as zero.

But [pciattach()](C:/DocumentNoSnc/CC/GXEMUL/_guest-src-openbsd22/sys/dev/pci/pci.c:138) reads `PCI_ID_REG` first and immediately skips IDs of zero or `0xffffffff`. It reads the header register only afterward, and repeats the ID guard before reading each function’s class and interrupt registers.

**Consequently, ordinary enumeration never reads nonzero registers of an absent function.** A direct configuration read there could observe the difference; this source trace does not establish an actual enumeration consequence. The normal LCA wrapper also selects type 1 only for a nonzero bus, so it does not itself generate the bus-zero/type-1 combination.
