## Defects in the brief itself

**D1 — Arithmetic off by 0x18 on every test address.** The handler's own comment says the address is constructed as `addr = (tag << 5) | ((regoffset & ~0x03) << 5) | (0x3 << 3)`. For reg=0 this is `tag << 5 | 0x18`. The brief computes `tag << 5` only:
- type-1 anchor: brief says `0x234000`, correct is `0x234018`
- type-1 alias: brief says `0`, correct is `0x18`
- type-0 dev 7: brief says `0x800000`, correct is `0x800018`

The tests still work because the handler discards `addr & 0x1f` via `>> 5`, so the mask `& 0xfc` and `& ~0xff` see the same values. **Not load-bearing, but the brief's "derived from the handler's own two lines, then confirmed by that printed tuple" is false — the printed tuple confirms `tag`, not `relative_addr`.**

**D2 — `t0 accept` table entry contradicts the 6/10 figure.** Four pre-fix FAILs are enumerated (bus kill, t1 alive, t1 anchor, t1 alias). Adding `t0 accept` as a fifth FAIL gives 5/10. The brief states 6/10. Either the bold `FAIL` is a typo (should be `ok`) or the count is wrong. The row's stated semantics ("the exact pre-fix value `0x304848086` is unchanged") is consistent with `ok | ok` — the diff does not touch the type-0 forwarding path. Likely a typo.

**D3 — `0x304848086` vs `0x0000000304848086`.** These are the same number (leading zeros dropped). Not a defect, just a notational switch between P4 and §F.

## Q1 — Vacuity floor, clause (d)

**Agree.** The two unrowed cells are `(type1=1, bus≠0, read)` and `(type1=1, bus==0, read)`. Both return `reg==0 ? -1 : 0`, identical to `bus ctlsig`'s output. No guest-observable channel distinguishes them:

- Timing differences (if any) are below the guest's resolution in a config-space probe.
- The WRITE cells ARE distinguishable (D3 of §G, t1 anchor prints, t1 alias does not) and are rowed.

The brief's closure is correct.

## Q2 — Refusal disposition

**(a) Silence is defensible.** A guest probing type-1 space is not in error — it is asking "is there a bridge?" The empty-slot all-ones answer is the correct PCI-semantic reply. A `(once)` latched announce would be appropriate if the refusal were unexpected from the guest's view; it isn't.

**(b) The asymmetry is defensible but should be disclosed in the round's commit message.** "Forwarding prints a diagnostic; refusing does not" is not a sibling-parity breach — they are different operations ("I tried and failed" vs "I declined to try"). But the round should say it.

**(c) Yes — disclose the convention.** §6.2.18 master-abort behavior is real hardware. The all-ones answer is an emulator-compatibility choice. The round should state this in one sentence; not disclosing it leaves a reader who knows the HRM to wonder why no MASTER_ABORT path exists.

## Q3 — De-escalation accept rows

**"No such state is constructible" is acceptable as written, with disclosure.** The forwarding mechanics (`bus_pci_setaddr` + `bus_pci_data_access` with the bus/dev/func tuple) are exercised by `t1 anchor`, which forwards to a NON-existent device and confirms the tuple reaches `bus_pci_data_access`'s `dev == NULL` arm with the right fields. The "device exists on bus>0" case adds nothing the forwarding mechanics don't already cover — `bus_pci`'s device lookup is the same code path as type-0 to a registered device (`t0 alive`/`t0 real`/`t0 accept`). The disclosure should say so explicitly.

## Q4 — Anchor row's fragility

**String coupling is the only available oracle, and it is acceptable with disclosure.** The brief's check is correct: `bus_pci_setaddr` prints nothing (per P2, itself UNVERIFIABLE — see above), `bus_pci_data_access`'s write-to-nonexistent arm prints exactly one diagnostic (READ), and there is no return-value, register, or status channel in the shown code. The diagnostic string is the only side effect.

Two ways the anchor could silently rot:
1. The diagnostic is reworded but still printed — the regex would need updating; a "still printed" check (e.g., count of `bus_pci_data_access` lines in the log) would be more robust.
2. `fatal()` is changed to actually exit — the diagnostic still prints, so the anchor still fires, but the host now dies on the type-1 anchor instead of surviving. This is a strictly worse defect, not a silent regression.

A more robust oracle would parse for the presence of *any* `bus_pci_data_access` line rather than the exact tuple. The brief should consider this; it does not invalidate the round.
