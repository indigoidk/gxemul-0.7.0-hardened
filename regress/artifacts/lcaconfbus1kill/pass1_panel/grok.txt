### Q1 — `dev = (tag >> 11) & 0x1f` is right. The comment’s `tag` is this `tag`.

The comment in `lca_pci_conf` is the composition of a *software* tag, then a sparse-space shift:

```
addr = tag << 5 | (regoffset & ~0x03) << 5 | 0x3 << 3
```

The code undoes that:

```c
reg = (relative_addr >> 5) & 0xfc;
tag = (relative_addr >> 5) & ~0xff;
```

`relative_addr` is `uint64_t` (`DEVICE_ACCESS` in `memory.h`). `>> 5` undoes `tag << 5`. `& ~0xff` strips the register (bits 7:2) that OpenBSD ORs in separately as `(offset & ~0x03) << 5`. `(0x3 << 3) >> 5` is 0, so the sparse size bits vanish. What remains is the software tag the comment named.

Worked example, OpenBSD type-1 `bus=1, device=5, func=2, offset=0x04`:

| quantity | value |
|---|---|
| software tag | `(1<<16)\|(5<<11)\|(2<<8)` = `0x12a00` |
| `relative_addr` | `(0x12a00<<5) \| (0x04<<5) \| 0x18` = `0x254098` |
| `reg` | `(0x254098>>5) & 0xfc` = `0x04` |
| `tag` | `(0x254098>>5) & ~0xff` = `0x12a00` |
| `(tag>>11)&0x1f` | `5` |
| `(tag>>8)&7` | `2` (already extracted below the `if`) |
| `(tag>>16)&0xff` | `1` |

OpenBSD `lca_conf_read` (`lca_pci.c`) builds that address for any `secondary != 0` and leaves the tag *unfrobbed*. The in-tree helper `bus_pci_decompose_1` is the same layout: bus 23:16, device 15:11, func 10:8, reg 7:0.

The wrong shift would be applying `>> 11` to `relative_addr` (device would land in bits 10:6 of the software tag — function/register junk). The sketch uses `tag`. Do not shift again.

`tag` is a signed `int` (`lca_pci_conf`). The config window is `0x20000000` bytes (`DEVINIT(lca)`), so `relative_addr>>5` is 24 bits. Arithmetic `>>` does not fire. (Linux’s type-0 walk stops at device 12; this model walks to 21. Pre-existing, not this round.)

### Q2 — `IOC_CONF` is cycle type. The bus number is in the tag. The sketch keeps the wrong source.

Three independent sources, none of them the model’s own `lca_ioc` comment:

1. **The header.** `alpha_lcareg.h`: `LCA_IOC_CONF /* Configuration Cycle Type */`. Same text in OpenBSD `lcareg.h`.
2. **OpenBSD `lca.c`**, citing the 21066 HRM §6.4.2: bits `<1:0>` are write-only; write `0x00` “for PCI Type 0 configuration access.”
3. **OpenBSD `lca_conf_read` / `lca_conf_write`:** decompose the tag to get the *bus number* (they name it `secondary`); if it is non-zero, write `LCA_IOC_CONF = 0x01` and put the **unfrobbed** tag — `(bus<<16)|(device<<11)|(function<<8)` — into the address. `0x01` is written for bus 2 the same as for bus 1. The actual bus number never enters `IOC_CONF`.

So `bus = d->ioc_conf & 1` in `lca_pci_conf` is using a 1-bit cycle-type latch as if it were an 8-bit bus number. That happens to match a guest that only ever scans bus 1. It mis-routes bus 2+ to `cur_bus=1`.

The `lca_ioc` comment (“PCI bus 0 vs bus non-0 selection bit”) is the model author’s collapse of those two quantities. Shipping the sketch *and* leaving that comment is a wrong record: the sketch still treats the bit as the bus number, which is what the comment says and what the header/OpenBSD contradict.

**In-tree precedent:** `DEVICE_ACCESS(uninorth_addr)` — the type bit (`idata & 1`) selects the *decode method*; on type-1 it calls `bus_pci_decompose_1` and takes `bus` from the tag. `SH4_PCIPAR` does the same extract (`(idata>>16)&0xff`). Mechanism-1 callers (eagle, cpc700, gt, ip32, footbridge) all take bus from the tag. The one sibling that *overrides* the extract is `dev_i80321.c` (`bus = 0; /* NOTE */`). Do not copy that.

**Does taking `bus` from the tag make type-1 “incoherent”?** Only for the pair no real driver emits: `IOC_CONF=1` with a tag whose bus field is 0. Hardware would generate a type-1 cycle; local devices respond to type-0 IDSEL, so the SIO at bus 0 device 7 would not answer. `bus_pci_setaddr(0, 7, …)` *would* hit `PCIINIT(i82378zb)`. OpenBSD/Linux never pair those. Disclose it; do not special-case it in this round.

Recommended `else` (then the existing tail):

```c
} else {
	/* type-1: IOC_CONF bit 0 is the cycle type; bus/dev are in the tag */
	bus = (tag >> 16) & 0xff;
	dev = (tag >> 11) & 0x1f;
}
```

That is one extra assignment, not a larger fix. `func` and `reg` stay where they are — they are already type-agnostic. Do not early-return; the common tail is `bus_pci_setaddr` → `bus_pci_data_access` → `memory_writemax64` → `return 1`.

On today’s `alphabook1` topology the extra assignment is observationally identical to the sketch for every access OpenBSD actually issues (the only `bus_pci_add` in `DEVINIT(lca)` is bus 0, device 7, `"i82378zb"`, an ISA bridge, not a PCI-to-PCI bridge). It is still the right line: `bus_pci` is bus-agnostic (`cur_bus` is a plain `int`; lookup is `dev->bus == pci_data->cur_bus`; `machine_cats.c` already places a device on bus `0xc0`).

### Q3 — IMPLEMENT (member 7). Decline is a lie at vendor ID.

This is a stubbed path, not a value refusal: the `else` is `fatal`+`exit(1)` with no decode. Member 7. Member 4 (ACCEPT) does not apply — nothing currently computes the type-1 fields and then discards them.

| member | what the guest sees at an empty-slot *vendor ID* read |
|---|---|
| silent decline / `return 1` without writing | `0` (`memory_rw.c` `#95` pre-zero) |
| `return 0` (FAULT) | `0` (unmapped) |
| hardcoded `odata = (uint64_t)-1` | all-ones at every register |
| IMPLEMENT via `bus_pci` | all-ones at `cur_reg==0`, **0 at every other register** |

PCI ID probes treat `0xffffffff` as “absent” and `0` as “vendor 0”. Decline that returns 0 can invent a device. The house idiom in all 10 `bus_pci_setaddr` callers is decode-and-dispatch, not decline.

The brief’s “absent device answers all-ones by itself” is **false as a universal**. `bus_pci_data_access`: empty READ returns `(uint64_t)-1` only when `pci_data->cur_reg == 0`; otherwise `*data = 0`. That is the discriminator between “fell through into `bus_pci`” and “hardcoded all-ones”.

A latched announce on top of IMPLEMENT is optional and not licensed by a measured delta. Bare IMPLEMENT matches type-0 in the same function (the `dev>=21` arm already deleted its `exit(1)`).

### Q4 — All-ones at the *current* armed address is not enough, and not even a type-1 cycle.

The witness’s armed `ldq` is `LCA_PCI_CONF+0` (`lca_confbus_probe.py`: `put d` of `k0(LCA_PCI_CONF)`, then `LDQ(T2, 0, T1)`). That is `relative_addr = 0` → `tag = 0`, `reg = 0`. It is a type-0-shaped empty slot. After the sketch:

- `bus = 1`, `dev = 0` → empty → all-ones
- architectural `bus = (tag>>16)&0xff` → bus 0, dev 0 → also empty → all-ones

Same number. The row cannot see Q1 or Q2.

Even at a *proper* type-1 address — `relative_addr = ((1<<16)<<5) = 0x200000` for bus 1, device 0, func 0, reg 0, well inside the `0x20000000` window — empty-slot data still cannot kill a wrong shift. `(tag>>11)&0x1f` versus `(tag>>8)&0x1f` versus `(tag>>16)&0x1f` all miss every device on this machine and all return all-ones at reg 0. **Q1 is a reading. It is not guest-measurable on the current topology.** Write that into the contract; do not pretend the all-ones row pins the extract.

What the detector *can* pin, cheaply, without adding a device:

1. **Survival** of the armed access (the witness already has this; it greens silent decline, latched announce, and IMPLEMENT alike).
2. **Reg 0 = `0xffffffffffffffff`** at a *type-1-encoded* address (bus 1 in the tag, not `+0`). Separates “serviced empty” from “`#95` zero / unmapped”.
3. **Reg 4 (or any `cur_reg != 0`) = 0** at that same tag. Separates `bus_pci`’s empty-slot policy from hardcoded `-1`. Together, (2) and (3) are the empty-slot signature `bus_pci_data_access` actually implements.
4. **Keep the type-0 control** at `ioc_conf==0` (already `bus ctlsig`).

Still conflated after that: IMPLEMENT vs “decline that forges the same two values”; `bus = ioc_conf&1` vs `bus` from the tag, on any empty secondary bus. Disclose both. Do not add a `bus_pci_add(..., 1, …)` to alphabook1 to pin them — that is a product topology change, not a detector row.

### Q6 — Other findings
