**Q2. Yes: `(tag >> 16) & 0xff` has the correct position and width.**

PCI type-1 assigns bus to `AD[23:16]`: eight bits, representing 256 bus numbers. Device occupies `[15:11]`, function `[10:8]`, and register number `[7:2]`. [PCI Figure 3-1 and accompanying definitions](https://e2e.ti.com/cfs-file.ashx/__key/communityserver-discussions-components-files/639/1016.PCI.Local.Bus.Specification.Revision.3.0.pdf#page=48)

The backend can represent and distinguish the entire bus range:

- `bus_pci_decompose_1()` already uses precisely that mask and shift.
- `cur_bus` and each device’s `bus` are plain `int`.
- `bus_pci_setaddr()` stores the supplied number unchanged.
- `bus_pci_data_access()` performs exact bus/device/function equality against a linked list.

There is no one-bit bus representation or bus-indexed array imposing a smaller range. [`bus_pci.c:72`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/bus_pci.c:72), [`bus_pci.h:83`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/include/bus_pci.h:83), [`bus_pci.c:192`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/bus_pci.c:192)

That establishes numeric capacity, not populated buses or bridge routing. Cycle-format selection must still precede extraction and remain based on the accepted `IOC_CONF` mode.

**Q3. Yes, forwarding can be worse on a guest-observable axis: it manufactures successful completion. That prevents an unqualified IMPLEMENT approval.**

The strongest case against my recommendation is that hardware reports a failed transaction, whereas the replacement updates the destination register and continues ordinary execution. The mandatory error indication matters: “arbitrary data” could happen to be all-ones, but it is accompanied by an instruction exception, internal interrupt, and error logging. [LCA §6.2.18](https://openwatcom.org/ftp/devel/docs/21066_66a_hrm.pdf#page=211)

There is a concrete software consequence. The historical OpenBSD `lca_conf_read()` initializes its result to all-ones and reads the register only if `badaddr()` succeeds. Consequently, hardware absence is normalized to all-ones **at any register offset**. A faultless backend zero at a nonzero offset can change that result. This is a source-derived consequence, not a claimed emulator boot measurement. [`lca_pci.c:142`](C:/DocumentNoSnc/CC/GXEMUL/_guest-src-openbsd22/sys/arch/alpha/pci/lca_pci.c:142)

There is also a routing defect requiring **no synthetic device**: unconditional forwarding of type-1 with bus zero can select the existing primary-bus `i82378zb`. The backend receives no cycle type and therefore cannot reject that alias. Ordinary PCI targets ignore type-1 transactions; the installed function is a PCI-to-ISA bridge, not a PCI-to-PCI forwarding bridge. My earlier caveat identified this, but **identifying it did not repair the proposed fix**. [`bus_pci.c:99`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/bus_pci.c:99), [`bus_pci.c:753`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/bus_pci.c:753), [PCI transaction-routing rules](https://e2e.ti.com/cfs-file.ashx/__key/communityserver-discussions-components-files/639/1016.PCI.Local.Bus.Specification.Revision.3.0.pdf#page=49)

The rebuttal has limits too:

- The existing host exit does not deliver the required guest exception or permit guest recovery.
- Handler `return 0` does not supply it either: the device-failure path has no Alpha exception arm, and the Alpha load returns before updating its destination. [`memory_rw.c:603`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c:603), [`cpu_alpha_instr_loadstore.c:68`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_instr_loadstore.c:68)

Therefore **IMPLEMENT remains defensible only as explicitly limited translation into this flat PCI model**, with a defined absence-completion contract and prevention of the type-1/bus-zero alias. It is not a complete LCA transaction implementation. If complete hardware behavior is the acceptance criterion, this prescription cannot satisfy it.
