**Q2. Are the five guards sufficient?  No — here are five filters that pass all five and still lie.** (All REASONED from the packet's own facts.)

1. **Multi-session row, partial execution.** Select `accept8`. The implementation runs 1 of its 8 sessions. `accept8`'s check is lenient (e.g., "did at least one sub-check pass"); it reports PASS. 2. **Stale transcript on a mutant.** Select row R. Replay serves R's transcript captured against binary B0; the current binary is B1 (mutant). R passes based on B0 evidence. Guards see a pass. **Lied.** The guards are content-blind — they don't bind the result to the executable that produced it. This is exactly the cache-by-pathname trap codex names.
3. **Required controls excluded but exempted.** Filter selects {R1}. Required controls = {C1, C2, C3}. Controls are exempt from the filter, so the implementation's exempt-list iteration is what counts them. If the exempt path silently drops C2 (typo, control renamed, control moved out of the exempt set), C1 alone passes `all([C1])` and the control line reports OK. Guard 5 only checks "nonempty OR hard-fail on empty." **Lied.** "Nonempty" is not "complete with required identities."
4. **Crash/hang silently skipped.** Select {R1, R2}. R2's session hangs and is killed. 5. **Substring token collision.** Filtered run emits `OPUS497T_DONE_FILTERED`. Gate substring-searches `OPUS497T_DONE` and accepts as a full run. All five guards pass. **The harness interface itself is a guard surface** and none of 1–5 covers it. Codex's "distinct token, no legacy substring" rule is mandatory, not optional.

Additional guards the packet's five lack: declared inventory validation pre-execution (reject mixed valid/invalid names); pre-run intent print (requested names, expanded execution set, planned sessions); per-row session-set membership check (every required session for a selected row is included); required-control identity list (not just nonempty); distinct completion token; provenance binding between result and the executable that produced it.

**Q3. Session-gating vs row-gating, and how a retrofitted probe would prove independence.**

Session-gating is necessary. The packet's own claim — "TEST this claim, do not accept it: 36 of 39 sessions are module-level, so a row()-level filter passes all five guards and saves nothing" — is **supported by the packet itself** (codex's static inspection: 36 direct `session()` assignments plus three call sites in module-level loops; `accept8` aggregates 8 emulator runs). READ: that claim holds as stated. Therefore row-gating alone cannot be the answer.

But session-gating requires a row→session mapping that the current source does not carry. A retrofitted probe would prove independence by one of three ugly mechanisms, each of which is the hidden execution framework codex rejects:
- (a) **Static declaration** — every row declares its session set. Per-site edits; honest.
- (b) **Instrumented runtime** that records session→row mappings during a calibration run, then replays the map. New execution model; reviewers must understand the recorder.
- (c) **Source rewrite** that materializes per-case functions. Honest but invasive; only viable for greenfield probes.

The honest answer: if you want session-gating on an existing probe, you do (a) by hand, not (b) or (c) automatically. For new probes, (c) is the default and `m88k_idle_probe.py` shows the shape.
