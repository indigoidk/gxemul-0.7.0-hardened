Q1: **Stores return status; loads return data without a failure indication.** Here are the complete definitions from [memory.c:763](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/memory.c:763) and [memory.c:886](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/memory.c:886):

```c
int store_64bit_word(struct cpu *cpu, uint64_t addr, uint64_t data64)
{
	unsigned char data[8];
	if ((addr >> 32) == 0)
		addr = (int64_t)(int32_t)addr;
	data[0] = (data64 >> 56) & 255;
	data[1] = (data64 >> 48) & 255;
	data[2] = (data64 >> 40) & 255;
	data[3] = (data64 >> 32) & 255;
	data[4] = (data64 >> 24) & 255;
	data[5] = (data64 >> 16) & 255;
	data[6] = (data64 >> 8) & 255;
	data[7] = (data64) & 255;
	if (cpu->byte_order == EMUL_LITTLE_ENDIAN) {
		int tmp = data[0]; data[0] = data[7]; data[7] = tmp;
		tmp = data[1]; data[1] = data[6]; data[6] = tmp;
		tmp = data[2]; data[2] = data[5]; data[5] = tmp;
		tmp = data[3]; data[3] = data[4]; data[4] = tmp;
	}
	return cpu->memory_rw(cpu, cpu->mem,
	    addr, data, sizeof(data), MEM_WRITE, CACHE_DATA);
}
```

```c
uint64_t load_64bit_word(struct cpu *cpu, uint64_t addr)
{
	unsigned char data[8];

	cpu->memory_rw(cpu, cpu->mem,
	    addr, data, sizeof(data), MEM_READ, CACHE_DATA);

	if (cpu->byte_order == EMUL_LITTLE_ENDIAN) {
		int tmp = data[0]; data[0] = data[7]; data[7] = tmp;
		tmp = data[1]; data[1] = data[6]; data[6] = tmp;
		tmp = data[2]; data[2] = data[5]; data[5] = tmp;
		tmp = data[3]; data[3] = data[4]; data[4] = tmp;
	}

	return
	    ((uint64_t)data[0] << 56) + ((uint64_t)data[1] << 48) +
	    ((uint64_t)data[2] << 40) + ((uint64_t)data[3] << 32) +
	    ((uint64_t)data[4] << 24) + ((uint64_t)data[5] << 16) +
	    ((uint64_t)data[6] << 8) + (uint64_t)data[7];
}
```

`MEMORY_ACCESS_FAILED` is zero; `MEMORY_ACCESS_OK` is one. Thus `swpctx` really does discard actionable store status. For loads, **the helper discards the status**: its caller cannot distinguish a failed read yielding zero from a successful read of zero. Testing the returned scalar would not fix that.

The 32-bit helpers used for CPC and ASN have the same distinction: `int store_32bit_word(...)` propagates status; `uint32_t load_32bit_word(...)` discards it. See [definitions](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/memory.c:794).

Q2: **The flags are `CACHE_DATA`, without either `NO_EXCEPTIONS` or `PHYSICAL`.** `CACHE_DATA` itself is zero. Consequently these accesses invoke translation; the translator receives zero for reads and `FLAG_WRITEFLAG` for writes. [Flag definitions](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/include/memory.h:116), [translation dispatch](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c:241).

Absence of `NO_EXCEPTIONS` does **not** establish that an exception occurs:

- Alpha’s translator does not act on `flags`. Its `not_found` path logs through `fatal()` and returns zero, without setting a guest exception or stopping the CPU. [memory_alpha.c:192](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_alpha.c:192).
- `fatal()` is a logging function here; it does not terminate execution. [debugmsg.c:384](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/debugmsg.c:384).
- On translation failure, shared `memory_rw` zero-fills the read buffer and returns failure; a write returns failure before accessing the target. It adds no Alpha exception. [memory_rw.c:259](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c:259).

So these failures are silent **to guest exception handling**, although diagnostics are printed. The comment claiming that the caller “raises the fault” is not implemented by this call chain.

“Unbacked” needs a separate distinction:

| Condition | Actual behavior |
|---|---|
| Failed translation | Failure status; failed read bytes become zero; failed write portion is skipped. |
| Translated address outside RAM, with no matching device and no configured halt | Reads return zero; writes are dropped; **status reports success**. |
| Valid RAM lacking an allocated host memblock | Reads return zero successfully; writes allocate backing. This is ordinary sparse RAM behavior. |

The latter two paths are in [memory_rw.c:662](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c:662) and [memory.c:539](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/memory.c:539). Adding caller status checks would not detect the success-reporting case.

There are exceptions to any blanket “zeroes and continues” description. The nonexistent-memory halt option can stop all CPUs and return failure **before** read-buffer initialization. Device failures have their own behavior. A split read can retain an already successful prefix. Thus neither “every failure is silent” nor “every failed load returns an entirely zero word” is universally correct.

Q3: **Both incomplete saves and corrupted incoming PCB contents are possible, conditional on which accesses succeed.**

The [save/load block](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_palcode.c:229) accesses these fields:

| PCB offset | Width | Field |
|---:|---:|---|
| 0 | 64 bits | `apcb_ksp` |
| 8 | 64 bits | `apcb_usp` |
| 16 | 64 bits | `apcb_ptbr` |
| 24 | 32 bits | `apcb_cpc` |
| 28 | 32 bits | `apcb_asn` |
| 32 | 64 bits | `apcb_unique` |
| 40 | 64 bits | `apcb_flags` |
| 48 | 64 bits | `apcb_decrsv0` |
| 56 | 64 bits | `apcb_decrsv1` |

During saving, successful writes remain committed. A translation-failed write leaves its target unchanged, and subsequent saves and the incoming load still happen. There is no rollback. An incomplete save requires mixed outcomes; if every save fails, none of the outgoing image is refreshed.

During loading, `ctx` changes to local `a0` **before** the reads. All nine values are collected into locals, then assigned unconditionally to the PCB. Completely failed translation reads contribute zeroes; successful reads contribute their actual values. If all nine reads fail completely, all nine PCB fields become zero.

A useful qualification: **the incoming PTBR is installed after all reads**, so those reads still use the outgoing PTBR. This is not a progressive switch of translation context between individual loads.

The handler then invalidates translation caches and returns. Translation failure itself leaves `running` unchanged, so instruction dispatch continues; subsequent execution can encounter further failures. The [PAL instruction wrapper](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_instr.c:53) contains no recovery for this case.

The observable consequences are concrete: PTBR controls subsequent translation, and PCB fields are written back on a later save. However, this block does **not** assign the general-purpose stack-pointer register merely because `apcb_ksp` changes.
