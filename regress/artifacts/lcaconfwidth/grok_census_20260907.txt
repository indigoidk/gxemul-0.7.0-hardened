### Reachability (why “CODE” ≠ “LIVE”)

- `memory_readmax64` starts at 0 and consumes exactly `len` bytes. Bits 32–63 are zero unless `len == 8`.
- Alpha `stq` is `loadstore_type = 3` = `LS_Q` = 8 bytes. LCA is on Alpha. **IOC_CONF is guest-reachable with a distinguishing value.** The same function already accepts `0x300800000ULL` at W_BASE0, which does not fit in 32 bits, so 64-bit stores are the native access.
- igsfb is NetWinder (ARM SA110). clmpcc is mvme88k (m88k). g2 is Dreamcast (SH4). Those integer ISAs issue `len <= 4` on ordinary stores, so every **guest** `idata` prints correctly even though the C is wrong.
- Debugger `put d` is a 64-bit `store_64bit_word` (and `put q` is still `TODO`). That can poke an 8-byte write on a 32-bit CPU, but it is not a guest instruction, so it is not a rung-3 witness as the ladder defines one.
- **`mb8696x` is not attached to any committed machine.** The only `device_add` is commented out in `machine_dreamcast.c`.

Same-function controls that are **not** members: TB_ENA / W_BASE0 / W_MASK0 / W_BASE1 / W_MASK1 already print `%" PRIx64 "` of `(uint64_t)idata`. TB_ENA is the same `idata & ~MASK` shape with the print already wide.

## Q2 — is S4 right?

**As a C-level discriminator, yes. As a complete membership rule, no — it mishandles both shapes you named, in opposite ways.**

**Address-guard defaults should not be members.** The kill is “this offset is unimplemented.” There is no accepted `idata`, so no value exists that trips the guard and prints as something the guard would accept. Truncating the payload can be *misleading*; it cannot name an accepted value. A text oracle that keys on the **offset phrase** is sound. Folding these into IOC_CONF’s round is a sweep.

**Latent sites (narrowing, but every reachable guest value fits in 32 bits) should be members of the class and tagged LATENT, not first-round fixes.** S4 as written includes them (the guard *can* be tripped by discarded bits in the C abstract). Treating them as live host-kill-wrong-records overclaims: on ARM/SH4/m88k a guest store cannot produce the distinguishing value. A blanket edit of latent diagnostics is the addition licence’s “cannot hurt.” Disclose them; do not sweep.

Two further holes S4 should name:

1. **Proximity ≠ subject.** A `debug()` of `idata` three lines above an `exit(1)` whose `fatal()` does not print the value (g2 CHAN_ENABLE) is not a member. A commented `exit(1)` is not a member. That is how 15 was born.
2. **`~` signedness.** `idata & ~1` (signed `int`) sign-extends and **does** test bits 32–63. `idata & ~(uint32_t)1` zero-extends and would **not**. S4’s “a guard testing only bits 0–31 is not a member” is a real category; these particular `~int` sites are not in it.

## Q3 — `dev_lca.c:313` and `dev_mvme187.c:88`

**Neither is a member of this class.** Both are the unimplemented-offset default: print `(int)relative_addr`, and on writes also `(int)idata`, then `exit(1)`. The guard is the address, not the value.

- LCA IOC window is `0x20000000` bytes; `relative_addr` fits in 32 bits, so the **address** half of the print is not truncated.
- Same split-print shape, two files. A consistency edit to `PRIx64` would be per-site (or a new helper, which needs a warrant). It is not the IOC_CONF fix and must not ride that round.

## Q4 — fix and blast radius

**The obvious form is already in this file.** Five sibling value-guard `fatal()`s in `dev_lca_ioc` use:

```c
" (0x%" PRIx64") ...", (uint64_t)idata
```

IOC_CONF is the leftover `0x%x` / `(int)idata`. The filed row’s “file’s own idiom is `%llx` + `(long long)`” is **false of this file**.

`PRIx64` is used widely in the tree (`src/devices/dev_lca.c`, `dev_wdc.c`, `dev_vr41xx.c`, `memory_rw.c`, …). `misc.h` includes `<inttypes.h>`; `dev_lca.c` includes `misc.h`. The `NO_C99_PRINTF_DEFINES` fallback still defines `PRIx64` as `"llx"` or `"lx"`. The sibling arms already compile.

**Blast radius of fixing IOC_CONF only: none measured.** Grep of `regress/*.{py,sh,c}` and `tools/*.{py,sh,c}` finds **no** match on `IOC_CONF`, `unimplemented bit of`, `IGS_VDO flags`, `FE_BMPR16`, `STCR byte`, or `extdma magic`. No current probe, hygiene grep, or gate keys on that text. A future `lcabadval` row that matches the unique phrase `"unimplemented bit of IOC_CONF"` (not the hex) will not invert when the specifier widens. A row that matches the full string including a 32-bit-only hex would.

**Do not sweep 226/309/15/18.** Most are 8-bit debug prints. Changing them can turn a green debug-text oracle red. First round is the one LIVE site; latent CODE sites file as class debt.

## Q5 — ordering vs `lcabadval`

**Not a prerequisite.** S2 overstates the oracle problem.

The interrupt confound forces matching **text rather than exit status**. It does not force matching the **hex payload**.

- `"unimplemented bit of IOC_CONF"` and `"lca_interrupt_assert: TODO"` are different strings. Phrase-match is sound today, including at that arm.
- A value-match oracle is unsound **only for high-bit-only killing values** (`0x100000000` prints as accepted). It is sound for `0x2`, which kills and prints `0x2`.
- The other five value-guard arms already print `PRIx64`. They can be witnessed without this fix.
- Alpha `stl` of `0x2` is a 32-bit store: high bits stay 0, print is accurate, host still dies. That is a complete IOC_CONF row for `lcabadval`’s “unimplemented bits kill” claim.

`lcaconfwidth` is a **sibling** whose own witness is the `stq`/`put d` of `0x100000000` and a check that the log says `0x100000000` rather than `0x0`. That row is this defect; it is not owed before `lcabadval` can be built.

If someone insists on driving IOC_CONF with a high-bit-only value **and** matching the hex, then the printf fix must land first. That is a choice of oracle, not a dependency of the row.
