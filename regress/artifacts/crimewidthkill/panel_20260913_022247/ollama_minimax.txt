## Question 1 — the fix

The declined access does exactly what the comment claims: skip the switch, return 0 on read (because `odata` is never populated for narrow lengths and the tail writes it), drop the write, advance the PC, raise no exception, announce once per device instance. READ.

**The prelude is not a problem for a declined access.**
- `d->reg[CRIME_REV] = use_fb ? 0xa1 : 0x11;` runs before the width arm. Under decline, `odata` is not populated from `d->reg`, so the refresh is invisible to the declined read. Under a hypothetical fall-through, the refresh would matter (a narrow read of CRIME_REV would see 0x11, not 0), but that is precisely what the goto prevents.
- The `>1024 MB` and `% mb_per_bank` fatals above the width arm are pre-existing and unchanged. With `-M 48` (not divisible by 32), the emulator exits at the first CRIME access regardless of width. This is filed as `crimebankorder`/`-M 48` and is not introduced by the fix.
- The `CRIME_HARDINT` save at function entry and the tail's restore are correct under decline: the save happens before any side effect, the restore happens at the tail, the goto does not skip the restore.

`int warned` + `CRIME_W_LEN` matches the house idiom (N=1 per device instance, `(once)` in the message, memset(0) at init claimed). I cannot verify the init line or absence of other writers from this packet (see "What the packet does not let me check").

## Question 2 — the smallest uncaught edit

The kill table covers 19 mutants. The packet itself flags the gap: **"address-conditioned fall-throughs (a goto keyed on relative_addr), which reach the switch only at the labels a refused access happens to name — owed as a pass-2 question, not yet measured."**

The detector's refusal rows are pinned to two addresses only: **+0x00 for reads** (lb rev pc, lh rev pc via the CRIME_REV PROM-probe hack) and **+0x08 for writes** (sh08 pc/run, sb08 msg via CRIME_CONTROL). No row tests a narrow access at +0x10 (INTSTAT), +0x18 (INTMASK), +0x30 (DOG narrow), +0x38 (TIME), or a narrow read at +0x08.

**Concrete uncaught edit** (smaller than the packet's own example, which *is* caught):

```c
		if (!(d->warned & CRIME_W_LEN)) {
			d->warned |= CRIME_W_LEN;
			fatal("[ crime: unimplemented len=%i at 0x%x -- declined."
			    "  (once) ]\n", (int) len, (int) relative_addr);
		}
		if (writeflag == MEM_WRITE || relative_addr == CRIME_REV)
			goto crime_declined;
```

**Why each tested row passes:**
- `lb rev pc` / `lh rev pc`: reads at +0x00 → `relative_addr == CRIME_REV` → declined. OK.
- `sh08 pc` / `sh08 run` / `sb08 msg`: writes at +0x08 → `writeflag == MEM_WRITE` → declined. OK.
- `lb`/`lh`/`lbu`/`lhu` at +0x6/+0x7: reads, not CRIME_REV → fall through. Hits `default` arm. `odata` is never populated for narrow lengths, so the tail writes 0. v0 = 0. No register side effect. OK.
- `sb`/`sh` at +0x1e/+0x1f: writes → declined. OK.
- Accept tests: 8/4-byte accesses never enter the `else` arm. OK.
- `latch x5`: latch is set on the first announce, regardless of whether the goto is taken. OK.
- All "said" rows: announce is printed exactly once per fresh session. OK.
- `live`, `devsig`, `devsig hi`, `rev pc ctl`, `sw08 halts`, `sw08 msg ctl`, `acc8 st+ld`, `acc4 rhi/rlo/wlo/whi`: unaffected (accept path or 4-byte at +0x00/+0x08 which is still accepted). OK.

**Why this breaks the fix:** a narrow **read** at +0x10, +0x18, +0x30, +0x38, or +0x08 falls into the switch. For +0x08 (CRIME_CONTROL) and +0x30 (CRIME_DOG) the read path has no guest-visible side effect, so behavior coincides with the decline by accident. For +0x10/+0x18 (INTSTAT/INTMASK) the read calls `crime_interrupt_reassert(d)`; for +0x38 (TIME) it calls `crime_update_crime_time(d)`. Both are guest-observable. The fix's promise was "uniform decline", and this edit breaks that for three labeled registers with side effects, with zero rows reddening.

**Which row I expected to catch it and why it cannot:** `sh08 pc`/`sh08 run`/`sb08 msg` catch writes at +0x08, but this edit declines all writes. `lb rev pc`/`lh rev pc` catch reads at +0x00, but this edit declines reads at CRIME_REV. The detector simply has no row for a narrow read at +0x10/+0x18/+0x30/+0x38 or at +0x08. The packet's `DISCLOSED` block acknowledges the INTSTAT/INTMASK/TIME cells ("effects are idempotent or overwritten by the tail, and no observable here separates them") — this edit is the unmeasured counterpart of that disclosure.

**Smaller variants I considered and rejected:**
- `if (relative_addr != CRIME_CONTROL) goto crime_declined;` — the packet's own example. **Caught** by `sb08 msg` and `sh08 pc/run` (writes at +0x08 fall through into CRIME_CONTROL).
- `if (relative_addr == CRIME_CONTROL) goto crime_declined;` — **caught** by `lb rev pc`/`lh rev pc` (reads at +0x00 fall through into CRIME_REV).
- `if (relative_addr < 0x10) goto crime_declined;` — equivalent to my candidate for the fall-through set; passes all 40 rows; same gap (INTSTAT/INTMASK/TIME narrow reads).
- Removing the announce entirely — would fail every `<op> said` row.
- Moving the `crime_declined:` label — that is `fallsw`, score 35/40, caught.

The candidate I named is the smallest one-character-condition addition that passes all 40 rows and breaks the fix at a labeled register with a guest-visible side effect.
