## Reasons

**Q1(b), the demanded walk.** Writes to `d->reg[CRIME_TIME]` occur only inside `crime_update_crime_time` (READ), called only from the tick and the switch's `case CRIME_TIME` (READ). In a `tl` session: (1) the tick fires at the first step — the same `step 2` that executes the s0 load — with `last_microseconds == 0`, so baseline set, delta 0, `to_add < 1`, no register write (READ code). (2) The s0 `ld` reads reg[7] *before* the switch, then its case-call adds δ ≈ 0 (same wall instant) — at worst a trace ≪ SMALL = 6.6×10⁶. (3) The `lb` at +0x07 takes the decline path; the switch is skipped; the decline tail touches only HARDINT/INTSTAT (READ). (4) The op at +0x38 likewise declines on the fixed build — this is the one place a mutant inserts an update (δ ≈ 3–7 s of `rd()` pacing → to_add ≈ 2–5×10⁸). (5) The s1 `ld` reads reg[7] *first* — s1 ≈ 0 — then its own case-call fires, after the read. So the fixed build's s1 is the tick's residue by update-freedom, not by timing luck; the mutant build's s1 is the step-4 update. Premise holds. One scope note: "exactly ONE tick per probe session" is true of step-driven sessions (all time/tl sessions — READ from the builders); a `<RUN>` free-run session decrements by `N_SAFE_DYNTRANS_LIMIT` per pass and would tick repeatedly — harmless here, but the premise should not be generalized to all 218 rows.
