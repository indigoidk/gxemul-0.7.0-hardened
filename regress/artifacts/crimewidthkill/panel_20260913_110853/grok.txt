### 1. Floor gap

The mapping is `[0, 0x280)` (`DEV_CRIME_LENGTH`, `memory_device_register`). The near end is `CRIME_REV` at `+0x00`, not `CRIME_DOG` at `+0x30`.

`DEVICE_ACCESS(crime)` takes `uint64_t relative_addr`. The smallest edit that undoes part of the fix (an 8-byte cycle at the first slot is accepted today) is the `len == 8` arm:

```c
if (len == 8 && relative_addr != 0) {
```

That refuses only 8-byte access at `+0x00`. Every 8-byte CRIME access in the probe is at `+0x18`, `+0x20`, `+0x30`, `+0x38`, `+0x210`, or `+0x278`. There is no `ld`/`sd` at `CRIME+0` (those accesses are `lw` / `lb` / `lh` / `sb` / `sh`).

Rows that look like they should catch it, and why they cannot:

| row | why it stays green |
|---|---|
| `acc8 st+ld` | 8-byte at **`+0x30`**, still accepted |
| `top8 st+ld` / `top4 *` | far slot **`+0x278`**, still accepted |
| `top8 anchor` | 8R at **`+0x210`**, still accepted (prelude still writes `1` there) |
| `rev pc ctl`, `devsig`, `devsig hi` | **4-byte** at `+0` / `+4` — they pin the 4-byte near end, not the 8-byte one |

A round-trip at REV cannot work (every access’s prelude does `d->reg[CRIME_REV] = …`). The cheap pin is the one this detector already used at `+0x210`: an **8R of `+0x00` expecting `0x11`**. Under the mutant that read is declined and answered 0.

This is not acc8mid. acc8mid was `len == 8 && relative_addr != 0x100` (interior, measured 71/71, disclosed). `relative_addr != 0` is the near-bound move the accept-row rule was written for: all accept rows sit away from the near end, so moving that end is invisible.
