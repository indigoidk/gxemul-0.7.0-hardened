## What I could not check from the packet

- **`roundtrip(A)` body.** The `hi keeps` row depends on it not writing to +0x278; the table 3 result (wst_mc 84/85, `hi keeps` red) says it doesn't, but the function isn't inlined. If a future edit moves the roundtrip to touch +0x278, `hi keeps` would go silently green for a store that lands there.
- **`AFTER` body.** Same concern for `dflt` offset-keying: I trust the table 3 results, but the session list is partially reconstructed from the diff hunk.
- **`CRIME_W_LEN` bit value.** I cannot tell from the packet whether it is bit 0 or some other bit. The F2 claim that `|= len` and `|= relative_addr` are detected by `latch x5` with lh-first depends on this. With CRIME_W_LEN at bit 0, my own walk says `|= len` with lh-first produces exactly one announce (lh sets bit 1; lb then sets bit 0; thereafter all checks pass), which would **not** be detected by `latch x5`. The table 3 row `lt_len 84/85 latch x5` says it *is* detected, so CRIME_W_LEN is almost certainly not bit 0 — but the proof is the table, not the packet.
- **The TIME threshold `SMALL = 66 * 100000` = 6,600,000 TIME units ≈ 0.1 s wall-clock.** The comment says "0.1 s of TIME", the code says 66×100000. Both are consistent if TIME is stored in units of 1/66 µs. The fall-through value "~1e8" gives ~1.5 s, well above the threshold on the measured machine. A faster debugger could compress that interval below SMALL; nothing in the packet rules that out as a future regression.
