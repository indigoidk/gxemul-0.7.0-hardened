## The seven changes

C1 | **The L2 coarse table at `0x5000` lies inside the L1 table.**  TTB `0x4000` with 4096 word entries spans `0x4000-0x7fff`; `0x5000` is L1 entries `0x400-0x4ff` (VA `0x40000000-0x4fffffff`).  Nothing in this vehicle translates those VAs, so no row is affected today, but a consumer that plants a high-VA L1 word (`hivec` at index `0xfff`, or `armdesc3kill` choosing an index above `0x400`) collides with the page table.  Move the L2 table outside `[0x4000, 0x8000)` (`0xa000` is 1 KB-aligned and free; `CODE` starts exactly where the L1 table ends, which is fine but worth a comment).

C2 | **Pin the `MCR c8` / `INVALIDATE_ALL` path with a pre-warmed abort row.**  As proposed, no row can see the c8-no-op edit: `dump` never consults the fast-path arrays (`memory_rw.c:245-252` calls `translate_v2p` directly), and every abort row's VA was never touched before the M bit.  **RAN (S2/S3):** with `put w 0x100000, 0x5a5a5a5a` issued while the MMU was off and the whole arming+stimulus in ONE `step N`, the LDR at VA `0x100000` aborts normally when `MCR c8` is present (FSR `0x05`, FAR `0x00100000`) and is **served from the warm entry when the flush is replaced by a NOP** (`r4 = 0x5a5a5a5a`, no abort, fall-through marker written).  So make `data trans` pre-warm its own VA (one extra `put w` before the M bit); then the c8-no-op mutant reds it.

C3 | **Anchor the index and offset arithmetic (clause (f)).**  The fault rows' L1/L2 entries are ZERO, and zero is invariant under most mis-indexings: `page trans` at L2 entry 1 stays red-for-the-right-reason under `>> 8` (reads entry 4 = 0), `>> 9` (entry 2 = 0) and `>> 11` (misaligned read `0x0000600f`, type 3, 1 KB-page arm, then AP=0 read-only -> the load SUCCEEDS, so that one is caught, but only by luck of byte layout); `page map` at entry 0 is invariant under every shift (0 x anything = 0).  Likewise `remap`/`page map` read at offset 0, so a narrowed `(vaddr & 0x000fffff)` or `(vaddr & 0xfff)` is invisible.  Repair: plant a second non-zero L2 entry at a non-zero index with its own target word (entry 1 -> a third page, entry 2 -> 0 for the fault), and read the remap/page-map words at a non-zero offset (`VA 0x002ffff8 -> PA 0x003ffff8`, `VA 0x00400ff8 -> PA 0x00600ff8`).  Section base bits: PA `0x00300000` pins only bits 20-21; a target such as `0x03e00000` pins 20-25, and only a device target (C-opt-1) reaches 24/28; bits 26-31 are unpinnable with 64 MB RAM -- say so in the contract.

C4 | **Choose a DACR/domain pair that pins `dav = (dacr >> (domain * 2)) & 3`.**  With DACR `0x1` and the fault section in domain 1, `>> domain` and `>> (domain * 4)` both still read 0 -> still a domain fault -> green.  DACR `0x105` (fields d0=01, d1=01, d2=00, d4=01, no field is 2) with the fault section in domain 2 (descriptor `0x00500c42`) gives FSR `0x29` on HEAD, and both shift mutants land on a client field and red the row.  Domain-extraction mutants (`(d >> 4) & 15`) are already caught because the FSR carries the domain.

C5 | **A fall-through marker after every faulting stimulus, and no result in a register the handler writes.**  RAN: S3 shows the shape -- when the access is serviced, the stimulus continues into `mov r5,#0x9000; str r3,[r5,#0x14]; b .` and DEST+0x14 reads the faulting VA while the handler slots stay poison.  "No abort" is then a VALUE, and three outcomes are distinguishable (handler marker / fall-through marker / poison = stopped CPU, dead process or short count).  Also RAN (S6): my handler reused `r6`, so an accepted page-map load's value was overwritten before `print r6` -- any accepted-load result read back in an abort process must be stored to DEST by the stimulus before the faulting access.

C6 | **Records, §1.6: `put h` is NOT a NO_EXCEPTIONS path.**  `debugger_cmd_put` byte: `memory_rw(..., CACHE_NONE | NO_EXCEPTIONS)` (`debugger_cmds.c:1506-1507`); halfword: `store_16bit_word` (`:1523`) -> `memory_rw(..., MEM_WRITE, CACHE_DATA)` (`memory.c:827-828`), exceptions ON, and `memory_rw.c:738-750` installs a translation whenever `!no_exceptions` -- so `put h` warms exactly like `put w` and, with the MMU on, delivers a data abort to the guest from the debugger.  Only `put b` and `dump` are NO_EXCEPTIONS.  Rule for the probe and its consumers: no `put w`/`put h` after the M bit in any process; plant Thumb halfwords as packed words (`put w 0x8100, 0xe7fe6818` worked, S10).

C7 | **A `ttb2` row.**  `cpu->cd.arm.translation_table` is re-resolved only when `ttb != last_ttb` (`memory_arm.c:133-138`); the vehicle writes TTB once per process, so removing the re-resolution is green everywhere. Exact counts, measured: every instruction consumes one step, INCLUDING the faulting one and the vector `B`.  With r1/r2 preset by the debugger the arming is 6 steps (my runs used 8 with two `mov`s); then the stimulus up to and including the faulting instruction; then 1 for the vector; then the handler (11 with `b .` in my layout).  S2 = 8+2+1+11 = 22 in one `step 22`; S4 = 8+3+1+11; S5 = 8+6+1+11; S7 = 8+3+1+11 -- all landed the marker.  Derive N in code from `len(arming) + len(stimulus) + 1 + len(handler)`, never by hand.  Overshoot is harmless (`b .` spins in section 0); undershoot loses the marker.  Any row that depends on a warm entry (C2) must be ONE `step N` command, because every debugger interaction invalidates (1b).

Is the last-store marker enough?  It proves the handler reached its end and nothing more: it cannot see overshoot (harmless) and it cannot tell "no abort" from "count too short" -- the fall-through marker (C5) does, and `enc ok` separates "the wrong instruction ran" from both.  Keep the msrmode probe's `@MARK` (`print 0x5eed5eed`) early/late split and its aligned-base dump parser; both carried over unchanged into my sessions.
