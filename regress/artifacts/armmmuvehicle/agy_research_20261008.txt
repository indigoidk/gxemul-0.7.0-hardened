### 3. Minimal Setup, Debugger `put`, and Single-Stepping (`step`)

* **Does `put` write physical or virtual memory?**
  * `put` writes **VIRTUAL memory**.
  * In [src/debugger/debugger_cmds.c:1459-1461, 1506-1508, 1543](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/debugger/debugger_cmds.c#L1459-L1461) and [src/core/memory.c:806-808](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/core/memory.c#L806-L808), `put` calls `cpu->memory_rw(..., addr, ..., MEM_WRITE, ...)` without the `PHYSICAL` flag.
  * In [src/cpus/memory_rw.c:186, 245-248](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c#L186), unless `PHYSICAL` is explicitly specified, `memory_rw` invokes `cpu->translate_v2p()` on `addr`.
  * When the MMU is OFF, virtual equals physical (`arm_translate_v2p` identity maps in [src/cpus/memory_arm.c:54-60](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/cpus/memory_arm.c#L54-L60)). Once the MMU is ON, `put` translates through `arm_translate_v2p_mmu`.

* **Does debugger `step` keep working after the MMU turns on?**
  * **YES**.
  * Entering the debugger calls `cpu_create_or_reset_tc()` and `invalidate_translation_caches(..., INVALIDATE_ALL)` ([src/debugger/debugger.c:792-797](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/debugger/debugger.c#L792-L797)).
  * On `step`, [src/cpus/cpu_dyntrans.c:287-288](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c#L287-L288) disassembles the instruction via `memory_rw` and [src/cpus/cpu_dyntrans.c:190, 679-680](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c#L190) resolves the translated physical page via `cpu->translate_v2p` (now `arm_translate_v2p_mmu`). As long as PC's virtual page has a valid mapping, `step` continues to single-step instructions without issue.

* **Minimal guest instructions / debugger writes to configure and enable MMU:**
  * CP15 registers cannot be modified directly via debugger commands (`reg` is read-only in [src/debugger/debugger_cmds.c:1644-1673](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/debugger/debugger_cmds.c#L1644-L1673), and CP15 is not part of `settings_access` in [src/debugger/debugger_expr.c:128-174](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/debugger/debugger_expr.c#L128-L174)). They must be set via guest `mcr` instructions.
  * **Section Descriptor Format:**
    For identity mapping section 0 (`0x00000000`–`0x000fffff`):
    `d = 0x00000c02` (bits 31:20 = base `0x000`; bits 11:10 `AP = 3` for full R/W access; bits 8:5 `domain = 0`; bits 1:0 `type = 2` for section descriptor).
  * **Debugger writes (while MMU is off):**
    Choose a 16 KB-aligned TTB address, e.g., `0x4000`:
    `put w 0x4000, 0xc02` (writes the L1 descriptor for virtual address `0x00000000`).
  * **Minimal guest instructions (placed at current PC):**
    ```arm
    mov   r0, #0x4000
    mcr   p15, 0, r0, c2, c0, 0    ; set c2 (TTB) = 0x4000
    mov   r1, #1                   ; domain 0 client (or 3 for manager)
    mcr   p15, 0, r1, c3, c0, 0    ; set c3 (DACR) = 1
    mrc   p15, 0, r2, c1, c0, 0    ; read c1 (Control)
    orr   r2, r2, #1               ; set bit 0 (M bit: MMU enable)
    mcr   p15, 0, r2, c1, c0, 0    ; write c1: MMU enabled
    ```
    *(If written purely by guest code without `put`, prepend `mov r3, #0xc02` and `str r3, [r0]` to populate the table).*
    Because `0x00000000` is identity-mapped, the next sequential instruction word at `PC + 4` executes seamlessly at the identical virtual address.
