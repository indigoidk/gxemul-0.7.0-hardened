There is a qualification to the truncation premise: **signed `int` alone does not prove the conversion result**. C99 permits an implementation-defined result or signal when converting an unrepresentable value to a signed type. Your two examples have the stated results under GCC with 32-bit `int`; GCC documents reduction modulo the destination width. Under that contract, the negative half is live. The unsigned input declaration does not make it dead. [C99 §6.3.1.3](https://www.open-std.org/JTC1/SC22/WG14/www/docs/n1256.pdf), [GCC integer conversions](https://gcc.gnu.org/onlinedocs/gcc/Integers-implementation.html).

The exact repair should make the PORT write transactional:

- For `idata >= DEV_FBCTRL_NPORTS`, preserve the selector and announce the refusal once per device instance.
- Otherwise, assign `idata` to `current_port`.
- Complete through the existing successful callback return.

Moving the assignment below a warning that returns would still accept the invalid value. It must become conditional. Likewise, the refusal must operate on every invalid write, independently of whether its warning has already been latched. The existing initialization `memset` would initialize the new latch; set it before printing, and do not clear it on valid selections. [The LCA helper](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_lca.c:316) supplies the corresponding per-instance house pattern.

The invariant argument is complete within normal device operations: initialization selects zero, and the PORT arm contains the only subsequent selector assignment. Restrict that assignment to `[0,7]`, and **both halves of the DATA range guard become unreachable after the repair**. That is a defensible dead-path finding with a warrant.

A refused PORT write remains observable: PORT readback returns the previous selection, and DATA continues to address that selection. Preserving established state is preferable to retaining an unusable index. It does mean a guest that ignores the failed selection can act on its previous port. There is no valid new destination corresponding to the refused index.

There is an interaction worth recording: **zero is COMMAND and is also the initial selection**. Preserving a previous COMMAND selection preserves command execution on subsequent DATA writes, including its separate termination path. This repair closes the selector-range failure; it does not establish that every later DATA write is harmless.

The intended input policy should be explicit:

| Received value | Model decision |
|---|---|
| Bit pattern representing a negative guest integer | Decode the transferred bytes as unsigned, as today; decline if outside `[0,7]`. |
| Huge unsigned value outside `[0,7]` | Decline before conversion to `int`. |
| Out-of-range value whose narrowed representation is a valid selector | Also decline; do not infer an alias from narrowing. |

The third case is the compatibility ambiguity. Today some such values select usable ports despite the warning. Rejecting them deliberately changes that accidental behavior. The header describes port indices and supplies no high-bit aliasing rule, so full-value validation is the more defensible contract. Also, `uint64_t idata` is an accumulator type: the device can validate only the bytes actually transferred, not high bits already discarded by the guest.

For the detector, use **state and routing assertions**, with distinct nonzero contents in ordinary data ports. These are contract-level rows, not a host-termination reproduction procedure:

Missing or malformed results must fail equality checks. Completion markers support result integrity; they cannot substitute for those observations. The original build can already fail on selector readback, without using host survival as the discriminator.

**The reinstatement requirement cannot honestly receive a passing entry.** Under the recommended edit, the DATA kill was never removed, so reinstating it changes nothing. Removing it while retaining the selector invariant would still leave its reinstatement unreachable through the normal interface. Restoring the old PORT arm is a meaningful mutation caught above, but it is not reinstatement of a removed DATA kill. If that literal fourth-state requirement is mandatory, this design cannot satisfy the floor as written.
