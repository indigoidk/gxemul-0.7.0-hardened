**The SFD1 question: NOT checkable from the packet — name the premise.**

The brief asserts: "every pre-fault PSR has SFD1 CLEAR, so a dropped `| SFD1` gives `0x80000003 != 0x8000000b` → `bad=psr` on every row." Two defects in that arithmetic, against the brief's own listed values:

(a) `PSR_EXC = 0x8000000b` = bits {31, 3, 1, 0}. Dropping bit 1 (standard MC88100 SFD1) gives `0x80000009`, not `0x80000003`. The value `0x80000003` is `PSR_EXC` minus bit 3.

(b) The listed pre-fault PSRs `0x80000002 / 0x00000002 / 0x90000002` all have bit 1 **set** (the `0x...02` suffix) and bit 3 **clear**. Under standard numbering (SFD1 = bit 1) the claim "every pre-fault PSR has SFD1 CLEAR" contradicts the listed values; under non-standard numbering (SFD1 = bit 3) it is consistent.

Under standard numbering, dropping `| SFD1` yields `PSR_EXC' = 0x80000009`; ORed with any pre-fault PSR that already has bit 1 set, the result is still `0x8000000b` — the dropped bit is masked by the existing bit. `bad=psr` does **not** fire. SFD1 is then uncovered: it sits in the enumeration alongside SFRZ/IND/MODE (which have `M_NOSFRZ`/`M_NOIND`/`M_NOMODE`) but has no mutant, and the claimed "exact compare" coverage does not work. That is a body-tested lvalue the enumeration's coverage argument omits.

Under non-standard numbering (SFD1 = bit 3), the arithmetic checks out and the exact-compare coverage holds — but this contradicts the MC88100 PSR convention where SFD1 = bit 1.
