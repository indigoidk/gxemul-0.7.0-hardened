### The four findings, graded

**(1) M_NOVBR — L2, floor breach, repair in-round.** `cr[VBR]` is a field the guarded body reads on the delivery path the seven added labels route through, so it is squarely inside the clause-(d) DEPENDS-ON closure, and dropping it is the canonical *keep the guard, null the repair* form: all seven `implemented = true` and all seven tail labels survive textually and the exception lands at the wrong address. **The probe never writes VBR** (`grep -i vbr` on the frozen probe: one docstring mention, no `stcr cr7`), so VBR is 0 in all twelve rows and `cr[VBR] + 8*vector` is arithmetically indistinguishable from `8*vector`. Guest effect: OpenBSD/mvme88k relocates its vector table, so every one of these seven exceptions would enter at the wrong address on the very guest the fix exists to serve. It is compounded by an **L4 wrong record in two places**: the fallback comment says *"DELIVERED (**VBR** + 8\*vector …)"*, and the probe's clause-(e) contract lists *"a wrong vector base"* among what it **catches** — M_VEC4 and M_VEC7 pin the *scaling*, nothing pins the *base register*.

**(2) M_SFRZTRAP — L2, an empty joint cell that the manual makes load-bearing.** The delivery path's own code tests two lvalues: `if (cpu->cd.m88k.cr[M88K_CR_PSR] & M88K_PSR_SFRZ)` and `if (!is_trap)`. The body-tested partition is therefore {SFRZ clear, set} x {is_trap 0, 1}. The rows hold three cells — (clear,0) most rows, (clear,1) bounds/privtb/errortb, (set,0) the `error` row — and **(set,1) is empty**. It is not hypothetical: `_scratchpad/mc88100.txt:8633-8636` says *"When the MC88100 is in the exception processing state, it cannot process another exception **except for trap instructions**"*, and 6.10 at `:10613-10614` repeats it, so the `!is_trap` guard is architecture, not defensiveness. And the reachable instance is the guest's own syscall: OpenBSD issues syscalls as `tb0`/`tb1` naming 0x80/0x1c2, so under this mutant **a syscall made from a handler that has not yet re-enabled shadowing becomes a fatal ERROR exception at 0x50**.

**(3) M_SFIPNOTGT / M_DSLOTSWAP — L3, a channel vacuous by construction.** This is not a missing cell; the `dslot` cell is rowed. It is the pre-table CHANNEL check's own failure mode, and it is arithmetic visible in the round's *own* BASE output: the row wants `snip=(fault_pc+4)|V` and `sfip=(CODE+4+8)|V`, written as two independent expectations that both evaluate to **0x1000e**. `br.n +8` at 0x10004 puts `delay_target` at 0x1000c and the slot at 0x10008, so `delay_target == slot_pc + 4` exactly. The two channels are one number, so the delay-slot arm's SFIP can stop reading `delay_target` altogether, or trade places with SNIP, and the row cannot vary. The round's own M_DSLOT kill (8/9, `sfip=0x10012`) proves only that *a numerically different* SFIP is caught — not that the `delay_target` channel is pinned. The `dslot` row is the sole carrier of the delay-slot arm's obligation, and half of it is vacuous.

**(4) M_DELAYALWAYS and M_TAILOFF — clause-(e) coverage debt, disclose and file.** Both leave the fix's own repair intact (the seven still deliver), so neither is a floor breach. M_DELAYALWAYS shows the `else` branch of the post-delivery `cpu->delay_slot` write is unpinned: the `if` branch *is* pinned, because `X(br_n)` (`cpu_m88k_instr.c:99-105`) overwrites `cpu->pc` with `delay_target` unless `EXCEPTION_IN_DELAY_SLOT` is set — that is what makes the `dslot` row work. The `else` branch needs a second **unfrozen** exception to show damage, and the only two-fault row (`error`) freezes. M_TAILOFF escapes because the probe has **no row for vectors 0..3**, whose tail arms do real work (`SNIP -= 4` for INTERRUPT, `SNIP/SFIP = 0` for INSTRUCTION_ACCESS, the DMT copy for DATA_ACCESS).

**M_ISTRAPBOUNDS is a result about the code, not an escape.** I enumerated every raise site (`grep -rn 'm88k_exception('` over `src/`): BOUNDS_CHECK_VIOLATION has **no literal-constant site at all** — `tb0`/`tb1`/`tcnd` at `cpu_m88k_instr.c:2529/2551/2564` are the only route and all three pass `is_trap = 1`. So `implemented = is_trap` on that arm is equivalent in today's tree; the mutant cannot die because the target is dead. Same for the ERROR arm (switch 1's ERROR case is reachable only by a trap naming 10 — which answers the brief's own open QUESTION at the end of §3: **no, there is no other route**, and the SFRZ re-route provably cannot reach it because it runs after switch 1). ## 3. THE REPAIRS — four, each one row or one constant

1. **VBR (M_NOVBR).** Add `stcr r5,cr7` with `r5 = 0x2000` to the **`bounds`** row's prologue (it is already supervisor and already single-instruction), plant its `br .` at `0x2038`, breakpoint `0x2038`, and expect `pc == 0x2000 + 8*vector`. **Channel: `cpu->pc`** — 0x2038 on the fix, 0x0038 under M_NOVBR (which the classifier scores STOP). One instruction and one expectation; no new session. This also upgrades the row from relative to *anchored* in clause-(f)'s sense: it is the only row that would red if the whole vector table moved.
2. **The trap-in-a-frozen-handler cell (M_SFRZTRAP).** New row `trapfrozen`: `divu r2,r3,r0` at 0x10004 delivers to 0x40 with SFRZ set; the handler at 0x40 is `tb1 0,r3,7` (`f003d807`, r3 = 1). Correct model: vector 7 is a trap, the re-route does not fire, `pc == 0x38`, and the shadows stay frozen at the first fault's values (`sxip=0x10006 snip=0x1000a sfip=0x1000e`, `epsr=0x80000002`). **Channel: `cpu->pc`** — 0x38 on the fix, 0x50 under the mutant. This is structurally the existing `error` row with the second fault changed from a misaligned `ld` to a `tb1`, so it reuses that row's whole scaffold, and it fills the last cell of the {SFRZ} x {is_trap} product.
3. **The dslot geometry (M_SFIPNOTGT / M_DSLOTSWAP).** Change the branch from `br.n +8` (`c4000002`) to `br.n +16` (`c4000004`). `delay_target` becomes 0x10014 while `slot_pc + 4` stays 0x1000c, so the expectations separate: `snip = 0x1000e`, `sfip = 0x10016`. **Channel: SFIP** — 0x10016 on the fix, 0x1000e under either mutant. **Zero new rows: one instruction constant and one expectation constant.** The branch is never taken (the slot faults and the exception owns `pc`), so nothing else in the row moves.
4. **The carry bit (F14).** In the **`ovf`** row's prologue — 6.6 is the citation that mentions carry — write `0x90000002` to PSR with `stcr r5,cr1` before the overflowing `add`, and expect `PSR == 0x9000000b`. **Channel: PSR bit 28** — set on the fix (unchanged, per 6.6), clear under any mutant that clears carry on the exception path. One instruction, one constant.
