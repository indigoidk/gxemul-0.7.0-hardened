  ## Q3 — OPTION-SET COMPLETENESS (Q-D1a..e) AND THE CROSS-CORE PRECEDENT

  Precedent, measured in this tree: **MIPS** delivers every exccode — even the explicitly-unmodelled cache error falls through to 0x180 (`grep -n 'cache error  (not implemented yet)' GXEMUL-SEC/src/cpus/cpu_mips.c`). **SH** delivers everything it raises; only never-raised defined vectors `exit(1)` (`grep -n 'exception 0x%x is not yet' GXEMUL-SEC/src/cpus/cpu_sh.c`) — and the fork's own #217/#315/#457 converted former SH exit-paths into deliveries. **ARM** delivers the six modelled exceptions, stops on RESET/out-of-range. **PPC** `ppc_exception` always delivers. So the house rule is *deliver what you recognise and can raise; stop only on the never-raised/unknown* — D1 is exactly that, one layer up from #302/#306/#307/#323. No missing member; D3 correctly doesn't apply (architected classes with guest handlers; suppressing them lies to the guest).

  - **Q-D1a (level):** INFO is right. I read gate 6's marker list (`gate_hygiene.sh:769-776`): the bounded patterns are `panic`, `FATAL`, `zero-length`, `FIFO overrun`, `short DATA_IN/OUT DMA`, `unimplemented format`, `could not find physical` — the exception core's `[ exception CLASS: ]` line matches **none** of them (note `unimplemented format` ≠ `unimplemented vector=`), so no hygiene row reds *either way*. The real arguments for INFO are consistency with the four implemented classes and that a delivered-and-handled exception is routine guest traffic, not emulator distress. Keep the fallback at ERROR — an unimplemented vector *is* distress.
  - **Q-D1b (BOUNDS_CHECK):** leave unimplemented. Zero raise sites, `tbnd` undecoded, SH precedent tolerates stopping on never-raised vectors, and the halt is the honest signal if `tbnd` is ever implemented. If the panel prefers zero-cost consistency, include it — unobservable either way; my negative row (`tb1→7`) must then target a different vector (e.g. 11).
  - **Q-D1c (ERROR):** out of scope, file — **but the brief's mechanism is wrong.** In this fork `fatal()` is print-only (`GXEMUL-SEC/src/core/debugmsg.c:384-391`, no exit). A double fault today is: print → reroute vector=10 → PSR switched, pc moved to VBR+0x50 → tail `default:` stops this CPU. Not an abort, and not even a clean pre-delivery halt. Consequence for the follow-up row: delivering ERROR requires *removing/softening that `fatal` and adding a tail arm*, not just a flag — genuinely a separate design. (This also re-reads agent-visible precedent: SH/ARM stops come from explicit `exit(1)`/`running=false`, not `fatal`.)
  - **Q-D1d (MISALIGNED):** correct as designed. The template raises *before* `memory_rw` (`cpu_m88k_instr_loadstore.c:169-172`), matching "detected before the memory access is dispatched" (9236-9237); DMT0=0 is right. Note the retrospective sketch's "MISALIGNED already populates DMT" is misleading: the template dirties only the *internal* `dmt[]/dma[]` (:131-136), which reach the CRs only via the DATA_ACCESS tail arm. No scoreboard in the fork (SSBR written 0) — OpenBSD's handler decodes the instruction at SXIP rather than consulting a scoreboard, so nothing guest-visible is wrong; disclose.
  - **Q-D1e (fcr2/4/5):** agree, follow-up row. Conditioning on "OpenBSD's SIGFPE path doesn't read them" — m88k isn't in `_guest-src-openbsd22` (2.2 predates the port; verified absent), so no on-disk check. Manual 10309-10314 confirmed (plus its caveat: fcr5 can't distinguish div from divu).

  **Answers to the §6 detector questions** — exact encodings from the decoder (`cpu_m88k_instr.c:3159-3195`, masks verified arithmetically):
  - `stcr r5,cr1` (PSR) = **0x80058025** (mask `(iword & 0x03e0f800) == 0x00008000`, and the fork enforces the manual's s2==s1 rule at :3178-3179 — the low 5 bits repeat s1).
  - `ldcr r2,cr1` = **0x80404020** (mask `(iword & 0x001ff81f) == 0x00004000`; s1 field and low 5 bits must be 0).
  - `tb1 0,r0,0x10` = **0xf000d810** (major 0x3c, op10 = bits 15-10 = 0x36, VEC9 = bits 8-0; cross-checked against the fork's own comment `f020d8ff tb1 1,r0,0xff`).
  - user-mode UNIMPL row: plant **0xf400fc92** (`M88K_PROM_INSTR`, `cpu_m88k.h:221`); raises only in user mode (`X(prom_call)` :2448-2451), which is what you want — on testm88k the *supervisor* path hits "unimplemented machine type" instead.
  - **Mode-switch safety:** the ic translation cache is *not* mode-tagged, but `m88k_stcr` invalidates **all** translations on any MODE change (`cpu_m88k.c:549-551`, instantiated as `DYNTRANS_INVALIDATE_TC`), and `X(rte)` takes that same path on every return-to-user — i.e. the booted rig exercises it constantly. Privilege checks are runtime PSR reads inside the X() bodies, so an already-translated next instruction re-checks. The stcr route behaves as hardware. One disclosure: clearing MODE via non-rte `stcr` prints the `stcr: WARNING! the PSR_MODE bit is being cleared…` line at WARNING level (`cpu_m88k.c:535-540`) — expect it in the row transcripts; don't write transcript-cleanliness assertions that trip on it.

  ## Q4 — THE GUEST

  Boot-neutrality is proved by contradiction: today *any* raise of the five halts the emulator, and the gates are green, so no gated boot path raises any of the five — D1 cannot move gate_ab (gate 7) or gate 5 on healthy boots. What changes post-fix, all guest-triggerable: a userland `div`/`divu` by zero (vector 8 → OpenBSD T_ZERODIV → SIGFPE — pre-fix the *whole emulator* dies from one userspace fault; that's the severity paragraph for the CHANGELOG), a userland `stcr`/`ldcr`/`.usr`/`rte` (vector 6 → SIGILL), a userland misaligned word access with MXM clear (vector 4 → kernel fixup or SIGBUS), a userland `tb1` to vectors 0-127 (vector 6). Two adjacent truths the records should carry: the fork **stops the machine if any guest sets MXM** (`cpu_m88k.c:542-547`, "stcr: TODO: MXM support") and the template ignores MXM's round-down rule (9243-9246) — so "misaligned with MXM clear" is the only reachable mode, and today's green boot proves OpenBSD never sets MXM on this rig. A *kernel* divide-by-zero post-fix would panic the **guest** (gate 6 greps `panic`) where pre-fix it halted the emulator — a behavior delta to note, not fear: none occurs on healthy boots. Measuring seat: run gate_ab plus the new gate-11 section; for a guest-OS witness, boot luna88k and run a one-line userland divide-by-zero — pre-fix emulator halt, post-fix `Arithmetic exception` (SIGFPE).
