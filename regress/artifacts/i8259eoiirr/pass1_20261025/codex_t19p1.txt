**3. Option-set completeness and candidate effects**

**DERIVED:** None of A–E, as written, satisfies every stated constraint.

| Candidate | Assessment |
|---|---|
| **A** | Correctly removes EOI’s destruction of held requests. Both retained output-recalculation guards become false because IRR is unchanged. It exposes the PIT’s missing release/retirement behavior. |
| **B** | Adds service state, but does not cure the PIT: EOI clears ISR and immediately makes the still-pending request eligible again. Poll-only acknowledgement also leaves other vector paths untreated. |
| **C** | Can preserve the current distinction between repeatedly delivered timer events and held device requests, but needs an explicit producer/mode contract. Keeping PIT IRR clearing does not itself retire its pending-event count. It is not a complete edge model merely because a device never deasserts. |
| **D** | Restoring a bit from an independently maintained high level has A’s held-level effect. The PIT would also remain high. Shadow ownership must include V3 and cascade behavior; Jazz’s destructively cleared latch is not an independent physical-level shadow. |
| **E** | Leaves immediate post-EOI request loss intact. RTC periodic requests already reassert; changing keyboard behavior would shorten lost-request duration without satisfying A’s proposed immediate preservation rows. |

**READ:** There is an omitted existing idiom: **the source owns assertion lifetime and pending-event retirement**. `dev_bt459.c`, `DEVICE_TICK(bt459)`, explicitly deasserts a retrace pulse on a subsequent tick. `dev_rtc.c`, `DEV_RTC_INTERRUPT_ACK`, retires pending work and deasserts. MC146818 and GT have comparable source acknowledgements.

**DERIVED:** That supports **A accompanied by a separately specified PIT lifetime/accounting correction** as a missing design direction. It is not yet a complete construction: event consumption, pulse lifetime, and pointer ownership remain unresolved.

**READ:** Searches for ISR/service terminology do not reveal a reusable 8259 service implementation. Other similarly named registers are not evidence of one.

**DERIVED:** B also requires more than adding `isr |= bit`:

- Existing recalculation guards compare IRR/mask state, so ISR changes need corresponding output recalculation.
- Generic ISA and V3 cascade/output paths must obey the same eligibility rule.
- The current poll selects raw IRR without masking and retains `current_command == 0x0c`.
- Existing non-specific EOI clears every ISR bit, whereas hardware normally clears the highest-priority applicable service bit.

**DERIVED:** The packet’s own descriptions also show that A and B are not equivalent to the complete cited rs6000 commits: those include routing, selection, initialization, and other changes.

**5. The 8253**

**READ:** In [dev_8253.c](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_8253.c), `timer0_tick` increments the pending count; `DEVICE_TICK(8253)` asserts; counter/mode accesses do not clear that count or deassert. Once a pending event exists, reprogramming does not retire it.

**DERIVED:** With A, a normal PIT guest has **no implemented device-completion path that clears master IRR0**. Masking suppresses delivery but preserves the request. EOI no longer clears it. Under B, completing service likewise exposes that same retained request again.

**READ:** Today’s specific EOI clears PIC IRR directly; it does not call the ISA IRQ0 deassert handler and therefore does not consume a pending PIT event.

**DERIVED:** Yes, repeated assertion from an unretired pending count is already a separate correctness defect. A removes the temporary suppression supplied by specific EOI, potentially exposing continuous eligibility. The qualification matters: non-specific EOI already leaves IRR unchanged today, so the existing behavior is not universally hidden.

**DERIVED:** Both missing PIT retirement and the stale captured counter pointer should be recorded. Neither merely preserving the old PIT-specific IRR clear nor adding ISR establishes correct event accounting.
