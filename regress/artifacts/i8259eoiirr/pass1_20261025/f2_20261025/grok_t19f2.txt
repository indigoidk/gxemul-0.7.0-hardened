## Q3

Yes. Two sequences in the sketch are worse than HEAD on malta, and one is worse on every machine that consumes with EOI.

The cascade pre-fold is worse, and it is a bug in G2 rather than a property of acknowledging. G2 writes pic1 bit 2 itself and then `INTERRUPT_ASSERT`/`DEASSERT` on `d->irq`. For pic2 that irq is the demux line 2 (`bus_isa.c:232`, `dev_v3.c:300`). `isa_interrupt_assert` samples `old` before it sets the bit, then `isa_interrupt_common` returns when the mask did not change. The pre-fold makes the mask already include bit 2, so the assert is swallowed. Concrete case, two slave lines only: the master acknowledge clears bit 2 and deasserts the CPU pin (`mips_cpu_interrupt_deassert` is not refcounted); the slave acknowledge of the first line pre-folds bit 2 and then no-ops; the second slave IRR bit stays set and the CPU pin stays low. A later re-assert of that same bit also no-ops, because the bit and the cascade are already set. HEAD's master EOI clears bit 2, so the next re-assert is a real delta and the CPU pin comes back within a tick. Delete the manual fold. Line 2's existing assert/deassert already folds. V3's pic1 irq is the line-16 recalc, so it does not need a second policy. DERIVED from those functions. R9 is not optional while the fold stays in the round.

EOI with no preceding acknowledge is worse under G1 as written. HEAD's specific EOI clears that IRR bit and runs the recalc. (G) clears ISR only and deletes the recalc, so the CPU pin stays where the assert left it. The 8253 never deasserts, so irq 0 stays high forever instead of pulsing every batch. The ns16550 stays high until its next tick. Sources that deassert in the handler (pckbc queue drain, mc146818 register C, wdc status, GT cause) still clear IRR themselves. Linux/malta and NetBSD/malta do not use this sequence: the GT read and the poll are their acknowledges (§1.7, §1.8). PReP and footbridge do: the read returns `last_int` and does not change IRR, and the guest then EOIs. Cats hits the footbridge read. Iyonix and cobalt have the 8259 and no reader in the `last_int` set; whether their guests poll was not checked. NOT CHECKABLE for those two guests. The hybrid in D2 keeps HEAD's consume when ISR is clear, so this stops being a regression, and R4 as written (bit stays 1 with no prior poll) must be rewritten or it fails. Pure G1 plus R4-as-written requires the prep and footbridge calls in the same edit.

Poll with nothing pending is not worse. Both return `0x00` and change nothing. READ of the `0x0c` and default scans. The datasheet's INTA-with-nothing is a separate case (it reports level 7).

Ack of a masked line is not a stuck line. G2's `irr & ~ier` returns -1, writes nothing, and the poll byte is `0x00` instead of HEAD's `0x84`. That is F11's row, and it matches a mask. It is worse only for a guest that depended on the mask-blind byte. Neither documented malta guest does.

A second command-port read after one `0x0c`, and any read that hits the default arm, are worse if G3 is built as written. The model latches `current_command`, so one poll write makes every later command read a poll. HEAD reports twice and consumes nothing. (G) would consume twice. Acknowledge only `current_command == 0x0c`, and make that latch one-shot. NetBSD writes `0x0c` before the read, so one-shot still matches §1.7. DERIVED.
