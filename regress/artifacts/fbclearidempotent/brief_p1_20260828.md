# PASS 1 DESIGN BRIEF — `fbclearidempotent`: a timer clear with nothing pending reloads a timer it should not touch

> ## *** PANEL OUTCOME.  THE DEFECT SURVIVES; THE BRIEF'S MECHANISM, SYMPTOM, OPTION SET AND
> ## ONE PREMISE DO NOT.  Read this before the body. ***
>
> **The defect is REAL and every seat agrees on it**: `TimerNClear` wrongly invokes
> `reload_timer_value()`, and the datasheet says the write has no effect when nothing was
> pending.  Beyond that, four things in this brief are wrong.
>
> **(1) §5's CENTRAL QUESTION WAS A FALSE DICHOTOMY, and reading the source dissolves it.**
> I asked "is reload-at-CLEAR a shortcut standing in for the automatic reload?"  Neither.
> **The model has no count-to-zero at all.**  `reload_timer_value()` calls
> `timer_add()` / `timer_update_frequency()`, and the generic timer core supplies periodic
> delivery by itself — `timer->next_tick_at += timer->interval`, **with no acknowledgment
> involved.**  The timer is armed at `TIMER_1_LOAD` and at `TIMER_ENABLE`; CLEAR is a third,
> redundant caller.
>
> **(2) THE SYMPTOM I CLAIMED DOES NOT FOLLOW.**  §2 says the timer SLIPS a full period and a
> guest clearing faster than the period "could starve its own timekeeping indefinitely."
> **Refuted:** `next_tick_at` is ABSOLUTE-scheduled, so reloading does not restart an
> already-armed steady-rate timer.  The MMIO defect is real; the runaway consequence I dressed
> it in is not.  *A real defect with an invented consequence is still a wrong record, and it is
> the kind that gets a round prioritised for the wrong reason.*
>
> **(3) THE OPTION SET WAS INCOMPLETE — AFTER I DECLARED IT CLOSED.**  §4 runs the
> option-completeness grep, reports a NEGATIVE result, and concludes "the choice really is
> between the three already named."  **There is a fourth: REMOVE the reload from CLEAR
> entirely.**  It was not in the tree's idioms — which is what I grepped — it is in the code's
> own redundancy, which is what (1) establishes.  *The completeness grep answers "what does
> this fork already do?"  It does not answer "is this call needed at all?", and I treated the
> first question's negative as closing the set.*
>
> **(4) THE ALIAS-BLINDNESS PREMISE IS STALE.**  §6 says the sibling `fbclearaliases` is not
> detector-backed because "every `#474` row exercises timer 1."  Measured against HEAD:
> `regress/diff_footbridge.c` contains **`TIMER_2_CLEAR` ×2 and `TIMER_4_CLEAR` ×1** alongside
> its timer-1 rows.  Carried forward from a research note without re-deriving it.
>
> *Every one of these was found by a seat opening a file I had not.  (1) I did reach
> independently while the panel ran — by reading `reload_timer_value()` and its three callers —
> which is the only one I can claim.*
>
> ### *** AND (2) IS NOT MERELY REASONED — BOTH FLAGSHIP SEATS MEASURED IT, INDEPENDENTLY. ***
>
> The mechanism is `src/core/timer.c`'s **`if (t->freq == new_freq) return;`** — an early-out
> ABOVE the `next_tick_at` reset.  The CLEAR arm writes neither `timer_load` nor
> `timer_control`, and `emulated_hz` is a machine constant, so `reload_timer_value()` recomputes
> a **bit-identical** freq and `timer_update_frequency()` returns without touching phase:
>
> ```
>   after arming:  freq=100000.0000000000  interval=0.0000100000  next_tick_at=0.0000100000
>   CLEAR, nothing pending:  next_tick_at 0.0000100000 -> 0.0000100000   delta 0.0  UNCHANGED
> ```
>
> **`timer.c` says so in words** at its `#427/#429` comment: *"Clamping above the comparison
> makes a repeated request idempotent again."*  So the slip is not merely absent — **it is a
> property this fork deliberately engineered**, and my brief proposed fixing a symptom the code
> was built not to have.
>
> ### THE DISPOSITION: OPTION 2, ONE ROUND, PLUS THE `0x34C` ROW
>
> Guard ONLY the reload, nested inside the existing `pending > 0` test.  Not option 1 — the
> unconditional `INTERRUPT_DEASSERT` is pinned by a **shipped accept row** whose counted channel
> option 1 would change on the `pending == 0` path for no fidelity gain.  Not option 4 (delete):
> the two seats split on this, and nesting is the smaller diff that leaves the accept row a home.
>
> **The only detector channel is the `TIMER_x_VALUE` read-back**, and §6.4 asked the wrong
> question.  I asked "is there a non-timing channel?" fearing a fragile wall-clock oracle.  The
> answer is that **the timing channel does not exist** — so a timing row here would not be
> fragile, it would be **pinning a symptom the code cannot produce.**  And `DEVICE_TICK`, the
> only competing writer of `timer_value`, is inert in exactly the state under test: it writes
> only when `pending > 0`, and these rows' whole premise is `pending == 0`.
>
> ### FOUR NEW FINDINGS, NONE OF THEM IN THIS BRIEF
>
> * **N1 — `TimerNValue` is READ-ONLY** (§7.3.40's R/W column reads `R`) and the model accepts
>   `timer_value[nr] = idata & TIMER_MAX_VAL`.  Measured: wrote `0xABCDEF`, read it back.
> * **N2 — the same family one arm over.**  §7.3.41 bit 7 says a re-enabled timer *"will resume
>   from the current TimerNValue"*; the CONTROL arm **reloads**.  The documented reload triggers
>   are exactly two — a write to TimerNLoad, and reaching zero in periodic mode — and **neither
>   Clear nor Enable is one.**  The round is really *"`reload_timer_value()` has three callers
>   and only one is a documented trigger."*
> * **N3 — a bare CLEAR at reset arms a host timer**, `timer_add()` and a live SIGALRM callback,
>   for a timer the guest never enabled.  Bounded at four, so not a leak — but it is state
>   created by a write specified to have no effect.
> * **N4 — the ONE real phase reset, and it is not the one I claimed.**  A CONTROL write with
>   ENABLE clear changes `timer_control` **without** reloading, leaving the core on a stale
>   rate; a later CLEAR then applies the deferred rate change *and* resets phase —
>   `next_tick_at 0.000010 -> 1.002560`.  **This is the sharpest guest-visible consequence the
>   round has, and the brief does not contain it.**
>
> > *** VACUITY LANDMINE, from N1: *** if a detector row plants its `value != load` sentinel via
> > a `TIMER_x_VALUE` WRITE, then a later round making that register read-only **silently stops
> > the sentinel being planted and every row greens.**  Plant by struct field after
> > handler-arming, or ship a row pinning write-acceptance so the two move together loudly.

* **The offsets are right, and they were STRADDLE-CALIBRATED rather than guessed.** DC21285
  Table 7-12 renders with the NAME column shifted two rows against the ADDRESS column, so a
  naive read gives `Timer1Clear 324h`. Pairing strictly in order down each column gives

## 2. THE CODE, INLINED WHOLE — `grep -n 'case TIMER_1_CLEAR' src/devices/dev_footbridge.c`

```c
	case TIMER_1_CLEAR:
		/*  #474: a READ must not perform the clear.  ...
		    FOUR addresses, not one: the fold above normalises 0x30C/0x32C/
		    0x34C/0x36C onto this single case.
		    GUARD THE BODY, KEEP THE break.  An early return here would skip
		    the function's common tail, which writes odata back on a read ...  */
		if (writeflag == MEM_WRITE) {
			if (d->timer_control[timer_nr] & TIMER_MODE_PERIODIC) {
				reload_timer_value(cpu, d, timer_nr);
			}

			if (d->pending_timer_interrupts[timer_nr] > 0) {
				d->pending_timer_interrupts[timer_nr] --;
			}

			INTERRUPT_DEASSERT(d->timer_irq[timer_nr]);
		}
		break;
```

**THREE EFFECTS, AND ONLY ONE IS UNFAITHFUL:**

| effect | guard | verdict |
|---|---|---|
| `pending_timer_interrupts[n]--` | `> 0` | **already idempotent** |
| `INTERRUPT_DEASSERT(...)` | none | **harmless** — deasserting a clear level is a no-op |
| `reload_timer_value(cpu, d, n)` | `TIMER_MODE_PERIODIC` **only** | *** THE DEFECT *** |

**So a guest writing TimerNClear with NOTHING PENDING restarts a periodic timer's countdown,
where the datasheet says the write has no effect.** Guest-visible symptom: the timer SLIPS —
the next tick arrives a full period late — and a guest that clears more often than the period
could starve its own timekeeping indefinitely.

## 3. WHY NO EXISTING ROW SEES IT — blind BY CONSTRUCTION, not by omission

Every `#474` row in `diff_footbridge.c` and every row in `fbpending_drain_probe.py` **sets up
a pending interrupt and then clears it.** Nothing exercises a clear with **nothing** pending —
which is precisely the state the defect lives in. This is not a gap someone forgot; the rows
were built for a different question and cannot reach this one.

## 5. *** THE QUESTION THAT MADE THIS FILED RATHER THAN FIXED — and it is a panel question,
## not a reading question ***

**Does reload-at-CLEAR belong in the model at all?**

On real hardware a periodic timer **reloads itself at zero** and needs no Clear write to do it.
So the model's reload-at-clear may be a MODELLING SHORTCUT standing in for the automatic
reload. If it is:

* hoisting it under a pending guard is right **for a different reason than the datasheet
  sentence gives**, and the comment must say the real reason;
* and the round should ask whether the shortcut should be replaced rather than guarded.

If it is **not** a shortcut, then adding the guard **changes when periodic timers reload** —
which is a behaviour change to a working timer, not a fidelity fix.

**Neither branch is decidable by reading the diff, which is why this needs the panel.**
