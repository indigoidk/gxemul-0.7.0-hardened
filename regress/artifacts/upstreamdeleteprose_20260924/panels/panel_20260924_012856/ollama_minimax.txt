## 3. What all nine seats missed

Five things, in order of likely consequence:

**(a) The `git()` failure mode and section L's grep are a coupled failure.** F11 caught the `git()` discard, but the interaction with section L (which greps only for the PASS token) means the silent pass cannot be caught downstream — the script must catch it itself. The fix in `attrcheckgaps` should be `subprocess.run(..., check=True)` or an explicit returncode check, plus the script must exit non-zero on git failure. Filed correctly, but the fix design should be specified now, not when `attrcheckgaps` is picked up.

**(b) The `reopened` field's new false-positive surface.** R's `names(row.get("reopened"), full)` extracts *all* 7-40 hex tokens from `reopened` and credits the row if *any* is a prefix. Before R, only exact substring matches worked, so a stray hex-looking word in prose wouldn't match. After R, any 7-40 hex token in `reopened` (including future lcaisalane-style data corruption, or a commit hash mentioned in prose) credits the row. This is the same surface as F17 (hex-word hole) but on the `reopened` field specifically. F17 was recorded extending note 2, but the `reopened` side wasn't called out as the *new* exposure R introduces — note 2 should now mention both fields.

**(c) The interaction between F23 (repack timing) and the fix.** The fix uses `%H` (40 chars), which is independent of git's core.abbrev. But the ledger rows were captured at the time of closure using whatever `%h` git printed then. The fix works because 7-char tokens are prefixes of 40-char hashes. But what about a row captured when git's abbreviation was 6 chars (e.g., a very old repo)? Then a 6-char token would *not* match the SHA regex's `{7,40}` and the row would never be credited. Today this doesn't happen (no 6-char ledger tokens), but the regex's lower bound is a load-bearing assumption about the ledger's history. Worth a sentence in the comment.

**(d) The `tools/pipeline/` exemption's interaction with the witness for U.** F7 says "none — comment-only" for U, but the witness only covers *behavior* (preprocess/compile byte-identical). It doesn't cover the gate's *interpretation* of the comment change. The gate checks for `delete ` (delete followed by space); the comment had "delete and RETURN" (matches); the new comment has "remove and RETURN" (doesn't match). This is the load-bearing property, and it's testable but wasn't tested in the witness — only the preprocess/compile identity was. Minor; the gate measurement (upstream exits 1 without U, 0 with U) covers it, but the witness text is incomplete.

**(e) The Q6 control's residual value.** F19 says Q6 is vacuous as matcher coverage because section L reads the worktree ledger. But Q6 also exercises the *committed* ledger on a fresh clone — which is the ledger the rows were authored against. If the worktree ledger has drifted from the committed ledger (e.g., uncommitted ledger edits during a failed session), Q6 catches that. The disposition to keep Q6 "only as the committed ledger's result on a fresh clone" is right, but the *reason* — drift detection — wasn't named.

## Anything else I found

One thing the panel and the author both seem to have stepped past: the `SHA` regex uses `(?<![0-9A-Za-z])` and `(?![0-9A-Za-z])` lookarounds, which means a hex token next to an underscore, hyphen, dot, or any non-ASCII letter is matchable. So `commit_abcdef0` matches `abcdef0`, and `commit.abbbccc` matches `abbbccc`. This is rarely exploited in prose, but in code or paths it's common. Not a finding against R (the old code had the same shape via `h in commits`), but worth knowing if the ledger ever carries commit-ish references in code blocks. Noted; not filed.
