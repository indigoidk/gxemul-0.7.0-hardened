### (a) Dossier's Chosen Disposition Member and Machinery Verification

1. **Is Member 3 ("Decline and announce once per CPU") right?**
   - **Yes.** Architectural specification ARM DDI 0100I, section A4.1.20 (pp. A4-38–A4-39, lines 8167–8168) explicitly designates LDM(3) executed in User or System mode as **UNPREDICTABLE**:
     > *"User and System mode: This instruction is UNPREDICTABLE in User or System mode."*
   - ARM DDI 0100I Glossary (p. Glossary-12, lines 45063–45065) restricts emulator latitude for UNPREDICTABLE behavior:
     > *"UNPREDICTABLE instructions or results must not represent security holes. UNPREDICTABLE instructions must not halt or hang the processor, or any parts of the system."*
   - The current behavior in `src/cpus/cpu_arm_instr.c:1795-1799` directly halts the CPU (`cpu->running = 0`), creating an unprivileged denial-of-service / availability vulnerability.
   - Declining the instruction before any memory operations, register publication, or writeback, and logging a single latched diagnostic per CPU (`"(once)"`), satisfies the architectural requirement that the instruction must not halt or hang the processor, adheres to the fork's established UNPREDICTABLE policy (e.g. `OUTSTANDING_BUGS.md:17062-17071`), and avoids inventing unprescribed exception behavior.

2. **Is its machinery really present on this CPU?**
   - **Instruction Decline Execution Path:** **Present.** Declining at the top of `arm_pop()` (`src/cpus/cpu_arm_instr.c:1602-1620`) prior to the memory loops (`:1622-1740`), register publication (`:1742-1772`), and writeback (`:1777-1778`) allows an immediate `return;`. Because the dyntrans instruction dispatcher at `src/cpus/cpu_dyntrans.c:113-114` (`#define I ic = cpu->cd.DYNTRANS_ARCH.next_ic ++; ic->f(cpu, ic);`) advances `next_ic` before invoking the instruction handler, an ordinary `return;` without setting `cpu->cd.arm.next_ic = &nothing_call` naturally resumes execution at the subsequent instruction word.
   - **Per-CPU Warning Latch:** **NOT present; must be added.** In `struct arm_cpu` (`src/include/cpu_arm.h:136-288`), there is currently no latch bitfield or warning mask for this instruction rejection. The file-static variable `warned_undef` at `src/cpus/cpu_arm_instr.c:4698` is a single C static variable, not per-CPU instance state. To satisfy Member 3's contract (`"(once), per CPU"`), a latch field (such as `uint32_t warned;`) must be introduced into `struct arm_cpu` in `src/include/cpu_arm.h`.
   - **Exception Delivery Machinery (Lines and Delivery Code):**
     If an exception were proposed (Member 5), delivery machinery **IS genuinely present in the emulator code**, located at:
     - `src/cpus/cpu_arm_instr.c:1020-1027`: `X(und)` synchronizes PC (`cpu->pc &= 0xfffff000; cpu->pc += ic->arg[0];`) and calls `arm_exception(cpu, ARM_EXCEPTION_UND);`.
     - `src/cpus/cpu_arm.c:669-733`: `arm_exception()` performs complete exception delivery:
       - `line 671`: `arm_save_register_bank(cpu);` saves current register bank.
       - `lines 673-674`: Updates CPSR with ALU flags.
       - `line 681`: `cpu->cd.arm.spsr_und = cpu->cd.arm.cpsr;` saves CPSR to `spsr_und`.
       - `line 693`: Clears Thumb bit `cpu->cd.arm.cpsr &= ~ARM_FLAG_T;`.
       - `lines 699-700`: Switches mode to `ARM_MODE_UND32`.
       - `line 716`: Sets interrupt disable bit `cpu->cd.arm.cpsr |= ARM_FLAG_I;`.
       - `line 720`: `arm_load_register_bank(cpu);` loads the new banked registers (`r13_und`, `r14_und`).

### (b) Siblings the Dossier Missed in the Same Files

The dossier confined its sibling census to `src/cpus/cpu_arm_instr.c` and its shared `cpu_dyntrans.c` decoder rejection label. In doing so, it missed the following siblings in the same product files and directly coupled ARM CPU files:

1. **Unlatched `fatal()` Logging DoS in User-mode LDM(2) (`src/cpus/cpu_arm_instr.c:1612-1615`):**
   In `arm_pop()`, when an instruction executes with `s_bit == 1` and `iw & 0x8000 == 0` (LDM(2), loading user-bank registers without PC) from User mode:
   ```c
   1612:		if ((cpu->cd.arm.cpsr & ARM_FLAG_MODE) == ARM_MODE_USR32) {
   1613:			fatal("[ bdt_load: s-bit: in usermode? ]\n");
   1614:			s_bit = 0;
   1615:		}
   ```
   Clearing `s_bit = 0` allows the instruction to complete without halting (`return_flag` remains 0). However, `fatal()` is called unconditionally on **every single execution** without a latch or rate limit. An unprivileged guest user process executing this in a loop can flood host stderr and disk logs. Furthermore, in System mode (`ARM_MODE_SYS32`), this test is completely skipped, silently executing the user register load without any warning, even though STM(2)/LDM(2) in System mode is also UNPREDICTABLE in hardware (`_scratchpad/ddi0100i.txt:8043-8046`).

2. **DPI SPSR Exception-Return Sibling in User/System Mode (`src/cpus/cpu_arm_instr_dpi.c:215-235`):**
   `src/cpus/cpu_arm_instr_dpi.c` is the sister implementation for data-processing instructions writing PC with S set (`MOVS PC, Rn`, etc.), which is the architectural companion to LDM(3) for SPSR restoration.
