### (a) Dossier's Chosen Disposition Member

**Chosen Member:** Disposition Member 7 ("Implement missing behavior" -- accept the reserved load field where required, and provide a proper guest Program-exception path for invalid forms selected to fault).

#### 1. Is its machinery really present on this CPU?
**NO.** The machinery to deliver a guest Program exception (`0x00700`, illegal instruction cause in SRR1) is **completely absent** from this CPU implementation at `db8b1a33`:
- **No exception declaration:** In `src/include/cpu_ppc.h:251–257`, only six exceptions are declared:
  ```c
  #define PPC_EXCEPTION_DSI 0x3
  #define PPC_EXCEPTION_ISI 0x4
  #define PPC_EXCEPTION_EI  0x5
  #define PPC_EXCEPTION_FPU 0x8
  #define PPC_EXCEPTION_DEC 0x9
  #define PPC_EXCEPTION_SC  0xc
  ```
  There is no `#define PPC_EXCEPTION_PROGRAM 0x7`.
- **No vectoring or cause bit delivery:** In `src/cpus/cpu_ppc.c:318–345` (`ppc_exception()`):
  - Line 321 sets `cpu->cd.ppc.spr[SPR_SRR0] = cpu->pc;`.
  - Lines 323–326 construct SRR1:
    ```c
    if (exception_nr >= 0x10 && exception_nr <= 0x13)
        cpu->cd.ppc.spr[SPR_SRR1] = (cpu->cd.ppc.msr & 0xffff)
            | (cpu->cd.ppc.cr & 0xf0000000);
    else
        cpu->cd.ppc.spr[SPR_SRR1] = (cpu->cd.ppc.msr & 0x87c0ffff);
    ```
    The mask `0x87c0ffff` clears bits 11–15 of SRR1 (where the Program interrupt cause flags reside, such as bit 12 / 44 for illegal instruction per `ppc_pem32_rev2_2001.txt:12035–12040` and `ppc_oea_book3_v201.txt:3962–3963`). There is no logic to accept or encode an illegal-instruction cause into SRR1.
  - Lines 337–339 compute `cpu->pc = exception_nr * 0x100; if (cpu->cd.ppc.msr & PPC_MSR_IP) cpu->pc += 0xfff00000ULL;`. While `0x7 * 0x100 = 0x700` would compute the vector address `0x00700`, no caller invokes it.
- **No PC synchronization in `X(llsc)`:** In dynamic translation, `cpu->pc` is not updated before each instruction call. Synchronous exceptions must reconstruct the offending instruction PC from `ic` and `cpu->cd.ppc.cur_ic_page`. The only place doing this is `CHECK_FOR_FPU_EXCEPTION` at `src/cpus/cpu_ppc_instr.c:215–225`:
  ```c
  uint64_t low_pc = ((size_t)ic - (size_t)cpu->cd.ppc.cur_ic_page)

  cpu->pc = (cpu->pc & ~((PPC_IC_ENTRIES_PER_PAGE-1) << PPC_INSTR_ALIGNMENT_SHIFT))
  ```

- **No existing Program exception callers:** Searching all PPC source files at `db8b1a33` yields zero calls delivering a Program exception or referencing vector `0x700`.

#### 2. Is it right?
- **Load instructions (`lwarx`, `ldarx`):** Yes. Book I v2.01 (1.5.2, line 432) and Book II v2.01 (lines 1259–1266) explicitly designate bit 31 as a reserved field `/` and mandate that reserved fields are ignored by the processor. Accepting the load and establishing the reservation without checking `rc` is the required architectural behavior.
- **Store Conditional instructions (`stwcx.`, `stdcx.`):** Under Book I v2.01 (1.5.1, lines 1116–1128) and PEM32 (4.1.3.2.2, lines 6856–6857), encoding bit 31 as 0 is an invalid form. The architecture specifies that attempting to execute an invalid form *either invokes the illegal instruction error handler (a program exception) or yields boundedly-undefined results.*
- **Assessment of Member 7:** While Member 7 represents the ideal architectural end-state, choosing it creates a heavy cross-subsystem dependency on unbuilt exception machinery (`cpu_ppc.h`, `cpu_ppc.c`, and PC synchronization macros). If the review panel's mandate is bounded to eliminating host crashes within existing CPU capabilities, Member 4 (accepting the computation under the boundedly-undefined rule) or routing invalid forms to the existing dyntrans stop path (`goto bad;`) would accomplish survival without inventing stub exception machinery. The dossier acknowledged this limitation in Section 5 (lines 123, 133–136).

### (b) Siblings the Dossier Missed in the Same Files

The dossier studied `src/cpus/cpu_ppc_instr.c` and its included tail `src/cpus/cpu_dyntrans.c`, and referenced callers / machine files. It missed several sibling issues in those exact files:

1. **`X(extsw)` in 32-bit mode (`src/cpus/cpu_ppc_instr.c:3125–3130`):**
   `extsw` (Extend Sign Word, `PPC_31_EXTSW`) is a 64-bit-only instruction. The decoder at `src/cpus/cpu_ppc_instr.c:5027–5028` decodes it unconditionally without checking `cpu->is_32bit` or `cpu->cd.ppc.bits == 64`:
   ```c
   case PPC_31_EXTSW:ic->f = instr(extsw);
                     rc_f  = instr(extsw_dot); break;
   ```
   In 32-bit mode (`MODE32`), `X(extsw)` executes:
   ```c
   X(extsw) {
   #ifdef MODE32
       fatal("TODO: extsw: invalid instruction\n");
   #else
       reg(ic->arg[2]) = (int64_t)(int32_t)reg(ic->arg[0]);
   #endif
   }
   ```
   At runtime on any 32-bit PowerPC model, executing `extsw` triggers `fatal("TODO: extsw: invalid instruction\n");` (line 3127) and returns without updating `reg(ic->arg[2])`.
