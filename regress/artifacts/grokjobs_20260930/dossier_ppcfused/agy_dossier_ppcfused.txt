### (a) Chosen Disposition Member & Machinery Presence

**Is Member 7 (Implement) right?**
Yes. Instructions `fmsubs`, `fmsubs.`, `fmadds`, `fmadds.`, `fnmsubs`, `fnmsubs.`, `fnmadds`, `fnmadds.` are architecturally valid PowerPC User Instruction Set Architecture (UISA) problem-state instructions (`_scratchpad/ppc_pem32_rev2_2001.txt:19633`, `:19845`, `:20269`, `:20439`). When `MSR[FP]=1`, hardware executes them to compute single-precision floating-point results in `frD` with status updates to `FPSCR` (and `CR1` if `Rc=1`). The current path abruptly stops guest execution by branching to `bad:` (`src/cpus/cpu_ppc_instr.c:5218`) and executing `cpu->running = 0` (`src/cpus/cpu_dyntrans.c:2014`). Deleting the stop (Member 1) would leave the instruction unhandled at `&nothing_call` (`src/cpus/cpu_dyntrans.c:2023`); declining silently (Member 2) or announcing once (Member 3) fails arithmetic; accepting an existing result (Member 4) is impossible as no result is computed and double aliasing fails single-precision rounding; inventing backing store (Member 6) is unneeded as FPR registers exist (`src/include/cpu_ppc.h:92`); and raising an architectural exception (Member 5) is invalid when `MSR[FP]=1`. Member 7 is the only correct disposition.

**Is its exception machinery really present on this CPU?**
The exception machinery is **partly present**:

1. **Floating-Point Unavailable Exception (`PPC_EXCEPTION_FPU`) — FULLY PRESENT:**
   When an emulated floating-point instruction is executed while `MSR[FP] == 0`, hardware generates an FPU unavailable interrupt (vector `0x00800` / `0xfff00800`). The machinery to deliver this interrupt is completely implemented and wired:
   - Check & trigger: `src/cpus/cpu_ppc_instr.c:216–225` (`CHECK_FOR_FPU_EXCEPTION`) verifies `!(cpu->cd.ppc.msr & PPC_MSR_FP)`, recalculates `cpu->pc` from the instruction call entry, calls `ppc_exception(cpu, PPC_EXCEPTION_FPU)`, and returns.
   - Record-form twin trigger: `src/cpus/cpu_ppc_instr.c:205–206` (`FDOT`) invokes `CHECK_FOR_FPU_EXCEPTION` prior to running the base instruction handler or updating CR1.
   - Vector define: `src/include/cpu_ppc.h:255` defines `PPC_EXCEPTION_FPU 0x8`.
   - Interrupt delivery: `src/cpus/cpu_ppc.c:318–345` (`ppc_exception`):
     - Line 321: `cpu->cd.ppc.spr[SPR_SRR0] = cpu->pc;`
     - Line 327: `cpu->cd.ppc.spr[SPR_SRR1] = (cpu->cd.ppc.msr & 0x87c0ffff);`
     - Line 335: `cpu->cd.ppc.msr &= ~(PPC_MSR_EE | PPC_MSR_RI | PPC_MSR_PR);`
     - Line 337: `cpu->pc = exception_nr * 0x100;` (`0x8 * 0x100 = 0x800`)
     - Lines 338–339: `if (cpu->cd.ppc.msr & PPC_MSR_IP) cpu->pc += 0xfff00000ULL;` (`0xfff00800`)
     - Lines 341–344: Synchronizes translation pointers via `ppc32_pc_to_pointers(cpu)` or `ppc_pc_to_pointers(cpu)`.

2. **Floating-Point Enabled Arithmetic Exception Traps — NOT PRESENT:**
   For enabled floating-point exception traps (e.g. invalid operation when `FPSCR[VE]=1`, overflow when `FPSCR[OE]=1`), real hardware delivers a Program Interrupt (vector `0x00700`). On this emulated CPU:
   - `src/cpus/cpu_ppc.c:1941–1942` explicitly states:
     > `"This never touches FPCC, never consults the enable bits, and never traps. Enable-driven result suppression and trap delivery are a separate round."`
   - `ppc_fpscr_raise()` (`src/cpus/cpu_ppc.c:1944–1951`) and `ppc_fpscr_recompute()` (`:1890–1912`) derive and latch sticky status flags (`FX`, `FEX`, `VX`, etc.), but never call `ppc_exception()` to trap or deliver a program interrupt.
