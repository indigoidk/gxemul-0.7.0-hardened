## Q1 — Is the fix right?

**Conditional yes.** Given premises 1, 2, 3, 5 the lower bound `CLKOFF + MK48TXX_ICSR` is exactly the case address and the change cannot disturb the case: under the new condition the switch is reached for `addr ∈ [0x1ff8, 0x1ff9)`, i.e. exactly one byte, which is the byte the case handles. The case is the only thing the switch implements, so the lower bound cannot "swallow" anything except the seven offsets the brief claims are plain RAM. (REASONED, conditional on premises 1–3.)

If premise 3 is wrong — if the MK48T08 actually implements 0x1ff0..0x1ff7 as clock registers that should be in the switch — the fix is a regression that turns eight live registers into dead bytes the user can no longer address. The diff's defence ("plain non-volatile RAM") is the only thing protecting this claim and it is the single point that needs a real datasheet, not a header file, to settle.

## Q2 — Is the upper bound still right?

**Conditional yes, but the upper bound is doing more work than the brief admits.** Under the new condition the switch handles exactly one byte (0x1ff8). Offsets 0x1ff9..0x1fff (seven bytes) fall through `relative_addr >= CLKOFF + ISEC` to the RAM path. The brief justifies this by saying update_regs populates that RAM. That is fine for *reads after a CSR-driven refresh*. It is **not** fine for *writes*: writing to 0x1ff9 stores into `d->reg[0x1ff9]`, which the next update_regs overwrites with the RTC's seconds field. The MK48T08 datasheet (not the header) is what tells you whether time-of-day writes are expected to round-trip; the brief asserts they need not and does not cite a source.

This is a separate defect from the one being fixed and is correctly out of scope for this round, but the diff comment should not say "The upper bound stays at MK48TXX_ISEC *deliberately*" as though that has been re-justified here — it has not; it has been inherited. (REASONED.)

## Q3 — The floor question

**M_OLD is a legitimate floor for the 32-row kill population, but the round is not meeting clause (b) literally and the round should say so.**

Clause (b), read literally, requires "verbatim reinstatement of the removed defect". The diff does not remove a statement; it modifies a lower bound and leaves the `default: exit(1)` arm in place but unreachable. The *only* way to make that arm fire again from the diff is to walk the lower bound back to a value smaller than 0x1ff8. M_OLD does exactly that and re-creates exit(1) on 0x1ff0..0x1ff7. So M_OLD is a *semantic* reinstatement of the user-visible defect, even though it is not a *literal* reinstatement of the removed text.

That distinction matters because:

- M_OLD re-creates the defect in the same place, with the same mechanism. A floor that wants to verify "the instrument can detect exit(1) at these eight offsets" is met.
- But a floor that wants to verify "the instrument can detect this specific boundary edit *in isolation*" is **not** met by M_OLD: M_OLD bundles the lower-bound edit with all the other differences between the diff and HEAD. If a future developer introduces only the *upper-bound half* of the defect (`addr >= CLKOFF + ICSR`), M_OLD will not detect that; only M_ICSR would, and M_ICSR is in the breach-detection role, not the floor role.

The honest answer: **the round's floor is met for the lower-bound class of edits; the round is silent on the upper-bound class.** If clause (b) is meant to cover both, then the round is claiming a floor it does not meet. ## Q6 — The width defect

**Leaving it out is right for this round, but the diff makes the framing slightly off.**

The diff says "those eight are ORDINARY NVRAM on this part, which is what licenses accepting them". That is the licence for the boundary correction. The width defect is a property of the *accept path itself*, not of any specific offset: any read or write routed to `goto ret` returns a single byte regardless of `len`. The diff routes *eight more offsets* to that path, but the path was already byte-wide before the diff and remains byte-wide after it. The diff does not introduce the bug; it does not widen its blast radius (the path was always len-blind); it does not change the symptom in any new way.

Two reasons it would become this round's business:
- If the kill rows tested multi-byte accesses at 0x1ff0..0x1ff7 and asserted something about the *width* of the returned data. The brief says the rows check "access ran to completion" / "death message present" / "no message", not width — so the rows pass either way.

The framing concern: the diff comment is silent on the width defect.
