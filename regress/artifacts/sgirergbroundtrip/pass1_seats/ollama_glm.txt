* **Reframe that sharpens the whole brief** [REASONED]: both RGB arms *agree* on the register format (R at bits 31..24, low byte unused — as PUT's `buf[0]=*color>>24` and GET's output both show), and the register convention is mode-consistent everywhere (RGBA word 0xRRGGBBAA, ABGR word 0xAABBGGRR, both arms agreeing within each mode). The question "which byte holds which channel" reduces to: **where is the pad byte in a 32-bit CRIME RGB container.** That is a hardware fact.
* **"Opposite byte orders" — challenged, as you asked** [READ claim, REASONED correction]: for the same color, RGBA and ABGR write **identical memory bytes**, `[R,G,B,A]`; they differ only in register word order, i.e., in the buf↔word *mapping*. This coincidence is worth more than the opposition: all three 4-byte PUTs emit `[R,G,B,x]`. Caveat that bounds the argument: round-trip consistency cannot detect a wrong-but-self-consistent container, so ABGR is a vote only *if* its own container is hardware-right (RGBA — big-endian word on a big-endian platform — is the solid neighbor; ABGR's `[R,G,B,A]` could be an emulator invention).
* **S4** [READ value; REASONED trace]: arithmetically consistent with S1 given big-endian seeding `[aa,bb,cc,dd]` and a byte-faithful readback; the 0xdd in result bits 15..8 can only have come from a memory-loaded `buf[3]`, which all but proves bufdepth ≥ 4 in that run (an unstated premise the measurement itself confirms). But it is **representation-neutral**: under `[pad,R,G,B]`, the engine read pad=aa, R=bb, G=cc, B=dd and correctly promoted to RGBA `[bb,cc,dd,00]`. ## Q1 — which arm

* **Ground 1 is circular** [REASONED]: "PUT writes 0 at buf[3], so buf[3] is the pad" assumes PUT is right to prove GET wrong. Under the opposite convention that same line is the *bug* — and a worse one: PUT would be **zeroing the guest's blue byte on every RGB draw** (write-side destruction of memory) rather than misreading it.
* **Ground 2 survives and extends** [REASONED]: ABGR *also* places R at `buf[0]` (see above), so among the five 4-byte arms, the RGB GET is the lone container outlier — your case is stronger than you stated. Add the promotion-continuity argument: under `[R,G,B,pad]`, RGB→RGBA keeps every channel at the same byte offset; under `[pad,R,G,B]` every channel shifts a byte.
* **The other side, stated as strongly as I can** [REASONED]: 24-bit color right-justified in a 32-bit container (pad in the MSB, i.e., byte 0 on big-endian O2) is a real hardware tradition. Under it, GET is a correct left-justifying read (container 0x00RRGGBB → register 0xRRGGBB00 — precisely the shift-by-8 your measurement shows), PUT is the wrong arm, and the fix belongs in PUT (`buf[0]=0; buf[1]=*color>>24; …`). * **My position**: internal consistency identifies the *deviant* (the RGB GET), not the *guilty*. Settle Q2 before writing "GET is wrong" into any record.

## Q5 — mutants

* **The fix is not unique**: G1a `(buf[0]<<24)+(buf[1]<<16)+(buf[2]<<8)` vs G1b `…+buf[3]` (≡ the RGBA GET). Both round-trip against PUT (pad written as 0); they differ only on raw-seeded pixels with a nonzero byte 3 (G1a → 0xaabbcc00, G1b → 0xaabbccdd for your seed). This is a sub-question of Q2 (does the hardware's RGB GET return the pad in the low byte?) and must be decided before the oracle is written.
* **Your three rows**: if they are CI/RGBA/ABGR (or the three S4 controls), **every** mutant confined to the RGB GET line escapes all three — none of them executes the RGB GET arm. Trivially, all your listed edits escape.
* With an RGB round-trip row added, **still** uncaught: (i) the **fix-in-PUT pseudo-fix** (make PUT write `[0,R,G,B]`) — round-trips perfectly and reads like a repair; only an externally-seeded row with a hardware-derived oracle rejects it, which requires Q2 settled first or the detector blesses either arm; (ii) the G1a↔G1b pad toggle — needs a nonzero byte at byte-3 in the seed; (iii) any permutation if the probe color has repeated bytes.
* Caught by a well-formed RGB row: the wholesale reindex {0,1,2}→{1,2,3} (the original bug), index↔shift pairing swaps, dropped lowest term, single ±8 shifts — provided the seed has pairwise-distinct bytes and the assertion is exact 32-bit equality.
* **`+`→`|` is a null mutant** [REASONED]: every term is a uint8_t shifted into disjoint bit ranges, so sum == OR always. No test can or should catch it. (Pre-existing footnote: `buf[i]<<24` on bytes ≥0x80 is signed-overflow UB in both forms, in every arm today.)
