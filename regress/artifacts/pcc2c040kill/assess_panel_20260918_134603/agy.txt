##### **P1. Legal Guest Behavior vs. Guard**
> *"Is a byte store to the PCC2 General Control register with the C040 bit set LEGAL guest behaviour (an MVME187 driver may program it), so that ending the host was a defect and not a guard?"*

* **Status:** **CONFIRMED**.
* **Evidence:**
  * **Primary Hardware Specification:** Motorola MVME187 / PCCchip2 Programmer's Reference Guide (`VMESBCA2/PG1`, preserved in [`_scratchpad/vmesbcp2.txt:4859-4916`](file:///C:/DocumentNoSnc/CC/GXEMUL/_scratchpad/vmesbcp2.txt#L4859-L4916)):

      > *"C040: CPU040. This bit should be set when the MPU is from the M68000 family. It should be cleared when the MPU is an MC88100. When the bit is set, EIPL<2..0>* are driven as outputs which carry the priority encoded interrupt request from the PCCchip2 interrupt sources. When the bit is cleared, EIPL<2..0>* are not driven as outputs, but are inputs only."*
  * The PCCchip2 ASIC was shared across Motorola 68040 boards (MVME167) and 88100 boards (MVME187). A guest OS driver, boot firmware probe, or porting test performing an 8-bit store with bit 2 set is executing architecturally valid, documented hardware I/O.
  * Terminating the host process with `exit(1)` upon an ordinary peripheral write is an unhandled emulator DoS crash, not an access guard.

##### **P2. Shipped Fix Disposition**
> *"Did the shipped fix keep the guest's C040 write, suppress interrupt ASSERTION while C040 is set (because the model has no 68040 EIPL path), and announce it once via a per-device latch bit -- and is that the right disposition, versus implementing EIPL delivery or declining the write?"*

  * **Suppresses Assertion:** In [`src/devices/dev_pcc2.c#L410-L422`](file:///C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_pcc2.c#L410-L422):
    ```c
    if (d->pcctwo_reg[PCCTWO_GENCTL] & PCC2_C040) {
        if (!(d->warned & (1u << PCC2_W_C040))) {
            d->warned |= (1u << PCC2_W_C040);
            fatal("[ pcc2: C040 (MC68040 EIPL) interrupt delivery not "
                "implemented; assertion suppressed  (once) ]\n");

    if (assert)
    ```

    `assert = 0;` forces the CPU interrupt line to [`INTERRUPT_DEASSERT`](file:///C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_pcc2.c#L422).
  * **Per-Device Latch:** `PCC2_W_C040` is defined in the enum at [`src/devices/dev_pcc2.c#L153`](file:///C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_pcc2.c#L153).   * **Disposition Adjudication:**
    * *Declining the write* (dropping C040 or returning bus error) would violate hardware register semantics: C040 is R/W, and guests expect readback to match written state.
    * *Implementing 68040 EIPL delivery* is impossible for the MVME187 machine model because the simulated CPU is an MC88100, which has an `INT` pin (`d->cpu_irq`) rather than 3-pin `EIPL<2..0>*` lines. Routing EIPL requests to the 88100 INT pin would deliver interrupts intended for 68040 pins into an 88100 CPU.
    * *Suppressing assertion on `d->cpu_irq`* correctly models the hardware state: setting C040 disconnects PCC2 from the 88100 `INT` line and switches output to the EIPL pins.

##### **Q2. Severity and Option Set Adjudication**
* **Severity Ranking:** **HIGH (Host Denial of Service / Crash on unprivileged guest store)**.
  * A single guest memory write to an emulated peripheral device terminating the hypervisor/emulator host process is a high-severity security vulnerability in any isolation/virtualization boundary.
* **Option Set Evaluation:**
  1. `ACCEPT (silent)`: Hardware-inaccurate. Storing the byte while allowing normal INT assertion routes 68040 EIPL interrupts into the 88100 INT pin.
  2. `DECLINE (write rejection / bus fault)`: Hardware-inaccurate. Violates register R/W architecture and breaks guest readback.
  3. `IMPLEMENT`: Out of scope / unavailable. The modeled CPU is an MC88100 without an MC68040 EIPL pin bus.
  4. `DECLINE ASSERTION + LATCHED ANNOUNCE (shipped)`: **Optimal and correct**. Preserves register readback, prevents spurious INT assertion on the 88100, and warns once without log flooding.
