## Q1 — premises, settled from the tree (not from the packet)

### 1. `buf` is uninitialised on every path that uses it. Yes.

Block-scope `uint8_t buf[8];` at `:284`, no initialiser, no `memset` of `buf`. The five `memset`s in this file are `d`, `rop_used` (twice), a comment, and `zerobuf`. C99 does not zero it. There is no compiler-visible store that fills `buf[4..7]` on any colour arm, and no arm fills more than four bytes.

Early returns (`x/y` reject, `tile_nr >= 256`, `tlb_mode` default, `tile_nr >= 32`, high-bit clear) never reach `buf`. Those paths are not leaks; they also do not initialise it.

### 2. `#95` does not cover PATH A. It does not cover PATH B's extra bytes either. The round is not dead.

`#95` is `memory_rw.c:485-492`:

```c
if (writeflag == MEM_READ)
    memset(data, 0, len);
```

inside the **device-hit** arm, before dispatch. Three independent misses:

| path | why `#95` cannot save it |
|---|---|
| PATH A | `MEM_WRITE`. The `if` is read-only. |
| PATH B, extra bytes | even on a device read it zeroes `len` = `bufdepth` bytes. The combine then reads **past** `len`. |
| both, on the real destination | see Q1.3: this access never takes the device arm. |

`#95`'s CHANGELOG sentence is about **device handlers filling the caller's `data`**. This helper is the opposite: a local stack buffer used to read/write **framebuffer RAM**. `#100` grew `buf[4]`→`buf[8]` to stop a **stack overflow** when `bufdepth==8`. It did not initialise the new bytes. That converted overflow into a well-defined uninit write. Different class, same function, both claims in the packet survive.

### 3. `tileptr + ofs` is RAM. `#95` does not run. PATH B is worse than the brief said, in the way the brief feared.

Case 4 (`LIN_A`) is the witness vehicle:

```c
tileptr = 0x80000000 | (d->re_linear_a[tile_nr] << 12);
ofs = x & 4095;
...
tileptr &= ~0x80000000;
cpu->memory_rw(..., tileptr + ofs, buf, bufdepth, ..., PHYSICAL);
```

The shipped probe sets `re_linear_a[0] = 0x10` → physical **`0x10000`**. CRIME is at `0x14000000` (`machine_sgi.c`). `0x10000` is ordinary RAM.

Successful RAM path (`memory_rw.c:778-782`) is `memcpy` of `len` bytes. No pre-zero. Failed RAM (`memblock == NULL`, `paddr >= physical_max`) zeroes `len` only, still not the tail of `buf`.

So on the path the probe already uses: PATH A writes host stack into guest RAM; PATH B's `memcpy` fills `buf[0 .. bufdepth-1]` from RAM and leaves `buf[bufdepth .. 7]` as stack. No `#95` anywhere.

### 4. The two fields are independent. No caller guard.

Enumerated producers of `mode`:

- `CRIME_DE_MODE_DST` / `CRIME_DE_MODE_SRC` (`:1033-1043`): stored as raw `idata` into `de_reg[]`. No mask.
- `draw_primitive` (`:679-680, :794, :840, :855, :860, :906`): passes those registers straight through. The only related check is XFER `step_x != src_bufdepth`, which **warns and continues**.
- MTE (`:1342-1364`): synthesises a mode from the MTE depth field. No DE colour/depth cross-check. (And it currently *generates* a mismatch — see “something else” below.)

`DE_MODE_PIXDEPTH_*` (bits 2–3) exists in `crmfbreg.h` and is **used nowhere in `src/`**. Third independent field, unused.

### 5. Depth field = 3 (`bufdepth` 8) is reachable as a guest store. PATH A does **not** rest on it.

Walk of bits 8–9, the actual producer (`(mode >> 8) & 3`):

| bits 8–9 | `bufdepth` | header name |
|---|---|---|
| 0 | 1 | `DE_MODE_BUFDEPTH_8` `0x00000000` |
| 1 | 2 | `DE_MODE_BUFDEPTH_16` `0x00000100` |
| 2 | 4 | `DE_MODE_BUFDEPTH_32` `0x00000200` |
| 3 | 8 | **no constant** |

Nothing in the DE store path rejects `0x300`. `#100`'s comment is evidence they believed 8 was reachable. It is, as a raw store.

**The brief's PATH-A headline is still the wrong vehicle.** Walk of PUT fill vs transfer, documented depths only:

| colour | fills | bd=1 | bd=2 | bd=4 | bd=8 (undocumented) |
|---|---|---|---|---|---|
| CI | `buf[0]` | clean | **leak `buf[1]`** | **leak `buf[1..3]`** | leak `buf[1..7]` |
| RGB/RGBA/ABGR | `buf[0..3]` (RGB sets `buf[3]=0`) | clean (short write) | clean | clean | leak `buf[4..7]` |
| default / YCRCB | `buf[0..3]=random()` | (random, not uninit) | same | same | uninit `buf[4..7]` on top of random |

**Documented PATH A is `CI` + `BUFDEPTH_16` or `BUFDEPTH_32`.** Mode word for the existing LIN_A apparatus: **`0x1200`** = `LIN_A | BUFDEPTH_32 | CI`. The brief's `0x1320` is real but is the undocumented extra.

PATH B, documented, GET combine vs fill:

| colour | combine reads | bd=1 | bd=2 | bd=4 |
|---|---|---|---|---|
| CI | `buf[0]` only | clean | clean | clean |
| RGB | **`buf[1], buf[2], buf[3]`** (not `buf[0]`) | leak | leak | clean for those three |
| RGBA / ABGR / default | `buf[0..3]` | leak | leak | clean |

`0x1020` = `LIN_A | BUFDEPTH_8 | RGBA` is a valid PATH-B word made of **documented** fields. Arithmetic in §7 is correct for the three words given; it just picked the weak PATH-A member.

### 6. `YCRCB` (`0xf0`) is unimplemented here. Yes.

`grep YCRCB src/devices/dev_sgi_re.c` is 0. Mask is `0xf0`, so bits 4–7 have 16 values. Five are named; four have `case`s; `0xf0` and the other eleven hit `default:`. Confirmed.

## Q2 — smallest edit that re-opens the defect and stays green on the obvious detector

Assume the fix is `memset(buf, 0, sizeof buf)` (or `= {0}`) **before** the `if (put)`.

**The one-token (d) mutant is `sizeof buf` → `bufdepth`.**

- PATH A, CI + bd=4: `memset` of 4, fill `buf[0]`, write 4. Extra bytes are still 0. **A “bytes are not stale / extra bytes are 0” row stays green.**
- PATH B, RGBA + bd=1: `memset` of 1, read 1, combine 4. `buf[1..3]` are stack again.

That is exactly the refactor the brief named. A detector that only pins PATH A cannot see it.

## Something else, found while checking premises

**1. MTE `if (depth == 4)` is dead. The emulator itself emits PATH A's documented pair.**

```c
int depth = 8 << ((mode & MTE_MODE_DEPTH_MASK) >> MTE_DEPTH_SHIFT);
/* depth ∈ {8,16,32,64} bits */
...
if (depth == 4) {           /* never true */
    src_mode |= DE_MODE_TYPE_RGBA;
    dst_mode |= DE_MODE_TYPE_RGBA;
}
```

16- and 32-bit MTE TLB fills therefore always run as **CI + matching bufdepth**. 32-bit fill writes `bg`'s low byte plus three uninit bytes. Comment at `:1322` says NetBSD `crmfb_fill_rect` uses this. File as its own row (`sgimtedepth4` or similar). Do **not** join: fixing `== 4` to `== 32` changes MTE 32-bit *colour* semantics, which memset does not. Memset would turn that path into “low byte + zeros” — defined, still wrong.

**2. RGB GET is not the inverse of RGB PUT.** PUT stores R,G,B,0 in `buf[0..3]`. GET does `(buf[1]<<24)+(buf[2]<<16)+(buf[3]<<8)` — **never reads `buf[0]`**. GBE `CRMFB_MODE_TYP_RGB8` matches the PUT packing, not this GET. Separate correctness bug; file it; it also makes RGB+bd=1 PATH B worse (the one byte actually read is the one the combine ignores).

**3. Scan limit 3:** I did not re-run the scanner. I grepped `uint8_t buf[` under `src/devices/`: maple (memset-then-fill, safe) and this site. The maple idiom is the transferred warrant for (1). I am not treating “only member in the tree” as corroboration of the defect; the function is.
