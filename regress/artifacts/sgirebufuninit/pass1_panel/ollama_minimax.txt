## Premises I can confirm from the inline code (READ)

- **`buf[8]` is never initialised.** No `memset`, no initialiser, no preceding assignment in the function. The inlined source shows the declaration as `uint8_t buf[8];` with only a comment after it. (Q1.1 — yes, within the function.)
- **PATH A is structurally present.** All five PUT arms assign at most `buf[0..3]`. Enumerated from inline code:
  - `DE_MODE_TYPE_CI` → `buf[0]` assigned; `buf[1..7]` not.
  - `DE_MODE_TYPE_RGB` → `buf[0..3]` assigned (including `buf[3]=0`); `buf[4..7]` not.
  - `DE_MODE_TYPE_RGBA` → `buf[0..3]`; `buf[4..7]` not.
  - `DE_MODE_TYPE_ABGR` → `buf[0..3]`; `buf[4..7]` not.
  - `default:` → `buf[0..3] = random()`; `buf[4..7]` not.
  So any PUT with `bufdepth > bytes-filled-by-arm` leaks. RGBA at depth 3 (`bufdepth=8`) writes 8 bytes with only 4 assigned. CI at depth 2, 4, or 8 leaks at depths above 1 (brief mentions this in passing but the reachability table focuses only on RGBA-at-8 — see "real defect" below).
- **PATH B is structurally present.** GET reads `bufdepth` bytes into `buf` and the `DE_MODE_TYPE_RGBA` arm combines `buf[0..3]`. With `bufdepth=1`, only `buf[0]` is filled; `buf[1..3]` are stale.
- **Reachability table arithmetic is correct.** I re-decoded:
  - `0x1220` = `0001 0010 0010 0000`: bits 4-7 = `0010` (RGBA), bits 8-9 = `10` (2 → `bufdepth=4`), bits 10-12 = `100` (LIN_A).
  - `0x1320` = `0001 0011 0010 0000`: bits 8-9 = `11` (3 → `bufdepth=8`), rest same.
  - `0x1020` = `0001 0000 0010 0000`: bits 8-9 = `00` (0 → `bufdepth=1`), rest same.
- **`YCRCB` (0xf0) hits `default:` in both switches.** (Q1.6 — yes.) Documented in `crmfbreg.h` per the inlined `#define`s, no `case` in either switch.

- **Q2** — the brief's smallest-edit hypothesis is the right shape: `memset(buf, 0, bufdepth)` would silence a "is there a memset?" detector while leaving PATH B leaking, because PATH B's combine reads `buf[1..3]` which `bufdepth=1` does not touch. - **Q3** — I cannot name a member the brief missed; the five cover the design space. The "we do not know what the hardware does" fallback the brief mentions is a legitimate answer and has precedent in this project.
- **Q4** — the proposed oracle has a real weakness the brief acknowledges: the compiler may not preserve `buf`'s stack slot between the two calls. An oracle that rests on "the stale bytes are the previous pixel's" is, by the author's own framing, an oracle that can pass by luck. - **Q6** — the unification argument is plausible but the brief's own caveat applies. Two purpose-built oracles over a shared weak one is the safer record. The brief invites honest disagreement and I'd record disagreement here.

## A real defect I noticed (READ)

**§3a's enumeration claims "exactly two paths" but does not surface CI-at-depth-2 and CI-at-depth-4 as separate rows in §7's reachability table.** §3a's table correctly shows CI assigning only `buf[0]`; the prose correctly says "CI leaks at any depth above 1"; but §7's witness table shows only `(0x1220, 0x1320, 0x1020)` — all RGBA. The CI-at-depth-2 case is reachable through a different mode-word value than `0x1320` (e.g., `0x1210` = LIN_A | depth 2 | CI) and is not captured in the witness design. The brief does not need a third witness row if the disposition covers all depth/mode mismatches uniformly, but the table gives the reader the impression RGBA is the only relevant colour mode.
