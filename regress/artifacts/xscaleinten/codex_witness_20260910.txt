**2. An ordinary ARM-state coprocessor register transfer can reach the requested read arm.**

The execution path is:

`guest instruction fetch → arm_instr_to_be_translated → condition-selected arm_instr_mcr_mrc → arm_mcr_mrc → coproc[6] → arm_coproc_i80321_6`

The ARM translator fetches the instruction from guest memory. In main-opcode `0xe`, an instruction with bit 4 set selects `cond_instr(mcr_mrc)` and saves the instruction word. This is execution decoding, independently of the disassembler. See [cpu_arm_instr.c](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_arm_instr.c:4901).

The runtime wrapper synchronizes `cpu->pc` and calls `arm_mcr_mrc`. That function extracts `opcode1`, `l_bit`, `crn`, `rd`, `cp_num`, `opcode2`, and `crm`, then calls the selected non-null handler. Consequently, a CP6 read with `crn=0`, `crm=0`, and `l_bit=1` reaches precisely the assignment and termination in question. See the [runtime wrapper](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_arm_instr.c:948) and [dispatcher](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_arm.c:2643).

**There is no privilege or processor-mode check in that transfer wrapper, dispatcher, or CP6 handler.** In particular, dispatch does not consult CPAR. CPAR is stored and read through CP15, but the source explicitly notes that it is not otherwise used; the source-wide references confirm no access-enforcement check. See [cpu_arm_coproc.c](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_arm_coproc.c:273). This describes the emulator’s implementation, not a claim about real hardware permissions.

There are ordinary execution prerequisites:

- ARM conditional execution must select the instruction. A failed condition skips the transfer wrapper. See the [condition wrappers](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_arm_instr.c:132).
- The instruction must be fetched successfully and decoded in ARM state. Thumb state takes a separate interpreter. See [cpu_dyntrans.c](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c:254).
- The executing CPU must have CP6 installed. With a null coprocessor entry, `arm_mcr_mrc` prints its generic TODO diagnostic and does not call this handler. **Its undefined-exception call and `exit(1)` are commented out**, so absence does not itself terminate execution there.

The cold CPU initialization already selects SVC32 with IRQ/FIQ masked. No privilege transition is needed. See [cpu_arm.c](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_arm.c:127).

CP6 register selection is not an MMIO address translation. The guest instruction needs accessible code memory, but the coprocessor register itself is selected directly through the handler table. The existing device shares the CPU’s `i80321_inten` storage through `d->enable`. See [dev_i80321.c](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_i80321.c:445).

**4. A naive readback assertion has several indistinguishable outcomes.**

For an assertion equivalent to “write `W`; read; require result `W`”:

| Fault | When the naive assertion can still pass |
|---|---|
| Always returns zero | When `W` is zero. |
| Returns a stale value | When the stale value equals `W`, including repeated writes of the same value. |
| Never executes the read | When the destination already contains `W`. Using the write-source register as the read destination makes this especially easy. |
| Never executes the relevant program | When the inspected register or result memory already contains the expected value, or the parser accepts an old observation. |

A discriminating oracle would check **successive state changes**: two distinct nonzero values, each written and subsequently read, with the read destination deliberately initialized to a different value before each read. The second expected value must differ from the first. This rejects constant zero, retention of the preceding value, and a read that leaves its destination untouched. Separate write-source and read-destination registers avoid the simplest false pass.

Execution evidence must accompany those values: check the intended instruction address and decoded coprocessor/register fields, require the destination transition, and require a subsequent guest effect or successful continuation. Missing observations must fail rather than become zero or reuse earlier output.

One correction to the probe commentary is relevant here: **a printed step disassembly alone does not prove the handler completed—or even that its condition passed.** The execution engine prints disassembly before executing the instruction. See [cpu_dyntrans.c](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c:282), followed by execution at [line 324](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c:324).

For this proposed change, the oracle also needs **continuation and silence**. The current implementation assigns the destination before exiting, so the assignment alone is not the desired outcome. The unchanged source predicts the named diagnostic and exit status 1; the proposed behavior requires the correct value, continued execution, and no diagnostic from this read arm. A register round trip tests this storage contract, not the entire interrupt-controller model.

Your corrected **read-direction** asymmetry is accurate. There is another premise correction: `crm=1` has **sixteen implemented direction arms—eight reads and eight writes—not fourteen**.
