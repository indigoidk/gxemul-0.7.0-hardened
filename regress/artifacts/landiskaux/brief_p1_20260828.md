## 1. THE DEFECT, AND IT IS A ONE-LINE OMISSION

`DEVINIT(wdc)` computes the alternate-status / device-control register address, then applies
per-machine overrides. Verbatim:

```c
	alt_status_addr = devinit->addr + 0x206;

	/*  Special hacks for individual machines:  */
	switch (devinit->machine->machine_type) {
	case MACHINE_MACPPC:
		alt_status_addr = devinit->addr + 0x160;
		break;
	case MACHINE_HPCMIPS:
		/*  TODO: Fix  */
		if (devinit->addr == 0x14000180)
			alt_status_addr = 0x14000386;
		break;
	case MACHINE_IQ80321:
		alt_status_addr = devinit->addr + 0x402;
		break;
	}

	memory_device_register(devinit->machine->memory, "wdc_altstatus",
	    alt_status_addr, 2, dev_wdc_altstatus_access, d, DM_DEFAULT, NULL);
	memory_device_register(devinit->machine->memory, devinit->name,
	    devinit->addr, DEV_WDC_LENGTH * devinit->addr_mult, dev_wdc_access,
	    d, DM_DEFAULT, NULL);
```

**There is no `case MACHINE_LANDISK:`.** landisk registers its wdc at `0x14000000` with
`addr_mult = 2`, so the main block covers `0x14000000-0x1400000f` — and the guest's device
control writes go to **`0x1400002c`**, which is outside it and matched by nothing.

## 3. *** THE THING THAT MAKES THIS NOT A FREE FIX ***

The whole device-control write arm, comments stripped, is:

```c
	if (idata & WDCTL_RST) {
		d->cur_command = COMMAND_RESET;
		wdc_new_command_reset(d);
	}
```

A read returns `status_byte()` and has no side effect. So mapping the register does exactly
two things, both gated on `0x04`: latch the ATAPI signature, and reset the ring/tenant state.

> **AND THE MEASURED HISTOGRAM SAYS THE GATE FIRES.** Write 1 is `0x0c`, which carries
> `WDCTL_RST`. **So this round does not merely stop discarding writes — it starts performing
> a real reset on a machine that has never had one.** That is a behaviour change on a booting
> guest, and it is the round's actual risk.

*(`WDCTL_RST` is `0x04` and not `0x08`; `#481` fixed a version of this that tested the wrong
bit. `COMMAND_RESET` is not a reset ACTION — it is read at exactly two sites, both making the
cylinder registers return the ATAPI signature `0xEB14`. It is the SIGNATURE LATCH.)*

## 4. A STRUCTURAL OBSERVATION THAT LOOKED LIKE THE EXPLANATION AND IS NOT

All four existing rules consult `devinit->addr` and **never `devinit->addr_mult`**, while the
main registration uses `DEV_WDC_LENGTH * devinit->addr_mult`. **And landisk is the ONLY
in-tree wdc with `addr_mult != 1`** (it passes 2; every other instantiation omits it and gets
1). So it is the only machine where the two conventions can disagree — which reads like a
complete explanation for why it is the only machine whose control writes land nowhere.

**IT IS NOT THE EXPLANATION.** Scaling does not produce the measured address:
`0x206 * 2 = 0x40c`, and the driver writes `+0x2c`. Neither the raw ISA offset nor any
scaling of it predicts `0x2c`. landisk's aux block genuinely sits somewhere machine-specific,
so `case MACHINE_LANDISK:` is the right SHAPE — but **not for the reason the addr_mult
asymmetry suggests**, and a round that says otherwise ships a wrong record.

**PREMISE TO CHECK:** I claim `+0x2c` is machine-specific rather than derivable. If you can
derive it from the SH-4 landisk memory map or from NetBSD/OpenBSD's landisk `obio` attachment,
say so — that would change the fix from a hardcode to a computation.

## 5. NO COLLISION — checked, not assumed

landisk registers exactly one wdc block, `0x14000000-0x1400000f`, and `+0x2c` lies outside it.
Nothing else in the machine claims that address. **PREMISE TO CHECK:** verify independently;
