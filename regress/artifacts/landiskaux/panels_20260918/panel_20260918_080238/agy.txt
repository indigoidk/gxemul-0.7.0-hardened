## VERDICT: GO-WITH-CHANGES

The defect is real and the diagnosis is correct: `dev_wdc_init()` fails to match `MACHINE_LANDISK`, leaving the auxiliary device (`wdc_altstatus`) at the x86 default `devinit->addr + 0x206` (`0x14000206`) where it receives zero accesses, while the guest kernel issues 12 byte stores to unmapped `0x1400002c` (including an ATA soft-reset `WDCTL_RST | WDCTL_4BIT = 0x0c` that is silently discarded).

However, the brief's proposed fix:
```c
case MACHINE_LANDISK:
	alt_status_addr = devinit->addr + 0x16 * devinit->addr_mult;
	break;
```
**must not be accepted as written.** As proven below against kernel driver sources and hardware architecture, `0x16` is a fictitious "register unit" resulting from dividing the observed byte offset `0x2c` by 2 (`44 / 2 = 22 = 0x16`). In ATA hardware, the control register is register 6 (not 22) and CS1# is board address line A5 (`0x20`). Scaling by `devinit->addr_mult` is an unprincipled over-generalization that conflicts with every existing case in `dev_wdc.c` (all of which use literal byte offsets: `+ 0x160`, `+ 0x402`, `+ 0x206`). 

The fix must be changed to the literal byte offset:
```c
case MACHINE_LANDISK:
	alt_status_addr = devinit->addr + 0x2c;
	break;
```

*   **Main WDC Command Block Span**:
    *   Base: `0x14000000`
    *   Length: `DEV_WDC_LENGTH * devinit->addr_mult = 8 * 2 = 16 = 0x10` bytes.
    *   Span: `0x14000000 .. 0x1400000f` inclusive.
    *   Registers (stride of 2 bytes):
        *   `+0x00`: Data
        *   `+0x02`: Error / Features

        *   `+0x08`: Cylinder Low (LBA 8..15)

## 3. Adversarial Answers to the Review Questions

### Q1 — Is the Multiplier Form Right, or Should It Be a Literal?
**The multiplier form is WRONG; it must be a literal `+ 0x2c`.**

1.  **House Idiom Consistency**:
    In [dev_wdc.c:2098-2110](file:///C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_wdc.c#L2098-L2110), every case uses a literal byte displacement or absolute address:
    *   `MACHINE_MACPPC`: `alt_status_addr = devinit->addr + 0x160;` (plain literal byte offset)
    *   `MACHINE_IQ80321`: `alt_status_addr = devinit->addr + 0x402;` (plain literal byte offset)
    *   Fallback: `alt_status_addr = devinit->addr + 0x206;` (plain literal byte offset)
    *   `MACHINE_HPCMIPS`: `0x14000386` (literal absolute address)
    Not a single case in `dev_wdc.c` multiplies by `addr_mult`.
2.  **Architectural Violation**:
    `alt_status_addr` is a *physical bus address* passed to `memory_device_register()`. The auxiliary callback `dev_wdc_altstatus_access()` does not decode or scale by `addr_mult`.
    If `devinit->addr_mult` were 1, `0x16 * 1 = 0x16 = 0x14000016`. But on the Landisk hardware bus, the auxiliary register is hardwired to `0x1400002c`. Writing `0x16 * addr_mult` creates a fake relationship between the register address and the command block stride.

### Q2 — Where Does 0x16 Come From, and Is It Load-Bearing?
**`0x16` is completely fictitious and NOT load-bearing.**

1.  **Deconstruction of 0x16**:
    In standard ATA (ATA-1 through ATA-7; see also `src/include/thirdparty/wdcreg.h`), an ATA controller has:
    *   Command Block: Chip Select 0 (CS0#), with DA0..DA2 addressing registers 0 to 7.
    *   Control Block: Chip Select 1 (CS1#), with register 6 being Alternate Status / Device Control.
    There is **no register 22 (`0x16`)** in ATA.
2.  **Hardware & Kernel Evidence**:
    On the I-O DATA Landisk (SH7751R, Area 5):
    *   Address lines A1..A3 are wired to ATA DA0..DA2 (providing the 2-byte register stride `addr_mult = 2`).
    *   Address line A5 is wired to ATA CS1# (`0x20`).
    *   The Device Control register is ATA register 6 (`DA = 110_2`). At stride 2, register 6 is `6 << 1 = 12 = 0x0c`.
    *   Adding CS1# at `0x20` yields `0x20 | 0x0c = 0x2c`.
3.  **Kernel Source Verification**:
    In NetBSD's official Landisk driver (`sys/arch/landisk/dev/wdc_obio.c`), the offset is explicitly declared as a byte literal:
    ```c
    #define WDC_OBIO_REG_NPORTS     WDC_NREG
    #define WDC_OBIO_REG_SIZE       (WDC_OBIO_REG_NPORTS * 2)
    #define WDC_OBIO_AUXREG_NPORTS  1
    #define WDC_OBIO_AUXREG_SIZE    (WDC_OBIO_AUXREG_NPORTS * 2)
    #define WDC_OBIO_AUXREG_OFFSET  0x2c
    ```
    And mapped directly as:
    ```c
    oa->oa_io[0].or_addr + WDC_OBIO_AUXREG_OFFSET
    ```
    The BSD driver itself never heard of `0x16`. `0x16` was back-calculated by dividing `0x2c` by 2 (`44 / 2 = 22 = 0x16`). It must be discarded.
