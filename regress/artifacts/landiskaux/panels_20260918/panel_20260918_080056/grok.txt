## Q1 — literal `+ 0x2c`, not `0x16 * addr_mult`

Both produce `0x1400002c` **today**. They name different things.

The switch’s house idiom is a **physical byte offset** (or an absolute), already multiplied:

- MACPPC: `+0x160`, while the machine actually passes `addr_mult=0x10`. They did not write `0x16 * addr_mult`.
- IQ80321: `+0x402`.
- HPCMIPS: absolute.

Landisk is the only `wdc` with `addr_mult=2`. Putting the only product in the only new arm looks like generalisation from one data point, and it is.

Worse, the product is the **wrong coupling**. Command-block stride (`addr_mult`) and the CS1/aux gap are independent. If TODO 2 in `machine_landisk.c` ever selected a variant with a different stride, `0x16 * addr_mult` would move aux; OpenBSD would still store at base+`0x2c` unless the **board** moved. The multiplier form then silently mis-maps — the exact failure mode the brief named.

Write what the guest and both BSD trees write: `devinit->addr + 0x2c`. Relative, not HPCMIPS-style absolute, so it still tracks the hardcoded `0x14000000` if the base ever moves.

## Q2 — `0x16` is not load-bearing; `0x2c` is

Independent pins of **`0x2c` as bytes from the command base**:

- OpenBSD landisk `WDC_OBIO_AUXREG_OFFSET 0x2c` (TUHS 4.6).
- NetBSD landisk, same spelling and `bus_space_map(..., or_addr + 0x2c, ...)`.
- OpenBSD 7.6 on this rig: twelve `len=1` stores at paddr `0x1400002c` from `obio_iomem_write_1` (`RESULTS.txt`, watchpoint log A4, hook log B1).

`0x16` is `0x2c / 2`. That arithmetic is correct and **not** a source. `wdcreg.h` places `wd_aux_altsts` / `wd_aux_ctlr` at offset **0 of the aux region**, not at 0x16 from the command block.

A wrong multiplier is silent: no crash, no diagnostic, control register nobody reads. That is why the form has to name `0x2c`, and why a detector that only asserts `case MACHINE_LANDISK` exists is vacuous.

## Q5 — smallest surviving edit, and the other three arms

**Smallest edit that keeps a lazy detector green and still misses the guest:**

- Drop `* addr_mult` → maps `0x14000016` (gap `0x10..0x2b`, still unmapped). Case present.
- Copy macppc: `+ 0x160` → `0x14000160`.
- Empty case / omit the assignment → keeps `+0x206`.
- `0x2c * addr_mult` if someone “fixes” the literal → `0x14000058`.
- Omit `break` **and** place the arm immediately above `MACHINE_MACPPC` → landisk is overwritten to `+0x160`. Omit `break` above HPCMIPS: the `if (addr == 0x14000180)` is false, so the landisk assignment **survives** — a check-that-cannot-fail on fall-through.

A detector that only greps for `MACHINE_LANDISK` passes all of those. Pin **paddr `0x1400002c`** (device-list base and/or a store that reaches the handler). Then `+ 0x16`, `+ 0x206`, and `0x2c * addr_mult` all red. That is the (d) mutant for a literal `+ 0x2c`.

**Existing three arms:** adding a fourth `case` with `break` cannot take MACPPC/HPCMIPS/IQ80321. `machine_type` values are disjoint. HPCMIPS’s extra `addr == 0x14000180` vs landisk `0x14000000` is the same SuperH Area-1 window on **different machines**; `dev_pcic.c` is the only producer of `0x14000180`, and only under HPCMIPS. No machine reaches two arms.

Do not “unify” the switch as `0x16 * addr_mult`. It coincidentally hits macppc (`0x16*0x10=0x160`) and landisk (`0x16*2=0x2c`) and is wrong for IQ80321 (`+0x402`) and the ISA default (`+0x206`).
