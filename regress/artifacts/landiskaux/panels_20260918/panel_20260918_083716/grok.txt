### Q2. Ask-again (the sixth)

**Smallest product edit that still scores 6/6:**

```c
alt_status_addr = devinit->addr + 0x16 * devinit->addr_mult;
```

Landisk hardcodes `addr_mult=2`, so `0x16 * 2 = 0x2c`. The probe never sees the C expression; it sees physical `0x1400002c`. Predicted **6/6**. Not re-built — the equality is the machine’s own `addr_mult`.

That is the form this round’s CHANGELOG already calls *not the address* and says it nearly shipped. `M_0x16` is the **unscaled** cousin (`+ 0x16` → `0x14000016`, measured 3/6). It does not cover the scaled spelling. The detector’s contract line “any value != 0x2c” is true of the **registered address** and false of the **source form**.

Disposition: **coverage debt, not a floor breach.** Guest-visible landisk behaviour is unchanged. Clause (d) enumerates the offset as a value; this mutant does not change that value on this board. Disclose it next to `wdcaltwidth` / machine-type-only keying, or leave it. Do not replace the literal with this expression — the BSD source and `add #44,r5` are the warrant.

Same class, even smaller, same 6/6: `+` → `|` (`0x14000000 | 0x2c` coincides because the base is 16-byte aligned); `0x2c` → `44`; hardcoded `0x1400002c`. All guest-identical here.

**If the edit is allowed to touch the detector instead:** change the old-address oracle from `0xb4000206` to `0xb4000207` (one hex digit, in `r5=` and in session 3’s CTRL). On the fix, `0x207` is unmapped → read `0`, write nowhere → still 6/6. Under `M_both`, `0x207` is offset 1 of the 2-byte window; after `#494`/`#525` that read returns `0` and the write is ignored, so **`M_both` becomes 6/6**. That is the smallest detector edit that lets a mutant the table already killed escape. Do not make it.

There is no one-token edit of **only** the landisk assignment that moves the guest-visible address and still greens: any address other than `0x2c` reddens the three `0x2c` rows, and keeping `0x206` mapped as a live aux is `M_both` (4/6).

### Q3. Vacuous rows

No.

| Row | Named killer | Channel under that mutant |
|---|---|---|
| `live` | none (control) | `0x09` on every leg, including pre-fix. PRETABLE says so. |

A 2026-08-28 claim that `+ 0x2b` with width 2 still contains `0x2c` is **true of the window and false of the handler** after `#494`: offset 1 is declined. That mutant is 3/6 today, same shape as `M_0x2d`.

### Q4. Removing landisk’s answer at `0x206`

No legitimate landisk guest is using it.

- OpenBSD 7.6 census: **zero** accesses to `wdc_altstatus` at `0x14000206` for the whole boot; all twelve control writes go to `0x2c`.
- Both BSD `wdc_obio.c` files map aux at `or_addr + 0x2c`, not at `+0x206`.
- Device list (`A5_device_list.log`): `wdc` `0x14000000` len `0x10`, old `wdc_altstatus` `0x14000206` len `2`, then a 32 KB `ram` at `0x1e000000`. The brief’s collision sentence is right: `0x1400002c..2d` is free. (Main RAM is `0x0c000000`, 64 MB; that is *before* wdc, not the `0x1e000000` region.)
- `0x206` on landisk was the PC default, not this board. A guest written against GXemul’s old mapping would break; that is the bug.

`AUXREG_NPORTS` is **1**; the 2-byte map is 16-bit spacing of one register, not the PC altstatus+drive-address pair. Offset 1 on landisk is padding the shared handler already declines. Existing, and already filed as `wdcaltwidth`. Not a reason to keep `0x206`.
