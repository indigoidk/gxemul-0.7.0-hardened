# GXemul hardened fork -- WHICH PROPOSED FIXES COULD SHARE A ROUND? (109 drafts, oldest first; a defensive project's planning)

PROJECT FRAMING -- a defensive software-robustness project: GXemul is a computer-architecture emulator, and this fork fixes
crash-on-malformed-input and wrong-behaviour defects in its device and CPU models, ONE ROUND PER FIX.  Each line below is a
filed issue with a drafted fix that compiles: its id, the fix's review verdict, the files and functions it edits, and its
title.  You cannot read files; work from these lines.  This is PLANNING, not a ruling.

## The project's rule for combining (quoted)

> A round takes ONE site; a second joins only if it is witnessed, in the SAME device and SAME semantic class (so one fix
> design covers both), and covered by the SAME detector with no new oracle.  More witnesses create more candidate ROUNDS,
> never bigger rounds.

## What to return

1. CANDIDATE GROUPS: sets of drafts in the SAME device (or the same CPU's instruction decoder) AND the same semantic class
   (e.g. 'an undecoded instruction that should raise the architecture's illegal-instruction exception', 'a guest-triggerable
   diagnostic with no once-per-device latch', 'a register write whose value is stored unmasked').  For each group: the ids,
   the shared device and class in one line, and the ONE fact that would most likely split it (a different detector needed,
   different semantics).  Only propose a group you would defend against that rule; most drafts stay single.
2. DUPLICATES: any two ids that look like the SAME defect filed twice.
3. CONFLICTS: any two drafts that edit the same function in ways that would collide if both landed.
Every id appears at most once across sections 1 and 2.

End with one line: `GROUPING: <g> GROUPS covering <n> DRAFTS, <d> DUPLICATE PAIRS, <c> CONFLICTS`.
