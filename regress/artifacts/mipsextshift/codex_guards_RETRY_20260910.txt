**2. Plain DEXT is genuinely safe for this particular arithmetic.**

Its shift count is

```text
64 - b - (m + 1) = 63 - (b + m).
```

Since `0 <= b + m <= 62`, the count is **1–63 inclusive**. Its final right shift uses `b`, which is 0–31. Neither shift has an invalid count.

The other handler’s range check is still needed for EXT. This conclusion about DEXT is specifically about the field ranges and shifts, not a certification of every aspect of instruction support.

**3. The 496 count is correct for each affected opcode.**

For EXT:

```text
32 - b - (m + 1) = 31 - (b + m).
```

For DEXTM:

```text
64 - b - (m + 33) = 31 - (b + m).
```

For DEXTU:

```text
64 - (b + 32) - (m + 1) = 31 - (b + m).
```

All three therefore have a negative expression exactly when `b + m >= 32`.

For each fixed `m`, the invalid `b` values run from `32 - m` through 31, giving exactly `m` invalid values. Hence:

```text
0 + 1 + … + 31 = 31 × 32 / 2 = 496.
```

Each affected opcode has 528 valid pairs and 496 invalid pairs. I independently enumerated all 1,024 pairs per opcode using integer arithmetic and obtained those counts.

These are **field-pair counts**. Actual execution also depends on reaching this decoder and selecting the handler; the current `rt == zero` rewrite avoids handler execution.

Your C description needs two qualifications:

- In `X(ext)`, the negative count directly causes undefined behavior.
- In `X(dext)`, the negative `int` expression is converted to `uint64_t`, producing an enormous unsigned count. That count exceeds the operand width and still causes undefined behavior.

C99 does **not** guarantee modulo-width masking. A particular generated host instruction may mask its count, but neither that outcome nor silent continuation is guaranteed by the C program.
