### Q1 — Is `0x800U` sufficient and is anything else perturbed?

**REASONED.** The fix's correctness rests on a single fact the packet asserts but does not prove: the **declared type of `tag`**. The brief's wording — *"tag is already a wider unsigned quantity"* — is doing two jobs and only one is needed.

Walking the usual-arithmetic-conversions cases for `tag & (0x800U << dev)`:

| `tag` type | result of `&` at every iteration |
|---|---|
| `unsigned int` (same width as RHS) | identity on the bit pattern; truth value depends only on `tag` bits 11..31. |
| `uint32_t` / `uint64_t` (wider unsigned) | RHS is converted to the wider type; bit pattern is unchanged; truth value depends only on `tag` bits 11..31. |
| `unsigned short` / `unsigned char` (narrower unsigned) | `tag` promotes to `int`, then `int & unsigned int` → `unsigned int`; same bit pattern for the bits that matter. |
| signed `int`/`long`, **non-negative** | conversion to `unsigned int` is identity on bit pattern. |
| signed `int`/`long`, **negative** | conversion to `unsigned` is a bit-flip — truth value COULD change. Not a hardware-register scenario in practice. |

So the *correct* claim is "`tag` is unsigned (or non-negative signed of at least `int` width)", not "wider". The brief is sloppy about "wider" but the conclusion holds for any unsigned `tag`.

**Defect in the brief:** the type of `tag` is not inlined. The single fact that settles Q1 is the declaration of `tag` in `DEVICE_ACCESS(lca_pci_conf)`'s parameter list (the macro is almost certainly defined in `src/devices/dev_lca.c` near the diff, but the packet doesn't show it). A seat that opens "let me check the declaration" is the seat this panel has been warned off; I name the fact and stop.

**Independent concern about the differential:** the probe in `regress/lca_confbus_probe.py` runs with `tag == 0`, so the loop's `&` always yields 0 at all 21 iterations. That means the differential proves "no UBSan fires after the fix" and "the tag==0 path is unchanged" — it does **not** independently prove the truth value is preserved at every iteration for arbitrary `tag`. The bit-pattern argument above is what carries the load, and that argument depends on `tag` being unsigned. The brief's sentence "no guest-visible value moves" is therefore weaker than advertised if `tag` is signed — still fine in practice, but not airtight from the packet alone.

### Q2 — Exactly one iteration overflows?

**VERIFIED (READ).** Loop bound is `dev < 21`, so `dev ∈ {0,1,…,20}`.

- `dev = 19`: `0x800 << 19 = 0x40000000 = 1073741824`. `INT_MAX = 0x7FFFFFFF = 2147483647`. Fits.
- `dev = 20`: `0x800 << 20 = 0x80000000 = 2147483648 > INT_MAX`. Signed overflow.

Shift count of 20 is below the 32-bit `int` width on every host this project targets, so only the *value* overflows, not the count. Exactly one iteration. The claim is right.

### Q3 — The one to attack: unwired differential as sole detector

**REASONED.** The author flags this themselves and is right to. Let me steelman each side.

**Why this round is acceptable despite the gap:**
1. The fix is one token. A regression to `0x800 << dev` would be visible in `git blame`/`git diff` on the next code review of this file — not catchable by UBSan, but catchable by a human reading the diff.
2. The detector was actually *run*, not asserted-in-passing. The round produced `ubsan_HEAD_20260907.raw` with 1 diagnostic; that's not a vacuous measurement — it's a measurement whose lane isn't in the gate.
3. Wiring a new lane inside a fix round mixes process artefacts (the lane) with the artefact under review (the fix). Keeping them in separate rows (`ubsanshiftlane`) is correct separation of concerns.
4. A source pin (regex on `\b0x[0-9a-fA-F]+\s*<<`) would be cheaper to add but only catches the *literal pattern*, not other signed-shift overflows in the same file (`shiftubcensus` is the right row for that).

**Why this must NOT set precedent:**
- The argument "measured two-direction differential beats a source pin because it tests behaviour not text" only holds when the measurement is **actually re-runnable on every future commit**. Here it isn't. The differential is a one-shot artifact in `artifacts/lcashiftub/`, not a CI step.
- The vacuity-floor concern is real: if this round's pattern is ratified (fix + unwired one-shot + "trust the diff"), the next round with a less-trivial fix could ship the same shape with a much weaker differential — and the panel has no mechanical backstop.
- A source pin would have caught *this* defect (it is a literal-pattern defect) at near-zero cost.

**My read:** acceptable here because the fix is mechanically trivial, the measurement was actually executed, and the panel retains `ubsanshiftlane` as a gate-side follow-up. The right answer for the next similar-but-non-trivial fix is "wired lane or it doesn't ship". I would record this as a panel precedent, not bless it as a general rule.
