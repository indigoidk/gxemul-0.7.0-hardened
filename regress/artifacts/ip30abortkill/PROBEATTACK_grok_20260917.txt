## Q4 — the `sw` trap. No second inert write. `acc imask` does not prove what it claims.

`memory_readmax64(..., len)` with `len=4` yields a value `< 2^32`. HEART `imr`/`isr`/`count` are `u64`. `OP_SW_T0_A3` is the only store in this file. Measured: `sw 0xffffffff` + 70000 steps → **alive** (`swcontrol.out`); `sd 1<<50` + `step 1` → **SIGABRT** (`tickprobe_run2.out`).

**Other rows, against the claim they actually score:**

- `acc 18` `0xDEADBEEF`, `acc 20000` `0x1234`, `acc 30000` `0x5678`, `kill 30 wr` `0x1` — all in the low 32 bits. Width-valid for those oracles.
- Kill rows at `0x10020`/`0x10028` are **loads**. Width N/A.
- Loads are `lw`, not `ld`. Fine for every current want (bit 18, `0x1234`, sign-extended `0xdeadbeef` / `0x80010000`). A future bit-50 readback with `lw` would be inert; `ip30_tick_probe.py` already uses `ld`/`sd` for that reason.

**`acc imask` proves:** `case 0x10000` accepts a **word** write of bit 18 and `lw` reads `0x40000`. That claim is true.

**`acc imask` does not prove:** “THE accept row for the tick predicate.” The predicate that gated death is `imask0 & (1<<50)`. This row never writes that bit. Bit 18 is not adjacent to 50; bit 49 is, and the tick probe already uses it as the discriminator. De-escalation accept for the tick is: `sd 1<<50`, host lives, `ld` readback still has bit 50. That is post-fix `tick50 s1` + `sd rt`, not this row.

The comment is now honest that `sw` cannot set bit 50, and then still labels the row as the tick accept. Those two sentences cannot both be load-bearing. Reason (1) (writes bit 18) is why the row is *safe*. Reason (2) is why a copy of it as a kill row is a false green. Neither makes it the tick accept.

No other current row is silently inert **by store width**. `acc 20000` is inert/inverted by **tick order**, not width.
