## Q2 — weakenings

**(a) `printf("\nFBBOUND_PASS\n")` unconditionally — FAILS gate 2.**
The self-mutant lane's mutant arm never emits a `_FAIL` token, so `selfmutant.py` reports SELFMUTANT_FAIL on the missing-FAIL-token check; gate 2 REDs. Independently, gate 2's own #442 verdict `check "fbpending bound: offline verdict" "$(grep -c '^FBBOUND_PASS$' …)" "1"` would also pass vacuously — but that's the *fifth vacuity class* the brief warns about. PRECOMMIT: FAILS.

**(b) gate 2 verdict grep `^FBBOUND_$` instead of `^FBBOUND_PASS$` — FAILS without the harness fix.**
The old form `FBBOUND_VERDICT=PASS` starts with `FBBOUND_`, so gate 2's main verdict check would go GREEN on the pre-fix harness — but the self-mutant lane's `<WORD>_FAIL` regex still won't match `FBBOUND_VERDICT=FAIL`, so the lane SETUPs (this is exactly L1 in §3). With the harness fix applied, both checks go GREEN — so weakening (b) is REDUNDANT given the fix and HARMFUL without it. PRECOMMIT: FAILS without the harness fix; PASSES with it (but pointless).

**(c) drop `! -name 'dev_footbridge.o'` — FAILS.**
The harness `#include`s `dev_footbridge.c` directly (mutated copy) and `dev_footbridge.o` is also linked (pristine). Every non-`static` Footbridge symbol is defined twice → linker error → pristine arm SETUP → lane RED. PRECOMMIT: FAILS.

**(d) R4 condition `failures <= 1` — lane still works; harness quality regresses.**
The mutant forces R4 red in all 7 cases, so `failures = 7` (at minimum) and `7 > 1` → R4 still FAILs in the mutant arm. The lane catches the mutant. The harness overall verdict (`failures ? "FAIL" : "PASS"`) is unchanged and still emits `FBBOUND_FAIL` in the mutant arm. But the harness now treats a single failing case as a passing run — vacuity in the harness itself, not in the gate. PRECOMMIT PASSES on the lane; the harness is more lenient than the brief intends.

**(e) drop `"$PMAX"` from the mk48 line — FAILS.**
The probe is invoked with the single argument `gate`, no binary path. Either the probe errors out before producing any rows (then `MK48_WITNESS_DONE` is absent → "probe completed: no" reddens), or it picks up a default/embedded binary that is not the gate's `$PMAX` and produces different row contents (then the named-row `check`s reddens). Either way, the gate's mk48 section reds. PRECOMMIT: FAILS.

**(f) M5b uses LATEST dated detector instead of EARLIEST — works today, BROKEN tomorrow.
The current re-dated block is uniform 2026-09-27, so LATEST == EARLIEST and the test passes.
But the day M5a/M5b exists is to verify the expiry logic against a table that has *varied* dates — that's the whole point of deriving from the table. With LATEST, M5a (LATEST − 1) is no longer guaranteed to be a day on which every detector is live: any detector dated before LATEST − 1 is already expired, so the checker REDs and M5a fails. The negative control in §3 already proves the *derivation* is load-bearing — flipping the pole from EARLIEST to LATEST is the symmetric mistake in the other direction. PRECOMMIT: PASSES for the current single-date table; FAILS the first time the table has mixed dates.
