## 3. MY CENTRAL CLAIM — THEY ARE THREE CLASSES, AND TWO CORRUPT IF THE KILL IS SIMPLY DELETED

**This is the claim I most want attacked.**

**CLASS B — bare removal CORRUPTS. The kill is currently the only thing preventing it.**

| site | guard | what deleting the `exit(1)` reaches |
|---|---|---|
| `:662` | `cmd_count >= 12` | `d->cmd[d->cmd_count++] = …` **twice**, into a `uint8_t cmd[12]` — an out-of-bounds write |
| `:357` | `cnt != 408` | `alloc_data()`, which mallocs `d->cnt` bytes for a writer that expects 408 — under-allocation for any `cnt < 408`, and `malloc(0)` at `cnt == 0` |

*So at these two the guard is a load-bearing BOUNDS CHECK wearing diagnostic clothing.
An explicit decline is mandatory, not stylistic.*

**CLASS A — bare removal is SAFE, because the control flow already handles it.**

- `:486` — falling through reaches the common tail, and that tail is **correct** for an
  unhandled command: `d->data` is NULL, so it sets `cnt = 0`, clears `COND_DATA_AVAIL`
  and fires `SYSASIC_TRIGGER_EVENT`. That is "the command did nothing", reported
  properly. **But an early `return` here would skip `SYSASIC_TRIGGER_EVENT` and leave
  the guest waiting forever.**
- `:761`, `:701` — fall to a `break`. No state mutation.

**CLASS C — the file already decided, one line up.**

- `:409` — the arm immediately above prints *"Continuing anway"* for `cmd[1] == 0x24`
  and lives. An unimplemented data format **already** survives for one value and dies
  for every other.
- `:701` — the same shape *inside one case*: the READ arm's `exit(1)` is already
  commented out; only the WRITE arm still dies.

**Is that asymmetry a decision that generalises, or was it specific to `0x24`?** I do
not know, and I would rather the panel answered it than have me tidy it away.

## 4. THE OPTION SET

This fork's de-fatalisation option set has **four** members, and the fourth was added
recently after a round framed the choice as two:

1. **delete** the kill;
2. **decline** — refuse the operation, silently;
3. **decline + bounded announce** — the house idiom being an `N = 1` **per-device-instance
   latch** with `(once)` in the message text (censused: `(once)` 9, `(further occurrences
   suppressed)` 3, `(reported once)` 2);
4. **accept** — where the model already computes the correct answer and then discards
   it, keep the value and say nothing, because there is no event to announce.

  all six carefully — please check.

**`:662` IS NOT GUEST-REACHABLE.**  Confirmed by reading before this was written:
`busy |= 0x08` has exactly ONE writer and the very next line is `d->cmd_count = 0`; stores

**My re-census conflated 'the `exit(1)` is still in the file' with 'guest-reachable'.**
Those are different questions and I asked only the first.  Everywhere this brief says all

## 3b. *** TWO PREMISES OF

Two packet-fed seats refused to certify these from the packet -- correctly, because I had

**`:357` IS A GUEST-CONTROLLED HEAP OVERFLOW.**  The open question was whether the TOC
writer writes `d->data_len` bytes (safe under any `cnt`) or a fixed 408 (unsafe below it).
Neither, and the answer is the bad one: it `memset`s `d->cnt` bytes (safe) and then writes
**hardcoded indices**. Derived mechanically:

```
grep -oE "d->data\[[0-9]+\*4(\+[0-9])?\]" src/devices/dev_dreamcast_gdrom.c
  -> highest byte index 407, so the writer needs 408 bytes REGARDLESS of cnt
```

`cnt` is guest-supplied.  So deleting the `exit(1)` gives `malloc(cnt)` followed by writes
up to index 407 -- **an overflow of up to 408 bytes whose size the guest chooses.**  The
kill is the only thing preventing it.

*This means `:357` and `:662` are not merely 'bare removal corrupts'.  Both guards are
load-bearing BOUNDS CHECKS on guest-controlled quantities, and both fixes must decline
BEFORE the guarded statement, not after.*

**`:486`'s Class-A claim HOLDS.**  A seat asked whether `d->data` is reliably NULL on entry
to `default:` -- a stale non-NULL would make the common tail set `COND_DATA_AVAIL` wrongly.
It is: `handle_command()` calls `free_data(d)` at `:343` (tagged `#465`) before the switch,
and `free_data()` sets `d->data = NULL` and `data_len = 0`.

**AND A CLASSIFICATION ERROR OF MINE:** `:701` appears in BOTH Class A and Class C above.
It genuinely has both properties -- its WRITE arm falls to a `break`, its READ arm's
`exit(1)` is already commented out -- but listing it twice without saying so may mean the
class boundary is drawn on the wrong axis.  **If it is, say so; that is more useful than

**A FIFTH OPTION MEMBER, proposed by a seat and not yet evaluated:** a *guest-visible ERROR

## 4c. PREMISES ALREADY SETTLED, RE-INLINED SO NOBODY SPENDS AN ANSWER RE-DERIVING THEM

The previous round lost three seat-answers to facts it had settled and then failed to carry
into the packet.  So, stated here:

* **`fatal()` RETURNS in this fork.**  `src/core/debugmsg.c` defines it as
  `va_start / va_debug / va_end` -- zero `exit(`, `abort(`, `longjmp`, `_Noreturn` or
  attributes.  So a `fatal()` immediately before an `exit(1)` does NOT itself terminate, and
  removing the `exit(1)` leaves the diagnostic intact and execution continuing.
* **`fatal()` cannot be silenced by `-q`.**  Unlike `debug()`, it has no verbosity early-out,
  which is why a guest-drivable `fatal()` needs a LATCH and not a verbosity flag.
* **The house latch idiom is `N = 1` per DEVICE INSTANCE with a suppression marker in the
  message text**, and the marker's plurality spelling is `(once)` (censused: `(once)` 9,
  `(further occurrences suppressed)` 3, `(reported once)` 2).

## 5. WHAT THE ROUND OWES BEYOND THE EDIT


**The de-escalation clause.** Removing a host-fatal guard **deletes an accidental
tripwire**: today, growing one of these guards means an immediate `exit(1)` on the first
legal input — unmissable. Afterwards the same edit means a **silently refused
operation** and nothing notices. So the detector shipping with this fix must pin the
**accept side** of each predicate the fix de-fatalises — a row per adjacent legal value,
proving legal inputs still land.

**And an accept row is discharged by a MEASURED KILL, never by existing.** For each
de-fatalised predicate, build the smallest realistic growth mutant and require the
accept row to redden under it.

**The two Class-B guards are squarely inside clause (d)'s DEPENDS-ON bound** — they
dominate the edited lines — so mutants weakening `>= 12` or `!= 408` are owed, not
optional.

## 6. THE CLOSURE GATE — READ THIS BEFORE PROPOSING AN ORDER OF WORK

**De-fatalising the three command-layer sites (`:357`, `:409`, `:486` — exactly the
three) DESTROYS a sibling row's detector oracle.** `gdrompionull`'s discriminating power
is the **death mode**: a probe *coding error* currently lands on `exit1` and is thereby
distinguishable from the `sig11` defect. Once these three survive, a mis-encoded probe
falls through instead of dying, and **a coding error becomes indistinguishable from the
defect**.

The obligation is already recorded with its order baked in, and it is the
oracle-correction rule: **re-pin the affected oracles FIRST, measure the
pre-de-fatalisation build RED under the new pins, THEN de-fatalise.** Same scripts,
opposite colour. Without that red, the re-pin is observationally identical to fitting
the test to the binary.

**Does that ordering work? Is there a cheaper way to preserve the discriminator** — for
example a distinguishable exit code, or a marker the probe can read — **that does not
reintroduce a host kill?**
