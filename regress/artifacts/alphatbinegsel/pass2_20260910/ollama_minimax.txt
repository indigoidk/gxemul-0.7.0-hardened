## §E.2 Smallest edit that breaks the fix and passes the 13 rows

**The unrowed axis is the cast width / cast target type** (READ + REASONED).

The guard now has three things: a lower bound (rowed by M_A, M_D), an upper bound (rowed by M_B, M_C), and a signed cast. The four "sides" of the bound window are all rowed. The cast sign is *not* load-bearing here — `(uint64_t)a0 >= 1 && a0 <= 3` produces the same predicate as `(int64_t)a0 >= 1 && a0 <= 3` because `(uint64_t)x in [1,3]` and `(int64_t)x in [1,3]` are the same set of `uint64_t` values given the upper bound is present. So changing the cast sign isn't the worry.

What *is* unrowed is **the cast width**. The smallest single-token edit is **`(int64_t)a0` → `(int32_t)a0`** (or any smaller signed width). This:
- passes every row in the 13-row table, because every row's `a0` is small enough (the visible set is `{-2, -1, 0, 1, 2, 3, 4}`, all of which `(int32_t)` and `(int64_t)` agree on for being in/out of `[1,3]`);
- breaks the fix for inputs whose high 32 bits shift the value, e.g. `a0 = 0x1_0000_0001`: `(int32_t)0x1_0000_0001 == 1` (selective), `(int64_t)0x1_0000_0001 == 4294967297` (conservative). The fix's correctness for such inputs is the unobserved claim.

**Row I expect to stay green**: the liveness `pos obs` row (a0 = 2, a1 = 0x6000) — both arms flush the target page in the model, so over-invalidation cannot surface; only an *omitted* invalidation reddens it, and that omission is independent of cast width.

The 13-row detector cannot see this edit for the same reason it could not see M_D in the 10-row detector: the rows never exercise the bit pattern that makes the two casts diverge. The shape I am worried about repeating is exactly the M_D shape: a fourth side of the predicate is unrowed.
