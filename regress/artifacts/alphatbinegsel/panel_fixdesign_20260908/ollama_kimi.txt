## Q1 — the guard

## Q2 — signed vs unsigned spelling

**REASONED: no input distinguishes them — provable, not empirical.** The unsigned form is true exactly on bit patterns {1,2,3}. The signed form is true exactly when `(int64_t)a0 ∈ [1,3]`; any pattern with bit 63 set is negative and fails `>= 1`, and any pattern with bit 63 clear has equal signed and unsigned magnitude. So both truth sets are {1,2,3}; the symmetric difference is ∅. No input, including 0, 4, -1, -2, changes behavior.

On robustness against later edits: **REASONED: prefer the signed spelling, written as a named local with named constants** — `int64_t sel = (int64_t)a0; if (sel >= PAL_TBIS && sel <= PAL_TBISI)` (modulo the label check above). The original defect was a signedness mismatch between the architecture's description and the C type; the guard should be legible in the architecture's domain at the site where the bug lived. The bare unsigned window's `<= 3` looks arbitrary to a future reader and invites "simplifications" (see Q3). Two caveats: casting out-of-range `uint64_t` to `int64_t` is implementation-defined pre-C23 (universally wrap on gxemul's toolchains — harmless here, comment it); and if a later edit changes the parameter itself to `int64_t`, both spellings remain correct. The constants and the comment do more defensive work than the cast; do both.

## Q3 — the smallest edit the witness would not catch

**REASONED: the smallest uncaught edit is one character — `a0 <= 3` → `a0 <= 2`.** The witness exercises only -2, -1, and 2; a0=3 (and a0=1) are never exercised, so the row set stays green while a documented selector silently degrades to ALL. Dropping the lower bound (`if (a0 <= 3)`, moving a0=0 to VADDR) and widening (`<= 4`) are equally small and equally invisible.

The deeper finding: **no extension of the current row shape can catch `<= 2` either.** A pos-style a0=3 row (fill VA, remap, tbi(3, VA), observe) wants the new value — but ALL also produces the new value for that same VA. The harness cannot distinguish "invalidated exactly this VA" from "invalidated everything." The only distinguishing observable is a **bystander**: fill and remap VA-B, then tbi(3, VA-A) with VA-A ≠ VA-B, and assert VA-B still reads the OLD value. Under correct per-VA dispatch the bystander's entry survives (stale-by-design); under ALL it re-walks. Verdict: **worth exactly one bystander row, at the a0=3 boundary** — it pins the documented selectivity at the edge most likely to be off-by-one'd (a0=1 is redundant given the shared branch, and the pos row already covers the window's interior and the a1 pass-through). The undocumented-value defaults (0, ≥4 → ALL) are contract, not rows — they are only observable with more bystander rows, and they pin behavior no guest depends on.

## Q4 — what a regression row owes against a future partial ASM implementation

**REASONED from the packet:** fill is walked from guest page tables, and `ALPHA_PTE_ASM` exists as a PTE bit (`alpha_cpu.h:223`, READ as stated), so a guest can construct an ASM=1 mapping today even though nothing consumes it. The row that prevents a partial ASM implementation from reading as complete is the **ASM=1 bystander under TBIAP**: fill VA-B via an ASM=1 PTE, remap it, TBIAP(-1), assert VA-B still reads OLD. Correct selective semantics preserve ASM=1 entries across TBIAP; the current coarse fix (TBIAP ≡ TBIA) fails this row — which is the point: it ships today as an expected-fail documenting deferred semantics. Two companions complete the contract: (a) the existing `tbiap obs` row already pins ASM=0-dies; (b) a **TBIA + ASM=1 bystander asserting NEW** pins TBIA ≠ TBIAP, so a lazy partial implementation that maps TBIAP to TBIA fails row (b). Any ITB-only partial implementation (the HRM quote at `21066_66a_hrm.txt:1486`, READ, describes ITBASM specifically; the packet shows no I/D split consumed in this layer) fails whichever leg it skipped. Until ASM is represented, rows (b) and the ASM=1 bystander are contract/expected-fail, never greens.
