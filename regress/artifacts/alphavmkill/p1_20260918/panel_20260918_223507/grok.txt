## Q1 -- premises, as questions

**Is `0xfffffffd80000000` special?** Yes, for NetBSD, and not in the way that would license ACCEPT.

NetBSD `sys/arch/alpha/include/vmparam.h:123` is exactly the brief's constant:

```c
#define VPTBASE  ((vaddr_t)0xfffffffc00000000)  /* Virt. pg table */
```

An 8 KB page × 8-byte PTEs × 2^30 pages is an 8 GB window: `[0xfffffffc00000000, 0xfffffffe00000000)`. `0xfffffffd80000000` is 6 GB into that window (same L1 slot, `i1 = 1022`). It is **not** `VPTBASE` itself.

It is **not** K0SEG. `ALPHA_K0SEG_END` is `0xfffffdffffffffff`; this VA is K1SEG (`ALPHA_K1SEG_BASE` `0xfffffe0000000000`). The K0SEG arm does not swallow it. Exact equality, not a range: `+8` never hits the kill.

Linux/Alpha is a different VPT layout (`VMALLOC_END = -PGDIR_SIZE`, last PGDIR slot). This constant is a NetBSD VPT interior, not an architectural singleton.

**That does not make the kill a VPT implementation.** VPT is a recursive map of an existing page table. The kill lives in `!userMode && base == 0`, i.e. **before** a table exists. A guest that used VPT with `ptbr == 0` would be wrong on real hardware too (MM fault, not identity). Once `ptbr != 0`, this VA is supposed to **walk** — which is the AYONA3 path, not the kill path. I found no in-tree guest that uses this constant (same finding as the 2026-09-08 assess).

**Member 4 is a wrong translation that silently succeeds.** The identity store is *already done* before the kill:

```c
*return_paddr = vaddr & 0x000003ffffffffffULL;  /* 0x3fd80000000 */
```

None of the three remaps match, so that value sticks. `0x3fd80000000` is ~4.37 TB. On the witness machine (`-M 64`) `physical_max` is 64 MB. `memory_rw.c` then takes the “outside of physical RAM” arm:

- `memory_warn_about_unimplemented_addr` does **not** fail: `paddr` is far past `physical_max + 0x40000`, and the probe does not pass `-T`, so `halt_on_nonexistant_memaccess` stays 0 and the helper returns `false`
- a **read** `memset`s the buffer to 0 and `goto do_return_ok` — **success**
- a **write** is a silent drop, also success
- Alpha has no DBE/IBE on that path (`#ifdef MEM_MIPS` / `MEM_M88K` only)

So member 4 is: host lives, load dest becomes **0**, store appears to land, translation reports writable (`return 2`). A 0 in a VPT slot looks like `PTE_VALID = 0`. That is an accident of unmapped-phys zero-fill, not a modelled empty page table, and it becomes a real mapping if anything is ever placed near 4 TB.

**Member 2/3 is better for a guest than that.** `#215` abandons the load/store and **does not write the destination**. `#244` zeroes the `memory_rw` buffer; the instruction never copies it. Dest stays whatever it was (the witness’s `0x0bad1d8a`). No translation is installed. Stale dest is still not an MM fault — FAULT is unavailable — but it is not a fabricated successful map.

**I-fetch reading, checked against `cpu_dyntrans.c:670-733`.** It holds.

- `alpha_translate_v2p` never writes `cpu->pc` (no PAL MM delivery, `flags` unused)
- on `!ok`, dyntrans does `cached_pc = cpu->pc` (unchanged), re-looks-up, re-translates, then `fatal("FATAL: could not find physical address of the exception handler?"); exit(1);`
- so a **decline** (`return 0`) recovers load and store and **does not** recover I-fetch of this VA

Something else on that path: `cpu_alpha_instr.c:812-815` `to_be_translated` does `fatal("... read failed: TODO\n"); goto bad;` (a “nothing” instruction, not `exit`). Under member 2/3 that site is **not reached** — `pc_to_pointers` dies first. Under member 4, I-fetch translation *succeeds*, `host_page` is NULL, the fetch reads zeros, and the I-fetch cell leaves the `alphaifetchkill` set. That is a reason not to ACCEPT: it hides this VA from the class-kill census.

`#194`/`#215` comments saying the translator “signalled a fault” / “the caller raises the fault” are still false (`alphafaultclaim`). Do not copy them into the new comment.
