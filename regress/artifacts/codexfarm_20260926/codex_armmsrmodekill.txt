## 2. Architectural behavior

`ls C:\DocumentNoSnc\cc\GXEMUL\_scratchpad\*.txt` returned 428 files. Manual-like entries included `21066_66a_hrm.txt`, `ata2_x3t10_948d.txt`, `dc21285.txt`, `ddi0100i.txt`, `ddi0406.txt`, `i8254.txt`, `idt_r30xx.txt`, `mc88100.txt`, the MIPS and PPC books, `sh4_manual.txt`, `sh4_programming.txt`, `sh7750_hardware.txt`, and `vmesbcp2.txt`. Only the two ARM architecture manuals cover this behavior; `dc21285.txt` is a companion-chip document, not a CPSR specification.

Read from the manuals:

- `C:\DocumentNoSnc\cc\GXEMUL\_scratchpad\ddi0100i.txt:1861-1879` lists exactly the seven valid 32-bit modes and declares any other M[4:0] UNPREDICTABLE.
- Its MSR description identifies the c field at `:9523-9567`, says “Exceptions: None” at `:9577-9578`, and specifically calls writing a reserved mode UNPREDICTABLE at `:9690-9693`.
- Its glossary says UNPREDICTABLE behavior must not halt or hang the processor or any part of the system at `:45062-45065`. Ending the emulator process is therefore unsupported.
- ARMv7’s later manual independently says changing CPSR.M to a value that is not a processor mode is UNPREDICTABLE at `ddi0406.txt:102530-102537`, and applies that rule to immediate MSR at `:103921-103930`.

The architecture does not prescribe one deterministic replacement result. A no-op/decline is permitted, but not uniquely required. Moreover, the later glossary explicitly permits implementing an UNPREDICTABLE instruction as UNDEFINED at `ddi0406.txt:143206-143216`. Thus the row’s categorical claim that hardware cannot take an Undefined Instruction exception is too broad; what the documentation establishes firmly is that killing the emulator/system is wrong.

- Defect stimulus: in a fresh session, plant and re-dump `0xE321F014` at an aligned RAM PC, set PC there, and `step 1`. That single guest instruction is the minimum sequence.
