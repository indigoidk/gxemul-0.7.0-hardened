## 3. Options and precedents

The one default arm covers three semantically different populations.

- **Offsets with no named register.** Options are:

  - Keep a fatal host exit, as legacy [dev_clmpcc.c:246–252](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_clmpcc.c:246) does. This is precedent for the defect, not a defensible repair.
  - Decline with deterministic zero/ignored write and a latched announcement, as [dev_lca.c:479–513](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_lca.c:479) does.
  - Back the offset as storage, as [dev_dreamcast_g2.c:250–282](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_dreamcast_g2.c:250) does.
  - FAULT with `return 0`, as [dev_unreadable.c:41–51](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_unreadable.c:41) does. MVME187 itself installs that device three times for omitted hardware at [machine_mvme88k.c:105–123](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/machines/machine_mvme88k.c:105).

  Evidence supports **FAULT**, described narrowly as “the emulator cannot service this access,” not as proven real-hardware behavior. `memory_rw()` converts zero to failure and raises M88K `DATA_ACCESS` at [memory_rw.c:595–624](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c:595).

- **The 26 named-but-uncased register bases.** Options are full implementation, explicit conservative FAULT, LCA-style decline, or synthetic backed acceptance. Existing VME stateful cases are the implementation precedent; LCA explicitly declines documented-but-unimplemented registers; Dreamcast G2 is the backed-accept precedent. Evidence supports either actual implementation or, until then, an explicitly labelled **FAULT-as-model-limitation**. It does not support silently inventing register values or claiming device-faithful bus-error behavior.

- **Interior lanes, particularly the 12 lanes of the four stateful cases.** Same-architecture [dev_m8820x.c:257–260](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_m8820x.c:257) groups addresses by containing word; same-machine PCC2 instead serves addressed bytes with `memcpy` at [dev_pcc2.c:471–485](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_pcc2.c:471). FAULT is also possible if the real device rejects that width.

  The available evidence supports only **separate handling**, not a particular lane policy. Blindly masking `relative_addr` to a word base is unsafe: narrow writes would replace an entire backing word, and `T1COUNT` reads have a side effect. The header itself warns that the chip has “rather insane access rules” at [mvme88k_vme.h:40–42](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/include/thirdparty/mvme88k_vme.h:40), while the needed manual chapter is absent.

- supported VBR and offset-zero controls.

## 5. Smallest witness

On the unmodified in-tree `-E mvme88k -e mvme187 -M 64` machine:

1. **Liveness control, separate session:** use guest instructions to store `0x5a5a5a5a` into scratch RAM and load it back, then reach a breakpoint or self-loop.

2. **Device-signature control, separate session:** guest word-load `0xfff40088`, the VME VBR case. The expected value is `0x67000000`, derived from the reset seed at [dev_vme.c:160–162](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_vme.c:160) and the shift definitions at [mvme88k_vme.h:257–260](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/include/thirdparty/mvme88k_vme.h:257). This distinguishes the VME device from zero-filled RAM or an unmapped fallback.

3. **Killing sequence:** with `0xfff40000` in a base register, the site-reaching core is one aligned guest word load from `base + 0x30`. `0x30` is documented as `VME2_DMACTL` at [mvme88k_vme.h:58](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/include/thirdparty/mvme88k_vme.h:58) but has no case. For a robust harness, put it between a scratch-RAM canary store and post-access canary load/marker. HEAD exits with status 1; the post-access marker is absent.

Run that guest with `continue`, not debugger single-step, because single-step makes `debug()` visible. The expected pre-fix observation is therefore: reaped exit status 1, absent post-access marker, and no explanatory VME message at default verbosity. A direct debugger memory peek is not a substitute because no-exception accesses can bypass the ordinary guest callback/fault path.

This is a described witness, not a measured result; I did not run it.
