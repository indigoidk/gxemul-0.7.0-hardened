That behavior applies when the device returns a nonpositive result and `NO_EXCEPTIONS` is clear. If the callback changes `cpu->running` from true to false, an earlier check returns failure immediately. With `NO_EXCEPTIONS`, the device callback can be skipped unless its flags permit access, and the ordinary failed-device branch is bypassed, reaching the success return. These distinctions matter: a failure return is not itself Alpha exception delivery.

For **Q5**, the proposed behavior is coherent as degraded emulation. The interrupt macros make ordinary calls through **void** callbacks; they have no acknowledgement return value or waiting protocol. LCA maintains no acknowledgement state. I checked the ISA request/mask calculations, cascade, `last_int`, timer acknowledgement decrement, PIC EOI/mask notifications, and WDC interrupt clearing on status reads. Those paths update state and return; none waits for an acknowledgement from the LCA callback. The `fatal` function itself is a logging wrapper, so the explicit `exit(1)` supplies the termination here. [interrupt macros](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/include/interrupt.h:74), [fatal](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/debugmsg.c:384), [WDC acknowledgement](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_wdc.c:1938)

Pending PIC/device state can nevertheless remain uncleared, and unchanged pending state can suppress subsequent upstream notifications. A guest relying on timer or disk interrupts can therefore wait indefinitely. The source supports **no callback-handshake deadlock on the inspected path**; it does not support a promise that the guest will continue making progress or boot successfully.
