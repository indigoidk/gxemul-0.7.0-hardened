**TASK 1**

**(a) Inputs and conditions**

[THE SPACE, lines 845–853](C:/DocumentNoSnc/cc/GXEMUL/_scratchpad/fbd5/q2c/frozen/diff_footbridge.c:845) names all the **arm-local semantic inputs**: address/case, direction, width, `idata`, the four interrupt fields, and the five warning flags. Its account of the arm bodies’ conditions is correct:

- Four status arms test `writeflag == MEM_READ`, then their own `!warned_*`.
- IRQ Clear tests `writeflag == MEM_WRITE`, then `irq_status & irq_enable` **after updating the enable**; its declined branch tests `!warned_irq_clear_r`.

That covers all **11 arm-local branch predicates**. It is not a literal inventory of the surrounding function’s tests:

1. **Write-data fetch**, [device line 514](C:/DocumentNoSnc/cc/GXEMUL/_scratchpad/fbd5/q2c/frozen/dev_footbridge.c:514): `writeflag == MEM_WRITE` controls loading `idata` from `data` over `len`. This reuses the named direction/width/data inputs. Among these five arms, the fetched value affects only a **legal IRQ Clear write**. The four declined writes ignore it. Reads leave `idata` at its initial zero.

2. **Timer-range fold**, device lines 517–520: the conjunction tests both `relative_addr >= TIMER_1_LOAD` and `relative_addr <= TIMER_4_CLEAR`; if true, it computes `timer_nr` and clears address bits `0x060`. THE SPACE mentions the fold, but leaves these comparisons implicit.

   The five canonical addresses are outside the current timer interval. Independently, each is a fixed point of the mask:

   | Arm | Address | `address & ~0x060` |
   |---|---:|---:|
   | IRQ_STATUS | `0x180` | `0x180` |
   | IRQ_RAW_STATUS | `0x184` | `0x184` |
   | IRQ_ENABLE_CLEAR | `0x18c` | `0x18c` |
   | FIQ_STATUS | `0x280` | `0x280` |
   | FIQ_RAW_STATUS | `0x284` | `0x284` |

   Thus merely widening the range to include these addresses would not change their dispatch. The computed timer index would also be zero, and these arms do not use it. Widening the range **could admit other addresses**, such as `0x1a0`, which masks to `0x180`.

3. **Common read tail**, device lines 777–778: `writeflag == MEM_READ` controls writing `odata` into the buffer. That direction test matters to both legal reads and the declined Clear read.

CPU/buffer transport and interrupt callbacks are surrounding dependencies fixed by the harness, rather than separately enumerated dimensions of THE SPACE.

The broad legal-access Cartesian-product claim therefore has gaps:

- No narrow legal Clear write with flags already set.
- No narrow legal Clear write carrying zero, even with flags clear.
- No latched all-ones Clear write.
- Latched width-4 zero Clear writes occur in X7, but their value/output effects are not checked.
- X10–X12 do not check handler return values.

A concrete static counterexample is changing the Clear write condition to:

`writeflag == MEM_WRITE && (len == 4 || !d->warned_irq_clear_r)`

Every existing Clear-write row still takes the same branch: the narrow rows have that flag clear, and the latched rows use width 4. A narrow legal write after that flag is set would silently lose its clear and interrupt effects. This is a static argument; I did not apply or execute the change.

The zero/ones states exercise both outcomes of individual bit predicates. That alone does not guarantee an observable failure: for example, a legal read diverted into an already-latched decline can remain indistinguishable when its correct value is zero. X7’s announcement-only oracle cannot resolve that distinction.
