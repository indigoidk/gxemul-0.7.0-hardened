## REASONED CAVEATS (not measured, but worth naming)

### C1. The CSR "zeros are read" rule is in a different address space
The brief's "VALUE warrant for a declined READ is 0" cites `:1652`, which is the SA-110 **CSR** read rule (address 0x41xxxxxx). The footbridge lives at 0x42000000 — a memory-mapped device, not a CSR. The analogy is reasonable (a declined read should return a benign value, and 0 is the obvious choice), but the brief presents it as datasheet-derived when it is really a model-policy choice. The five-row "return 0" decision is defensible either way; just don't claim it as a datasheet warrant.

### C2. The "model must leave ... UNCHANGED" for a declined WRITE is also a policy choice
For a write to a read-only register, the datasheet says nothing (Table 7-10 "Write: --"). "Leave state unchanged" is the only non-destructive choice, but the brief states it as a derivation rather than as the obvious safe default. Acceptable.

### C3. Q4: smallest "cheat" that leaves K1/K2 green while proving nothing
- **K1 cheat:** don't launch anything; always record exit 1. The K1 row would pass but the launcher is never exercised. The "unknown-emulation diagnostic names that input" check would never run.
- **K2 cheat:** skip the `reg` prologue verification; send `quit`; reap exit 0. The K2 row would pass on any well-behaved emulator, but the prologue-is-live check (MMU off, RAM 0x11223344, VENDOR 0x1011, timer mask) would never run.
- **The row that "stays green" with the smallest edit:** K2 without the `reg` step — many emulators exit 0 on `quit`, so this passes by default. K1 is harder to fake silently (the launcher has to actually produce exit 1 with a diagnostic naming the input).

### C4. The "5 = 1 class under the reopening rule" argument
The five sites share device, semantic class (undefined direction), and detector. This is a defensible single-round grouping. The SDRAM pair is correctly excluded as a different class ("missing value" vs "undefined direction"). ✓
