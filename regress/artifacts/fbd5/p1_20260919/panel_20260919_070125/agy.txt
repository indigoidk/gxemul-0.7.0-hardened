#### Q1 -- Premise Audit

**(a) Datasheet direction, Member 3 vs 2 vs 4/5, and FAULT availability on ARM:**
- **Datasheet Direction Verification**:
  - `+0x180` (IRQStatus): Table 7-10 (`:6824`) defines Read: `IRQStatus`, Write: `--`. Section 7.3.29 (`:6888`) specifies "read-only register".
  - `+0x184` (IRQRawStatus): Table 7-10 (`:6825`) defines Read: `IRQRawStatus`, Write: `--`. Section 7.3.30 (`:6903`) specifies "read-only register".

#### Q2 -- Candidate Weakenings Analysis

- **(a) Decline keeps `exit(1)` at one of the five sites**:
  *Reds immediately*. The corresponding D row (e.g., D1 for `+0x180`) expects the arm to survive with exit 0. Reaching `exit(1)` terminates the host during step execution; the row sees `status == HOST-DIED` and `exit == 1`, failing the survival assertion.
- **(b) Announce unlatched (fires on every access)**:
  *Reds immediately*. Each D row executes two accesses and counts occurrences of the announcement. If unlatched, count is 2 (want 1).
- **(c) One latch bit shared by two sites (second never announces)**:
  - If both sites are executed within the **same arm/process run**: the second site sees the bit already set and produces 0 announcements; the second D row sees count 0 (want 1) and *reds*.
  - *Escape hazard*: If the test runs each D row in an isolated process with a fresh `memset`, a shared bit between two distinct sites *escapes* unless an arm sequentially exercises both sites.
- **(d) `+0x18c` decline keeps `odata = d->irq_enable`**:
  *Reds immediately*. Row D3 performs reads of `+0x18c` with enable initialized to `0x30`. The retained assignment returns `0x30`; D3 asserts `got == 0`, failing the value check.
- **(e) WRITE decline stores written value into `irq_status`**:
  *Reds immediately*. Row D1 writes `0x10` to `+0x180`. A subsequent status read returns `0x10` instead of `0`, failing the unchanged state assertion.
- **(f) Decline also swallows legal direction (IRQ_STATUS READ returns 0 always)**:
  - **ESCAPES proposed row A1!**
  - *Proof*: In a cold debugger run without external hardware interrupts, `d->irq_status` is `0` ([`dev_footbridge.c:80`](file:///C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_footbridge.c#L80)). Legitimate code computes `odata = d->irq_status & d->irq_enable == 0 & 0x30 == 0`. A buggy mutant returning `0` always produces `0`, perfectly matching `want = 0`. Row A1 only catches OR instead of AND (`d->irq_status | d->irq_enable`), not a constant 0 return.
- **(g) Announce text misnames the register**:
  *Reds immediately*. The D row regex searches for the specific register name. A mismatch results in count 0 (want 1).
- **(h) K1's startup leg passing on ANY nonzero exit**:
  *Escapes*. If GXemul crashes with SIGSEGV (signal 11) or `execvp` fails (exit 127 in [`Session.__init__`](file:///C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/regress/fbpending_drain_probe.py#L293)), an unpinned check passes, masking invalid process failures as clean startup rejections.
- **(i) K2's quit leg passing when child died BEFORE prologue completed**:
  *Escapes*. If the harness does not check the prologue register readback (`reg`) prior to sending `quit`, an early startup/prologue crash falsely registers as a successful post-execution death.
- **(j) Latch cleared by a read**:
  *Depends on ordering*:
  - If sequence is Write 1 -> Read -> Write 2: Write 2 fires a second announcement; count becomes 2 (want 1), and D row *reds*.
  - If sequence is Write 1 -> Write 2 -> Read: the back-to-back writes produce count 1, and the read clears the latch *escapes* unless followed by Write 3.
- **(k) Harness legs implemented in one launcher only**:
  *Reds immediately*. If [`fbpending_drain_probe.py`](file:///C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/regress/fbpending_drain_probe.py) or [`fbpending_witness.py`](file:///C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/regress/fbpending_witness.py) retains the old kill arm reading `+0x18c`, the retired kill site no longer crashes the host (`status == SURVIVED`, `exit == 0`), causing their K checks to fail.

#### Q3 -- Option-Set Completeness

The brief proposes Member 3 (DECLINE + LATCHED ANNOUNCE) for all five sites.
- **Did the brief overlook Member 2 (Silent Decline)?**
  Yes, as an engineering alternative. In [`dev_footbridge.c:628-636`](file:///C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_footbridge.c#L628-L636), `FIQ_ENABLE_SET` and `FIQ_ENABLE_CLEAR` **already implement Member 2** for reads:
  ```c
  case FIQ_ENABLE_SET:
      if (writeflag == MEM_WRITE)
          d->fiq_enable |= idata;
      break;

  case FIQ_ENABLE_CLEAR:
      if (writeflag == MEM_WRITE)
          d->fiq_enable &= ~idata;
      break;
  ```
  On a `MEM_READ`, both fall through the switch without diagnostic or exit, returning `odata = 0`. Similarly, offsets `0x04..0x18` ([lines 522-528](file:///C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_footbridge.c#L522-L528)) implement Member 2. Adopting Member 3 for `IRQ_ENABLE_CLEAR` read while `FIQ_ENABLE_CLEAR` read remains Member 2 creates an asymmetry, though Member 3 is acceptable under the latched diagnostic policy.
- **Members 1, 4, 5, 6, 7**:
  - Member 1 (DELETE): Unacceptable; falling through to `default:` spams unlatched warnings on every access.
  - Member 5 (FAULT): Unacceptable; hardware does not fault, and ARM has no exception plumbing for device access failures in GXemul.
  - Member 6/7 (ACCEPT / IMPLEMENT): Unacceptable; status registers are strictly hardware-driven and cannot be made writable; clear registers are write-only strobes and cannot be meaningfully read.
