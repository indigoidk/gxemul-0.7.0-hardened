**Q4: Yes—add an independently discriminating `exhaust event` row.**

The observable is **SYSASIC pending word 1, bit 0**, read at `0xa05f6904`: GD-ROM event 32. Existing `bad event`, `fmt event`, and `unk event` rows observe command-dispatch completion paths, not the final PIO read.

The crucial qualification is that [command dispatch already raises this event](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_dreamcast_gdrom.c:940). Its pending bit is sticky. Reading “set” after exhaustion without acknowledging that earlier event proves nothing about exhaustion.

The event oracle therefore needs:

1. A demonstrated dispatch event.
2. Its acknowledgement using the register’s 32-bit write-one-to-clear semantics, followed by a verified clear reading.
3. A clear reading immediately before the final valid halfword.
4. A set reading immediately afterwards, before any excess DATA read.

The [existing regression commentary](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/regress/gdrom_decline_probe.py:433) already explains why writing zero clears nothing; the [ASIC implementation](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_dreamcast_asic.c:195) confirms it.

This observes pending status, **not CPU interrupt delivery**. Multiple event calls before acknowledgement coalesce into one bit, so this is not an exact event-call-count oracle.
