A rigorous, adversarial audit of [`brief_sent.md`](file:///C:/DocumentNoSnc/cc/GXEMUL/_scratchpad/panel_20260924_102737/brief_sent.md) against the codebase under `GXEMUL-SEC/` confirms the core defect diagnosis: [`dev_fbctrl_access`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_fbctrl.c#L106-L154) stores an unvalidated selector into `current_port` before checking bounds, leading to an immediate host `exit(1)` upon the subsequent access to `DEV_FBCTRL_DATA`.

However, the brief cannot proceed without changes due to three critical omissions and apparatus traps:
1. **Gate 16 Skips Without Kernel:** Wiring `fbctrl_port_probe.py` into [`gate_mips_folds.sh`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/regress/gate_mips_folds.sh#L35) places it behind a preflight check (`PMAX_KERNEL`) that skips the entire gate if the DECstation kernel is absent, even though `fbctrl` runs on `-E testmips` and needs no kernel.
2. **Hidden Gate 6 Hygiene Pin Failures:** The brief mentions [`check_probe_wiring.py`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/tools/pipeline/check_probe_wiring.py), but completely ignores [`regress/gate_hygiene.sh`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/regress/gate_hygiene.sh#L385-L726). Introducing a new PTY probe without updating `EXPECT_PTY_PROBES` (73) and `EXPECT_CONVERTED` (24) will cause Gate 6 to break.
3. **Detector Escapes:** The proposed detector tests `sw -1` (a 32-bit store zero-extended in `uint64_t idata`), which fails to detect a mutant using signed comparison `(int64_t)idata >= DEV_FBCTRL_NPORTS`. A 64-bit store `sd -1` (`0xffffffffffffffffULL`) would bypass that faulty guard, write `-1`, and kill the emulator on DATA. Furthermore, testing on single-instance sessions fails to distinguish a global `static int warned_port;` from a per-instance `d->warned_port`.

### Numbered Findings & Review-Asks (Section 3 Questions)

#### 1. Premise Audit

* **(a) Writers of `current_port`:**
  **VERIFIED.** An exhaustive search across `src/` (`git grep -n "current_port" src/`) shows that [dev_fbctrl.c:120](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_fbctrl.c#L120) (`d->current_port = idata;`) is the **sole writer** of `current_port` in the entire codebase, besides the zeroing `memset` in [`DEVINIT(fbctrl)`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_fbctrl.c#L157-L173) at line 162.

* **(b) Reachability of DATA arm `exit(1)` & Range Enumeration:**
  **CANNOT BE REACHED.**
  - `dev_fbctrl` is registered at length `0x20` ([`dev_fbctrl.c:169`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_fbctrl.c#L169)).
  - In [`dev_fbctrl_access`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_fbctrl.c#L106-L154), accesses are switched on `relative_addr`. Only `relative_addr == 0x00` enters `case DEV_FBCTRL_PORT`. Any access at offsets `0x01..0x0f` or `0x11..0x1f` immediately jumps to `default:`, exiting with `unimplemented relative addr` (see Finding 7 below).
  - Unaligned MIPS stores ([`mips_unaligned_loadstore`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/cpus/cpu_mips_instr_unaligned.c#L44-L136)) align addresses to `aligned_addr = addr & ~(wlen-1)` before calling [`memory_rw`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c#L587).
  - In `case DEV_FBCTRL_PORT`, `idata` is `uint64_t` (unsigned).
  - Under the fix (`else if (idata >= DEV_FBCTRL_NPORTS)`), any value $\ge 8$ is rejected. The `else` branch executes **only** when `idata < 8`.
  - Since `idata` is unsigned, the only values reaching `d->current_port = idata` are strictly $\in \{0, 1, 2, 3, 4, 5, 6, 7\}$.
  - Storing these into signed `int current_port` guarantees $0 \le \text{current\_port} \le 7$.
  - Therefore, the DATA guard condition `(d->current_port < 0 || d->current_port >= DEV_FBCTRL_NPORTS)` evaluates to `FALSE` for every possible subsequent guest access. The DATA arm's `exit(1)` is mathematically unreachable once PORT validation refuses out-of-range values.

* **(c) The `sd` Truncation Row on `-E testmips`:**
  **VERIFIED.**
  - Machine `testmips` selects CPU `5KE` by default ([`machine_test.c:410-413`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/machines/machine_test.c#L410-L413)). `5KE` has `isa_level = 64` ([`mips_cpu_types.h:104`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/include/mips_cpu_types.h#L104)).
  - Instruction `sd` sets `store = 1, size = 3, x64 = 1` ([`cpu_mips_instr.c:5440`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/cpus/cpu_mips_instr.c#L5440)), invoking an 8-byte transfer (`len = 8`).
  - In [`memory_readmax64`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/core/memory.c#L55-L78), for `len = 8` on big-endian MIPS, all 8 bytes are shifted into `uint64_t x` across 8 loop iterations. It delivers the full 64-bit word.
  - For `sd 0x0000000100000003`, `idata = 0x100000003ULL`. In current HEAD:
    - PORT checks `0x100000003ULL >= 8` (true $\rightarrow$ prints WARNING).
    - PORT stores `d->current_port = 0x100000003ULL`. Truncation to 32-bit `int` yields `current_port = 3`.
    - DATA checks `3 < 0 || 3 >= 8` (false $\rightarrow$ access is serviced on port 3!).
    - The brief's analysis of the `sd` row is physically and mechanically accurate.

#### 2. Adversarial Smallest Edits (Mutant Analysis)

The following mutants break the fix or its intent while staying **completely green** across all proposed probe rows:

1. **The 64-bit Sign-Extension Escape (`(int64_t)` mutant):**
   * *Mutant:* `else if ((int64_t)idata >= DEV_FBCTRL_NPORTS)`
   * *Why it breaks:* For any 64-bit value with bit 63 set (e.g. `sd -1`, yielding `0xffffffffffffffffULL`), `(int64_t)idata` is negative ($-1$). It evaluates $-1 \ge 8$ as `FALSE`, falls through to `d->current_port = idata`, sets `current_port = -1`, and the next DATA access exits.
   * *Why the proposed detector misses it:* The proposed detector only tests `sw -1` (`sw` is 32-bit). In [`memory_readmax64`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/core/memory.c#L55-L78), a 4-byte read into `uint64_t` zero-extends the word to `0x00000000ffffffffULL`. Interpreted as `int64_t`, this is $+4294967295$, which is $\ge 8$! All proposed rows stay green.
   * *Required Detector Amendment:* Add a 64-bit negative row: `sd 0xffffffffffffffff` (or `sd -1`) to PORT.

2. **The Shared Static Latch Escape:**
   * *Mutant:* Using `static int warned_port;` instead of `d->warned_port`.
   * *Why it breaks:* Global state suppresses warnings across distinct device instances or subsequent machine boots.
   * *Why the proposed detector misses it:* The probe runs each row on a fresh `-E testmips` instance containing exactly one `fbctrl` device. It never tests multiple device instances or secondary instances.
   * *Required Detector Amendment:* Explicitly assert that the latch is per-device instance.

#### 3. DATA Arm Disposition

* **Verdict: KEEP `exit(1)` in the DATA arm as an unreachable belt-and-braces invariant assertion.**
* **Rationale:**
  - Once the PORT arm declines out-of-range writes, `current_port` is constrained to $[0, 7]$. The DATA guard becomes unreachable by guest code.
  - If a future regression or refactoring breaks PORT validation, keeping `exit(1)` in the DATA arm prevents an out-of-bounds array access (`d->port[d->current_port]`).
  - Converting the DATA guard to a silent decline would mask regressions and create duplicate decline paths.
  - **In-tree Precedent:** In `#521` (`mk48nvramkill`, commit [`21e75609`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/CHANGELOG.md)), the project retained the unreachable fatal arm as belt-and-braces rather than deleting it. Furthermore, [`tools/pipeline/ledger.json`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/tools/pipeline/ledger.json) explicitly mandates for `fbctrlportkill`:
    > *"A FLOOR NOTE THE ROUND MUST CARRY: 'a verbatim reinstatement of the removed kill' is INCOMPATIBLE with a repair that RETAINS that kill. This disposition leaves the DATA arm's 'exit(1)' in place as belt-and-braces... and the same answer: name the distinguishable mutant (restoring the store-before-validate order) rather than pretending the literal clause is met."*

#### 6. Scope & The Reopening Rule

* **Leaving the two other `exit(1)` sites to separate rounds is CORRECT.**
* **Reopening Rule Compliance:**
  The project's reopening rule requires: *same device, same semantic class, same detector, no new oracle* ([`CHANGELOG.md:17478`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/CHANGELOG.md#L17478), [`CHANGELOG.md:18432`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/CHANGELOG.md#L18432)).
  - `fbctrl_command()` `default:` (L101) is an **unimplemented command opcode** defect. It requires deciding semantics for `FILL` and `COPY` and designing an oracle for command dispatch.
  - `DEVICE_ACCESS` `default:` (L147) is an **unmapped MMIO address offset** defect.
  Neither shares the semantic class of index selector validation, and both require new test oracles. Merging them violates the reopening rule.

#### 7. Something Else Found (Unmapped Byte Offset Trap)

While auditing access paths in [`dev_fbctrl.c`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_fbctrl.c#L114-L148), an adjacent fragility was surfaced:
[`dev_fbctrl_access`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_fbctrl.c#L114) switches on `relative_addr`. If guest software attempts a byte store to the low byte of `DEV_FBCTRL_PORT` on a big-endian system (`sb val, 3(t0)`), `relative_addr` is `3`. It misses `case DEV_FBCTRL_PORT (0x00)` and hits `default:`, terminating the emulator with `unimplemented relative addr 0x3`. This confirms the author's observation in Section 4 and warrants a separate issue row as planned.
