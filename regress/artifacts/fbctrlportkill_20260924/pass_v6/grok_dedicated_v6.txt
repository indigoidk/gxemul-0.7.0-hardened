## Why every one of the 117 rows stays green

On this compiler the weakened compare accepts a write only when `warned_port` is still 0 and `idata` is in 16..23. Clearing bit 4 then leaves 0..7. Every later out-of-range write sees the latch already set and uses the original compare.

The latch is set only inside the refusal arm. A legal store does not set it. The only probe writes that see it clear are each session's first out-of-range store:

| First refusal | Value | Bits that actually flip `>= 8` |
|---|---|---|
| P, W, B | 8 | bit 3 only |
| F, V, R, K, Y, Z, X2, X6 | 9 | bit 3 only |
| X7 | 0x100 | bit 8 only |
| X3 | 0x100000005 | bit 32 only (masking it leaves 5) |
| X4 | all-ones | none (any one bit still leaves a value `>= 8`) |

None of those is in 16..23, and none has bit 4 as a decisive bit. After that first refusal the latch is set, so the mask is gone.

The rows that look like they should catch 16 all run with the latch already set:

- P's three `refuse 16` rows (sw, sb, sh) follow P's first refusal of 8.
- V's later 16 follows V's first refusal of 9.
- Each of B's four width rows includes 2^4, but B's first store is 8, which sets the latch. The later store of 16 is refused, `current_port` stays 5, and the one `lw` per width still reads 5. The count row still sees one announce, on that first 8.

K's witness stays green for the same reason: K's refused value is 9, the selector stays 5, and the DATA read/write never sees port 16. No probe access takes the new branch, so the announce, cell, accept, and read rows are on the same trace as the fixed binary.

## The exit comes back

On a fresh device (`warned_port` is 0 from `memset` in `DEVINIT`), a guest `sw` of 16 to PORT takes the accept arm and sets `current_port` to 16. The next DATA access hits the kept check `current_port >= DEV_FBCTRL_NPORTS` and `exit(1)`. The same is true for 17..23. A store of 24 is still refused: masking bit 4 leaves 8.

A narrower form, `idata >= 8 && !(idata == 16 && !d->warned_port)`, also scores 117 and restores the exit on 16 alone. P, V, and B do write 16, but only after the latch is set.

## What that means for the contract

`(0)` calls every two-axis edit unclaimed. That sentence is aimed at the unbounded product (value × width × previous selector, and so on). It does not reach this cell. The refusal block reads `warned_port`, and `idata >= 8` tests bits 3..63. The floor product is that latch state times those bits. Held at latch-unset, with a channel that goes red if the bit is masked: **bit 3, bit 8, bit 32**. Open: **4, 5, 6, 7, 9..31, 33..63** — 58 bits. Bit 4 is the smallest.

Session B cannot close them. Its first store is bit 3, which sets the latch, and the four `lw`s happen after that. A leak conditioned on the latch still being clear never starts, so there is nothing for the later refusals to preserve.

The repair owes those 58 cells in one diff: a fresh device, a legal `PORT=5` (that does not set the latch), one `sw` of `2^k`, then a PORT read that must still be 5. One width is enough. A third qualifier (`len == 1` as well as the latch) is a real `(0)` joint; an `sw`-only row does not kill it.
