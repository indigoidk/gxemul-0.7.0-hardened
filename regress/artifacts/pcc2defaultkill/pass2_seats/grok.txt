## 1. The fix is right

The whole arm plus tail:

```664:701:GXEMUL-SEC/src/devices/dev_pcc2.c
	default:
		/*  #501 ... */
		if (!(d->warned_unimpl & (1ULL << relative_addr))) {
			d->warned_unimpl |= 1ULL << relative_addr;
			if (writeflag == MEM_WRITE)
				fatal("[ pcc2: unimplemented write to offset "
				    "0x%x: 0x%x -- declined.  (once) ]\n",
				    (int) relative_addr, (int) idata);
			else
				fatal("[ pcc2: unimplemented read from offset "
				    "0x%x -- served 0x%02x.  (once) ]\n",
				    (int) relative_addr,
				    d->pcctwo_reg[relative_addr]);
		}
		break;
	}

	return 1;
```

| Question | Answer |
|---|---|
| Does `break` reach the single `return 1`? | **Yes.** This handler has no `memory_writemax64` tail. Reads were already written into `data` by the memcpy at 425–437. Early `return 1` and `break` are equivalent here; `return 0` would still be a failed transaction (codex's member-5 correction). |
| Is `1ULL << relative_addr` always defined? | **Yes, after the fold.** `relative_addr` is `uint64_t` (`memory.h` `DEVICE_ACCESS`). Line 420 does `relative_addr %= PCC2_SIZE` with `PCC2_SIZE == 0x40`, so the shift count is 0..63. `1ULL << 63` is defined. Bit 0 is wasted (offset 0 is CHIPID, cased). There is no sibling of the width field's compile-time fit typedef; residual, not a ship-blocker. |
| Does the read announce print a wrong value? | **Not on any byte the detector uses.** After an in-range memcpy, `pcctwo_reg[relative_addr]` is what was served. On an **end-spanning wide read** (`relative_addr + len > 0x40`) the memcpy is skipped, `data` is zero-filled, and the announce still prints the array byte. At reset those bytes are 0, so it matches by accident. Byte offsets cannot end-span (`0x3f+1 == 0x40`). |
| Latch collision with `warned`? | **No.** Width uses `uint32_t warned`; this uses `uint64_t warned_unimpl`. Separate fields, separate `memset` at `DEVINIT` 731. `pcc2_width_decline` messages do not contain `pcc2: unimplemented`. |
| Is memcpy served content different? | **The copy is unchanged.** What changed is observability: the old arm memcpy'd then `exit(1)`, so the guest never saw the buffer. A wide uncased read (e.g. len=4 at `0x14`) now returns adjacent cased bytes the memcpy already packed (PSCALEADJ is initialised to `256-33`). Pre-existing copy, newly visible. Not a reason to back the write. |
| OpenBSD 2.2? | **The success path does not touch this arm.** `clock.c` / `cl.c` / `pcctwo.c` use cased offsets only (`psclkadj` 0x15, timers, SCCERR/SCCICR/SCCTX/SCCRX, SCCRXIACK 0x27, IPL/MASK). `if_ie.c:609/612/655` would hit IEICR/IEBERR/IEERR; match fails at `if_ie.c:409` because `machine_mvme88k.c:106` installed `unreadable` at `0xfff46000`. `ie0` **is** in `conf/M187:99` and `conf/NFS:100`. The guest boot does not change; a probe still would have killed the host. |

Member 3 for writes, keep-served for reads, is the right option. I was on that side at pass 1; scrutinising it: GPIO_ICR and IEICR **are** writable on the part, so “read-only” is not a warrant for those two. The warrant that holds is the one the brief actually leans on: **one store from this arm cannot be correct for all 43** (SCCERR/IEERR are write-to-clear — SCLR at `vmesbcp2.txt:5430`; ICRs mask and `reassert_interrupts`; PSCALECNT/SPEED/IACKs are not stores). A split-by-class predicate was rightly rejected for this round. IACK 0x23/0x25 declined, `pcc2c040kill` first: also right; modelling them on the SCCRXIACK shape (no `writeflag` test, and `cl.c` reads 0x27) would open two new entries into that kill.
