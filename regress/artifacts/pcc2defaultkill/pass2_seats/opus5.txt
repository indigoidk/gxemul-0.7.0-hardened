# Q1 — IS THE FIX RIGHT?  **YES.  Ship it unchanged.**  Every sub-question checked.

* **`break` reaches the single `return 1`.** `grep -n "return\|exit(" ` over the whole
  `DEVICE_ACCESS(pcc2)` body: exactly one `return 1;`, zero `exit(`. The `default:` arm is the
  LAST arm, so `break` and fall-through are identical here — which is why "delete the `break`"
  is an equivalent mutant and correctly absent from the table.
* **`1ULL << relative_addr` is always defined.** `PCC2_SIZE` is `0x0040`
  (`src/include/thirdparty/mvme_pcctworeg.h:14`) and `relative_addr %= PCC2_SIZE` is the
  function's FIRST statement, on every path, before every `return`. Range 0..63; `uint64_t`
  has 64 value bits. No UB, no truncation. `1U` or a `uint32_t` field would have been UB —
  the type choice is load-bearing and correct.

  blocks, indexed by the `PCC2_W_*` enum); `warned_unimpl` is a separate `uint64_t` indexed by
  byte offset. Different fields. Both zeroed by the ONE `memset(d, 0, sizeof(struct
  pcc2_data))` at `dev_pcc2.c:731`, which is what the comment claims and it is true.
* **Nothing the memcpy served is different.** `git diff` has exactly TWO hunks (`@@ -138,6`
  struct field, `@@ -658,13` default arm). The read-service block above the switch is
  byte-untouched.
* **The read announce CAN print a wrong value — but only under a mutant, not as shipped.**
  Measured above: shipped prints `served 0x34`, correctly. Two latent wrinkles worth one line
  each, neither a defect today:

    default arm then says `served 0x%02x`. Today `pcctwo_reg[0x3d]` is 0 (nothing writes
    uncased offsets under the fix), so the announce coincidentally tells the truth. It becomes
    a wrong record the moment anything backs an uncased offset — i.e. exactly under `M_O2`.
  - *width-blind*: the announce names ONE byte for an access of `len` bytes and never prints
