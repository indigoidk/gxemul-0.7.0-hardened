## Q2. `response_after` is not sound

`t.find("GXemul> step %d" % len(second))` takes the **first** substring. That is “that command’s own echo” only if the string occurs once, as a whole token.

**What this producer actually emits**

- `first = load_const(T0, SCRATCH) + [LDQ, CALL_PAL]`
- `second = load_const(T0, SCRATCH) + [LDAH(V0, SENT>>16), LDQ, CALL_PAL]`
- `SCRATCH = 0x01020000` → `lo=0` → one `LDAH`. So **`len(first)=3`, `len(second)=4`**.
- Structurally **`len(second) = len(first) + 1`** for any `load_const` length. Equal counts cannot appear unless that extra `LDAH` is removed or first is padded.
- `str(4)` is not a prefix of `str(3)`. Searching for `GXemul> step 4` cannot hit `GXemul> step 3`.
- `printf("GXemul> ")` exists only in `debugger_readline` (four sites, all prompts). The banner is `GXemul ` + VERSION, no `>`. Help is `syntax: step [n | call]\n`, no prompt. The probe never issues `help`, tab, or a third `step`.

So: **no banner hit, no equal-count hit, no prefix hit against the other step, on this encoder.** The genuine `cmds` list is `step 3` then `step 4`. One `STEP2` string.

**Where the helper is still unsound**

1. **Equal counts.** Two `GXemul> step 4` echos. `find` binds the first. First v0 after that is call 1. (rfind would pick the last echo; it would not enforce uniqueness and still treats `step 4` as a prefix of `step 40`.)
2. **Unanchored `find`.** `"GXemul> step 4"` is a prefix of `"GXemul> step 40"` and `"GXemul> step 4 extra"`. Not emitted today; the helper still accepts them.
3. **Any earlier exact echo of `GXemul> step 4`.** Same bind-to-call-1. Not in `cmds`. One inserted line is enough.

The session loop writes a command, then reads, then writes the next, on one PTY. Bytes are not reordered. A delayed call-1 print cannot land after the step-2 echo unless the cmds list itself is reordered or a line is spliced in. The hole is the helper’s uniqueness assumption, not PTY merging.

The `v0 bound` row cannot see (1)–(3): `v0_bound` is still non-`None`, the row stays `yes`, and its note (“the scored v0 is the response FOLLOWING the second `step`”) is false.
