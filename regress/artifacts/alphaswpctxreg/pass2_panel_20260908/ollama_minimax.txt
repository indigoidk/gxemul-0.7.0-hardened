## Q1 — The vacuity floor, clause (d)

**Acceptable as stated, with one caveat.** The argument-by-construction is sound for the specific mutant it names (`r[V0] = cpu->cd.alpha.r[ALPHA_A0]`, i.e., "return the incoming context"): with `a0 = N` going into the second call, this mutant produces `v0 == N`, which fails the row that demands `v0 == C`. The oracle's three distinct values are what makes this work — they are not decorative, they are load-bearing for the "common misrepair" case.

**Caveat:** "by construction" covers the mutant the brief names, not the universe of conceivable edits. A built `v0 = a0` mutant + a measured score would be empirical confirmation. Whether that is *owed* depends on the testing standard the project applies. The brief is honest about the distinction (argument vs. measurement); I would not block the round on this.

A weaker but related mutant the brief does not name: `r[V0] = cpu->cd.alpha.r[ALPHA_A0]` *before* the `ctx = a0` assignment. This would also produce `v0 == N` on the second call (because `a0` is still `N` at that point in the function), and is likewise caught by construction. Same argument, same answer.

## Q2 — Edit to product the probe would not catch

**The first-call `v0` result is not asserted.** `v0_after1` is captured and feeds the `v0 read` control row (regex matched), but its value is never compared to anything. A fix that returns the old context correctly on the *second* call but returns something wrong on the *first* call would pass all four rows. For a one-line fix that does not branch on call count this is implausible, but it is a real gap on paper.

Other edits the probe *would* catch, for completeness:
- `r[V0] = r[ALPHA_A0]` (returns new context): `v0 ctx` row fails (would read `N`).
- Restore original code: `a0 land` fails (`a0 == C`); `v0 ctx` fails (`v0 == S`).
- Delete the line entirely: `v0 ctx` fails.
- Write `v0` from a wrong source (e.g., a constant): `v0 ctx` fails.
- Overwrite `v0` with `N` later in the "Load new context" block: `v0 ctx` fails.

What it does *not* catch:
- Subtle endianness / sign-extension issues in the *handler's* own internal use of `ctx` (the probe only observes the final `v0` and `a0`).
- A fix that works under the test's specific `a0 = N` value but mishandles other `a0` values (e.g., alignment requirements the model checks). The probe does not vary `a0`.

## Q3 — Edit to probe that makes it pass on the broken build

**Hard to construct.** For `v0_final == C` (`0x01000000`) to hold on a build where the handler does not write `v0`, something between the `LDAH(V0, S)` seed and the second `print v0` would have to put `C` into `v0` by a path that is not the handler writing it. The instruction sequence between is `LDQ(A0, 8, T0); CALL_PAL(0x30)`. `LDQ` writes `A0`, not `V0`. `CALL_PAL` is the only thing that could touch `V0`, and on the broken build it does not. So `v0` should remain `S` after the call. Spurious pass requires either:
- a debugger quirk that makes `step N` skip the `LDAH` (unlikely; one-step granularity is normal for these emulators);
- a parse quirk where `re.findall(... 'print v0' ...)[-1]` picks up a value from before the second `print` (would require an earlier transcript line of the shape `print v0\n0x01000000`, which has no source);
- the regex silently matching across an unrelated line. The pattern requires a literal `\n` followed by `0x[0-9a-f]+`; this is tight enough.

The probe does have one soft parse-dependency: it assumes the debugger's `print` output is `<value>` on its own line after the command. If the model ever changes its `print` format to `print v0\nv0 = 0x...`, the regex breaks. That would *fail* the row, not pass it spuriously, so it does not buy a green on the broken build — it buys a red on both.

## Q4 — The attribution control

**It separates the two stated hypotheses. But it has a model-dependent assumption.**

The two hypotheses:
- Handler ran and wrote the wrong register: `a0` ends as `C` (because the handler wrote `ctx = C` into `a0`).
- Handler never ran: `a0` ends as `N` (the value loaded by the probe before the call).

The row's expectation (`a0 == N`) distinguishes these.

**The assumption:** the fixed handler leaves `a0` unchanged. The brief justifies this by saying "the architecture marks `a0` UNPREDICTABLE, which permits it to remain unchanged." "Permits" is true; "does" is not guaranteed by the architecture — UNPREDICTABLE means the *caller* cannot rely on `a0`, not that the implementation will preserve it. A future "improvement" to the model that has the handler clobber `a0` (still architecturally legal) would break the `a0 land` row, *not* because `swpctx` regressed, but because the probe's attribution is now reading through a clobber. This is empirical, not architectural, and the brief should say so.

A *third* explanation I considered and rejected: a register-file caching artefact where `print a0` reads a stale slot. If such a thing existed it would itself be a model bug worth surfacing; not a real concern.

A subtler third explanation worth naming: if the model's swpctx path touches `a0` for some reason other than writing the old context (e.g., it uses `a0` as a scratch register inside the handler and restores it), then `a0 == N` is "handler ran and was careful with a0", which is fine for the attribution. But the *strength* of the attribution (proving the handler *wrote* the wrong register) is weakened — if on the broken build the handler writes `C` to `a0`, then restores it from a saved copy elsewhere, you could get `a0 == N` on the broken build too. I do not think this is happening — the witness shows `a0 == C` on the broken build — but the row's claim is "post-fix `a0` keeps the incoming context", which is a *correctness* claim about the handler, not just an attribution claim.
