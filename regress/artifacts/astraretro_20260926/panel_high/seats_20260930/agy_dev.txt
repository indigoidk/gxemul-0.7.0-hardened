### Q1. The Premise Audit

#### H7: Dreamcast GD-ROM DMA Self-Aiming Re-entry
* **Is the path reachable from code running in the guest?**
  **Yes.** A guest kernel on the Dreamcast can stage data via a standard GD-ROM command (such as reading the TOC or disc sectors), program `dst = 0x005f7418` (or P1/P2 aliases `0x805f7418` / `0xa05f7418`, which line 1501 masks with `0x0fffffff` to `0x005f7418`), set `count = 1` (`+0x0c`) and `enable = 1` (`+0x14`), and trigger the transfer by writing non-zero to `+0x18`.
* **The ONE premise that would make the finding false if it failed:**
  **The first 8 bytes of staged data (`d->data[0..7]`) must contain at least one non-zero byte.**
  *Check result:* **Checked and verified.** In [`src/core/memory.c:55-78`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/core/memory.c#L55-L78), [`memory_readmax64`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/core/memory.c#L55) on a little-endian CPU executes `for (i = len - 1; i >= 0; i--) { x <<= 8; x |= buf[i]; }`. For `len = 0x68` (104 bytes), every byte from `i = 103` down to `i = 8` is shifted left by at least 64 bits and discarded. Only `buf[0..7]` (`d->data[0..7]`) form `idata`. If `d->data[0..7]` were all zeroes, `idata` would be `0`, failing `if (idata != 0)` at line 1389 of [`src/devices/dev_dreamcast_gdrom.c`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_dreamcast_gdrom.c#L1389), terminating recursion on the first call. Because standard GD-ROM commands stage non-zero data (e.g. TOC track 1 has `0x10` at offset 0; disc sector headers/data are non-zero), the guest can satisfy this condition.

#### H8: SGI O2 (IP32) CRIME Control Register Lane Defect
* **Is the path reachable from code running in the guest?**
  **Yes.** Any supervisor/kernel code on MIPS can issue a 32-bit store (`sw 0x800`) to physical address `0x14000008` (CRIME base `0x14000000` + offset `0x08`).
* **The ONE premise that would make the finding false if it failed:**
  **The register dispatcher must match `case CRIME_CONTROL:` (0x08) on raw unshifted `relative_addr` without inspecting access width (`len`) or register lane alignment (`relative_addr & 4`), while omitting a `case 0x00c:`.**
  *Check result:* **Checked and verified.** In [`src/devices/dev_sgi_ip32.c:269-292`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_sgi_ip32.c#L269-L292) and lines [326-350](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_sgi_ip32.c#L326-L350), when `len == 4` and `relative_addr == 0x08`, `relative_addr & 4` is 0, storing `idata` into bits 63..32 of `d->reg[1]`. The switch matches `case CRIME_CONTROL:` (0x08) directly on `relative_addr` and evaluates `if (idata & CRIME_CONTROL_HARD_RESET)`. Since `idata == 0x800`, it immediately executes lines 342-343 (`cpu->machine->cpus[j]->running = 0`). A 32-bit store to `0x0c` sets the low 32 bits in `d->reg[1]`, but has no `case 0x00c:` in the switch, falling into `default:` and doing nothing.

#### H9: SuperH Double-Precision Arithmetic Past FR Array
* **Is the path reachable from code running in the guest?**
  **Yes.** With `FPSCR.PR = 1`, the guest can execute double-precision floating-point arithmetic (e.g., `FADD FR15, FR0` or `FADD FR0, FR15`). The instruction decoder in [`src/cpus/cpu_sh_instr.c:4951-4956`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/cpus/cpu_sh_instr.c#L4951-L4956) extracts 4-bit fields `r4` and `r8` without checking for odd register numbers or `FPSCR.PR`.
* **The ONE premise that would make the finding false if it failed:**
  **`fr[16]` must be exactly adjacent to `xf[0]` in host memory with zero padding.**
  *Check result:* **Checked and verified.** In [`src/include/cpu_sh.h:104-105`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/include/cpu_sh.h#L104-L105), `struct sh_cpu` declares `uint32_t fr[SH_N_FPRS];` immediately followed by `uint32_t xf[SH_N_FPRS];`. With `SH_N_FPRS == 16` and 4-byte alignment, `sizeof(fr) == 64` bytes. `(size_t)&cpu->cd.sh.fr[15] + sizeof(uint32_t)` evaluates precisely to `(size_t)&cpu->cd.sh.xf[0]`.

### Q2. Which of These Three Dispositions Is Wrong?

**Count: 2 dispositions are wrong.** Both **H8** and **H9** were wrongly graded/confirmed as **HIGH**.

1. **H8 is MED, not HIGH.**
   * *Rule Analysis:* Under this project's rules, HIGH requires that guest input ends the emulator process, leaves a buffer's bounds, or halts progress unexpectedly. CRIME is an MMIO device accessible only to privileged kernel code. Privileged code on IP32 already possesses the architectural authority to shut down or reboot the machine via a 64-bit store of `0x800` to `CRIME_CONTROL`.
   * GXemul models a machine reset gracefully by setting `cpu->running = 0` across all CPUs, which lets `emul_run()` finish and `main()` return 0. The lane defect causes a 32-bit write to reserved bits (`+0x08`) to trigger that reset, while failing to trigger on the correct lower half (`+0x0c`). The guest gains no capability it did not already possess, no host safety invariant is breached, and no crash/hang occurs. It is an address-decoding / sub-word bus lane defect contrary to hardware documentation: **MED**.
2. **H9 is LOW (or at most MED), not HIGH.**
   * *Rule Analysis:* The confirmation reviewer's literal reading ("makes one of its memory accesses leave a buffer's bounds") misapplies host memory safety rules to intra-struct guest CPU state. As previously established by project precedent (where "load-bearing host memory safety" was reduced to "intra-struct corruption" after measuring `offsetof`), indexing 4 bytes past `fr[15]` accesses `xf[0]`. Both arrays reside entirely within `struct sh_cpu` inside `struct cpu`. No host allocation boundary is crossed; no host metadata or foreign memory is touched.
   * Furthermore, in the SH-4 architecture manual, specifying an odd register field under `FPSCR.PR = 1` is an undefined/reserved combination whose operation is explicitly "not guaranteed". Emulating an undefined opcode by reading/writing another architectural guest register (`xf[0]`) creates zero host memory hazard. It belongs at **LOW** (or **MED** if strictly requiring an architectural exception), never HIGH.

* **Is there a member this list does not name?**
  **Yes:**
  1. **Re-entrancy / In-flight Guard:** Latching a busy/active state to serialize or suppress nested recursion without dropping the initial request.
  2. **Index / Alignment Masking:** Sanitizing register indices or address operands (e.g. `r & ~1` as done in `#315` for `fmov`, or address alignment masking) before indexing.
  3. **Asynchronous Deferral / Scheduling:** Queueing the DMA or hardware event onto an event loop / timer rather than executing device operations synchronously inside guest store instructions.

### Q4. Real-World OS Likelihood Ranking

1. **H8 (SGI O2 CRIME): Most likely.**
   * *Basis:* Real operating systems actually execute this path. As documented in the code comment at line 328 of [`src/devices/dev_sgi_ip32.c`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_sgi_ip32.c#L328), 32-bit kernels like NetBSD 1.6.2 issue 32-bit stores to `+0x00c` when rebooting. Because GXemul omits `case 0x00c:`, NetBSD cannot reset the machine. Furthermore, any 32-bit OS probing or clearing upper 32-bit registers via `+0x008` unexpectedly halts the emulator.
2. **H9 (SuperH FP Arithmetic): Intermediate.**
   * *Basis:* Standard compilers (GCC, Clang, Hitachi SH C) generate double-precision instructions using even register numbers per ABI specification. However, hand-crafted assembly, JIT engines, or corrupt binaries can easily emit odd register indices under `PR = 1`.
3. **H7 (Dreamcast GD-ROM DMA): Least likely.**
   * *Basis:* Ordinary OS drivers (e.g., NetBSD `sys/arch/dreamcast/dev/gdrom.c` or Linux `drivers/cdrom/gdrom.c`) program the DMA destination register to physical system RAM (`0x0c000000`..`0x0cffffff`). No legitimate OS driver would target a disk read DMA directly at the GD-ROM controller's own MMIO register window (`0x005f7418`). This path is only triggered by fuzzers or adversarial payloads.

### Standing License: Additional Findings

1. **H7 Destination Discrimination:**
   [`memory_rw()`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c#L478) performs a single dispatch based on `paddr`. A DMA block transfer targeting `dst = 0x005f7404` passes `relative_addr = 0x04` to `dreamcast_gdrom_dma_access`, which matches `case 0x04:` (a no-op break) and stores into `d->dma_reg[1]`. It does **not** iterate through subsequent register offsets. Hence, **only** destination addresses where `dst & 0x0fffffff == 0x005f7418` will trigger recursion.
2. **NetBSD Reboot Failure in H8:**
   The TODO comment in [`src/devices/dev_sgi_ip32.c:327-328`](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/devices/dev_sgi_ip32.c#L327-L328) (*"TODO: 64-bit write to CRIME_CONTROL, but some things (such as NetBSD 1.6.2) write to 0x00c!"*) directly corroborates the finding: the missing `0x00c` case breaks rebooting under standard NetBSD 1.6.2.
3. **Contrast Between FMOV and Arithmetic in H9:**
   For `fmov` register pairs with `SZ=1`, lines [792-795](file:///C:/DocumentNoSnc/cc/GXEMUL/GXEMUL-SEC/src/cpus/cpu_sh_instr.c#L792-L795) explicitly handle odd register numbers by redirecting them to the XD bank: `r1 = (size_t)&cpu->cd.sh.xf[ofs & ~1]`. In contrast, the arithmetic handlers (`fadd`, `fsub`, `fmul`, `fdiv` at lines 3371-3387) omit this redirect and directly do `reg(ic->arg[...] + sizeof(uint32_t))`, inadvertently walking into `xf[0]` when given register 15.
