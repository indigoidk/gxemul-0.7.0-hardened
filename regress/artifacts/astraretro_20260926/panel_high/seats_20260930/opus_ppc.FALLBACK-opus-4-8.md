## Q1 -- The premise audit (reachability, and the one load-bearing premise per finding)

**H1 -- BAT deny ends the process. REACHABLE, and broader than stated.**
The code path is exactly as described. `ppc_bat_block()` (`memory_ppc.c:48-79`) returns `0` in two cases -- a matching entry with `PP==BAT_PP_NONE` (00) for any access, and a *write* through a matching `BAT_PP_RO`/`BAT_PP_RO_S` entry (`:73` `return (flags & FLAG_WRITEFLAG)? 0 : 1;`) -- and `-1` when no entry matches (`:79`). `ppc_bat()` propagates that value, and `ppc_translate_v2p()` reaches the `res == 0 -> fatal("[ TODO: BAT exception ]"); exit(1)` arm at `:273-276` **before** the `FLAG_NOEXCEPTIONS` test at `:299`. So the brief's three code premises all hold, including "the test sits before the no-exceptions test" (confirmed: `:273` precedes `:299`), which is why a debugger `dump` -- `memory_rw(..., NO_EXCEPTIONS)` -> `FLAG_NOEXCEPTIONS` -- also hits it.

- **The one premise that would make it false: that a reachable guest actually programs a `PP=00` or read-only BAT and then an access violates it.** The fork's default BATs are all `BAT_PP_RW` (`cpu_ppc.c:105-118`), so the stock machine never triggers it; it needs the guest to reprogram a BAT restrictively. **Can I check it?** Partially. I confirmed the code path and the defaults statically. I could not confirm a specific NetBSD/macppc configuration that sets a deny/RO BAT and violates it, because macppc stalls in skeletal OpenFirmware before a full boot (OB-35 residual), so a live witness is blocked.
- **The brief's premise 3 is answered, and the answer widens the finding rather than narrowing it.** The brief asks whether only the kernel can reach this. **`X(mtspr)` has no privilege check** -- `cpu_ppc_instr.c:2807-2810` is `/* TODO: Check permission */ reg(ic->arg[1]) = reg(ic->arg[0]);`, and there is **no `MSR_PR` reference anywhere in `cpu_ppc_instr.c`**. So in this model *user* code can write `IBAT*/DBAT*` SPRs, set a deny BAT, and then fault it -- H1 is reachable from problem state, not just supervisor state. (On real silicon `mtspr` to a BAT is privileged; see "found something else".)

**H2 -- opcode-59 FMA family halts. REACHABLE (finding true); disposition contestable.**
Confirmed: `switch (xo & 31)` at `cpu_ppc_instr.c:5197` handles only `FDIVS`(18)/`FSUBS`(20)/`FADDS`(21)/`FMULS`(25); its `default` (`:5216`) does `switch (xo) { default: goto bad; }`, so opcode-59 words with `xo&31 in {28,29,30,31}` -- `fmsubs`, `fmadds`, `fnmsubs`, `fnmadds` -- and any other opcode-59 word reach `goto bad` (S2). `opcodes_ppc.h` defines only `PPC_59_FMADDS 29` and no constant for 28/30/31. `goto bad` sets `cpu->running = 0` (not `exit()`), which on a plain single-CPU run ends the process cleanly via S3, or drops into the debugger under `-V`/`-K`/a breakpoint.

- **The one premise that would make it false: that these words reach `goto bad`.** CONFIRMED by reading the decoder; no premise failure.
- The *other* premise the brief flags -- "gcc emits `fmadds` for ordinary float, so it is the most frequently executed instruction still in this set" -- I **measured and it does not hold for the kernel here** (see Q4): zero opcode-59 words in 1,197,838 instruction-slot words of `netbsd401-macppc-GENERIC`.

**H3 -- invalid `lwarx`/`stwcx.` form ends the process. REACHABLE from user state (finding true).**
Confirmed: the decoder keys on `xo = (iword >> 1) & 1023` (`:4614`), so bit 0 is dropped; cases `LWARX`/`LDARX`/`STWCX_DOT`/`STDCX_DOT` all route to `instr(llsc)` (`:4866-4872`). Inside `X(llsc)` (`:2276`), `rc = iw & 1` (`:2279`); a load form with `rc` set -> `fatal("ll: rc-bit set?"); exit(1)` (`:2305-2308`), a store form with `rc` clear -> `fatal("sc: rc-bit not set?"); exit(1)` (`:2331-2334`). These are unprivileged instructions, so one crafted word from user state ends the host.

- **The one premise that would make it false: that the decoder ignores bit 0, so the invalid `lwarx`-with-Rc=1 and `stwcx.`-with-Rc=0 reach `X(llsc)` and hit the exits.** CONFIRMED statically; no premise failure.
- One wording caveat on the brief's premise 2: "one word in an **ordinary** user program ends the emulator." These are **invalid instruction forms** (reserved bit 31 miscoded); a correct compiler never emits them, so it is one word in a *crafted or corrupted* program, not an ordinary one. The finding (user-reachable host abort) still holds.

## Q2 -- Which of the three dispositions is wrong? **ONE. H2.**

H1 and H3 are `exit(1)` -- an unconditional host-process abort right after `fatal()` (S1 confirms `fatal()` only prints and returns, so it is the `exit(1)`, not `fatal()`, that ends the process). Both are correctly HIGH, both reachable from the guest, neither a duplicate (H3's rc-bit exits are exactly the two `#216` left behind when it removed the memory-fault exits from the same function; H1's BAT exit is at most inside the `cpusexitsweep` *population* but was never individually triaged).

**H2 is the wrong disposition, on the duplicate + severity axes:**
1. **Duplicate.** `fmadds`/`fmsubs` are explicitly already recorded (`OUTSTANDING_BUGS.md:1712-1716`) and **gate 15 already has PEND rows for them** (`ppc_halt_probe.py:269-270`, class `PEND`, asserting they halt on purpose). The brief concedes this and claims novelty only for `fnmadds`/`fnmsubs` -- and those two genuinely have no individual record and **no gate-15 row** (I checked: the probe has no `fnmadds`/`fnmsubs` rows; it carries `fnmadd`/`fnmsub`, the *double* forms, marked FIXED by #344). But `fnmadds`/`fnmsubs` are the same opcode-59 FMA family the record already dispositions as deferred decode "out of #326 for round size alone."
2. **Severity.** `goto bad` -> `cpu->running = 0` is the *graceful* halt every undecoded instruction in the whole emulator produces; under `-V`/`-K`/a breakpoint it is recoverable into the debugger, and on a plain run it exits with status 0. H1/H3 are hard `exit(1)`. Grading H2 HIGH-and-new elevates two more members of an already-dispositioned, gate-asserted deferred-decode class to the crash tier that H1/H3 occupy. If "a single undecoded opcode halts the CPU" is HIGH, the entire decode backlog is HIGH, which is not how the project grades it.
- **The honest counter, stated because the brief asked me not to just ratify:** by the *letter* of the brief's severity rule, "stops it making progress" is itself a HIGH criterion, and `cpu->running=0` does stop progress. So H2 is not *factually* wrong -- the words do halt. My claim is narrower and is a grading-consistency claim: H2's disposition should be the deferred-decode class the project already uses for this family (a MED/deferred decode gap, `fnmadds`/`fnmsubs` folded into the existing `OUTSTANDING_BUGS.md:1712` entry and given gate-15 PEND rows), not a new HIGH defect alongside two genuine host aborts.

## Q3 -- What should a correction round do, and is the machinery available on THIS CPU?

First, the governing fact I measured: **this PPC model has no program/illegal-instruction interrupt.** `cpu_ppc.h:252-257` defines only DSI(0x3), ISI(0x4), EI(0x5), FPU(0x8), DEC(0x9), SC(0xc). There is no `PPC_EXCEPTION_PROG`/0x7. That is exactly the "missing exception model" the record alludes to, and it constrains option (5) per finding.

- **H1 -> (5) FAULT. AVAILABLE, and the smallest of the three.** Deliver a DSI (data) / ISI (instruction) block-protection violation, which the PEM mandates (`ppc_pem32_rev2_2001.txt:13312` and `:13334-13336`: "a block protection violation exception condition (DSI or ISI) is generated"; DSISR bit 4 / SRR1 bit 4 set). The machinery already exists **and is already used 25 lines below in the same function**: the page-translation no-match path at `memory_ppc.c:315-323` sets `SPR_DAR`/`SPR_DSISR` (with `DSISR_PROTECT = 0x08000000`, which exists) and calls `ppc_exception(DSI/ISI)`. The fix is to let the BAT `res==0` case fall through to that same delivery (with `DSISR_PROTECT` for a protection violation) instead of `fatal()+exit(1)`. Note the PEM carve-out at `:13495` -- `dcbt`/`dcbtst` must *not* fault on a block protection violation -- is already satisfied, because the decoder maps those to `instr(nop)` (`cpu_ppc_instr.c:4788,4790`) and they never translate.

- **H2 -> (7) IMPLEMENT. AVAILABLE.** The record's own judgment (no technical blocker; these are in the G4's instruction groups) points to decoding them, not faulting them. The double-precision handlers already exist (`X(fmadd)`/`X(fmsub)`/`X(fnmadd)`/`X(fnmsub)` at `cpu_ppc_instr.c:1836-2024`), and the single forms can alias their double forms exactly as `fadds`/`fmuls` do today (`X(fadds)` is `instr(fadd)`, `X(fmuls)` is `instr(fmul)` -- `:2144-2148`, `:1924-1928`). So it is the few-lines-each decode-plus-alias the record describes. **Option (5) is NOT available for H2** -- the faithful response to a truly-out-of-group op is a program interrupt, and this CPU models none; that is why the `fsqrt`/`fctid` sub-group genuinely "rides on the missing exception model" while the FMA sub-group does not.

- **H3 -> (1) DELETE the terminating call (treat as boundedly-undefined), following `#216`'s own precedent in this function.** The architecture (Book I 1.9.2 `ppc_uisa_book1_v201.txt:1107-1120`; PEM 4.1.3.2.2 `ppc_pem32_rev2_2001.txt:6856`) says an invalid form "either invokes the illegal instruction error handler (a program exception) or yields boundedly-undefined results." **Option (5) is NOT available** (no program interrupt modeled), so the remaining in-scope choice is to stop aborting the host: drop the two `exit(1)` calls and let the handler proceed (boundedly-undefined is explicitly permitted), the same move `#216` made for the two memory-fault exits in this exact function. A clean refinement is to **ignore the reserved record bit and execute the defined instruction** -- i.e., treat `lwarx`-with-Rc=1 as `lwarx` and `stwcx.`-with-Rc=0 as `stwcx.` -- which real hardware commonly does and which is within boundedly-undefined.

- **Is there a member the 7-item list does not name?** Essentially no, but H3 surfaces a hybrid worth naming explicitly: **"ignore the reserved/record bit and run the defined sibling instruction."** It is not cleanly (1) delete, (2) decline, or (4) accept-a-value -- it is "the behaviour is already defined and computed; just stop gating it on a reserved bit." It is the natural disposition for a reserved-bit invalid form and is the one I would pick for H3. Also worth noting for completeness: options (2)/(3)/(5) that *announce* or *fault* presuppose an exception or a refusal; for H2/H3 the real precondition is the absent program-interrupt model, so any "fault properly" plan for them is really "add `ppc_exception` program-interrupt support first," which is a larger round than either finding.

## Q4 -- Rank by what an OS in ordinary operation would actually meet (most likely first)

**H2 > H1 > H3**, with the measurement foregrounded because it cuts against the brief's own premise.

Static ELF census of `_images/netbsd401-macppc-GENERIC` (big-endian PPC32, `.text` = 4,791,352 bytes, **1,197,838 instruction-slot words scanned**):
- **opcode-59 (single-precision FP) words: 0.** Zero `fmadds`/`fnmadds`/`fadds`/`fmuls`/anything in opcode 59. So in THIS kernel, H2's "gcc emits `fmadds`... most frequently executed" is **not borne out** -- the kernel is built without single-precision FP (typical: kernels use soft-float / no FP). That is a measured refutation of the record's frequency claim, for the kernel.
- **`lwarx`/`stwcx.` words: 12, all well-formed** (`lwarx` bit31=0 x4; `stwcx.` bit31=1 x8). **Zero invalid forms.** H3 is never met by correct code, as expected.
- **`mtspr` to a BAT SPR (0x210-0x21f): 84** (plus 19 `mfspr`). The kernel programs BATs heavily and early, so H1's *precursor* code definitely executes; whether any of those 84 writes sets a `PP=00`/RO value that is then violated is not visible to a static scan.

Ranking rationale -- I read "an operating system in ordinary operation" as including the userspace it runs:
1. **H2 (`fmadds`/FMA family)** -- single-precision FMA is ubiquitous in userspace float code and gcc emits it, so across a *running* system it is by far the most likely of the three to be executed. Caveats, stated honestly: measured 0 in this kernel, and in GXemul macppc specifically the guest rarely reaches userspace (OF stall), so in *this emulator's practice* it may seldom be hit -- but the question asks about ordinary OS operation, where float math is the common case.
2. **H1 (BAT deny/RO + violation)** -- BAT programming is measured present and executes on every PPC boot (84 writes), but the trigger additionally needs a *restrictive* PP and a violating access, which is kernel-configuration-dependent and less common than ubiquitous float math. Ranked second on that conditional.
3. **H3 (invalid `lwarx`/`stwcx.` form)** -- an invalid instruction encoding; never produced by a correct toolchain (measured 0), so essentially never met in ordinary operation. It matters only against a buggy or malicious guest. Last.

Basis: the ELF census above (measured presence/absence in the one PPC guest I can read), plus the architectural base rates (float everywhere; restrictive BATs occasional; invalid forms never in correct code).
