5. **Recommended bounded correction: member 3, applied to the unsupported B-bit request, while accepting the other serviced control bits.**

   The proposed contract is: retain effective byte order; make B read back consistently with it; announce a declined change once per CPU with a `(once)` marker; continue processing the other serviced control bits. This combines the manual’s fixed-endian latitude with the existing control handler’s independent MMU and other-bit processing (`_scratchpad/ddi0100i.txt:28079–28081`; `_scratchpad/ddi0406.txt:135297–135298`; `src/cpus/cpu_arm_coproc.c:134–183`).

   | Member | Assessment |
   |---|---|
   | **1 — delete termination** | Insufficient alone: the handler has already stored the requested B, while effective byte order remains unchanged. Readback and execution would disagree (`src/cpus/cpu_arm_coproc.c:95,135,157–177`). |
   | **2 — silently decline** | Could preserve fixed-endian semantics if state/readback are corrected, but provides no notice of the unsupported request. The same architectural qualification as member 3 applies. |
   | **3 — decline and announce once** | Recommended containment disposition. Decline B’s unsupported change, preserve truthful readback, and retain independently serviced bits. |
   | **4 — accept an already-correct operation** | Fits a matching B request. It does not fit a mismatching request: no endian switch is implemented in the control block (`src/cpus/cpu_arm_coproc.c:134–184`). |
   | **5 — architectural fault** | Machinery exists on ARM, but an unsupported emulator feature does not itself make an otherwise legal privileged c1 write architecturally undefined. It is relevant to the separate privilege violation. |
   | **6 — invented backing store** | Storing a B value disconnected from execution merely exposes fictitious state; that is the inconsistency left by member 1 (`src/cpus/cpu_arm_coproc.c:95,135,157–177`). |
   | **7 — implement switching** | Required if the intended CPU contract promises software-controlled switching. This is broader work involving instruction decoding, cached handlers and memory behavior (`src/cpus/cpu_arm_instr.c:4060–4063,4765–4773,4791–4838`). |

   **Fault delivery exists.** The nearest coprocessor-family precedent is `"arm_exception(cpu, ARM_EXCEPTION_UND);"` in `arm_cdp()` (`src/cpus/cpu_arm.c:2674–2679`). Delivery saves UND status, selects exception mode and sets the vector (`:669–698,714–733`). The enumerated UND vectors are **`0x00000004`** with V clear and **`0xffff0004`** with V set (`src/include/cpu_arm.h:116–123`; `src/cpus/cpu_arm.c:731–732`). The missing-handler MCR/MRC branch has its exception call commented out; it is not evidence that ARM lacks delivery (`src/cpus/cpu_arm.c:2656–2662`).

   The nearest nonterminating **CP15-write** precedent is ID/cache-type writes: they diagnose and continue without changing those registers (`src/cpus/cpu_arm_coproc.c:67–89`). The per-instance house latch is clear in Footbridge: `"else if (!d->warned_irq_status_w)"`, latch assignment, then a diagnostic containing `"(once)"` (`src/devices/dev_footbridge.c:570–581`). ARM would need CPU-local warning storage; its existing `warned_undef` is function-static, not per CPU (`src/include/cpu_arm.h:136–288`; `src/cpus/cpu_arm_instr.c:4698–4710`).

   **A disposition missing from the list is partial acceptance/normalization.** The existing TTB write stores, masks unsupported low bits, and continues (`src/cpus/cpu_arm_coproc.c:186–197`). The proposed control policy uses this distinction: declining B need not discard a simultaneous, otherwise supported MMU change. That precedent demonstrates the pattern; the manual passages supply the architectural qualification.

   The #378 invariant is real: the optimized LDM/STM installation reads byte order at translation time (`src/cpus/cpu_arm_instr.c:4791–4838`). Preserving effective byte order preserves that assumption. A full-switch design must not assume address-cache invalidation alone rebuilds instruction handlers; item 7 documents that error.

6. **Regression observations should distinguish survival, state consistency and preserved neighboring behavior.**

   These are proposed observations, not measured results:

   | Channel | Current mismatch behavior | Proposed member-3 behavior |
   |---|---|---|
   | Process continuation | `exit(1)` terminates; subsequent guest observations cannot execute. | Execution continues. |
   | Diagnostic | `"ERROR: Trying to switch endianness. Not supported yet.\n"` | A bounded decline diagnostic containing `(once)`. |

   | Effective byte order | The handler does not change it before exiting. | Remains unchanged. |
   | Exception vector | The mismatch path delivers none. | None for the proposed privileged fixed-endian policy. |
   | Repeated declined requests | First request ends the process. | Continuation remains possible; the CPU’s warning does not repeat. |

   Current behavior is established by `src/cpus/cpu_arm_coproc.c:95,134–177`; the proposed warning lifetime follows the per-instance precedent at `src/devices/dev_footbridge.c:570–581`.

   There is an additional readback observation to specify explicitly: big-endian startup can currently report B clear. A truthful fixed-endian contract should report B set even before a control write; normalization only on rejected writes would leave that inconsistency (`src/cpus/cpu_arm.c:128–137`; `src/machines/machine_test.c:176–183`; `src/cpus/cpu_arm_coproc.c:95`).

   Neighboring behavior to preserve includes matching-B control writes, control reads, auxiliary-control reads/writes, and independently serviced MMU changes—including a combined request whose B change is declined (`src/cpus/cpu_arm_coproc.c:91–155,179–184`). Conditional instructions whose condition fails must remain inert (`src/cpus/cpu_arm_instr.c:132–199,4980`).

   Existing little- and big-endian load/store behavior should remain unchanged because effective byte order remains fixed. The existing endian probe describes both configurations and warm/cold multi-transfer controls, but does not establish runtime B-switch support (`regress/arm_endian_probe.py:18–40`). No such checks were run here.

   If privilege enforcement is corrected in the same round, user c1 access has a **separate oracle**: Undefined Instruction delivery before control mutation. That expectation comes from `_scratchpad/ddi0100i.txt:27724–27731`, with delivery supported by `src/cpus/cpu_arm.c:669–733`. It should not be confused with the privileged fixed-endian decline policy.

7. **Some records require correction; the central fixed-byte-order dependency remains valid.**

   **The #378 source comment attributes the wrong effect to address-cache invalidation.** It says:

   > “invalidate_translation_caches(  
   > cpu, 0, INVALIDATE_ALL) so cached ic->f handlers are  
   > re-picked”  
   > `src/cpus/cpu_arm_coproc.c:170–172`

   That call’s `INVALIDATE_ALL` branch invalidates address-translation entries and returns (`src/cpus/cpu_dyntrans.c:1276–1288`). The ARM helper clears mappings, including `"cpu->cd.DYNTRANS_ARCH.phys_page[index] = NULL;"`; it does not reset physical cached instruction handlers (`:1015–1035`). A later lookup can find the existing physical page and reuse `"&ppp->ics[0]"` (`:765–807,830–833`).

   Corrected sentence:

   > “An endian switch requires rebuilding cached instruction translations as well as reviewing address translations; `invalidate_translation_caches(cpu, 0, INVALIDATE_ALL)` clears address mappings and does not itself cause cached `ic->f` handlers to be re-picked.”

   ARM binds address and code invalidation separately (`src/cpus/cpu_arm.c:115–117`). Actual handler reset appears in the physical-address branch of code invalidation as `"ppp->ics[i*m + j].f = TO_BE_TRANSLATED;"` (`src/cpus/cpu_dyntrans.c:1339–1445`). Merely substituting that function with `INVALIDATE_ALL` is not established as sufficient: its inspected ALL handling clears virtual associations (`:1447–1482`).

   **“This exit is LOAD-BEARING” needs a more precise invariant.** The current exit and translation-time dependency are correctly described (`src/cpus/cpu_arm_coproc.c:163–174`; `src/cpus/cpu_arm_instr.c:4802–4823`). Termination itself is not necessary if effective byte order stays fixed. For a member-3 correction, the replacement should say:

   > “Cached translation-time byte-order decisions require effective byte order to remain fixed. Unsupported B changes are declined while preserving that invariant.”

   **The changelog wording is broader than the actual condition.** It says “the CP15 c1 B-bit write calls `fatal()` and **exits**” (`CHANGELOG.md:30090`). In context it means an endian-switch request; read literally, it also includes matching-B writes. Precise replacement:

   > “A CP15 c1 write whose B bit disagrees with `cpu->byte_order` calls `fatal()` and exits.”

   **The ISTEER record is false as written.** It describes both load and store arms, then says the case “carries **no `fatal()` and no `exit()`**” (`OUTSTANDING_BUGS.md:18686–18688`). The nonzero write still exits (`src/cpus/cpu_arm_coproc.c:315–322`). Corrected sentence:

   > “The ISTEER read arm returns the modeled value without diagnostics or exit; a nonzero ISTEER write still terminates.”

   **The older location summary is stale and misclassified.** “`cpu_arm_coproc.c` CP15 writes 165/252/407/518” appears at `OUTSTANDING_BUGS.md:2688`. Replace it with:

   > “Remaining coprocessor exits cover CP15 PC operands, byte-order mismatch and nonzero PID; CP6 nonzero interrupt-steering writes, interrupt-source writes and unknown selectors; and CP14 unknown selectors.”

   The supporting live sites are enumerated in item 4. Conversely, the old INTEN exit excerpt is explicitly superseded by “SHIPPED as `#526`”; it must not be counted as live (`OUTSTANDING_BUGS.md:18674–18684,19488–19494`; `src/cpus/cpu_arm_coproc.c:310–314`).
