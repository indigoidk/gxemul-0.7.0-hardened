CODEXPACK_DOSSIER_PPCFUSED_ALIVE
VERDICT: finding TRUE -- disposition member 7 -- the single-precision fused forms reach the CPU-stop path.

All repository citations below refer to **`db8b1a33` in `GXEMUL-SEC`**, not the working tree. Manual citations refer to the permitted on-disk `_scratchpad` files. These are static findings; no build, test, emulator execution, patch, or file write was performed.

**1. TRUE: instruction fetch → missing decode → CPU stop**

The affected forms are explicitly:

| Instruction | Primary opcode | Extended selector | Rc |
|---|---:|---:|---|
| `fmsubs`, `fmsubs.` | 59 | 28 | 0, 1 |
| `fmadds`, `fmadds.` | 59 | 29 | 0, 1 |
| `fnmsubs`, `fnmsubs.` | 59 | 30 | 0, 1 |
| `fnmadds`, `fnmadds.` | 59 | 31 | 0, 1 |

The architecture lists these selectors in `_scratchpad/ppc_uisa_book1_v201.txt:11755`, `:11757`, `:11759`, `:11761`. The source defines `PPC_59_FMADDS` as `29`, but has no corresponding opcode-59 definitions for selectors `28`, `30`, `31`: `src/include/opcodes_ppc.h:231–236`.

The execution path is:

1. **Guest instruction address.** The translator derives the instruction address from the current translation entry, writes `cpu->pc = addr`, and aligns the fetch address. The exact assignments are at `src/cpus/cpu_ppc_instr.c:4083–4090`.

2. **Guest instruction bytes enter.** With a cached page, the fetch is:
   > `memcpy(ib, page + (addr & 0xfff), sizeof(ib));`

   Otherwise it calls:
   > `cpu->memory_rw(cpu, cpu->mem, addr, ib, sizeof(ib), MEM_READ, CACHE_INSTRUCTION)`

   The finding’s path requires that fetch to succeed. A failed uncached fetch instead reaches a separate `exit(1)`. `src/cpus/cpu_ppc_instr.c:4110–4119`.

3. **Instruction word interpretation.**
   > `iword = *p;`  
   > `iword = BE32_TO_HOST(iword);`

   These are `src/cpus/cpu_ppc_instr.c:4125–4127`.

4. **Debugger interception, if configured.** Before decoding, the included dyntrans head checks host-configured breakpoints. A matching, non-ignored breakpoint can enter the debugger before instruction execution. This is an execution prerequisite, not acceptance of the instruction. `src/cpus/cpu_ppc_instr.c:4130–4132`; `src/cpus/cpu_dyntrans.c:1799–1848`.

5. **Primary opcode selection.**
   > `main_opcode = iword >> 26;`  
   > `switch (main_opcode) {`

   The selected arm is `case PPC_HI6_59:`. `src/cpus/cpu_ppc_instr.c:4139–4141`, `:5176`.

6. **Extended opcode and record bit.**
   > `xo = (iword >> 1) & 1023;`  
   > `rc = iword & 1;`  
   > `rc_f = NULL;`  
   > `switch (xo & 31) {`

   The source also extracts destination, FRA, FRB, and FRC fields, but the unsupported path never dispatches an arithmetic handler. `src/cpus/cpu_ppc_instr.c:5177–5197`.

7. **No matching arithmetic case.** The accepted selectors are explicitly `18` (`fdivs`), `20` (`fsubs`), `21` (`fadds`), and `25` (`fmuls`), with record twins. `src/include/opcodes_ppc.h:232–235`; `src/cpus/cpu_ppc_instr.c:5198–5215`.

   Each studied selector—`28`, `29`, `30`, `31`—therefore reaches:
   > `default:/* Use all 10 bits of xo: */`  
   > `switch (xo) {`  
   > `default:goto bad;`

   `src/cpus/cpu_ppc_instr.c:5216–5219`. Both Rc values follow this route **before** the record-form substitution at `:5221–5226`.

8. **Common stop, with the read-ahead qualification.** The tail is included at `src/cpus/cpu_ppc_instr.c:5430–5432`. Its `bad:` path first does:
   > `ic->f = TO_BE_TRANSLATED;`  
   > `if (cpu->translation_readahead)`  
   > `return;`

   Thus speculative translation alone does not stop the CPU. On actual execution, it sets `about_to_enter_single_step`, emits `"UNIMPLEMENTED instruction at …"`, optionally disassembles, and executes:
   > `cpu->running = 0;`

   It then resets the debugger and redirects execution to `nothing_call`. `src/cpus/cpu_dyntrans.c:1983–2024`.

This is a **CPU-progress failure**, supporting the supplied HIGH rationale. The selected path contains a CPU stop, not a host `exit()`, and does not deliver an architectural exception. `src/cpus/cpu_dyntrans.c:1994–2024`. The negative single forms are absent from the specific pending list and regression rows examined; the broader halt class was already recorded. `OUTSTANDING_BUGS.md:1705–1716`; `regress/ppc_halt_probe.py:229–280`.

**3. What the hardware specifies**

These are user-level instructions: each entry says **“Architecture Level UISA”**, and the manual defines UISA as the base user-level/problem-state instruction set. `_scratchpad/ppc_pem32_rev2_2001.txt:1512–1522`, `:19633`, `:19845`, `:20269`, `:20439`.

Fusion is explicit:

> “These instructions combine a multiply and an add operation without an intermediate rounding operation.”

`_scratchpad/ppc_uisa_book1_v201.txt:6427–6431`.

For `fmadds`, the manual specifies FRA×FRC+FRB and states:

> “The result is rounded to single-precision under control of the floating-point rounding control field RN of the FPSCR and placed into frD.”

`_scratchpad/ppc_pem32_rev2_2001.txt:19613–19615`. The corresponding subtraction rule is FRA×FRC−FRB at `:19825–19827`.

For `fnmadds`:

> “The result is rounded to single-precision under control of the floating-point rounding control field RN of the FPSCR, then negated and placed into frD.”

`_scratchpad/ppc_pem32_rev2_2001.txt:20246`; the equivalent `fnmsubs` requirement is at `:20416`.

Therefore the negative forms require **round, then negate**. The manual separately preserves a propagated QNaN’s sign, specifies zero sign for a newly generated invalid-operation QNaN, and preserves a quieted SNaN’s sign. `_scratchpad/ppc_pem32_rev2_2001.txt:20249–20251`, `:20419–20421`.

The rounding modes are explicitly `00` nearest, `01` toward zero, `10` toward positive infinity, and `11` toward negative infinity. `_scratchpad/ppc_uisa_book1_v201.txt:5040–5043`. Single arithmetic produces a single-format result represented in the double-format FPR; status describes that single result. Its operands must be representable in single format for the specified arithmetic result to be defined. `_scratchpad/ppc_uisa_book1_v201.txt:4884–4890`, `:5268–5276`.

For record forms:

> “For all floating-point instructions in which Rc=1, CR Field 1 … is set to the Floating-Point exception status”

copied from FPSCR. The copied fields are **FX, FEX, VX, OX**. `_scratchpad/ppc_uisa_book1_v201.txt:1345–1368`.

The listed affected FPSCR fields include **FPRF, FR, FI, FX, OX, UX, XX, VXSNAN, VXISI, VXIMZ**, with invalid-enable qualifications. `_scratchpad/ppc_pem32_rev2_2001.txt:19617–19629`, `:19829–19841`, `:20253–20265`, `:20423–20435`.

With FP disabled, hardware instead takes the floating-point-unavailable exception:

> “an attempt is made to execute a floating-point instruction … and … MSR[FP] = 0”

with execution resuming at offset `0x00800` from the MSR[IP]-selected base. `_scratchpad/ppc_pem32_rev2_2001.txt:12057`, `:12084`.

**5. The option set**

**Member 7—implement the missing behavior—fits.** These are architected arithmetic operations; the current path never calculates their result. The closest same-CPU acceptance precedent is the double fused family, decoded with record twins at `src/cpus/cpu_ppc_instr.c:5261–5274` and implemented at `:1836–1921`, `:1938–2079`.

| Member | Assessment for this finding |
|---|---|
| 1 — Delete termination | Removing the stop supplies neither arithmetic nor architectural completion; the current failure path resets translation and diverts execution to `nothing_call`. `src/cpus/cpu_dyntrans.c:1987–2024`. |
| 2 — Decline silently | Leaves a valid arithmetic instruction without its required result and status. Manual requirements are cited in item 3. |
| 3 — Decline, announce once | Same semantic failure. The house latch exists, for example `d->warned` plus `"declined. (once)"` at `src/devices/dev_dreamcast_gdrom.c:734–741`; it does not implement arithmetic. |
| 4 — Accept existing correct result | No result exists on this path. Merely selecting a double handler would also miss required single rounding. `src/cpus/cpu_ppc_instr.c:5216–5219`, `:1990–2013`. |
| 5 — Architectural fault | Appropriate when the architecture requires one, including FP-unavailable; not a substitute for a supported, FP-enabled arithmetic operation. Existing machinery and limits are below. |
| 6 — Invent backing store | Not applicable: destination FPR storage already exists, as used by the double handlers. `src/cpus/cpu_ppc_instr.c:5271–5273`, `:2012–2013`. |
| 7 — Implement | Supplies the absent decode and required arithmetic/status behavior. |

There is an additional disposition absent from the list: **stop emulated execution and enter the debugger**. That is the existing `bad` policy and the separately implemented breakpoint behavior. `src/cpus/cpu_dyntrans.c:1846–1848`, `:2002–2024`.

The implementation requirements, rather than a patch, are:

- **Operand routing and record handling already have precedents.** The double fused handlers receive destination/FRA pointers and the instruction word, from which they read FRB/FRC. `FDOT` checks availability before the base handler, then copies FPSCR exception status into CR1. `src/cpus/cpu_ppc_instr.c:205–206`, `:1838–1850`, `:1940–1952`, `:5271–5273`; `src/cpus/cpu_ppc.c:1853–1856`.
- **Double FMA handlers are not complete numerical templates for the singles.** They call host `fma()` and store `IEEE_FMT_D`; the negative variants negate its result. They do not read guest RN for fused arithmetic. `src/cpus/cpu_ppc_instr.c:1860–1876`, `:1902–1918`, `:1990–2013`, `:2056–2079`.
- **Single rounding helpers exist.** `ppc_single_narrow` rounds a finite double pattern according to the supplied mode; `ppc_single_widen` produces the FPR representation. `frsp` demonstrates their RN-controlled composition. `src/cpus/cpu_ppc_instr.c:1353–1471`, `:1476–1503`, `:1600–1602`.
- **Narrowing an already rounded ordinary double result is insufficient.** The shared helper documentation describes the lost-residue problem and supplies `ieee_sum_round_to_odd`, including signed cancellation-zero handling. `src/core/float_emul.c:722–759`, `:1209–1254`.
- **An existing fused-single numerical precedent exists on SH.** Its `fmac` comment says the product of single operands is exact in double; its handler uses the round-to-odd sum followed by mode-aware single storage. This supports reuse for finite, single-representable inputs, without establishing PPC-specific status or NaN correctness. `src/cpus/cpu_sh_instr.c:3533–3554`.
- **PPC-specific obligations remain:** guest RN, single-result representation, post-round negation, signed zero, NaN rules, final-result classification, required sticky flags, and record-form CR1. The manuals cited in item 3 specify these; existing cause classification and summary machinery are at `src/cpus/cpu_ppc_instr.c:151–180` and `src/cpus/cpu_ppc.c:1890–1951`.

Exception delivery is **partly present on this CPU**. `ppc_exception()` saves SRR0/SRR1, clears EE/RI/PR, selects the vector, and updates execution pointers. `src/cpus/cpu_ppc.c:318–345`. For `PPC_EXCEPTION_FPU`, the source’s address choices are explicitly **`0x00000800` with IP clear** and **`0xfff00800` with IP set**, from `src/include/cpu_ppc.h:255` and `src/cpus/cpu_ppc.c:337–339`.

That does not establish complete FP exception semantics. The cause helper explicitly states:

> “This never touches FPCC, never consults the enable bits, and never traps.”  
> “Enable-driven result suppression and trap delivery are a separate round.”

`src/cpus/cpu_ppc.c:1941–1942`. A correction must distinguish existing unavailable-exception entry from the missing enabled-arithmetic trap/suppression behavior.
