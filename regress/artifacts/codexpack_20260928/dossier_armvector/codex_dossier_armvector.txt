**The disk manuals support architectural exception delivery, not host recursion.** DDI 0100I states:

> “A Prefetch Abort exception is generated if the processor tries to execute the invalid instruction.”

That is `_scratchpad/ddi0100i.txt:2185-2188`. Its entry pseudocode includes:

> `R14_abt = address of the aborted instruction + 4`  
> `SPSR_abt = CPSR`  
> `CPSR[4:0] = 0b10111 /* Enter Abort mode */`

See `_scratchpad/ddi0100i.txt:2194-2208`. It lists the destinations **`0xFFFF000C`** and **`0x0000000C`** at `:2212-2218`.

The ARMv7 manual explicitly recognizes vector-fetch faults:

> “An instruction fetch from an exception vector address that generates an MMU fault, MPU fault, or synchronous external abort cannot generate an address matching Vector catch debug event.”

That is `_scratchpad/ddi0406.txt:108212-108213`. Its ordinary Abort entry ends with `BranchTo(ExcVectorBase() + vect_offset);` (`:59240-59272`). DDI 0100I also warns that nesting the same exception type puts the exception mode’s SPSR “in danger of being corrupted” (`_scratchpad/ddi0100i.txt:9506-9512`).

The defensible inference is that another attempted instruction fetch can produce another architectural abort and overwrite banked state. The checked passages do **not** specify “already in Abort mode → stop the CPU,” and they do not say “loop forever” verbatim. A separate processor-specific lockup rule was **not checked**; none was located in these passages. The ARMv7 security and virtualization branches are broader than this emulator’s implementation (`_scratchpad/ddi0406.txt:59195-59238`).

**Member 7 fits the correction; member 5 remains the access disposition.** ARM already attempts the architectural fault at `src/cpus/memory_arm.c:268-273`, and its state-delivery machinery exists at `src/cpus/cpu_arm.c:616-734`. The missing behavior is safe, nonrecursive delivery and resumption.

The nearest same-access precedent is `#193`:

> “an L2 page-table page outside mapped RAM must fault the guest, not exit() the host.”

It selects `FAULT_TRANS_P` and branches to `exception_return` (`src/cpus/memory_arm.c:169-174`). This proves the intended disposition, but it shares the defective tail and therefore does not prove safe nested delivery.

| Member | Assessment |

| 1 — delete termination | Insufficient: the ARM failure occurs before the generic exit is reached. |
| 2 — silently decline | Would suppress the required architectural abort. |

These assessments follow the existing failure contract and exception path (`src/cpus/memory_arm.c:103-112,257-276`; `src/cpus/cpu_arm.c:730-733`). They are design recommendations, not implemented changes.

Simply removing `quick_pc_to_pointers` is not a complete design: callers depend on exception PC state and instruction-dispatch pointers being coherent (`src/cpus/cpu_arm.c:725-733`; `src/cpus/cpu_dyntrans.c:830-833`). The correction should return control to a bounded dispatcher, retain the fault, and permit another architectural fetch attempt without growing the host call chain. A permanently faulting guest must still permit scheduling and debugger control.

The list does not expressly name **contained CPU suspension** or **deferred exception delivery**. Suspension is a possible emulator containment policy, but no checked ARM manual passage establishes it as the hardware result. Deferred delivery describes the implementation mechanism rather than a different access disposition.

The house latch is illustrated by `src/devices/dev_footbridge.c:573-580`: it tests an instance field, sets it, emits a diagnostic containing **`(once)`**, and returns without ending the process. Its fields are at `:86-95`. That precedent supports bounded diagnostics if needed; it does not justify dropping the ARM exception.
