**3. Hardware behavior**

The supplied manuals do **not** support “both cases must take an illegal-instruction exception.”

The older manual says:

> “Attempting to execute an invalid form of an instruction either invokes the illegal instruction error handler (a program exception) or yields boundedly-undefined results.”

It explicitly includes a reserved bit shown as zero being encoded as one. Its load and store diagrams show the required terminal values. (`_scratchpad/ppc_pem32_rev2_2001.txt:6856–6857,22738–22742,27667–27671`.)

Book I v2.01 instead states:

> “Reserved fields in instructions are ignored by the processor.”

It defines `/` as a reserved field. Book II’s diagrams use that designation for the low bit of **both `lwarx` and `ldarx`**. Under this edition, that load bit must be ignored. (`_scratchpad/ppc_uisa_book1_v201.txt:432–439`; `_scratchpad/ppc_vea_book2_v201.txt:1259–1266`.)

Store Conditional is treated differently. Book I explicitly classifies a disagreement with its specified fields as an invalid form, while Book II’s store diagrams require the terminal value one. Invalid forms may invoke the illegal-instruction handler **or** yield boundedly undefined results. (`_scratchpad/ppc_uisa_book1_v201.txt:1116–1128`; `_scratchpad/ppc_vea_book2_v201.txt:1298–1309`.)

“Boundedly undefined” constrains outcomes to those achievable through defined instructions starting from the preceding machine state. Treating a malformed instruction as an appropriate valid instruction is a possible inference from that definition—not an explicitly prescribed normalization rule. (`_scratchpad/ppc_pem32_rev2_2001.txt:48039`; `_scratchpad/ppc_uisa_book1_v201.txt:451–465`.)

For a chosen Program-exception disposition, the older manual specifies the excepting instruction’s address in SRR0, the illegal-instruction cause in SRR1, and execution at offset `0x00700` from the applicable base. Book III v2.01 likewise specifies the Program vector, saved instruction address, and illegal-instruction cause. (`_scratchpad/ppc_pem32_rev2_2001.txt:12026–12045`; `_scratchpad/ppc_oea_book3_v201.txt:3906–3918,3962–3963`.)

Exact manual-edition applicability to **each emulated CPU model is not checked**. The 2005 combined manual also contains tension between excluding reserved fields and retaining the reserved-zero example; it should not be used to erase the clearer edition distinction above. (`_scratchpad/ppc_pem_32and64_2005.txt:6229–6230`.)

**5. Disposition**

**Member 7 is the recommended complete design:** implement the applicable instruction-validity policy, accept the reserved load field where required, and provide a proper guest Program-exception path for invalid forms selected to fault. Choosing that permitted exception behavior is a design decision; the manuals do not uniquely mandate it.

| Member | Assessment |
|---|---|
| **1 — Delete terminating calls** | Removing only `exit` leaves the diagnostics and falls into normal LL/SC effects. That is an implicit acceptance policy, not a complete validity decision. (`src/cpus/cpu_ppc_instr.c:2304–2374`.) |
| **2 — Decline silently** | A blanket no-op is unsuitable for a load whose reserved field must be ignored and whose load/reservation effects must occur. (`_scratchpad/ppc_uisa_book1_v201.txt:432–433`; `_scratchpad/ppc_vea_book2_v201.txt:1272–1286`.) |
| **3 — Decline and announce once** | A possible documented fallback for forms assigned bounded behavior, but not a substitute for required reserved-bit acceptance. PPC needs new per-CPU latch state for the requested idiom. |
| **4 — Accept existing computation** | Fits the reserved load-bit case. Applying it to invalid forms requires an explicit bounded-behavior policy, rather than claiming a uniquely specified result. |
| **5 — Deliver an exception** | Generic PPC entry exists, but complete Program/illegal-instruction handling is missing. |
| **6 — Invent backing storage** | Does not address instruction validity; the handler already uses the memory subsystem and reservation state. (`src/cpus/cpu_ppc_instr.c:2309–2372`.) |
| **7 — Implement missing behavior** | Covers the architecture distinction and the missing exception semantics together. |

The existing foundation is `ppc_exception()`:

- Saves `cpu->pc` into SRR0 and constructs SRR1.
- Changes execution state.
- Selects a vector and redirects instruction pointers.

Those actions are at `src/cpus/cpu_ppc.c:318–345`. However, the declared exception set enumerates **DSI, ISI, EI, FPU, DEC, SC**, with no Program entry, and the checked PPC implementation has no dedicated illegal-instruction cause handling. (`src/include/cpu_ppc.h:251–257`; `src/cpus/cpu_ppc.c:318–345`.)

A new synchronous exception also needs the **actual offending instruction PC**. The FPU exception macro reconstructs it before calling `ppc_exception`; LL/SC currently does not. Thus simply inserting an exception call would leave a cached-execution correctness problem. (`src/cpus/cpu_ppc_instr.c:215–225,2276–2374`; `src/cpus/cpu_ppc.c:321`.)

Nearest precedents:

- **Same handler:** #216’s memory-failure returns preserve continuation through whatever fault processing already occurred. (`src/cpus/cpu_ppc_instr.c:2309–2314,2357–2362`.)
- **Same CPU, unsupported instruction:** `mtdcr` diagnoses and assigns `instr(nop)` without stopping. Its diagnostic is not latched. (`src/cpus/cpu_ppc_instr.c:4896–4899`.)
- **House per-instance latch:** fbctrl uses `if (!d->warned_port)`, announces `"the selector is unchanged (once)"`, and sets the latch. (`src/devices/dev_fbctrl.c:120–135`.)
- PPC’s existing SPR-warning bitmap is **process-global**, not per CPU. (`src/cpus/cpu_ppc.c:1746–1758,1789–1794`.)

The list omits **stop the emulated CPU while retaining the debugger/process**. The shared `bad` path implements precisely that disposition. It would not satisfy guest-execution continuity. (`src/cpus/cpu_dyntrans.c:2002–2024`.)

**6. Regression observations**

These are proposed observations, not test results.

| Case | Before correction | Expected after the recommended design |
|---|---|---|
| Invalid form assigned Program-exception behavior | Existing Rc diagnostic, followed by process exit status 1 | Host remains alive; guest exception entry exposes the offending PC and illegal-instruction cause |
| Reserved load field assigned ignore semantics | Existing load-side diagnostic and process exit | Ordinary load result and reservation establishment; no invalid-form exception |
| Legal load or conditional store | Existing normal behavior | Same register, memory, CR, and reservation behavior |
| Existing operand-memory failure | Handler returns after unsuccessful access | Preserve that behavior; do not restore a host exit |

The before evidence is `src/cpus/cpu_ppc_instr.c:2304–2333`. Normal effects are at `src/cpus/cpu_ppc_instr.c:2317–2328,2342–2372`; exception expectations come from the manual passages cited above.

For a chosen invalid-form exception, the operand-memory transaction must not occur before the validity decision. Normal operand effects currently occur after the Rc checks. Exception-state changes are expected; ordinary destination-register or conditional-store success effects are not. (`src/cpus/cpu_ppc_instr.c:2304–2372`.)

The legal neighbors that must remain supported are:

- `lwarx` and `stwcx.` with their defined fields.
- `ldarx` and `stdcx.` on models supporting those instructions.
- Base-register-zero and nonzero address formation.
- Successful reservation matching, absent reservation, and the model’s existing mismatched-reservation failure behavior.
- Both byte-order branches, load destination updates, store CR updates, and reservation clearing.

These paths are enumerated in `src/cpus/cpu_ppc_instr.c:2283–2372`. Hardware load/store effects are described at `_scratchpad/ppc_vea_book2_v201.txt:1272–1293,1344–1364`.

A regression must distinguish **host survival**, **guest exception entry**, and **ordinary fall-through**. Surviving in a stopped CPU/debugger state is a different observation. Guest execution following an exception depends on the guest handler; it cannot be promised merely because the host survives. (`src/cpus/cpu_dyntrans.c:2002–2024`; `src/cpus/cpu_ppc.c:337–344`.)
