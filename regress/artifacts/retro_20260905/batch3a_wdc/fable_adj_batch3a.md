## Q1 — THE #341 BE ODD-TAIL DEFECT: CONFIRMED

Read: `static uint64_t wdc_get_inbuf` returns `(uint64_t) -1` on `inbuf_head == inbuf_tail` with the `return` outside the latch (as its comment demands). `case wd_data:	/*  0: data  */` assembles exactly as the brief quotes; `odata` is `uint64_t` (`DEVICE_ACCESS(wdc)`, `uint64_t idata = 0, odata = 0;`). `src/core/memory.c` `^void memory_writemax64`: LE writes `buf[i] = data & 255` low byte first; BE writes `buf[len-1-i]`, so for `len == 2` `buf[0]` receives bits 15:8. No `MEM_PCI_LITTLE_ENDIAN` is in play: `PCIINIT(piix4_ide)` registers `"wdc addr=0x... irq=..."` with no `pci_little_endian=1`, and dev_wdc branches on `cpu->byte_order` directly.

Enumerated, with e = 2^64-1 (the empty pop) and v the last valid byte:

| access | arm | odata (mod 2^64) | bytes the guest sees |
|---|---|---|---|
| 2-byte, 1 valid | LE | v + (e<<8) = v - 256 -> low16 `0xFF00|v` | `[v, 0xFF]` — intact, 0xFF pad |
| 2-byte, 1 valid | BE | (v<<8) + e = (v<<8) - 1 | `[v-1, 0xFF]` — **valid byte decremented** |
| 2-byte, v=0x00 | BE | 0xFFFF | `[0xFF, 0xFF]` — 0x00 -> 0xFF |
| 4-byte, 1 valid | LE | v - 0x1010100 -> low32 `0xFEFEFF00|v` | `[v, 0xFF, 0xFE, 0xFE]` — intact |
| 4-byte, 1 valid | BE | (v<<24) - 0x10101 | `[v-1, 0xFE, 0xFE, 0xFF]` |
| 4-byte, valid 0x12 0x00 | BE | 0x11FFFEFF | `[0x11, 0xFF, 0xFE, 0xFF]` — **two valid bytes altered** (borrow through a zero) |

On LE the shifted sentinel has zero low bits so it can only pollute padding; on BE the shift-then-add is a subtraction of 1 from the accumulator and borrows into the payload. **The brief's premise "Astra wrote 0x23ff; the value differs" is a misreading, not a correction.** `^static void row_odd_width` queues `payload[36]` where `payload[i] = i`, i.e. **0x24**: (0x24<<8) - 1 = 0x23ff, exactly Astra's number; the brief's 0x22ff is for its own v = 0x23. Both are right; they used different inputs.

Reachability, confirmed by reading: `machine_evbmips.c` `MALTA (evbmips, big endian)` sets `cpu->byte_order = EMUL_BIG_ENDIAN`; the wdc arrives via `bus_pci.c` `^PCIINIT(piix4_ide)` whenever a `DISKIMAGE_IDE` exists. Odd lengths come from `case SCSICMD_INQUIRY:` (`retlen = xferp->cmd[4]`, minimum 36, no rounding). Note also `case wd_cyl_lo:`/`case wd_cyl_hi:` report `atapi_len & 255` / `>> 8` **unpadded**, so the guest is told an odd byte count — a real ATAPI device transfers whole words and reports an even count (BELIEVED, no spec on disk). Whether a real driver pops the tail is therefore driver-dependent: the in-tree OpenBSD 2.2 `isa/wdc.c` does `bus_space_read_raw_multi_2(iot, ioh, wd_data, ..., len)` with the odd `len`, and whether that pops ceil or floor of len/2 halfwords is arch-specific. **Cheap tell for the round: the `[ wdc: WARNING! someone is reading too much from the wdc inbuf! ]` line in a `maltabe` boot log with an ATAPI image proves a real driver pops the tail.**

(a) Severity: **MEDIUM**, re-rank HIGH if that tell fires under a real driver. Compared with the OPEN LIST head (`staticlatchscope`, diagnostics scope) this is a guest-visible payload corruption on one byte of odd-length transfers, BE machines only; the corrupted byte in the worked INQUIRY-37 case is vendor-specific data no driver reads.

(b) Witness: rung-3 IS available. `evbmips -e maltabe` with an ATAPI image (`-d c:`), a guest program (the `wdcringambig` witness already drove the wdc through the committed piix4_ide path on `-e malta` in 34 MIPS instructions): stage the 12-byte INQUIRY CDB with allocation length 37 through six 16-bit data-port stores, then nineteen 16-bit loads; pre-fix the 19th load returns `[0x23|…, 0xFF]`-shaped (last byte minus one), post-fix intact. Controls: the identical program on `-e malta` (LE) returns `[v, 0xFF]` through the same decode (liveness); the over-read latch line is the device signature. The differential alternative needs two things: `row_odd_width` must inspect `buf[]` (it checks `atapi_len`/`atapi_received` only), and the `void memory_writemax64` stub must honour byte order — today it always serialises LE regardless of `stub_cpu.byte_order` (and the default `stub_byte_order = 0` is `EMUL_UNDEFINED_ENDIAN`, which exercises the BE arm, as the file's own comment says).

## Q2 — THE #337 PACKET-STATUS DEFECT: CONFIRMED

Read: `void wdc_command` sets `d->error = 0;` first; `case ATAPI_PKT_CMD:` sets phase CMDOUT and nothing else. The dispatch (`if (d->atapi_cmd_in_progress && !badlen_this && d->atapi_phase == PHASE_CMDOUT && inbuf_len == 12)`) calls `diskimage_scsicommand` once; on `res == 0` it goes `PHASE_COMPLETED` + `int_assert` (`if (res == 0) {`), on `res == 1` it tests only `data_in != NULL`. **`atapi_st->status` is never read anywhere in dev_wdc.c** (every `atapi_st` use is `cmd`, `cmd_len`, `data_in`, `data_in_len`). `static int status_byte` ORs `WDCS_ERR` only when `d->error` is set. So a failed packet completes 0x50 (DRDY|DSC), ERR clear — with a medium present (else the earlier no-disk arm already returns ABRT).

Backend facts (diskimage_scsicmd.c): `return 0` only on structural errors (no machine, NULL cmd, `cmd_len < 1`, short CDB, disk not connected); `return 2` for WRITE/MODE SELECT wanting DATA OUT; **`return 1` for everything else including CHECK CONDITION** — the oversized READ (`SCSI READ: refusing oversized transfer`, `status[0] = 0x02; break;`) and, worse, the out-of-range READ: `diskimage__return_check_condition(xferp, d, 0x05, 0x21, 0x00)` after `memset(data_in, 0, size)` — the #416 repair whose own comment says "on its own it reports a successful read of zeros". **That repair never reached the IDE/ATAPI path**: wdc sees `res == 1`, `data_in != NULL`, enters PHASE_DATAIN with zeros, ERR clear. An unknown SCSI opcode hits the backend `default:` and returns 1 with no data -> PHASE_COMPLETED, no ERR, no message at all. So the #337 block's "`res == 0` — any packet command the SCSI layer rejects" is also inaccurate.

Consequence, **CONFIRMED against the in-tree guest source** (`C:\DocumentNoSnc\CC\GXEMUL\_guest-src-openbsd22\sys\dev\isa\wdc.c`, `case PHASE_COMPLETED:` -> `if (st & WDCS_ERR) { acp->error = bus_space_read_1(iot, ioh, wd_error); acp->status = ERROR; }` and nothing else; `atapi/atapiconf.c` `atapi_sense(acp, error >> 4, flags)` decodes the sense key from bits 7:4 and ABRT/EOM/ILI/MCR from the low bits). With ERR clear the OpenBSD 2.2 guest treats the command as SUCCESS whatever arrived; a refused READ is delivered as zeros. Severity **MEDIUM** (the main loop's ranking stands): a guest normally reads inside the capacity it was told, so the common trigger is an unsupported opcode reported as success rather than data loss.

Witness: rung-3 on the existing landisk wdc rig (`wdc_flood_probe.py`'s machinery, `-d c:` ATAPI image) or `maltabe`: stage a READ(10) CDB beyond the image end, or opcode 0xFF; read `wd_status` and `wd_error`. Pre-fix 0x50/0x58 and 0x00; post-fix ERR set and the error register non-zero. Controls: a valid INQUIRY through the same path shows DRQ with ERR clear (liveness); an out-of-range CHS READ on a plain disk shows ABRT (signature RAM cannot produce).

Option set: (1) `d->error = WDCE_ABRT` on `res == 0` and on `atapi_st->status_len >= 1 && status[0] == 0x02` — the guest's `atapi_error()` then reports ERROR (sense key 0 = NO SENSE, so no finer recovery); (2) mirror the backend's latched sense key into bits 7:4 (`(key << 4) | WDCE_ABRT`, ILLEGAL REQUEST -> 0x54) via an accessor to the diskimage's `sense_key` set by `diskimage__return_check_condition` — this is the option under which the guest's own NOT_READY/UNIT_ATTENTION/RETRY logic works; (3) on CHECK CONDITION with an allocated zeroed `data_in`, do not enter PHASE_DATAIN — complete with ERR and no data. Dependence on the online draft: only for spec conformance of the register layout (**BELIEVED**); what the in-tree guest expects is **CONFIRMED** on disk and agrees.
