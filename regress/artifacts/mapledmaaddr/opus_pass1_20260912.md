> `# CHECKPOINT -- 2026-09-12 ~12:4x   HEAD 7457c04 (records)`

**VERDICT: ACCEPT is the right fix. The detector as the brief condenses it is not safe: three plausible wrong fixes pass it, and one of them is the in-tree FAULT idiom, which on SH4 silently skips the load. The codex RETRY design already guards against all three; the brief's four bullets dropped the rows that did. The DMA leg is coverage for the separate cursor row, not floor.**

## Q1: Is ACCEPT right?

Yes. Taking the option set member by member:

- **DELETE / DECLINE.** Deleting the else-arm makes the read return 0, because `odata` starts at 0 and `memory_rw.c:491-492` pre-zeroes the buffer. That throws away a value the model already computes. The siblings `MAPLE_ENABLE` (`dev_dreamcast_maple.c:578-579`), `MAPLE_SPEED` (`:604-605`) and `MAPLE_STATE` (`:591-593`) all return quietly, so this arm's kill is the outlier in its own switch.
- **LATCHED ANNOUNCE.** It would print "unimplemented" about a read that is implemented, which is a wrong record in product code.
- **FAULT is not available, and its idiom is actively harmful here.**
  - `memory_rw.c:603-624` delivers an exception only under `MEM_MIPS` and `MEM_M88K`. `tmp_sh_tail.c:39` defines `MEM_SH`, but `memory_rw.c` has zero `MEM_SH` references (`grep -c`).
  - So a handler `return 0` gives `MEMORY_ACCESS_FAILED` with no exception pending. `cpu_sh_instr.c:1279-1285` then returns before `reg(ic->arg[1]) = data` at `:1292`. **Rn keeps its old value and execution continues.** That is a silent skip, worse than DECLINE.
  - The hardware has no such exception either: "bus error" appears nowhere in `sh7750_hardware.txt` or `sh4_programming.txt`.
- **BACKED ACCEPT.** There is nothing to fabricate; the field exists.
- **IMPLEMENT.** This would mean deciding premise 1, which cannot be settled here. `ls _scratchpad/*.pdf` has no Holly or Maple document, and `thirdparty/dreamcast_maple.h` defines no register semantics.

**ACCEPT is the better choice under either hardware answer, because it is policy-neutral.**
- The model keeps one lvalue, `d->dmaaddr`, and the next DMA restarts from it (`:382`).
- If hardware returns the programmed address, the cursor row deletes `:540` and the read arm is still correct unchanged.
- If hardware returns the cursor, `:540` stays.
- Either way the read arm is `odata = d->dmaaddr;`.

## Q2: Which wrong fix passes the detector?

**E-a, the FAULT idiom (`dev_unreadable`-style):**
```c
		} else {
			return 0;
		}
```
- The process survives, and the TODO text is absent (the `memory_rw.c:604` message is `debug()`, invisible at default verbosity).
- Suppose a value row stores Rn and then loads back into the same Rn (`mov.l r1,@r2; mov.l @r2,r1`). Then Rn already holds the expected value, so the "exact readback" and "second write replaces" rows both pass.
- The only leg that kills it without extra care is the DMA leg, and only by accident.
- This is a CHANNEL-line vacuity that can be seen at writing time: the channel "Rn after the load" cannot vary under this mutant.
- **Required:** every load destination is pre-poisoned with a value different from every expected value. The RETRY had this (`POISON 0xa5a55a5a`); the brief's summary lost it.

**E-b, a reworded or latched announce:**
```c
		} else {
			fatal("[ dreamcast_maple: read from dmaaddr ]\n");
			odata = d->dmaaddr;
		}
```
- It passes bullet 3, because that row is keyed to the literal `TODO: read from dmaaddr`.
- The unlatched form is a guest-drivable flood that `-q` cannot silence (`fatal()` has no early-out).
- The house-idiom `(once)` latched form also passes, and it is a wrong record.
- **Required:** key the silence row on the channel, meaning zero output lines between the pre-load and post-load markers. Negative-control it with both the verbatim form and the reworded form.

**E-c, a literal hoist:** `uint64_t idata = 0, odata = d->dmaaddr;` with the else-arm emptied.
- Every 0x04 row passes.
- Reads of `0x10`, `0x8c` and `0xe8` now return `dmaaddr` instead of 0.
- **Required:** the RETRY's `other read` row, which the brief dropped.

Minor gaps, also from dropped RETRY rows:
- A read-to-clear fix (`odata = d->dmaaddr; d->dmaaddr = 0;`) passes, because no bullet reads twice without a write in between. The RETRY's `off keep` / `dma2 hold` rows cover it.
- The zero cell is missing: the RETRY's `initial` row. The PROM emulation never touches Maple, so a fresh device reads 0.

**What clause (d) enumerates for this pure deletion.** The form is "re-introduce `fatal`+`exit` under a DIFFERENT predicate", bounded by DEPENDS-ON's BOUND:

1. *Dominating predicates:* `relative_addr == 0x04` and `writeflag != MEM_WRITE`.
   - The only different writeflag predicate is `else if (writeflag != MEM_READ) exit(1)`. That is **EQUIVALENT** (see Q3, premise 2), so it gets a disclosure, not a row.
   - `relative_addr` is constant inside the arm. It does not flow into `d->dmaaddr` or `odata`, so the JOIN ruling does not make the label a floor axis.
2. *Operand swaps from body-read fields:* the guarded body reads only `d->dmaaddr`, and **tests no partition of it**.
   - Under the joint-cells ruling its value domain is one class. Value-conditioned kills such as `if (d->dmaaddr & 0x1f) exit(1)` or `if (!d->dmaaddr) exit(1)` are clause-(e) disclosures.
   - The floor is met by one surviving poisoned read.
   - The unaligned `A`, aligned `B` and zero rows are cheap coverage beyond the floor.
   - `maple_do_dma_xfer`'s `& 0x1f` test sits outside the enclosing function, so the BOUND excludes it.
   - `len` is read by the common tail, not by the guarded body, so the contract should disclose "32-bit reads only".

**The DMA leg is COVERAGE of the cursor row, not floor.**
- The DMA tail writes a `uint32_t` that the `:559` arm can also write with any value (no masking). So DMA creates no new value cell.
- The only mutant it uniquely kills is a programmed-address shadow. That needs a new lvalue the body does not read, which is outside the BOUND.
- There is one caveat, from CLAIM→ROW: if the round writes "a read now returns the post-DMA cursor" into a comment or the CHANGELOG as an assertion, it owes a row or an explicit no-row sentence.
- Recommendation: write the no-row sentence here, and ship the DMA leg with the cursor row. That row edits `:540`, and the read arm is its observation channel, so the leg is load-bearing there.
- Wherever it ships, **never use the literal `P+12` as the expected value.** Use the RETRY's independent reference: the `NOT 32-byte aligned` refusal message that prints the live field (`E1`/`E2`). Otherwise the leg certifies the cursor arithmetic that the cursor row exists to question.

## Q3: Premises found false or unsettled

1. **Bullet 3's claim that it "catches keep-fatal-delete-only-exit" is true only of the verbatim text** (E-b). As a class claim it is false.
2. **Premise 2: there is no such path.**
   - The only dispatch site is `memory_rw.c:587`, and it passes the caller's writeflag through.
   - `memory.h:117-119` defines `MEM_READ 0`, `MEM_WRITE 1` and `MEM_DOWNGRADE 128`. `MEM_DOWNGRADE` is used only in `update_translation_table` (`cpu_dyntrans.c:1690-1730`), never in `memory_rw`.
   - I scanned all 279 `memory_rw(` calls in `src/`. Each passes `MEM_READ`/`MEM_WRITE`, a literal `0` (`dev_jazz.c:228`), or a forwarded writeflag (`dev_ram.c:80`, `dev_ps2_spd.c:70,75`, `dev_luna88k.c:613`, `dev_lca.c:291`, `dev_jazz.c:258`), which is itself 0 or 1.
   - So `else` ≡ `MEM_READ`. The mismatch with the tail's `== MEM_READ` is purely syntactic.
3. **The earlier codex review's re-entrancy caveat (readarm §2, "not established") is settled by the source: re-entry is impossible.**
   - Every `memory_rw` in `maple_do_dma_xfer` carries `NO_EXCEPTIONS|PHYSICAL`.
   - `memory_rw.c:584-585` calls a handler under `NO_EXCEPTIONS` only if it is `DM_READS_HAVE_NO_SIDE_EFFECTS`, and Maple is `DM_DEFAULT` (`:651-652`).
   - So a descriptor pointing at `0x5f6c04` is silently skipped.
4. **The same bypass is a trap for the witness.** Debugger `dump` (`debugger_cmds.c:716-717`) and `put` (`:1459-1461`, `:1506-1507`) pass `NO_EXCEPTIONS`, so they never reach this handler. A `dump` of `0x5f6c04` reads 0 with any fix applied. All register traffic must be guest instructions.
5. **Premise 1 cannot be settled locally.** Per Q1, ACCEPT is the right choice regardless of the answer.
6. **Premise 3 holds.** The cursor row is separate, as the earlier review ruled.
