### Q1. Edits the oracle cannot see

- **[REASONED] Deferred output via `atexit()` / late stderr flush.** `SNAP = buf` is taken immediately before `os.write(fd, b"quit\n")` (diff `+ global SNAP / SNAP = buf`). Anything queued for process termination — an `atexit(prints_something)`, a `fprintf(stderr, ...)` that the stdio buffer hasn't flushed, a debug log written in a cleanup hook registered during the read — lands in the pty AFTER the snapshot. Reachable from a C edit (one line: `atexit(diagnostic_print); odata = d->dmaaddr;`). No row in this instrument observes it: `exit status` would still see `exit0` from a quiet `atexit`, `marker survive` is unaffected, `read silent` reads `SNAP` which doesn't contain the bytes. The brief itself flags this ("output that arrives after the snapshot (a latched diagnostic deferred to exit, `atexit`, stderr buffering)") — i.e. the author already knows it and has chosen to leave it outside the contract.

- **[REASONED] Output on a channel the pty never carries.** A `FILE *` opened in the read arm (`fopen("/tmp/maple.log", "a"); fprintf(...);`), a `syslog(3)` call, a write to an inherited fd the harness hasn't bound to the pty. Same story: bytes never enter `SNAP`, no row sees them. Also outside the contract as stated; not reachable from a stock `fatal()` (which writes to the console), but reachable from custom C in the arm.

- **[REASONED] ANSI / `\b` overwrites — I do NOT believe these escape.** Three sub-cases, all caught:
  1. `\r…` overwrite → `bare_cr` count fires (the check is `raw.count("\r") - raw.count("\r\n")`).
  2. `\b…` overwrite → the diagnostic line is a SEPARATE entry after the disassembly's `\n` (disassembly prints before execute, per settled premise). That separate line begins with `\b`, the regex `^([0-9a-f]{8}):\s+([0-9a-f]{4})\s` is anchored at start, mismatch → surplus or wrong-kind fires.
  3. `\033[1A\033[2K…` cursor-positioning overwrite → same as (2): the escape bytes are at the start of the diagnostic line, the anchored regex doesn't match, surplus/wrong-kind fires. (Without a leading `\r` you cannot return to column 0, so you cannot overwrite the prior line in place; you only ever produce a new line, and that new line carries the escape bytes the regex refuses.)
  In every overwrite path I can construct, either `\r` is counted, or the diagnostic's own line begins with non-`[0-9a-f]` and fails the anchored regex.

- **[REASONED] No-newline output line-buffered into the next prompt.** `fatal("X")` with no `\n`: on a pty, the bytes accumulate into whatever the next output is. The resulting line is strictly longer than the owed echo (`ln == want` for echoes, anchored regex for hex/put/disasm). Caught.

- **[READ] The acknowledged partial comparison** ("a disassembly line is compared only on address and opcode — its mnemonic and comment are not; a `print` line only on being one hex line"). In principle exploitable: a diagnostic that emits a line of the exact form `XXXXXXXX: HHHH <anything>\n` AT the owed disassembly position passes. But to occupy that position without producing a surplus line requires an overwrite, and the overwrite paths above are all caught. So from a normal C edit to this arm, the partial comparison is not exploitable.
