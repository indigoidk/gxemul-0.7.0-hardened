## Premise audit

**P2 — Third value of `writeflag`.** [READ from packet structure] The function shape — top-level `if (writeflag == MEM_WRITE)` for the idata load, case-internal `if (writeflag == MEM_WRITE)` for the write arm, and the common-tail `if (writeflag == MEM_READ) memory_writemax64(...)` — leaves a third-value path that, after ACCEPT, assigns `odata`, skips the writeback, and returns 1. **P3 — Cursor row is separate.** [READ from earlier review, per brief] ACCEPT does not touch `maple_do_dma_xfer`; the cursor computation is preserved. ## ACCEPT vs the full option set [REASONED]

- **DELETE (remove case 0x04):** falls into `default`. Brief annotates default as `fatal(...)` for either direction with "no exit." Whether default exits or not, DELETE fails the detector — if default exits, fails (c); if default does not exit, `odata` stays 0 and the read returns 0, failing (a) "nonzero HIGH bits / nonzero LOW FIVE bits." Either way, caught.
- **DECLINE:** keeps `fatal`/`exit(1)`. Wrong on its face; the read is the operation being modeled, not a programming error.
- **DECLINE+LATCHED ANNOUNCE:** incoherent — a latched announce alongside a kill still kills.
- **ACCEPT:** delete `fatal`/`exit(1)`, keep `odata = d->dmaaddr;`. Aligns with the rest of the switch.
- **FAULT:** the brief itself flags SH4 availability as uncertain. Also semantically wrong — a normal MAPLE_DMAADDR read should succeed, not raise a bus-error equivalent.
- **BACKED ACCEPT:** backed by something other than `d->dmaaddr` (a separate register/mirror). If the backing tracks the field, equivalent to ACCEPT; if it doesn't, a wrong fix the detector will catch via (a)/(b)/(d).
- **IMPLEMENT:** speculative without the TRM.

ACCEPT dominates.

## Detector clause analysis [REASONED, anchored in packet code]

| Clause | What it pins | What wrong fix it catches |
|---|---|---|
| (a) distinct values, EXACT, nonzero HIGH and LOW5 | `relative_addr == 0x04`; read returns `d->dmaaddr` verbatim | constant return, zero return, `& ~0x1f` alignment mask, truncation, byte-swap |
| (b) second write REPLACES | `writeflag != MEM_WRITE` path; field updates on writes | write-side snapshot/latch |
| (c) process survives AND TODO string absent | kill removed; literal `"TODO: read from dmaaddr"` gone | keep `fatal`, keep `exit(1)`, keep the marker string, no-op replace (caught by (a)) |
| (d) post-DMA read equals field | read sees DMA-updated `d->dmaaddr` | cursor-row regression; cache that updates only on writes |

Clauses (a), (b), (c) are sufficient for the read-arm row. Clause (d) is *both* cursor-row coverage *and* necessary for the floor if "the read reflects DMA updates" is in scope — the brief's question. The dominating predicates for the ACCEPT body are `relative_addr == 0x04` ∧ `writeflag != MEM_WRITE`; (a) pins the first by addressing MAPLE_DMAADDR, (b) pins the second by reading after writing.

## Which wrong fix passes? [REASONED]

The pure deletion described — remove `fatal`/`exit(1)`, leave `odata = d->dmaaddr;` — *is* ACCEPT and passes everything.

A wrong fix that passes (a), (b), (c) but fails (d): a write-side cache (`static uint32_t last_written`) updated only in the write arm, ignoring DMA's update of `d->dmaaddr`. Clause (d) catches it.

A wrong fix that passes all four clauses: **read-to-clear**, e.g., `odata = d->dmaaddr; d->dmaaddr = 0;`. If the detector's (a) sequence is strictly write→immediate-read with no second read after the first, (a)/(b)/(c) all pass; clause (d) also passes because the read happens *after* the DMA tail's assignment and returns it before clearing. This is a real detector gap for read-side-effect bugs, but it is speculative hardware behavior, and adding a "second consecutive read equals first read" sub-clause to (a) would close it.

## False premise?

The brief's parenthetical on the `default` arm — *"fatal(... for either direction -- no exit"* — is suspect. In stock GXemul, `fatal()` calls `exit(1)`. If "no exit" is wrong and the default actually exits, then a PURE DELETION of case 0x04 fails (c) rather than (a); either way it fails the detector, so the verdict is unchanged, but the brief's annotation should be re-checked against the actual `fatal()` definition.
