For **A**, the consequential finding is another writer. DMA begins with a local copy of `d->dmaaddr`, advances that local address through the command list, then writes it back at 540, immediately below:

Consequently, “the read returns what the guest programmed” is true immediately after a write, but is **not the invariant maintained by this model after completed DMA**. See the [DMA tail](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_dreamcast_maple.c:539).

Sega’s documentation identifies MDSTAR as the command-table **starting address**. Flycast corroborates a preserved programmed-address model: it walks a separate local address, and its register implementation also masks address bits. Those are concrete reasons to challenge GXemul’s writeback and unrestricted stored value. [Sega system architecture, §2.6.8](https://segaretro.org/images/7/78/DreamcastDevBoxSystemArchitecture.pdf), [Flycast DMA implementation](https://raw.githubusercontent.com/flyinghead/flycast/master/core/hw/maple/maple_if.cpp), [Flycast register implementation](https://raw.githubusercontent.com/flyinghead/flycast/master/core/hw/holly/sb.cpp).

**Evidence limit:** I could read the indexed Sega description, but could not retrieve the complete vendor register specification establishing post-DMA readback and reserved-bit behavior. Flycast is corroboration, not a silicon specification. Therefore I am holding ACCEPT rather than claiming a conclusively proven hardware mismatch.

If MDSTAR must retain the programmed start address, this becomes **IMPLEMENT**: maintain that state correctly before exposing it. An immediate write/read detector would miss the defect. For **B**, the backing-state argument is substantially stronger. The interrupt controller’s `enable` pointer refers directly to `cpu->cd.arm.i80321_inten`; interrupt assertion/deassertion consults that field. The read therefore returns the programmed mask, rather than a disconnected shadow. Pending interrupt sources live in another field. See [controller binding](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_i80321.c:445) and [mask consumption](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_i80321.c:83).

That supports deleting the diagnostic and exit for the normal read. It does **not** establish “fully modelled both ways”:

- The store changes the mask without immediately recomputing the CPU interrupt signal. Correct register readback does not prove correct interrupt delivery.
- The quiet `isteer` read does not establish steering support: nonzero steering writes terminate.
- The generic dispatcher passes through `rd` and opcode fields without enforcing privilege, and CP6 does not validate `opcode1`/`opcode2`. A normal-register oracle does not cover special `Rd == PC` handling or noncanonical accesses.

I did not obtain the matching Intel 80321 register chapter, so the ACCEPT recommendation is not a vendor-document certification of reserved bits or every access form. No local evidence requires recomputation or clearing of **the enable mask on read**.

A TODO alone establishes neither implementation nor nonimplementation. If a read really requires missing behavior, a latch cannot supply it; member 3 would need an explicit, truthful decline contract.

These should be **two rounds** under your stated scope rule.
