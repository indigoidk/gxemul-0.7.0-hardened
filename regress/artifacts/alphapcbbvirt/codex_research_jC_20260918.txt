2. **The caller-side sequence is certain; the exact unmapped-access outcome is not.**

   `swpctx` first saves all nine outgoing fields, then publishes the old `ctx` in `v0`, then assigns `ctx = a0`. The incoming fields are loaded in the same order shown below. There are **seven 64-bit and two 32-bit accesses** in each direction. [cpu_alpha_palcode.c:230](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_palcode.c:230), [cpu_alpha_palcode.c:269](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_palcode.c:269), [cpu_alpha_palcode.c:273](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_palcode.c:273)

   | Order | Byte offset | Field | Width |
   |---|---:|---|---:|
   | 1 | 0 | KSP | 64 |
   | 2 | 8 | USP | 64 |
   | 3 | 16 | PTBR | 64 |
   | 4 | 24 | CPC | 32 |
   | 5 | 28 | ASN | 32 |
   | 6 | 32 | UNIQUE | 64 |
   | 7 | 40 | FLAGS | 64 |
   | 8 | 48 | DECRSV0 | 64 |
   | 9 | 56 | DECRSV1 | 64 |

   Both widths call `memory_rw` with `CACHE_DATA` and no explicit `PHYSICAL`. Store helpers return status, which `swpctx` ignores. Load helpers ignore status themselves and decode an initially uninitialized local byte buffer. [memory.c:782](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/memory.c:782), [memory.c:806](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/memory.c:806), [memory.c:886](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/memory.c:886), [memory.c:913](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/memory.c:913)

   Crucially, **load 3 only fills local `new_ptbr`**. The handler does not install it until all nine loads have returned. Reading a zero PTBR therefore does not itself disable translation for loads 4–9. The fields are then assigned, followed by translation-cache invalidation. [cpu_alpha_palcode.c:278](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_palcode.c:278), [cpu_alpha_palcode.c:293](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_palcode.c:293), [cpu_alpha_palcode.c:314](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_palcode.c:314)

   Under your assumed translation behavior, an unmapped incoming physical address is consequently submitted as an unmapped virtual address. **If the callbacks return normally**, the handler continues through all loads and commits their returned values; it has no failure branch or rollback. The earlier outgoing saves have the same addressing concern, independently of whether incoming `a0` is mapped.

   These files cannot establish whether failure zero-fills the buffer, leaves bytes untouched, changes CPU state, or terminates execution. Thus “nine zero loads,” a particular fault message/count, and a deterministic resulting PTBR are **not established**.

   `wrfen` similarly changes cached flags first, then performs an unchecked store at `ctx + 40`. [cpu_alpha_palcode.c:221](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_palcode.c:221)
