## Q2 — The smallest defect-bringing edit

**At S5, split the decline on the reset default**: `if (bytemask != 0xffffffff) { if (bytemask == 0) { fatal(...); exit(1); } ...latched decline... } }`. One line of substance. Every proposed row stays green, enumerated: `bytemask lo`/`hi` drive 0xfffffffe and 0x7fffffff (correctly declined); the S5 surv/nowrite/once rows drive 0x0000ffff; `lin fill` drives 0xffffffff; no other row reaches S5 at all (stipple/src rows decline pre-switch; lin copy/lin depth decline at S3/S4 first). **The row I expect to stay green: `bytemask lo`** — 0xfffffffe is declined, survives, paint intact. The defect is maximal: process death for any guest that never writes BYTEMASK — per Q1.5 the *common* case. The rows undersample the producer's domain; the producer of a BYTEMASK value is also "a guest that wrote nothing."

Runner-up, same family: share one latch bit across S3/S4/S5 (or reuse `SGIRE_W_BADMODE` — no enum edit at all). Per-site `once` rows each repeat *their own* site in a fresh session (the latch is per-instance and resets per process), so all five stay green while a session hitting two different unimplemented parameters sees only the first announced. Caught only by the two-different-sites row the table lacks.

## Q4 — Q-a to Q-e

**Q-a: member 1 is wrong.** At S4 the fill is `memset(zerobuf, bg, ...)` — at 16/32 bpp the destination gets bg's *low byte* repeated (0x11223344 → 0x44 bytes), silently after the latch. At S5 the loop applies no mask at all, so bytes the mask says to leave are written. At S1 stipple silently becomes solid. That is exactly the #509 defect shape (wrong-width write publishing wrong bytes) this campaign fixes. Note the `dst_y_step` "precedent" is itself this defect live in HEAD: the linear loop (1637-1677) never reads `dst_y_step`, so that site already announces-and-writes-approximately — it is a cautionary example, not a licence. "Untouched" beats "written approximately": the decline is observable once and fabricates nothing; the approximate write is silent after the latch and deterministically corrupts guest memory. Neither matches hardware; only one is contained.

**Q-b: decline exactly what is refused today; file the narrowing separately.** The emulator-internal claim is verified (Q1.4). Extra, REASONED: S2 is coarser than the code's own capability — src=4 (LIN_A as source) is refused at 1504 although `horrible_getputpixel` implements linear-A source reads (3d case 4, lines 264-271), and src=3 would be declined per-pixel by the helper's own default arm anyway (3d) — so S2 is partly redundant and partly over-broad. That is evidence of over-breadth, not a hardware warrant. No warrant in packet → the conservative disposition is the guard verbatim; the COPY-scoping narrowing (which also makes the helper's case-4 path reachable from the MTE — a real functional change, not a harmless accept) is its own row. Consequence: the `src tex`/`src clip` rows encode this choice (they drive fills and expect decline) and must flip if the narrowing ever lands.

**Q-c: no licence; member 7 is separate row(s).** S4 is a pattern-width change whose interaction with bytemask (per byte? per pixel?) is undefined without docs. S5 needs a read-merge-write, i.e. a TLB-gated *read* path the linear loop does not have — it only writes (1668). Nothing in the packet measures or transfers a warrant. The #509 comment's own "16-bit and reserved-3 cells not closed" shows the depth family has open landmines — more reason not to fold implementation in.

**Q-d: five bits, guard-as-site — but say so and make it testable.** The argument for 5: the announce's information ("this feature is unimplemented") is label-invariant, and the natural unit is the guard — splitting S3 by destination label invites splitting S4 by depth value, which nobody proposes. The argument for 8: 3d's width comment treats *windows* as sites ("six different address windows... walked in ONE session"), splits LINA from LINB, and dev_wdc.c licenses sharing only across mutually exclusive sites — LIN_A and LIN_B transfers are not mutually exclusive. The packet does not settle which reading governs transfer-parameter guards. My endorsement: 5 bits (1<<13..1<<17), label-agnostic texts, Q-d's silence (LIN_B quiet after LIN_A) accepted *in writing*. Either choice needs a detector that can tell them apart — today none can (see Q6).

**Q-e: nothing else should be skipped.** Between function top and the guards: `debug()` prints (verbosity-gated, no guest effect; S5 sits after the LINEAR debug at 1590 — harmless) and the `dst_y_step` unlatched fatal (1492), which will co-print on a declined transfer if a guest sets an odd step — pre-existing, its own row, not fixed here. The register store (1707) precedes the call and should stand: the access is legal, the *transfer* is declined. The caller's tail (1810-1813) is harmless for a START write (MEM_WRITE → no readback; `return 1`). Multi-guard transfers announce at the first failing guard only (S3→S4→S5 order preserved by the returns) — same first-exit-wins as HEAD.

- `<site> surv`: channel varies (process ends under reinstated exit) ✓.

- `lin fill`/`lin b fill`: vary under guard growth ✓ (accept side).
- Controls ✓; clause (c) honestly deferred to measurement.
