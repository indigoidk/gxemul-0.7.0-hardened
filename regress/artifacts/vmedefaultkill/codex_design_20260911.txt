   With the initialized `verbose = 0`, normal execution and no stepping produce `v = -1`. Thus `debug()` suppresses the message even without quiet mode, before the [default arm’s `exit(1)`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_vme.c:137) ends the process. “Invisible at default verbosity” is therefore correct **during normal execution**; startup and debugger contexts can behave differently.

   [`va_debug()`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/debugmsg.c:118) formats and prints directly. It neither terminates the process nor routes through structured subsystem logging.

   The `#261` check instead resides in [`debugmsg_va()`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/debugmsg.c:146), where the global toggle and message severity determine whether to request debugger entry. Legacy `fatal()` supplies no structured ERROR severity and bypasses this path entirely—even when the toggle is armed. The `fatal()` call inside the breakpoint branch merely prints its announcement; the surrounding branch sets `about_to_enter_single_step`.

   **One gate-relevant qualification:** `va_debug()` uses `printf`, so its destination is **stdout**, and it performs no explicit flush. Promotion ensures the message is not filtered; it does not guarantee immediate delivery through a buffered pipe. A gate must capture stdout and account for flushing. Immediate delivery before guest completion would require a separate flushing guarantee.
