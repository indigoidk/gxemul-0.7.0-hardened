After weighing both sides, **I choose FAULT because explicit failure better represents an unsupported emulated transaction than successful synthetic behavior**. The constructor’s treatment of omitted Ethernet emulation supplies concrete local precedent. The original “present device, therefore fault forbidden” veto does not survive. Its narrower objection—do not claim undocumented real-hardware behavior—does survive, and should remain in the ruling.

For a FAULT round, the remaining obligations are:

1. **Change the oracle to failed access plus architectural exception.** For ordinary M88K data reads and writes reaching the fallback, require callback failure, `MEMORY_ACCESS_FAILED` from the memory path, and dispatch of `M88K_EXCEPTION_DATA_ACCESS`. Instruction access has its separate exception selection. Removing the host exit alone is insufficient.

2. **Pin the caller behavior that a decline detector would not need.** Exercise or otherwise verify the M88K dispatch with exceptions enabled, the expected exception selection, and failure propagation. A zero-filled read buffer proves neither FAULT nor DECLINE. Checking only the callback’s return value proves less than checking its architectural consequence.

3. **Keep the announce as a bounded diagnostic.** I would retain one notice per device instance identifying an unimplemented VME access and its guest fault. The latch must gate only the notice: every subsequent unsupported access must still fail. The existing per-access default messages should not remain alongside it. However, `memory_rw.c` itself emits a debug message on every device failure, so a detector must distinguish a bounded VME announcement from a claim that *all* fault diagnostics are bounded. [memory_rw.c:604](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c:604)

4. **Preserve the supported behavior and own the byte-lane gap explicitly.** Failed accesses must not mutate register storage or serialize aliased `odata`. Existing explicit cases—including the successful offset-zero probe—must retain their intended behavior. Interior offsets need their own access-width decision and corresponding oracle; successful removal of the exit does not close that issue.

5. **Validate guest consequences separately from source-level availability.** Probe recovery and an ordinary driver’s fault response require integration validation. This review establishes the dispatch mechanism and its limitations; it does not establish continued bootability, complete exception metadata, or real-hardware equivalence.
