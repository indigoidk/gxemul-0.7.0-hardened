**VERDICT: NO. The macppc guest-store paths cannot place bits 32..63 in this register’s `idata` or `cur_addr`: the dispatcher clamps the four-byte address window before calling the handler. `MEM_PCI_LITTLE_ENDIAN` preserves these access widths.**

All references below are within `GXEMUL-SEC/src/`.

1. **`memory_readmax64()` can decode 64 bits, but this handler receives at most four bytes.**

   In [core/memory.c:55](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/memory.c:55), `memory_readmax64()` initializes an unsigned accumulator:

   ```c
   uint64_t x = 0;
   ```

   Its little-endian arm, lines 72–77, is:

   ```c
   for (i=len-1; i>=0; i--) {
       x <<= 8;
       x |= buf[i];
   }

   return x;
   ```

   `buf` is `unsigned char *`. Thus, for the handler’s forced little-endian decode, the exact result is `Σ data[i] × 256^i`, for `i = 0..len-1`. No input byte is sign-extended.

   | Handler `len` | Possible result | Bits 32..63 |
   |---:|---:|---|
   | 1 | `0..0xff` | Zero |
   | 2 | `0..0xffff` | Zero |
   | 3 | `0..0xffffff` | Zero |
   | 4 | `0..0xffffffff` | Zero |

   The same helper **would** admit high bits for decoded lengths 5–8, including all 64 bits at length 8. Those lengths do not reach this registered address handler through the examined guest-store paths.

3. **Your Q3 suspicion is wrong for these lengths: the flag is removed before either decoding loop.**

   [include/memory.h:98](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/include/memory.h:98) defines `MEM_PCI_LITTLE_ENDIAN` as `128`. [core/memory.c:60](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/core/memory.c:60), `memory_readmax64()`:

   ```c
   if (len & MEM_PCI_LITTLE_ENDIAN) {
       len &= ~MEM_PCI_LITTLE_ENDIAN;
       byte_order = EMUL_LITTLE_ENDIAN;
   }
   ```

   Consequently, lengths `1,2,3,4` become arguments `129,130,131,132`, then decode as `1,2,3,4` again. Likewise, `8|128` would decode as 8. **The OR changes byte order, not effective width, here.**

4. **There is no additional mask before the loop.**

   [dev_uninorth.c:55](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_uninorth.c:55), `dev_uninorth_addr_access()`, assigns the helper result directly to `cur_addr`; the loop arm leaves `idata` unchanged. The limiting operation is the **upstream buffer-length clamp**.

   That clamp retains the first four buffer bytes, rather than necessarily the source register’s low 32 bits: `LS_GENERIC_N()` emits doubleword-store bytes most-significant first ([cpu_ppc_instr_loadstore.c:163](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_ppc_instr_loadstore.c:163)). They still decode into only bits 0..31.

   The other arm also passes through a `uint32_t` parameter in [bus_pci.c:72](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/bus_pci.c:72), `bus_pci_decompose_1()`; that does not protect the loop arm.

5. **V3’s “upper bits are provably zero” argument needs correction.**

   [dev_v3.c:63](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_v3.c:63) declares `lb_map0` as `uint16_t`. In [dev_v3_pci_access():161](/C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/devices/dev_v3.c:161):

   ```c
   relative_addr &= 0xfffff;
   relative_addr |= ((d->lb_map0 & 0xfff0) << 16);
   ```

   With 32-bit `int`, `lb_map0` promotes to signed `int`; the shifted expression is also signed. Under the same two’s-complement behavior assumed in your question, setting its bit 31 can therefore produce upper ones when converted for the `uint64_t` OR.

   **However, those upper ones occur only when bit 31 itself is already set.** They cannot independently create the proposed false match at `dev == 31`. Your conclusion about that particular false-match mechanism holds; the zero-upper-bits proof does not.
