    For EnableClear, [§7.3.33](C:/DocumentNoSnc/CC/GXEMUL/_scratchpad/dc21285.txt:6937) specifies what writes do: set data bits clear corresponding enable bits; zero data bits have no effect. It supplies **no read result**.

    Thus:

    | Access | Documented behavior |
    |---|---|
    | WRITE to these read-only registers | No effect |
    | READ from EnableClear | No specified result; no explicit declaration that the result is “undefined” |

    The reserved-bit rule at [6836](C:/DocumentNoSnc/CC/GXEMUL/_scratchpad/dc21285.txt:6835) does **not** specify zero for an entire read of a write-only register.

    | Situation | Discriminating observation |
    |---|---|
    | Correct decline | Observed result is zero under each of two distinct, confirmed nonzero masks; enable state remains unchanged |
    | Returns the live mask | Observed result follows those nonzero masks and fails the zero expectation |
    | Only tested with mask zero | Setup is insufficient for the leak claim; correct and defective results coincide |
    | Read never executed | A preloaded destination sentinel remains, execution evidence is missing, or the specific handler-path observation is absent |

    Mask setup must be checked independently. A controlled device fixture can inspect its initialized state directly. **Do not casually use a guest read of `+0x188` as that setup check: the present implementation still terminates there.**

    Require the actual target instruction, its effective address/direction, successful completion, and evidence that the intended device path handled it. A1/A2 establish other accesses, not this particular read. A fresh-instance decline announcement can provide positive path evidence under the recommended design; it does not replace the returned-value assertion.

    D1 also needs careful interpretation: the stepping loop breaks on failure **before** checking that step’s disassembly. Its current zero-mismatch result does not independently validate the terminal K instruction.

    The relevant confidentiality property is **independence from the enable mask**, not numerical inequality for every mask. A legitimate zero fallback necessarily equals a zero mask. Two distinct nonzero masks distinguish the named direct-mask defect; source review establishes that the return path has no mask dependency generally.

    Survival, unchanged device state, and announcement count cannot detect the mask-copy defect by themselves: that defect can preserve all three channels. Giving one of those rows responsibility for detecting the leak would be vacuous.

7. **Under the stated scope rule, this is two rounds: four writes together, and the read separately.**

    The four read-only writes share the same repair design and detector contract: the access completes, the host continues, and the attempted write causes no architectural state or interrupt-output change.

    `+0x18c` adds a distinct obligation: observing and validating returned data under varying enable state. A repair can satisfy every common completion/no-effect check while still exposing the mask. That establishes the need for an additional oracle.

    A shared helper or one probe script can accommodate all five, but it does not eliminate that additional oracle. The legal `+0x188` read remains a separate BACKED ACCEPT issue, and the current K1 witness belongs to that issue.
