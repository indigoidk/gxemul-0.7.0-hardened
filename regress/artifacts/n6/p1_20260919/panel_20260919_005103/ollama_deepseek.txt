### Q1 — premise audit

**(a) ACCEPT right?**  
READ: The inlined datasheet table and text make `+0x188` read legal, returning IRQEnable. The code already computes `odata = d->irq_enable;` before the fatal/exit.  
REASONED: ACCEPT is correct for this site.

The sibling `+0x288` FIQ_ENABLE_SET read is also legal per the same datasheet table, but the inlined code returns `0` silently and does **not** call `fatal()`/`exit(1)`. That is a separate correctness bug, not an exit site. Under the stated one-site-per-round reopening rule, it should stay separate. If the rule is “same semantic class,” it could join, but that expands scope beyond the exit-defect class.

**(b) `+0x100` temporary control sound?**  
READ: `0xE5907100` decodes as `ldr r7,[r0,#256]`, and `0x100` decimal = 256. The code path at `SDRAM_BA_MASK` read calls `fatal("[ footbridge read from sdram_ba_mask ]\n")` then `exit(1)`.  
REASONED: Yes, it gives each probe a host death with distinct text and exit 1, exactly the same class of control as `+0x188`. It is temporary by design because `+0x100` is a decline-class site.

**(c) P/Q inert?**  
UNCHECKABLE from packet. The claim that bits 1, 13, and 29 are never asserted during these probes depends on the full DC21285 interrupt bit table and the `cats` interrupt wiring, which are not inlined.  
If a write did assert the CPU IRQ, it could alter subsequent single-step behavior, so this must be verified before relying on P/Q.

**(d) Tree-wide dependence on `ENABLE SET` text?**  
UNCHECKABLE from packet. The brief says codex scoped only `src/` and `regress/` and found four sites; the tree-wide claim is explicitly not checked. This remains open.

**(e) Bind `waitpid` status?**  
REASONED: Yes. The drain and witness probes currently discard `waitpid` status and accept any host death after seeing the text. Moving the kill arm without binding status would preserve that blind spot. Binding exit 1 does not change surviving-arm verdicts, because those arms should exit 0.

### Q4 — campaign order

REASONED: Either order is defensible. The real requirement is a failability control that does **not** depend on a defect being present. The best move is to build that permanent control now if it can be specified and tested in the same commit. If not, moving to `+0x100` is an acceptable temporary step, but it guarantees another control move later. A permanent control should be a deliberate, documented kill mechanism outside the footbridge device model, so the one-instruction delta remains valid after all device exits are removed.
