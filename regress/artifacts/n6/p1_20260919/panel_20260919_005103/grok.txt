## Implementation constraints the brief did not name (will ship a vacuous E-suite)

1. **`run_arm` samples regs once, after the last step, and only r0,1,2,3,5,6,7** (`footbridge_sites_probe.py:188–194`). Final r7 can hold only the last read. E0–E5 are lost unless each result is published to RAM (drain-probe pattern) or `reg` is sampled between E instructions. Do **not** clobber r1 (A2) or r6 (A1); those are scored from the same final `reg`.

2. **Execution order is not the E-number order.** E6 is specified “after E2”, want `0x2002`. E5 clears P, after which a halfword is `0x0000`. Run **E0, E1, E2, E3, E6, E5**. E4 is a buf scan, order-free.

3. **Do not put E0–E6 on arm L if L is still the isolation arm.** I1 is `SURVIVED && exit==0 && not L["fatals"]` and the header says L/K differ by exactly one instruction. Either: (i) a fourth arm E for the value rows, L keeps NOP at the kill slot, K is `+0x100`; or (ii) E sequence *after* the kill slot so K dies before it and L steps it — then I1’s “untouched” comment is a lie (irq_enable becomes P then Q) but the one-instruction delta at 0x2c holds. Prefer (i). T must not score E rows (MMU-on aliases to RAM).

4. **E3’s `0x02` is also what RAM returns after a word store of P.** It is a width pin, not a device-signature. Keep A1/A2 as the signature; do not claim E3 distinguishes device from RAM.

5. **Test-first:** on HEAD, the first `+0x188` read still dies. K (today) is that witness. E1–E6 cannot show values on HEAD; they are post-fix floor rows. Do not invent a “pre-fix E1 red because value is 0” story — HEAD never returns the value.

6. **PRETABLE CHANNEL for the new rows**, named at writing time:

   - E0 kills (g) via host-death / missing 0
   - E1 kills (a)(b)(c)(d) via value ≠ P
   - E2 kills (h) and (l) via value ≠ P\|Q (and death under (l))
