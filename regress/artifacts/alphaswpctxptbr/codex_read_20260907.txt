**Q6.** Your claim is correct **for dispatch into `alpha_palcode()`**, with a material qualification about the callee.

In [`cpu_alpha_instr.c`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_instr.c:831), `(iword >> 26) & 63` determines the opcode. Case `0x00` assigns `instr(call_pal)` and puts the low 26 bits into `ic->arg[0]`. [`X(call_pal)`](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_instr.c:53) synchronizes the PC, then directly calls:

```c
alpha_palcode(cpu, ic->arg[0]);
```

There is **no PAL-specific privilege check, mode check, or enable-bit check before that call**. Ordinary instruction-fetch failure, debugger stops, and translation read-ahead still affect whether an instruction executes. See the [fetch handling](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_instr.c:807), [breakpoint handling](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c:1799), and [read-ahead return](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c:1917).

**Inside `alpha_palcode()`, however, there is a mode gate.** It derives `userMode` from `ps & ALPHA_PSL_USERMODE`, then checks a whitelist before the switch. A disallowed PAL number—including `0x30`—in user mode causes `cpu->running = 0` and an immediate return. Thus dispatch into the function is unconditional with respect to privilege; execution of the `0x30` handler is gated. [Source](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_alpha_palcode.c:165)
