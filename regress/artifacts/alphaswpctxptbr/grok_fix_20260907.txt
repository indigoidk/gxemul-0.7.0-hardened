## Q1 — the one-token fix is the whole *product* fix. It does not break a reader. It also does not pin what it repairs.

`apcb_flags = new_flags` at `:282` stops the PTBR clobber **and** installs the incoming flags. One token, both in-cpu consequences.

**Every `apcb_flags` site in `GXEMUL-SEC/src/`:**

| site | direction | relies on today’s stale value? |
|---|---|---|
| `wrfen` `:221` | **write** `a0` over the whole word | No. It does not read the old value. |
| `wrfen` `:222-223` | **write** that word to `ctx+40` | No. Uses what it just stored. |
| `swpctx` SAVE `:243-244` | **read**, publish to outgoing PCB | No. Today this **propagates** the bug: the next SAVE writes stale 0 (or last `wrfen`) into the outgoing `+40`, wiping the flags the guest planted. After the fix it writes the flags that were actually loaded — which is the PAL contract. |
| `ALPHA_PCB_FLAGS_FEN` / `_PME` | header only | Unused. |
| `ALPHA_IF_CODE_FEN` | header only | No FEN trap in `cpu_alpha_instr.c` or anywhere else under `src/`. |
| `PAL_clrfen` (`0xae`) | named, user-mode-whitelisted | **No `case`.** Hits the default arm and stops the CPU. |

`memory_alpha.c:46` reads `apcb_ptbr`, not flags. `alpha_invalidate_translation_caches` is the generic dyntrans walk of `vph_tlb_entry[]`; it does not touch the PCB.

So: making the field track the loaded value changes one observable, the SAVE to `ctx+40`. Nothing in this emulator uses that word for FP enablement, ASN, translation, or the debugger (`CPU_SETTINGS_ADD_REGISTER64` exports `pc` and the 32 GPRs, not PCB fields). Sticky-FEN-across-`swpctx` is a PAL bug, not a behaviour a reader is entitled to.

**What the token does not fix** (already filed or adjacent, not reasons to reject it): `alphaswpctxreg` (`A0` vs `v0`), `alphactxfail` (ignored `memory_rw` status), `wrfen` replacing the **entire** flags word rather than bit 0, `clrfen` unimplemented.

## Q2 — 9/9, and that is the detector gap, not a comfort.

Both red rows read **the same `got`**: `A+16` after the second `swpctx` SAVE. Neither reads `apcb_flags`. Neither reads `A+40`.

After the fix:

1. First `swpctx` loads A: `apcb_ptbr = PTBR_VAL` and is **not** overwritten. `apcb_flags = FLAGS_VAL` (unobserved).
2. Second `swpctx` SAVE writes `PTBR_VAL` to `A+16`.
3. `swpctx ptbr` wants `0xaaaa1111` → green. `swpctx notflags` wants not `0xbbbb2222` → green. `swpctx mapped` wants not `0` → still green.

The seven controls do not consult that field. **9/9.**

They also do not depend on flags staying stale. The probe writes PCB memory and reads PCB memory; the in-cpu flags field is never in the oracle.

The cost of that 9/9: a build that **only** stops clobbering PTBR — delete `:282`, or assign `new_flags` to any other field — also scores 9/9. Consequence 2 is unpinned.

A flags-oracle that would pin it, from the same session, no new machine: after the two swaps, `A+40` is **0 on HEAD** (SAVE of never-loaded flags) and `FLAGS_VAL` after the fix. Same page as `A+16`, so `swpctx mapped` already proved the backing exists. That row is not in the file.

## Q3 — `wrfen` interacts; `INVALIDATE_ALL` does not mask either consequence.

`:221` is `PAL_OSF1_wrfen`. It is the only writer of the in-cpu field besides the missing load.

**Interaction, and it is real:** without the load, FEN is process-global. `wrfen(1)` then `swpctx` to a PCB whose flags word is 0 leaves `apcb_flags == 1`. The SAVE of the *next* switch then publishes that 1 into the outgoing PCB. The fix makes FEN per-context: SAVE first (so the `wrfen` is preserved on the old PCB), then load the new PCB’s flags. That is the OSF order, not a regression.

`wrfen` itself does not need the load. It overwrites. Its own defect is separate and becomes slightly more visible after the fix: it stores **all of `a0`**, not `(PCBB+40)<0>`, so a later `wrfen(1)` would smash a PME bit the new load had just installed. Today PME is almost never in that field, because nothing loads it.

**`INVALIDATE_ALL` at `:287`:** generic TLB flush, no PCB read. It does not restore PTBR, does not touch flags, and does not hide the clobber. If anything it **exposes** the PTBR bug: cached translations from the old (often identity-mapped) `base==0` world are dropped, so the next non-K0SEG access re-walks with `base = flags<<13`. This probe never takes that walk — K0SEG is checked in `alpha_translate_v2p` **before** `base` is used — so for these nine rows the invalidate is a no-op on the oracle.

`PAL_clrfen` does not interact, because it is not implemented.

## Q5 — the comment is false as C and true as guest-observability.

`:276-284` are nine sequential stores with **no call** in between. The guest is inside `alpha_palcode()`. The debugger is waiting on `step`. `invalidate_translation_caches` runs **after** the block and does not read the PCB. Nothing in this emulator can see a half-updated `struct alpha_pcb`. For a guest, the updates are simultaneous.

The comment is still a bad description of the function around them:

1. `ctx` is switched at `:255` **before** any load or PCB store.
2. `r[A0]` is written at `:251` before the load (and the comment says `v0` — `alphaswpctxreg`).
3. The nine `load_*` calls use `memory_rw` **without `PHYSICAL`**, so they translate with the **old** `apcb_ptbr`. K0SEG / `base==0` is why that works at all.
4. Then the stores. Then the TLB shootdown.

Simultaneity of the nine assignments is real because there is no observer. Atomicity of the whole PAL, and atomicity under a failed load (`alphactxfail` / `#95` zeroes), are different claims the comment does not establish. Do not treat `:275` as a licence that the surrounding order is architectural.
