VERDICT: REAL -- a bare-PHYSICAL RAM access can install or replace a VA==PA entry in the CPU’s virtual translation cache.

Only the six permitted files were read. The insertion defect is established statically; some requested details about normal guest execution lie outside that scope.

1. **The guard reading is correct.**

   `PHYSICAL` sets `paddr = vaddr`, bypassing translation and leaving `ok = 2`. Once a non-null RAM backing pointer is obtained, the publication guard has no `PHYSICAL` exclusion. It additionally checks the MIPS R2000/R3000 isolated-cache condition. See [memory_rw.c:235](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c:235), [memory_rw.c:245](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c:245), and [memory_rw.c:728](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c:728).

   Both generated updater forms accept it:

   | Form | Key and behavior |
   |---|---|
   | `MODE32` | Uses the virtual page number; installs `host_load`, `host_store`, and `phys_addr`. An existing VA with a different PA has its mapping replaced. 2. **MIPS persistence is established locally, but not through every guest transition.**

   MIPS selects these two updater/invalidation implementations directly. A KUSEG address receives the same VA-only entry; the updater imposes no segment restriction. [cpu_mips.c:116](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_mips.c:116).

   “Until a guest TLB write” is too strong. Entries can disappear through replacement eviction or explicit VA-, PA-, or whole-cache invalidation. The 64-bit VA invalidator matches using `cpu->vaddr_mask`, without an ASID. [cpu_dyntrans.c:1572](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c:1572), [cpu_dyntrans.c:1227](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c:1227), [cpu_dyntrans.c:1276](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c:1276).

   The RAM write’s subsequent **code** invalidation does not remove `host_load`/`host_store`; it clears code-page associations. The shown MIPS exception-entry code also changes status and PC without explicitly flushing those mappings. [memory_rw.c:757](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/memory_rw.c:757), [cpu_dyntrans.c:1447](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c:1447), [cpu_mips.c:2206](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_mips.c:2206).

   A surviving entry can bypass architectural translation: the generic instruction lookup accepts the cached PA before calling `translate_v2p`, with no user-mode or ASID check there. [cpu_dyntrans.c:656](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_dyntrans.c:656).

   **Unsettled within this scope:** whether routine guest EntryHi/ASID writes, Status writes, TLB instructions, or return-to-user handling remove it first; and the exact user-mode data-load/store path. Those implementations are not present in the permitted files—`cpu_mips.c` includes external MMU/generated code. Consequently, I cannot certify an end-to-end user-mode witness. [cpu_mips.c:75](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_mips.c:75), [cpu_mips.c:2228](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/src/cpus/cpu_mips.c:2228).
