## Q1 — CHANNEL

### `s w32 pc`

**Control, not a kill.** It reuses `pc` from the same `run_word(sbfx(0, 32))` as `s w32` and asserts `pc == CODE+4`.

Under the original defect the SBFX width-32 **success** value is `0x89abcdef` and the **failure** value is `0`. A word that never ran leaves `r0 = 0` (the probe zeroes it). That **reds `s w32`**, it does not green it. So this row does not stop a false pass of the value oracle.

What it does is **attribute** a red `s w32`: executed-and-wrong (`pc` advanced) versus never-ran (`pc` stuck or vectored). `w32 pc` already does that for UBFX. This is sibling parity, and it is correctly labelled `CONTROL` in the row note.

The settled-premise wording that “the SBFX rows” (plural) have expected failure value zero is too wide. Only `s w32` has that shape for the original mask-zeroing. `s clear` fails to `0xfffffff7`, `s mid` to a non-extended `0xde`, `s w31` to `0x89abcdef` under mask-widening. A pc control on those rows is not doing the zero-vs-zero job.

**No edit named here reds `s w32 pc` while leaving `s w32` and `w32 pc` green.** If SBFX #0,#32 fails to decode, `r0` stays `0` and `s w32` already fails.

### `s w31`

Drives `SBFX #0,#31` of `0x89abcdef`. Arithmetic, from `X(sbfx)`:

- `x >>= 0` → `0x89abcdef`
- `mask = (1U << 31) - 1` → `0x7fffffff`
- `x &= mask` → `0x09abcdef`
- bit 30 of that field is clear (`0x09abcdef & 0x40000000 == 0`) → no sign-extend
- printed with `%x` as `0x9abcdef`, which matches the want and the 14/14 log

**Mutant it kills that `w31` cannot see:** SBFX-only bound-relax of the ternary,

```c
(width >= 31) ? 0xffffffffU : ((1U << width) - 1)
```

leaving UBFX alone. Then `s w31` gets the whole register `0x89abcdef` against want `0x9abcdef`. `w31` stays green (different function). `s w32` stays green (width 32 still takes the full mask, which is correct). `s mid` / `s clear` never hit 31.

That is the `#509` shape (`== K` → `>=` next legal value) applied to one of two sites. Observable: `r0`. Predicted score **13/14**, killed by this row alone.

It also reds always-extend (`if (width < 32)` with no bit test): `0x09abcdef | 0x80000000` → `0x89abcdef`. **`s clear` already kills that** (`0x7` vs `0xfffffff7`). So always-extend is not this row’s unique work.

**Channel hole on the row as written:** bit 30 is clear, so `s w31` **cannot** see `width < 32` → `width < 31` (sign-extend skipped at 31). Correct and mutant both leave the field unextended. See Q2.

## Q3 — is `s w31` load-bearing, or does `w31` already cover it?

**The “untested” half is right. The “therefore the headline might have been wrong about SBFX” half is not.**

`w31` is UBFX. `s w31` is SBFX. They do not cover each other’s site:

- UBFX-only `>= 31`: `w31` red, `s w31` green
- SBFX-only `>= 31`: `s w31` red, `w31` green

Generalising `w31` to SBFX was unwarranted as a **measurement**. Adding the row is the right repair for that.

It was **not** unwarranted as a **prediction about the original defect**. Both handlers used `(1 << width) - 1`. At width 31 that wraps to the correct mask on this host for UBFX **and** SBFX. `s w31` would have been green on the committed pre-fix build. It does not make the width-31 UB observable, and it does not support a claim that “only width 32 is observable” was false of SBFX. It was unmeasured, not untrue, for that specific claim.

`s w31` is still load-bearing: it is the only row on the SBFX ternary’s width-31 cell. That is coverage, not a second witness of `#510`’s red.
