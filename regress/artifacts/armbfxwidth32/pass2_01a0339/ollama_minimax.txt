## Q1 — CHANNEL for each added row

### `s w32 pc` — CONTROL, not a kill. [REASONED]

The channel is `pc`; the mutant class is "the SBFX word does not execute." Under that mutant:
- `pc` does not advance to `0x8004`, so `s w32 pc` is RED.
- But `r0` also retains its prior-row value (the row before `s w32` is a UBFX row, not `0x89abcdef`), so `s w32` is RED on the same observable (r0 ≠ 0x89abcdef).

Under any other mutant class ("executes but produces wrong r0"), `s w32` is RED and `s w32 pc` is GREEN (pc advances). So `s w32 pc` adds **no unique kill**. The only theoretical mutant where `s w32 pc` would be the sole catcher is "word does not execute AND r0 happens to equal 0x89abcdef from a prior row" — the probe does not preload that value, so this is not a realistic mutant.

The row is correctly labeled `CONTROL` in the diff. It documents the invariant but does not catch a mutant the other rows miss.

### `s w31` — kills SBFX sign-extension / mask mutants at width 31. [REASONED]

Drives `SBFX #0,#31` on `0x89abcdef`. With the fix:
- `mask = (1U << 31) - 1 = 0x7fffffff`
- `x = 0x89abcdef & 0x7fffffff = 0x09abcdef`
- Sign-bit test: `width < 32` is true, but `x & (1U << 30) = 0` (bit 30 is clear in `0x09abcdef`). No extension.
- Result: `0x09abcdef`, formats as `"0x9abcdef"`.

Mutants it catches that `w31` (UBFX) does not:
- "Always sign-extend": `s w31` gets `0x89abcdef` instead of `0x09abcdef`. RED. (`w31` is GREEN — UBFX has no sign-extension code path.)
- Width-31-specific bugs in the SBFX sign-bit test or guard.

Mutants it does **not** catch (because bit 30 is clear and bit 31 is also clear in `0x09abcdef`):
- "Check bit 31 instead of bit width-1": both bits are 0 here, so the result is identical.
- "Sign-extend when bit 31 is set": bit 31 is 0, no extension triggered.

So `s w31` is load-bearing relative to `w31` (Q3 below), but the chosen value (`0x89abcdef`) makes it test the **no-sign-extension** path at width 31 — the same path UBFX takes. It does not exercise the trigger. A value with bit 30 SET (e.g., `0xC9abcdef`) would exercise the trigger and catch "check wrong bit" mutants.

## Q2 — FLOOR: clause-(d) mutant exists. [REASONED]

**Yes.** The predicate `width < 32` in the sign-extend guard can be weakened to `width <= 32` (or `1`, or simply removed), which is the least-restrictive form that still reads like a comparison involving `width` and `32`. Since `width ∈ {1..32}`, `width <= 32` is tautologically true.

Under this mutant:
- **width = 32** (SBFX, `s w32`): the guard no longer suppresses the test. `1U << 31 = 0x80000000` (defined, unsigned). `x = 0x89abcdef` (mask is still `0xffffffffU` from the ternary). `x & 0x80000000` is true. Then `x |= ~mask = x | ~0xffffffffU = x | 0 = x`. **No-op.** Result `0x89abcdef`. GREEN.
- **width < 32**: the original guard was already true, so behavior is unchanged.

All 14 rows remain green. This is a clean sweep and per the brief's own rule is an **L2 breach**.

The ternary predicate `width == 32` cannot be weakened to a less-restrictive form that still reads like the same check — `width >= 32`, `width > 31`, `width < 33` are all equivalent on the domain `{1..32}`. Only the sign-extend guard is vulnerable.

**This must be repaired in-round** by adding a row that fails under this mutant. A row that asserts `pc` does NOT advance on an encoding the decoder rejects would do it — except the SBFX widths in scope are all legal encodings. The realistic defense is a row on an **illegal** encoding that should route to UND/bad, asserting `pc` lands on the UND vector — but that is a different probe. Alternatively, a comment pinning the guard against future "simplification" is the only in-round defense, since no value row can kill it. **The round has no such row and no such pin.**

## Q3 — `s w31` load-bearing? [REASONED]

**Yes, relative to `w31` (UBFX).** `w31` does not sign-extend; `s w31` does (conditionally). A mutant in SBFX's sign-extension logic (e.g., always extend, or check the wrong bit) makes `s w31` RED while `w31` stays GREEN. So `s w31` is not green under every edit that `w31` is green under.

**Caveat:** the chosen value has bit 30 clear, so the sign-extension trigger is false. `s w31` exercises the same code path UBFX takes (mask + no-extension) for this specific value. It catches mask errors and "always sign-extend" mutants, but not "check bit 31 instead of bit 30" mutants (bit 31 is also 0 here). The existing `s clear` row already catches "always sign-extend." So `s w31` is load-bearing in the sense of "exercises SBFX at width 31 with a different instruction than UBFX," but the coverage delta over `w31` + `s clear` combined is narrow.

The round's claim "SBFX at width 31 was untested" is correct (no row exercised SBFX's sign-bit test at width 31). The round's claim "generalising `w31` to SBFX was unwarranted" is correct. But "`s w31` now pins it" overstates — it pins the no-extension path, not the extension trigger.
