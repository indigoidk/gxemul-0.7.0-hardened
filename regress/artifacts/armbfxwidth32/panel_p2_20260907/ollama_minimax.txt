## Q1 — Repair correctness and the added comment

**At width=1.** `(1U << 1) − 1 = 1`. Original: `(1 << 1) − 1 = 1`. Same value, no UB. ✓
**At width=31.** `(1U << 31) − 1 = 0x7FFFFFFFU`. Original UB twice, but wraps to the same mask on the committed toolchain, which is exactly what the w31 row shows. ✓
**At width=32.** Guard returns `0xFFFFFFFFU`. Original UB, and on the toolchain `1 << 32` shifts by the type width and produces `0`, so mask = `0` and `x &= 0` gives `0` — which is what w32 HEAD shows. ✓

**The `&&` reorder is observably identical for every width ∈ {1..32}** — REASONED.
- Width 1..31: shift count in `[0, 30]`, both expressions evaluate to the same value, both branches of `&&` are evaluated, if-body fires iff original.
- Width 32: in the original, `1 << 31` is UB but on the toolchain yields `0x80000000`; `x & 0x80000000` is computed; `width < 32` short-circuits the if. In the new code, `width < 32` short-circuits *before* the shift. The if-body never executes in either; r0 is the value forced by the mask alone. Same observable result.

**But the reorder is not just cosmetic** — it eliminates the UB at width 32 in the SBFX operand. The comment in the diff is *slightly* misleading on this point: it says the reorder "is semantically identical for every width in {1..32}" and *separately* notes "short-circuits before the shift", which together read as "same behaviour, plus the shift doesn't run when guarded." That is accurate, but a future reader skimming will conclude "reorder only". Strictly: the reorder changes language-level behaviour at width 32 (UB → defined) while leaving observable behaviour identical. Worth tightening, not load-bearing.

**Does the comment claim anything the rows do not establish?** REASONED.
- "`UBFX r0,r1,#0,#32' of 0x89abcdef returned 0x0 ... because the mask became 0`" — w32 HEAD=0x0 (READ) supports this.

- "The guard defends 32" — supported by the w32 rows and by source.

No overclaim. The "load-bearing" claim is true but is not what the witness rows prove; the witness only proves the value. Flagging that for honesty.

## Q4 — Witness honesty: what it does not cover

The witness as shown has 5 displayed rows out of 11. Cells it should assert and does not:

1. **Width = 1.** The brief itself notes the codex fix-check ratified boundaries 1, 31, 32, but the *inlined witness* only covers 31 and 32. The width-1 case (mask = `0x1`, smallest field, sign-extension of the lowest bit for SBFX) is the natural symmetry to the width-32 case and is missing.
2. **SBFX sign extension at a small width.** SBFX at width=32 cannot exercise sign extension (the field is the whole register, `~mask = 0`, `x |= 0` is a no-op). A row like `SBFX #0,#4` of a value whose bit 3 is set, expecting `0xFFFFFFFF`, would cover the `x |= ~mask` arm.
3. **Initial register state.** The brief argues `pc adv = 0x8004` proves execution, which it does. But the witness does not, in what is shown, assert that `r0` started at a known value (presumably 0). Without that, "r0 = 0x0 after HEAD, 0x89abcdef after FIX" is consistent with the instruction never having executed *and* r0 happening to be 0x89abcdef before; the pc-adv row does exclude the latter, but a direct `r0 == 0 before` assertion would make the argument local rather than transitive.
4. **Six rows are not shown.** The brief says 11/11; the table has 5. The other 6 are unspecified — particularly the SBFX-w31 row I had to infer in arithmetic item 11. The brief's "drives four widths on one register value" undercounts the SBFX twin of each width.
5. **Non-zero lsb.** All visible rows are `lsb = 0`. UBFX with `lsb > 0` exercises the `x >>= lsb` half of the path; not covered.

The single most valuable missing cell is **width=1**, because the brief explicitly cites it as a ratified boundary while the inlined evidence does not actually show it.
