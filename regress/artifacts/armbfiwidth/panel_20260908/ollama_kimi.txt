## Q1 — minimal repair

```c
uint32_t mask = (width <= 0) ? 0 :
                (width == 32) ? 0xffffffffU :
                ((1U << width) - 1);
```

This is #510's form plus one clause. **[REASONED] No guest-visible value changes for valid pairs (msb ≥ lsb):** for width ∈ [1,30] the formula is arithmetically identical to the old code; at width 31/32 the old code had *no defined value* to preserve, and the chosen values (0x7fffffff, 0xffffffff) are the architecturally intended masks. The `width <= 0` clause also preserves the already-defined width == 0 case (old code yields mask 0 there; new code yields 0 — identical). Only genuine negative widths gain a value where none was defined; that is a *choice* on invalid encodings, disclosed as such, not a behaviour change on valid ones.

## Q4 — distinguishing observable

**[REASONED] The brief's own finding is correct and generalizes:** `1 << 31` and `1U << 31` yield the same mask after `- 1` on any platform in practice, and a negative-width UB produces compiler-dependent values with no portable oracle — so **no guest-value row can catch either regression class** (a `1U` → `1` slip, or deletion of the `width <= 0` guard, is value-invisible or value-unstable by turns). The regression row must therefore be: **(a)** a UBSAN-clean sweep executing all 1024 encodable (msb, lsb) pairs of BFI (re-running ubfx/sbfx is nearly free); **(b)** a source pin on the guarded expression; optionally **(c)** guest-value rows asserting the *chosen* msb < lsb semantics (destination unchanged) — those document the Q2 choice, they do not prove definedness.
