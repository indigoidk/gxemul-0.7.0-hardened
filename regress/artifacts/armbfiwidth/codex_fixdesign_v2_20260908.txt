**P2: zero is not a negative shift count.** `(1 << 0) - 1` is defined and equals zero. My independent enumeration gives:

| Width | Pairs | Original expression, with 32-bit `int` |
|---|---:|---|
| Negative | 465 | Undefined: negative count |
| Zero | 31 | Defined: zero mask |
| 1–30 | 525 | Defined |

| 32 | 1 | Undefined: excessive count |

Thus **468 pairs**, not 499, encounter undefined behavior under that host model. Separately, **496 pairs** have architecturally invalid field ordering. These are different counts. C99 does not require 32-bit `int`. [C99, §6.5.7](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1256.pdf#page=96)

For **Q1**, choose `mask = 0` and document it as the simulator’s **NOP policy for invalid field ordering**. Valid BFI replaces an ordered interval of destination bits with low source bits. A reversed interval has no defined BFI insertion semantics; “inserts no bits” is a sensible policy, rather than a uniquely mandated architectural result.

An early return immediately after calculating `width` is also sound here. I checked the macros: `X` declares a void function, and `Y` generates separate conditional wrappers. There is no handler epilogue that such a return would skip. Clamping invents an insertion; a diagnostic is optional and does not itself resolve the arithmetic.

For the mask expression’s C99 portability, I recommend this small revision:

```c
uint32_t mask = (width <= 0) ? 0 :
    (width == 32) ? 0xffffffffUL : ((1UL << width) - 1UL);
```

`1U` has type `unsigned int`, which can have only 16 bits. `unsigned long` is guaranteed sufficient range for this expression. This makes the **mask construction** portable across the stated width domain; it does not certify the surrounding function on every C99 implementation.

For **Q2**, negative and excessive counts use the same UBSan shift-handler entry point, but the full runtime produces different messages:

```text
shift exponent -1 is negative
shift exponent 32 is too large for 32-bit type 'int'
```

Width 31 instead concerns the signed shift result. [UBSan implementation](https://raw.githubusercontent.com/llvm/llvm-project/main/compiler-rt/lib/ubsan/ubsan_handlers.cpp)

**One instruction encoding cannot exercise both count failures:** its immediate fields fix `width`; changing register contents cannot change that. A zero-width case cannot demonstrate repair of a negative shift.

The cheapest useful coverage is:

1. **Arithmetic checks:** exercise negative, zero, ordinary, 31, and 32 widths. All 1,024 field pairs are inexpensive to compare against an independent per-bit mask oracle.
2. **Sanitizer checks:** distinguish negative-count, excessive-count, and signed-result failures in separate cases. Compile as C99 with `-fsanitize=shift`, or use the existing undefined sanitizer instrumentation. Shift-exponent checking alone misses the signed-result case. [GCC instrumentation options](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html)
3. **Integration controls:** reuse the existing vehicle with a nonzero destination sentinel, valid BFI cases that demonstrably change it, and PC/completion checks. Scope the source pin specifically to `X(bfi)`.

Two concrete traps matter here:

- **Inspect the captured transcript.** [`session()` consumes child output through its PTY](C:/DocumentNoSnc/CC/GXEMUL/GXEMUL-SEC/regress/arm_bfx_width_probe.py:149), while callers print parsed results. Grepping the Python process’s stderr can miss the sanitizer messages completely.
- **Keep cases in fresh processes**, as the current helper already does. Recovering UBSan suppresses subsequent reports at an already-reported instrumentation location. Therefore, diagnostic totals are not execution counts. With full undefined checking, width 31 can also produce a subtraction-overflow report; require the intended site and diagnostic class rather than exactly one total warning. [UBSan location handling](https://raw.githubusercontent.com/llvm/llvm-project/main/compiler-rt/lib/ubsan/ubsan_value.h)
