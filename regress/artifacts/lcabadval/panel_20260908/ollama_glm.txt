## Q2 — the guard

On the extracted field `f = (idata >> 20) & 0xfff`: **exactly bijective with Table 6-6**. f & (f+1) == 0 ⟺ f = 2^k − 1; over 12 bits that is k = 0..12 — precisely the 13 rows. ## Q3 — the six arms

Principle: hardware cannot `exit(1)`. "Unsupported" in a data sheet bounds a *guarantee*; it is not a trap. Process death is for host-side invariants, never guest data.

- **W_MASK0/1** — accept with backing storage; honor the XOR/AND rule for *any* value (the quoted rule is total over all 4096 field values; the table lists supported values, not the only decodable ones); `(once)` log for out-of-table values as a fidelity diagnostic, never fatal.
- **W_BASE0/1** — accept with backing storage, no legality gate. The manual (as quoted) enumerates nothing for base, and the matching rule is total in base too; terminating on any base except the one the reference image wrote is per-image hard-coding.
- **CONF, TB_ENA** — accept with backing storage; the field masks survive at most as `(once)` diagnostics. No manual basis is quoted for these two masks at all (READ).

Backing storage (not bare accept-and-store) for all six: firmware verifies registers by write-then-readback.

## Q4 — error direction

**Terminating on legal values**, as the code stands: a deterministic, guest-triggered host abort on documented behavior — it fires in the field for any OS that sizes windows differently, and in a service context is a guest-triggerable availability failure. The silent-accept hazard is **conditional**: it presupposes a decode that consults these registers, which the packet itself says is unknown; if the decode ignores them, acceptance is inert. If it does consult them, accept-but-ignore-with-readback becomes the classic silent-corruption worst case. So: "never fatal" is unconditional; the second hazard is conditional on exactly the fact worth establishing first.
