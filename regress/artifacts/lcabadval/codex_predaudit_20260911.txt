The unserviced-access question requires keeping the memory paths separate:

| Failure or nonservice mode | What the permitted code establishes for Alpha |
|---|---|
| Matched handler returns success without filling the read buffer | The dispatcher has already zeroed the buffer. It returns success, so a normally completed load receives zero. Ignored writes can likewise return success without changing state. |
| Matched handler returns `0` without filling the buffer | The buffer is zeroed, `res` becomes `−1`, and normal guest access returns `MEMORY_ACCESS_FAILED`. | Handler fills some data and then returns `0` | For these unsplit accesses, failure does not imply that the supplied data is erased. The same failure return and missing Alpha exception delivery apply. |
| Device callback skipped under `NO_EXCEPTIONS` | The pre-zeroed buffer remains zero and this path returns success. This explains the debugger issue; it is not the normal guest-instruction path. |
| No mapped device, outside physical RAM | The external warning helper can cause an early failure return. Otherwise the code explicitly zeroes reads, discards writes, and returns success. The helper’s behavior is not derivable here. |
| Original `exit(1)` behavior described by the probe | The host process ends. That is not an Alpha architectural exception delivered to the guest. |
